# Unit: Public Main Docker delivery

Files: Dockerfile, docker/entrypoint.sh, docker/seccomp-chromium.json, .dockerignore, docker-compose.yml, test/docker-compose.yml, test/docker-compose.code.yml, test/README.md
Secondary files: dotnet/Foxwarm/Delivery.targets, Dockerfile.node, scripts/start-sandbox-node.sh, scripts/test/compose-sandbox-node.test.mjs, .github/workflows/tests.yml

## Contract and rationale

Test Compose and local `docker build` use one root recipe whose default target builds from the checkout and starts complete native (NativeAOT) Main for the build host's architecture. Its `release` target places the extracted native Linux [release package](./release-packages.md#native-linux-package) on the same runtime base; that is the published `ghcr.io` image, which root Compose runs. Since 0.9.4 (user decision, 2026-11-10) neither target contains a .NET runtime. Node 24.17.0 on Debian 13 Trixie and the existing operational tools remain available for real JavaScript, public CLI and stdio MCP usage; changing Main runtime does not remove that environment. Microsoft's official Debian 13 signed package feed supplies the build SDK; the build stage adds clang and zlib headers for NativeAOT linking against the same Debian release as the runtime base, which adds ICU (`libicu76`) and OpenSSL (`libssl3t64`) for native Main. Debian supplies `/usr/bin/chromium` through ordinary package updates, independently of CI's test-browser pin. The runtime runs as the fixed non-root `node` account (`docker/entrypoint.sh`: a writability check of `/data` for uid 1000 that reports the host `chown -R 1000:1000` fix, then `setpriv` privilege drop without `no_new_privs`, for the `release` target too). By user decision the image never re-owns mounted data, which would have to be recursive; operators hand over a root-written volume once before upgrading, and the release smoke prepares a 1000:1000 volume. The account has passwordless `sudo` through a `/etc/sudoers.d/node` drop-in so Agents can install packages; the entry point has no account override. Chromium's sandbox is never disabled; `docker/seccomp-chromium.json` adds only `clone`, `setns` and `unshare` to Docker's default profile, referenced by both Compose files and the documented `docker run`. Without it the first browser call fails with a sandbox hint. A private image or browser cache is not a public delivery input.

The recipe prepares assets then publishes the [existing resource graph](./core-delivery-cli.md#build-and-resource-boundary); it has no separate asset copier. Docker context excludes host dependencies/build outputs, installation data and caches. Ordinary npm locks, pinned NuGet packages and pinned Monty acquisition run inside build layers. The runtime retains resources/native helpers/notices and has no baked experiment settings. Large optional Code workbench assets and optional HEIF remain external prerequisites.

After the dependency-install layer, the build stage explicitly copies `tsconfig.artifacts.json`, its extended root `tsconfig.json` and the three Main artifact helper sources (`managedPrepare.ts`, `reactCompiler.ts`, `rasterMetadata.ts`). These are the bounded Main inputs to `build:artifacts`; its Shared validator imports come from the preceding `build:node` output. Neither host-generated helpers nor the full Source Main tree are compiler inputs to this recipe.

## Consumers and side effects

The default command is `/app/Foxwarm`, installation root `/app`, data root `/data`, port 3001. The Vector owner, when enabled, is the same executable as a child process. Root Compose runs the published image and retains its data mount, init process, healthcheck and separately paired optional sandbox Node. That Node's only mount from the data directory is the read-only `state/node_token` file, the one data-directory file `scripts/start-sandbox-node.sh` reads (the client stores its approved credentials inside the container, outside any data mount); Main creates that file in place and never replaces it, so a single-file mount stays current, and `create_host_path: false` turns a missing file into an error rather than a Docker-created directory. Models, secrets, keys and Sessions are not visible to it. `scripts/test/compose-sandbox-node.test.mjs` checks the mount list statically; no container engine runs in that test.

Test Compose uses the same recipe as project/service `foxwarm-test` on host port 3002, with `test/state` at `/data/state` and `test/agents` as the canonical Agents root at `/data/agents`. Main lives beneath `main/` alongside other Agent directories and the global framework prompt. Its optional Code overlay mounts prepared `test/.temp/code-assets` read-only at the installed resource directory.

Both read ordinary mounted app YAML for the public `url` and `bot.httpPort`, with no environment port/bind/public-address override; the default listener is port 3001 on IPv4 wildcard. Both use Main's normal stop/drain. Test Compose retains a 30-second operational allowance for the five-second foreground grace, five-second cancellation window and remaining teardown. Forced deployment grace expiry is not successful drain.

`Dockerfile.node` remains an independent Node-only build and is not redirected to managed Main. Source/native-job adoption, Worker/controller hosting, Main TUI and public promotion remain outside this delivery candidate. Linux x64 image qualification establishes no other architecture or operating system claim; a source-built linux-arm64 image is unqualified.

## Validation

A clean public-source build must start native Main without host `dist`, `node_modules`, private native/browser caches or real data. Qualification covers original App/auth/Setup, packaged Node archive/resources, native ToolScript and a Main screenshot/image path using the actual image Chromium, plus normal stop/restart with preserved owned data. [Maintained test runners](./test-runner.md) own managed solution, complete-publish and default application tests; local equivalents are not a hosted Actions run.
