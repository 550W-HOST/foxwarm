## Contract and original ownership

The managed host implements the existing [Main Logs contract](./webui-logs.md), not another viewer. The original React App, LogsView and page realtime transport remain the consumers. `WebUIChannel` captures one destination from startup `ModelConfiguration`: selected data root, `state/logs`, and startup `bot.name || 'foxwarm'` plus `.log`. HTTP accepts no path. Global administrator authorization precedes the fixed `/api/webui/logs` history/time endpoint; scoped browser identities cannot read it or subscribe to its realtime topic.

`WebUiLogFile.Read` serializes opened-file reads. Each content window is at most 100 KiB with one preceding byte allowance, byte-addressed UTF-8 boundaries and withheld incomplete EOF codepoints. Missing and empty differ; observed identity change, disappearance or shrink invalidates old cursors with HTTP 409/reset frames. `OpenFileMetadata.Read` uses the open handle's Linux statx device/inode/birth facts, macOS fstat device/inode/birth facts, or Windows volume/file-index/creation facts and size, not a separate path stat or file hash. Darwin uses the stat64 layout with the Intel `fstat$INODE64` entry or the Apple Silicon `fstat` entry. The CLI transfer reader also uses this opened-handle regular-file check and supplies source-specific error context.

`Seek` executes the Source algorithm: latest/first samples, at most 20 bisection probes, one preceding sample for an undated probe and candidate-local reads. It recognizes full dated pretty and numeric JSON times after display-control removal while accounting for original raw bytes. It returns the selected record's actual position/time and `approximate: true`; absent dates and out-of-sampled-range targets fail without silently selecting Latest. It does not index or scan the whole file.

`LogWindow.Json()` reuses one camelCase-only serializer options instance. Its fixed window shape retains explicit null identity, zero counters and false flags, including `missing`; Web defaults or omit-default policies are not part of this boundary.

## Real producer and lifetime

The actual console and Desktop entries opt into one process Console capture owned by their `MainHost`. Existing bounded Console diagnostics retain their normal console text and stdout/stderr destinations, and additionally become dated, millisecond, numeric-zone, uncolored file records. `FOXWARM_LOG_STDERR` redirects ordinary output to stderr; `FOXWARM_NO_CONSOLE_LOG` suppresses console output. `FOXWARM_SYNC_FILE_LOG=1` writes synchronous numeric-time JSON and no console target, as Source does. Persisted `bot.enableTUI` stays ignored and does not suppress ordinary managed output. Framework logging providers remain cleared. `MainLog.Diagnostic` classifies ordinary typed WebSocket lifecycle records as INFO only while Main capture exists; actual transport failures remain ERROR. Outside Main, those diagnostics retain stderr so one-shot/CLI stdout remains a protocol/data stream. Fatal startup diagnostics are written at the live composition/start boundary before disposal, with a safe stderr fallback before capture exists; exception messages and raw configuration/vendor values are not echoed. A launcher that cannot rely on reading Main's console after an immediate exit names a file in `FOXWARM_STARTUP_FAILURE_LOG`: every `Main fatal startup failure at <stage>: …` line, including entry failures before capture exists, is also appended there, redacted like capture output. Main reads and removes the variable first thing at entry, so no process it starts inherits it; an unusable file is reported on stderr and does not change the exit. The [Unix package control](./release-packages.md#installed-layout-and-controls) uses it for tmux starts, because tmux discards output it has not yet read from an exited pane.

`AppendLogFile.Open` uses Linux/Darwin O_APPEND or Windows FILE_APPEND_DATA. Darwin writes use `write(2)` because positioned `FileStream` writes do not honor O_APPEND there; Apple Silicon also requires the creation mode on the variadic stack argument boundary. A persistent ordinary .NET FileMode.Append stream retains a write position and can overwrite bytes appended by another process; native append rights preserve the established shared-file producer path. There is no rotation, fanout, retry, recovery queue or flush-to-disk promise. Complete records are synchronously appended/flushed; normal host drain precedes the final stop diagnostic and writer disposal/partial-line flush. A write failure is reported to the original stderr and disables subsequent file writes; it cannot turn an already committed request/effect into a replay or retry.

**One capture per process, one sink per runtime.** The Console capture belongs to the process: the first `MainLog` installs it and the last one disposed restores the saved writers. Every `MainLog` is a sink with its own file, its own `InstanceSecrets` and, in hosted mode, its tenant, which the stdout JSON lines carry as `tenant`. A runtime binds its logical flow to its sink (`UseFor`, at composition, start and disposal). A line goes to the sink of the flow that wrote it. A line of no known flow goes to the process's sink, the oldest open sink without a tenant (else the oldest), and is masked with the secrets of every open sink. `UseProcess` marks a flow as the process's own. Partial lines are assembled per sink, so concurrent runtimes never join or mis-mask each other's text, and a sink that closes records only its own partial line. Work started without the caller's execution context (timer clocks, foreground processors, idle compaction, auto-title, copy transfers) goes through `MainLog.Detached`, which drops the caller's scopes but keeps its log sink. All sinks of one process share one console format; a sink with the other `jsonStdout` value is refused. Several hosted runtimes in one process therefore share one capture instead of wrapping each other's, which re-escaped every line at each level and grew memory exponentially.

**Logs view.** The history route and the realtime `logs` topic exist only with `RuntimeCapabilities.LogsView`. File mode has it. A hosted runtime doesn't: a replica's log records every tenant it serves and is the operator's (U16(b)), so tenant hosts answer 404 for the route and refuse the topic.

Main capture uses the published synchronized stdout monitor for pending lines, file records, console forwarding, flush, disposal and file-failure reporting. Saved console writers are acquired afterward because Unix console output can reacquire the current stdout monitor. This retains synchronous record completion with one consistent lock order, including stderr redirection and failure fallback.

One-shot model/archive commands, native helpers and the private Vector child dispatch before this capture exists, so their protocol framing and lifetimes remain unchanged. In-process embedding/test hosts do not replace global Console writers unless their entry explicitly opts in.

## Existing realtime sender integration

`WebUiRealtime` adds optional logical `logs.id`/reconnect cursor parsing to its existing subscription union. Logs begins behind that revision's existing subscriptions-applied send barrier. An unchanged ID survives unrelated Session/list revisions; replacement/unsubscribe/disconnect releases the subscriber and fences obsolete queued topic frames at the actual send gate. Log frames bypass the Session initialization pending list and revision filtering while retaining their own logical lifetime check.

The existing single output channel and serialized WebSocket sender remain. Queued JSON byte counts and direct in-flight send bytes expose managed outbound backlog; there is no claim to inspect kernel socket buffers. At 512 KiB the logs subscriber stops accumulating data and emits one gap after the backlog drains. Existing Session/list queue policies are unchanged. `WebUiLogFile.Subscribe` owns one non-reentrant 250 ms timer only while subscribers exist; more than 200 KiB of file catch-up, replacement/shrink, disappearance and read errors stop only the topic. Channel shutdown disposes the service; in-flight reads close their handles and cannot publish after disposal.

## Evidence

`LogFilePrimitivesTests` exercises shared append, seek-independent writes, synchronous/asynchronous overloads, cancellation/disposal, opened-handle identity across rename and same-size replacement, truncation, and non-regular-file rejection. macOS logging support does not imply support for unrelated native tools.

`WebUiLogsTests` compares actual Source reader windows/time results against managed results for multilingual/CRLF/partial lines, incomplete EOF, dated/JSON/ANSI/HH-only samples and 384 MiB sparse bounds. It also proves continuous paging, EOF completion, missing/empty, observed lifetimes, subscriber isolation, catch-up gaps and disposal. `WebUiStartupTests` exercises actual Main production/final exit, configured filename/TUI policy, synchronous JSON and console flags, real authenticated HTTP and the existing WS, scoped denial, logical lifetime/reconnect, shared-file append and replacement, plus a real failing diagnostic device without failing an accepted HTTP effect. `WebUiRealtimeRevisionTests` holds the actual sender to qualify byte-backlog gaps and retained unrelated subscription behavior.

`MainLogSinkTests` covers several sinks in one capture: routing by flow, the process sink, masking of unscoped lines with every sink's secrets, per-sink partial lines and their flush when one sink closes, detached work, and refusal of a mixed console format. `HostedRuntimesInProcessTests` starts twelve production hosted runtimes in one process and checks one capture, one record per line and each runtime's tenant field. `StartupDiagnosticsTests` uses the existing DevTools subprocess harness for concurrent ordinary stdout/stderr writes and flushes, including stderr redirection and a failing file device. It checks console content, synchronous complete file records, partial-line disposal and harmless writes through retained capture references after disposal. Its fatal-startup cases (occupied HTTP port, unusable catalog, invalid configuration at entry) also require the launcher-named startup failure file to hold exactly the fatal lines written to stderr.

The unchanged maintained `test/app-e2e/logs.e2e.mjs` exercises the production App's menu/sole-tab controls, bounded history/live/time/text safety, restore, popout, embedded and mobile dark-mode paths, partial UTF-8 and observed replacement. [Artifact publication](./dotnet-artifacts.md) has its own producer and application scenario. Native Windows qualification separately exercises the actual Main writer's append-only access, opened-object identity, HTTP/realtime delivery, shared external append, rename/reset and final flush; Linux test results alone do not establish those Windows behaviors.
