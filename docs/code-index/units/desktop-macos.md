# Unit: macOS Desktop host

Files: `dotnet/Foxwarm.Desktop.Mac/Foxwarm.Desktop.Mac.csproj`, `dotnet/Foxwarm.Desktop.Mac/Program.cs`, `dotnet/Foxwarm.Desktop.Mac/DesktopApplication.cs`, `dotnet/Foxwarm.Desktop.Mac/Info.plist`, `dotnet/Foxwarm.Desktop.Mac/README.md`, `dotnet/scripts/qualify-desktop-mac-package.mjs`

## Contract

The AppKit application owns one WKWebView window and the complete same-process [Main host](./host-runtime.md). It uses the original WebUI and [shared delivery resource graph](./core-delivery-cli.md); no separate backend, MAUI layer, privileged JavaScript bridge, or Desktop-specific Agent migration participates.

Main data defaults to the user's `Library/Application Support/Foxwarm/Desktop/data`, with the existing `FOXWARM_DATA_DIR` override. `HostPaths.ForDataRoot` and `ModelConfiguration` retain the canonical Agent layout and configured `paths.agentsDir`. There is no sibling Desktop workspace. WebKit owns its application-specific persistent profile under the user's Library (`WebKit`, `Caches` and `HTTPStorages` entries named by the bundle identifier), also when `FOXWARM_DATA_DIR` selects another data directory: public WebKit API offers only the default store, a non-persistent store or UUID-identified stores beneath that same profile, and a store in an arbitrary directory needs private SPI. The non-persistent store would lose the WebUI's browser preferences on every restart. Data directories therefore share one cookie jar, which is harmless because only one instance runs at a time and each startup installs its own token cookie before navigation. Main state and the compiled content-rule store stay outside the application bundle.

`Program.Main` restores `ObjCRuntime.Runtime.OriginalWorkingDirectory` before private helper dispatch. Apple's native launcher changes cwd to the bundle before managed entry; leaving that change in effect makes the real exec child ignore its caller-selected working directory and write into the bundle. It also sets the standard `APP_CONTEXT_BASE_DIRECTORY` to the bundle's `Contents/MonoBundle` before Main or helpers initialize: managed Apple builds already use that resource root, while NativeAOT otherwise defaults to `Contents/MacOS`. This preserves all existing Main consumers of `AppContext.BaseDirectory`, including login, bootstrap resources, Monty, artifacts, and the PTY helper, without a second resource graph. Exec, Vector, and terminal helpers return before the per-user mutex or `NSApplication` startup.

## Native shell and security

`DesktopApplication.StartAsync` starts Main with its ordinary canonical paths and lifecycle, then uses `CaptureDesktopAsync` and the remembered-port behavior documented by the [Desktop HTTP boundary](./host-runtime.md#desktop-boundary). It posts the token to the owned endpoint's existing `/api/auth`, then installs a native HttpOnly, SameSite Strict cookie before navigation. The startup status label is removed once the web view is attached so it does not remain in the accessibility tree. The token does not enter navigation URLs or JavaScript.

The navigation delegate accepts the owned HTTP origin. External HTTP(S) top-level navigation and popups use the default browser. WKContentRuleList blocks off-origin HTTP(S) resources; media capture is denied by the UI delegate. The host installs no script-message handler or injected host object. The Edit menu supplies standard native text-editing selectors. The UI delegate supplies native alert/confirmation sheets and the file chooser used by the original WebUI's existing browser APIs.

Close keeps the process and Main alive. Open Foxwarm and the application-reopen delegate restore the existing window. The per-user mutex admits one instance; a second launch, including an explicit `open -n`, asks LaunchServices to open the running instance's bundle URL, so the running instance is activated and its reopen delegate shows the window, as for a Finder or Dock launch, before the second process exits. Quit returns AppKit's deferred termination reply while startup settles and the existing Main drain/disposal completes. Ordinary Main shutdown also terminates the shell through its host observer. That observer is installed before the desktop publishes its port or initializes WebKit, and posts termination to AppKit's main thread; an immediate administrative shutdown must not wait for browser startup to install its lifecycle observer.

## Build and qualification boundary

The project uses bundle identifier `net.foxwarm.desktop`, matching the canonical project domain. It targets `net10.0-macos`, macOS 15 under the existing .NET 10 support policy, and the existing precompiled `osx-arm64` native dependency path. It references the full Main project. `PrepareMacBundleResources` maps inherited Main content beneath the Apple assembly/resource root while retaining Main's relative paths. It removes repeated source identities before Apple's native-library processing: the PTY library can arrive through more than one project-reference path, and duplicate processing races on the same temporary dylib. Main's `Delivery.targets` content, including the browser host bundle, travels through the same inherited-content mapping. The Apple SDK links every `DynamicLibrary` publish item into the executable as a load command; the target therefore marks bundled dylibs other than the .NET and Apple runtime packs' as `PluginLibrary`, which the SDK copies to the same bundle location and signs without linking. Main loads the PTY library by path and LanceDB, SQLite and Skia by `DllImport` name from the resource root, and sharp's addon reaches libvips through its own rpath, so none of them belongs in the executable's load commands. A missing or incompatible optional library then fails only its feature rather than every process start, and helper re-execs (exec, Vector child, PTY dispatch) no longer map LanceDB and libvips. The executable keeps only system libraries and the .NET runtime pack's libraries (`libSystem.*.Native` under NativeAOT); the extracted-app acceptance checks this with `otool -L`. `CreatePackage=false` stops Release publishes from producing the SDK's unsigned installer package.

Managed builds and `dotnet publish -p:PublishAot=true` use the Apple SDK directly. The latter remains subject to the complete application's trimming and NativeAOT constraints. The release ships the NativeAOT build as `foxwarm-desktop-osx-arm64.zip` ([release decision](./release-packages.md#macos-desktop-app)); there is no signing/notarization policy. The optional full Code workbench is not added here.

Managed and NativeAOT Intel x64 runs exercised the original WebUI/Setup, native cookie/WebSocket and resource policy, native dialogs and window/menu lifecycle, real ToolScript/exec and Darwin PTY helpers, canonical Agent paths, persistence/restart, and local/child Vector indexing/search/recall. The Intel Vector runs used a temporary native LanceDB build matching the pinned binding source; no x64 package, acquisition fallback, or release target is added. Managed and NativeAOT arm64 runs on Apple Silicon (macOS 26.5.2) repeated the WebUI/Setup, turn, ToolScript, exec, PTY, window/menu lifecycle, restart and Vector checks with the precompiled NuGet arm64 native assets; NativeAOT Main and its Vector child ran without CoreCLR. The release workflow's `macos-desktop` job repeats startup, native sign-in, PTY, Setup, ToolScript/exec, Vector, menu Quit, restart and second launch against the extracted release ZIP on every run ([qualification](./release-packages.md#desktop-producer-and-qualification)). Ad-hoc signatures do not establish Developer ID signing or notarization. Minimum-OS execution, complete browser/file-dialog behavior, the optional full Code workbench, and other optional services require separate evidence.
