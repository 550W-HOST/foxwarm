# Unit: Desktop packages, installer and qualification

Files: `scripts/release/foxwarm-desktop.iss`, `scripts/release/install-inno-setup.ps1`, `scripts/release/smoke-desktop-installer.ps1`, `dotnet/scripts/desktop-window.ps1`

Secondary files: `dotnet/scripts/validate-desktop-package.mjs`, `dotnet/scripts/qualify-desktop-package.mjs`, `dotnet/scripts/qualify-desktop-mac-package.mjs`, `dotnet/scripts/desktop-cleanup.mjs`, `scripts/release/package.mjs`, `scripts/release/package.test.mjs`, `.github/workflows/release.yml`, `dotnet/Foxwarm.Desktop/Foxwarm.Desktop.csproj`, `dotnet/Foxwarm.Desktop/README.md`, `dotnet/Foxwarm.Desktop.Mac/Foxwarm.Desktop.Mac.csproj`

The Desktop editions of the [release packages](./release-packages.md): their packaging decisions, the Windows installer, and the producers and acceptance lanes that qualify them. The hosts themselves are the [Windows Desktop boundary](./desktop-windows.md#desktop-boundary) and the [macOS Desktop host](./desktop-macos.md).

## macOS Desktop app

<a id="d-release-macos-desktop"></a>
**Decision: the macOS Desktop ships as a NativeAOT app in a zip without Developer ID signing** (user, 2026-11-12, Foxwarm 0.9.6). Apple Silicon trials favored NativeAOT for memory (about 70 MB against 160 MB or more for managed Debug), helper start-up (0.02 s against 0.10 s) and size (224 MB bundle). The `desktop-osx-arm64` target publishes the [AppKit host](./desktop-macos.md) with `-p:PublishAot=true`. It archives `Foxwarm.app` as `foxwarm-desktop-osx-arm64.zip` with `ditto -c -k --keepParent`. The Apple SDK ad-hoc signs the bundle; no files may be changed after signing, so it carries no `release.json` and uses `CFBundleShortVersionString` instead. It has no notarization, dmg, installer or updater. A dmg would still need the same Gatekeeper override; the install guide gives per-archive quarantine removal.

### Bundled Code on macOS Desktop

**Decision: bundle Code with the macOS Desktop** (user, 2026-11-18), revising the 0.9.6 choice to keep it optional. As on Windows Desktop, Code opens without a separate download, at the cost of a larger ZIP. The complete pinned Code OSS and YAML resources, built-in language extensions and notices enter the shared asset pack before signing. Server packages keep Code separate.

The Apple SDK writes the bundle to `bin/Release/net10.0-macos/osx-arm64/` and leaves the publish directory empty. `package.mjs` removes the stale bundle before publishing and copies the new bundle whole. The arm64 `macos-desktop` job selects Xcode 26.3 through `DEVELOPER_DIR` without changing the image default, and pins workload manifest 26.2.10233 for its macOS 26.2 SDK. See [Desktop producer and qualification](#desktop-producer-and-qualification).

## Desktop producer and qualification

### Windows Desktop app

<a id="d-release-windows-desktop-native"></a>
**Decision: the Windows Desktop ships as a NativeAOT app** (user, 2026-11-13, Foxwarm 0.9.6), as the [macOS Desktop](#macos-desktop-app) does, revising the earlier managed decision. The `desktop-win-x64` target (`kind: 'desktop'`, `native: true`) publishes the [WinUI host](./desktop-windows.md#desktop-boundary) with `-p:PublishAot=true`, keeps the Code workbench and ships no Visual C++ runtime ([static C runtime](./release-packages.md#visual-c-runtime-in-windows-packages)); it needs no .NET installation or redistributable. The asset name, layout (one `foxwarm-desktop-<version>-win-x64/` directory, `release.json` with `native: true`) and data location are unchanged, so an existing user replaces the extracted folder as before. Windows App SDK API metadata minimum is 17763; the supported Windows versions follow the .NET 10 policy.

Desktop uses the Windows App SDK WinUI component 2.6.5. Its manifest/XAML/PRI generation requires Windows tools, so the Windows job produces `desktop-win-x64` with `scripts/release/package.mjs` and the same `--native-libraries` directory as the server packages. The Ubuntu producer builds the Linux server targets and forwards the shared `code-resources` archive. Windows extracts that same pinned pack, builds the shared assets, produces Desktop, checks the Desktop's imports with `windows-imports.mjs`, fails when the NativeAOT compiler reports a warning in the Desktop's own code (`Foxwarm.Desktop.*`; Main's warnings are gated by the Tests native lane, and release publications carry no symbols, so warnings name only the caller), and runs the extracted-ZIP acceptance. The `foxwarm-desktop-win-x64.zip` artifact feeds checksums and tag publication after Windows qualification.

`validate-desktop-package.mjs` requires the NativeAOT layout: `release.json` with `native: true`, the native x64 executable, WinUI/Windows App SDK/WebView2 natives and resources, the shared resources and the Code workbench, and no .NET runtime, `*.runtimeconfig.json`, `*.deps.json` or managed assembly (any `.dll`/`.exe` outside `node_modules` with a CLR header). `qualify-desktop-package.mjs EXTRACTED_DIRECTORY REPORT` then launches the extracted app with a temporary data directory, configured Agent root, unrelated cwd and a local model and embedding peer. It attaches to WebView2 for native cookie sign-in, the authenticated WebSocket and Setup, executes the packaged esbuild/sharp, runs a native ToolScript turn with the exec helper, and indexes and searches through exactly one packaged Vector child (`Foxwarm.Desktop.exe --foxwarm-vector-child`), which loads `lancedb_ffi.dll` while Main does not. The process must not load `coreclr.dll`, `hostfxr.dll`, `hostpolicy.dll` or `clrjit.dll`. Window and notification-icon checks use `dotnet/scripts/desktop-window.ps1`, which touches only the Desktop process's own windows: Explorer must hold the icon (a no-op `NIM_MODIFY` succeeds only for an existing icon); closing the window (`WM_CLOSE`) hides it while Main stays ready and the icon stays; the icon's double-click notification shows it again; the icon's right-click opens the native menu (`Open`, `Exit`), whose **Exit** item is clicked with the mouse. Exit must end the process with status 0, log `Main stopped.` and end its child processes. A restart keeps origin, token, models and history, and `/admin/shutdown` ends the app with status 0. A `--tray` start must register the icon without a visible window or a WebView2 process; a further `--tray` start must exit by itself and leave the window hidden; a further ordinary start must exit and show the running copy's window, whose WebView2 must then sign in; `--exit` must end the app with status 0, one more `Main stopped.` and no remaining child process, and `--exit` with nothing running must succeed. Interactive file dialogs, Windows sign-out, real-keyboard and HiDPI behavior are outside this lane.

### Windows Desktop installer

<a id="d-release-windows-desktop-installer"></a>
**Decision: the Windows Desktop also ships as an Inno Setup installer** (user, 2026-11-19, Foxwarm 0.9.7). `foxwarm-desktop-win-x64-setup.exe` installs the publication of the [Windows Desktop app](#windows-desktop-app) for the current user without elevation; it becomes the primary download, and `foxwarm-desktop-win-x64.zip` keeps shipping unchanged as the portable app. There is no auto-update (Velopack was the rejected alternative): a newer setup run over the installation is the upgrade. Like every Windows package it is unsigned, and the documentation says nothing about SmartScreen ([native packages decision](./release-packages.md#native-macos-and-windows-packages)). Signing, auto-update, winget and a server installer are outside it.

Behavior: the default directory is `{autopf}\Foxwarm`, which per-user installation resolves to `%LOCALAPPDATA%\Programs\Foxwarm`; it adds a Start menu shortcut, an Apps entry under the fixed AppId `{6BE01B0C-EDFF-4777-A5DE-FB2F3BB5167D}` with the release version, and on request (unchecked by default) a sign-in start, the `HKCU\...\Run` value `Foxwarm` = `"<directory>\Foxwarm.Desktop.exe" --tray`. An upgrade keeps the directory and the sign-in choice, and runs the previous version's uninstaller silently before copying, so files a release no longer ships do not stay behind. Program files never hold data; the data directory (`%LOCALAPPDATA%\Foxwarm\Desktop`, which installed and portable copies share) is never touched by setup or uninstallation, and the single-instance lock keeps the two from running at once. The wizard is in Simplified Chinese when the Windows display language is Chinese and in English otherwise, without a language dialog (`LanguageDetectionMethod=uilanguage`, English first as the fallback); the uninstaller keeps the language of the installation, and `/LANG=` overrides it. Each custom message exists in both languages, which `package.test.mjs` checks. A missing WebView2 Runtime (Edge Update's `pv` value, machine or user) is reported on the last page with a link to Microsoft's download page instead of the launch option; the runtime is not bundled.

Stopping the app: setup and uninstallation run `Foxwarm.Desktop.exe --exit` from the installation (and from a previous installation location) before they change any file. The running copy started from that executable receives a per-user named event and exits through the tray's **Exit** path, so Main shuts down normally; the request waits up to 60 seconds until no process runs that executable, and fails otherwise. A failure stops setup with a message (exit code 7 when silent) and cancels uninstallation (Retry/Cancel when interactive). A copy running from another directory, such as an extracted ZIP, is not asked; it holds its own files, and the Desktop's single-instance lock is not tied to a directory. Restart Manager closing (`CloseApplications`) is off because it would end the app without its shutdown.

`--tray` starts Main with the notification icon only, when the local instance is selected ([Desktop instances](./desktop-instances.md#d-desktop-instances)). The window and WebView2 are created when the window is first opened, and a further `--tray` start exits without showing the window; a further ordinary start, such as from the Start menu after a sign-in start, shows the running copy's window ([Desktop boundary](./desktop-windows.md#desktop-boundary)). These two flags are the app's only installer-specific behavior.

Producer: `scripts/release/foxwarm-desktop.iss` is compiled by `package.mjs --inno-setup ISCC` from the staged `desktop-win-x64` directory, after the ZIP is written and before staging is removed, so both files carry identical program files without a second publish; the setup is listed in `SHA256SUMS` like any package. The Windows job installs the pinned Inno Setup 7.1.1 with `scripts/release/install-inno-setup.ps1` (SHA-256 checked, portable mode, nothing registered), because the `windows-2025` image's Inno Setup has not been stable across image versions. After the extracted-ZIP acceptance (which also covers `--tray` and `--exit`), `scripts/release/smoke-desktop-installer.ps1` installs the setup silently into a non-ASCII directory, compares the installed files with the ZIP's, checks the shortcut, the Apps entry and the Run value, starts the registered sign-in command from an unrelated directory (notification icon present, window hidden, no WebView2), reinstalls over the running app and uninstalls it while it runs, each of which must stop it through its shutdown (exit code 0, one more `Main stopped.`), and requires the data to remain and nothing else to. Windows sign-in itself is not exercised; the smoke runs the registered command line with only `FOXWARM_DATA_DIR` added.

The [macOS Desktop](#macos-desktop-app) producer extracts `code-resources` into the existing preparation paths, publishes with [Code bundled](#bundled-code-on-macos-desktop), and logs the ZIP size. `qualify-desktop-mac-package.mjs EXTRACTED_APP REPORT` runs on Apple Silicon against the extracted bundle with a temporary data directory, configured Agent root, unrelated cwd and `TMPDIR`, and a local model and embedding peer. It checks identity/version, required resources and notices, no managed assemblies, debug symbols, installers or instance data, and `codesign --verify --deep --strict`. `otool -L` must show only system and bundled .NET runtime libraries for the executable, and no Homebrew dependencies for any bundled native. It runs the bundle's esbuild and sharp. WKWebView has no remote debugging protocol, so the window is read through the Accessibility API (System Events, which the hosted runner allows for `osascript`): the signed-in application ("Open setup") must render, without "Sign in again" or the startup label. Unauthenticated `/api/auth/session` is refused. The check requires Code OSS, built-in language and YAML resources and notices in `Contents/MonoBundle/foxwarm.assets` and fetches the authenticated `/vscode-web` bootstrap and workbench JavaScript. The test then exercises PTY input/output/resize/cancel, Setup save, a native ToolScript turn with the exec helper, and Vector indexing and search through exactly one packaged Vector child, which maps LanceDB, while Main maps neither LanceDB nor libvips (`lsof`). Quit Foxwarm through the menu must end the process with status 0, log `Main stopped.` and leave no child process. A restart keeps origin, token, models and history, and a second launch while the window is closed must exit 0 and reopen the window. `/admin/shutdown` must also end the app with status 0. Interactive file dialogs, quarantine handling, the WebKit profile and real-keyboard or VoiceOver behavior are outside this lane; WebKit's profile under the runner's Library is left to the disposable runner.
