Contains a bounded .NET 10 host and compatibility probes outside the production Node.js runtime and normal test graph. One solution owns three projects; source folders do not represent separate assemblies.

## Local file usability

`Tools/FileToolCore` owns physical byte-line scanning, bounded text rendering, directory listing and atomic write mechanics; `WorkspaceTools` retains caller validation/path authorization, parent/cache handling and approved definitions. No symbolic-link traversal, FIFO/device reads, tilde/environment expansion, image dispatch, Node adapter or OS sandbox is added. Existing edit/patch limits and exec/cwd behavior remain unchanged.

Source-style physical lines recognize LF, CRLF and bare CR, including chunk-split CRLF; exact selected terminators remain intact. Empty files have zero lines, trailing terminators create no virtual EOF line, and a final unterminated segment receives a single tool LF before the metadata footer plus an explicit no-trailing-newline notice. Omitted/null/zero line bounds are absent; finite bounds floor, start clamps to 1 and end to 0. Small files up to 1 MiB are read fully and report exact totals. Source file bytes are never rewritten by read.

Expired/oldest entries are pruned under a short lock that never spans filesystem I/O. Retry requires overwrite:true and no content alongside contentRef, may select another authorized target, retains the reference on failure and consumes on success. Path validation precedes cache lookup and effects. No persisted cache, timer service or durable receipt is created; after restart an old ref is honestly missing/expired, while prior canonical error/result history and successful file bytes remain intact.

The concentrated Files workflow covers actual large/mixed/giant/chunk-boundary reads, directory pagination, newline/zero/negative/range metadata, Unicode/binary display, denied symlink/FIFO, cached retries/scope/consumption/entry and aggregate eviction, uncached oversized supplied writes and clean-process restart. ## Async and awaited compaction lifecycle

`SessionCompactor` owns one transient operation per Session with captured admission mode, exact operation identity, independent cancellation, planning/ready/applying state, producer completion and final completion. Async-capable explicit requests begin immediately while foreground requests or effects remain active. False-capability busy requests report unavailable; idle explicit requests own a strict standalone busy claim, while normal automatic boundaries may await planning inside the foreground owner. Background planning never replaces foreground draft, phase or cancellation state.
