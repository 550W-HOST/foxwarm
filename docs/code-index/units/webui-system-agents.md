## Purpose

The Agents section of the [System page](./webui-system-view.md): which Agents exist and how they relate, and for one Agent its Sessions, the layers its system prompt is built from, the rule layers its tool calls must pass, and its settings. It uses the System page's [list and detail layout](./webui-system-view.md#list-and-detail-layout); the routes are in [dotnet-webui-agents-setup](./dotnet-webui-agents-setup.md).

## Key Exports

- `SystemAgents` (`SystemAgents.tsx`) — the section; `creatorTreeOrder` orders the list; `AgentRegistryEntry` is the `GET /api/agents` row.
- `PromptLayers`, `FrameworkPromptDialog` (`SystemAgentLayers.tsx`) — the Prompt tab.
- `RuleLayers`, `RuleList`, `isAllowlistLayer` (`SystemAgentLayers.tsx`) — the Rules tab and its rule rendering.
- `AGENT_RULES_SCHEMA` (`packages/shared`, exported through `configSchemas.ts`) and `agentRulesYamlModelUri(agentId)` (`yamlConfigSchemas.ts`, registered for `**/foxwarm-agent-rules.yaml`) — the YAML schema of one Agent rule layer: v1 policy rules without the caller selectors `AgentRulePolicy.Parse` rejects.
- `AgentSettingsFields` — the settings form shared with New agent.

## Behavior

- The Agents summary counts real workspace directories, including valid zero-session Agents that do not appear in Session-derived catalog summaries. Counts use singular and plural forms ("1 agent", "4 agents").
- The list is the creator tree (`createdBy`): each Agent under the Agent that created it, `main` first among top-level Agents, then by ID; members of an unresolvable creator cycle are listed at the top level. A row shows an activity dot, the ID, its rule state (Blocked when its creator chain can't be resolved or a fail-closed migration layer is unchanged, Allowlist when its own layer ends in an enabled selector-free deny, otherwise its rule count), where its memory comes from (`memory from <inherit>` or own memory), its default Node, the Session count (or active count) and last activity (`lastActivity`). Hovering offers a New session button. Order is independent of selection.
- The inspector header shows the ID, memory source, creator and start Node with a New session action, the legacy-isolation migration notices, and four tabs: Overview, Prompt, Rules (with the rule count) and Settings. An `agentRequest` prop (`{ agent, nonce }`, used by the Sidebar's Agent group menu for Agent settings) selects the Agent on the Settings tab.
- **Overview**: the Agent's newest Sessions from the Agent-filtered `/session-list/architecture?agent=` query (the System list holds only a bounded window), merged with live loaded rows; eight are shown with "Show all", and when the Agent has more Sessions than were loaded, a link opens Sessions filtered to that Agent. A Session opens in the Sessions inspector. Short summaries of what the Agent can do (its rule state and the creator ancestors whose rules also apply) and of its prompt chain link to the Rules and Prompt tabs.
- **Prompt** lists the layers its system prompt is built from, in order: the Foxwarm framework prompt (View opens a read-only dialog with the text from `GET /api/agents/{id}/framework-prompt`; when parts depend on the model it names the default model the text is shown for), the installation additions `agents/00_SYSTEM.local.md` (Open in Code, or Create in Code when absent: an empty file is written through Code's `PUT /api/vscode-web/fs/write-file` with `create=true&overwrite=false`, then opened; an existing file is opened as is), the memory of each Agent it inherits from, and its own memory. Memory layers list the bounded, symlink-free Markdown manifest of `GET /api/agents/{id}/memory`; files and folders open in Code on master without copying content through the registry API.
- **Rules** shows the layers every tool call must pass, in evaluation order ([Agent-local authorization layers](./tool-authorization.md)): the installation policy from `GET /api/setup/authorization` (read-only, with its default action when not allow, and Edit in Setup, which opens Setup on its Authorization tab through App's `tabRequest`), each creator ancestor's layer (read-only, collapsed, with who may change it: administrators and the Sessions of that Agent's own strict creator ancestors), then the Agent's own layer. The own layer is edited as YAML in `SimpleCodeEditor` with `AGENT_RULES_SCHEMA` (policy rules without the caller selectors the server rejects) and saved with `PUT /api/agents/{id}` `{rules}`, which replaces the whole layer; YAML errors and server rejections show inline and leave the stored layer unchanged.
- **Settings**: the shared Agent settings form ([D-webui-agent-settings-form](#d-webui-agent-settings-form)) with the inheritance chain and one Reset/Save pair (`data-agent-settings-reset`, `data-agent-settings-save`) enabled only for changes. A save disables the form and both buttons (Save reads "Saving…") until the PUT and the following Agent-list reload finish; the draft then resets from the saved Agent. The server already reports the change before that reload ends, so `mainHostKnowledge.e2e.mjs` waits for the inspector to finish saving before it edits again. Agent update changes only mutable inheritance and new-session default Node/working-directory metadata; Agent ID is not renamed because it is a durable namespace, permission scope, and archive identity component.
- The section reuses `AgentCreationMenu` for Agent and Session creation. Its shared `+` opens New session directly, with Agent tags and a trailing New agent tag in the same modal flow.
- Agent deletion (Settings tab) requires exact typed Agent-ID confirmation. `main` is immutable; Agents inherited by another Agent and Agents with active Sessions are rejected. Confirmation authorizes destructive removal of idle owned Sessions and any queued work through canonical Session deletion, then removes the self-owned workspace and Agent metadata; durable Session archives and their reserved identities remain.

## Design Decisions

The section's layout follows [D-webui-system-split-view](./webui-system-view.md#d-webui-system-split-view).

### D-webui-architecture-agent-registry

[2026-08-25; the card layout is superseded by [D-webui-system-split-view](./webui-system-view.md#d-webui-system-split-view)] Persistent Agent CRUD belongs beside runtime topology because an Agent is a workspace/memory owner, not a Sidebar branch. Create and mutable metadata update are ordinary registry actions; rename is intentionally absent because Agent ID participates in Session namespace, permission scope, and retained archive identity. Memory navigation is manifest-only and path-confined, while destructive deletion uses typed confirmation and backend lifecycle blockers.

### D-webui-agent-settings-form

[2026-11-02, user decision] New agent and the Agents inspector use one `AgentSettingsFields` form, so creation and later editing offer the same settings with the same order, labels, choices and hints: Memory inheritance (excluding the Agent itself and Agents that are not inheritable) and Session defaults (Node, `master` by default, and working directory). [2026-11-10] The Isolation section was removed with legacy isolation. The master Node is shown by its Node name (`master`), not as "Main", which named the retired multi-process server role. Creation sends only chosen settings through the existing `POST /api/agents` fields. The working directory applies only on the default Node. New session shows the selected Agent's start location from its saved settings (`Starts on <Node> · <directory>`) but does not override it; the line is omitted when no placement is configured. When `GET /api/nodes` reports an installation `agentDefaultNode` other than master, the Node choice separates unset (`Installation default (<Node>)`) from an explicit `master`, and the start location and directory placeholder use that default for Agents without their own.
