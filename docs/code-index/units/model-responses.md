# Unit: OpenAI Responses HTTP and WebSocket adapters

Files: `dotnet/Foxwarm/Models/Responses/HostedResponsesTools.cs`, `dotnet/Foxwarm/Models/Responses/OpenAIResponsesClient.cs`, `dotnet/Foxwarm/Models/Responses/ResponsesRequestPlan.cs`, `dotnet/Foxwarm/Models/Responses/ResponsesStreaming.cs`, `dotnet/Foxwarm/Models/Responses/WebSockets/ResponsesWsChatService.cs`, `dotnet/Foxwarm/Models/Responses/WebSockets/ResponsesWsResource.cs`, `dotnet/Foxwarm/Models/Responses/WebSockets/ResponsesWsState.cs`, `dotnet/Foxwarm/Models/Responses/WebSockets/ResponsesWsTransport.cs`

## Purpose

Plans and sends Responses requests, collects event streams, executes supported hosted tools, and manages stateful Responses WebSocket leases/handshakes.

## Stable methods and callers

- `ResponsesRequestPlan` derives request JSON, previous-response/state handles, tool definitions, image parts, and journal-safe request text.
- `OpenAIResponsesClient.ExecuteAsync` owns HTTP response status/error handling and returns a streaming/non-streaming attempt result.
- `ResponsesEventAccumulator`/`ResponsesSseCollector.CollectAsync` parse response events, record output text/reasoning/tool calls/usage, and stop on terminal/error events.
- `HostedResponsesTools` exposes provider-hosted search/hosted tools as definitions/results; it does not grant local filesystem or Session authority.
- `ResponsesWsChatService`, `ResponsesWsResource`, `ResponsesWsState`, and `ResponsesWsTransport` own connection lease, handshake, resumable state, close/error, and resource disposal for WebSocket turns.

Callers: `SessionChatService`, `ModelRequestOwner`, model routing, image transport, and `LlmRequestJournalStore`. The turn host decides when a provider result becomes canonical Session history.

## Contract and side effects

HTTP/SSE and WebSocket attempts preserve provider request IDs and usage/error provenance. Both adapters return normalized result usage even when an empty completed response has no canonical assistant row, so the owner can commit cumulative totals without manufacturing history. A disconnected stream or invalid event leaves the attempt incomplete; retry preparation must use the safe request-history state rather than duplicating partial assistant/tool records. Hosted tools remain provider-scoped and are not confused with local ToolAuthorization.

## Replay and hosted output boundaries

WebSocket state belongs to the concrete request/cache generation and its owned connection lease. The complete semantic body is prepared and its digest recorded before connection-specific suffix selection or reconnect. Reuse depends on compatible committed input and tool pairs, not merely a prior response ID. A malformed function-argument string can remain a canonical tool call with `argsParseError` and an ordered tool error response; it must not erase valid sibling effects or be indiscriminately treated as another provider retry. A reconnect sends the appropriate complete request rather than pretending a failed socket retained state.

Native `web_search` and `image_generation` declarations are purpose-gated: normal turns and ToolScript one-shot requests may enable them; compact/background planning and Setup do not. Generated bytes pass through the existing blob store before canonical result/journal publication. Limits are 32 MiB decoded per image, 64 MiB cumulative per physical attempt, and eight successfully externalized images. Partial-image events carry status only, not preview bytes.

Same-concrete generated-image replay uses verified original blob bytes. Cross-concrete/protocol requests use bounded placeholder/local-ID guidance without reading that blob; a missing same-concrete blob fails locally before send. If all generated outputs fail validation/externalization, the result is a non-retryable, non-countable response error after provider output processing, not a pre-send hydration failure. Web-search metadata and generated-image allowlisting have different contracts; do not apply the image allowlist to search output. Canonical history and journal retain references, not hydrated base64. See [model request ordering](../threads/model-request-and-streaming.md) and [image ownership](../threads/images-and-attachments.md).
