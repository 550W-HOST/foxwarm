## Purpose

Implements shared canonical file reads/writes/patches over native or target primitives, native path/cwd rules, persistent native/provider and parallel exec, file delivery, and explicit handoff confirmation.

Storage: `LocalExecManager` reads and replaces `state/running-exec.json` as the `RunningExec` state document ([storage context](./storage-context.md#state-documents)).

## Stable methods and callers

- `MainNativePaths` resolves native file/exec defaults from the actual Agent directory and explicit Session cwd; the separate generic policy and Agent-local layers authorize physical destinations; `FileToolCore` scans/reads through the [shared native primitives](./dotnet-node-primitives.md); `FileToolCore.WriteBytes` performs ordinary native content writes and `PendingWriteRefs` tracks retryable write artifacts. `FileToolWrite` remains the separate atomic delivery/memory publication owner.
- `ITargetFileOperations` supplies opaque target primitives. `WorkspaceTools.Target` connects the existing workflow to those primitives without a second parser; `FileToolCore.ReadContent` and `FormatDirectory` share the scanner/formatting with native files. `TargetFileContent` composes bounded full reads and chunked transfer writes; [.NET providers](./dotnet-node-providers.md) maps actual generic consumers and target authority.
- `UnifiedEdit.Apply` owns original-source matching, nonoverlapping range validation and literal single/batch replacement shared by ordinary edit and operation-owned compact repair; each caller retains its own paths, authorization, effects and errors.
- `WorkspaceTools.Target.ReadHeaderAsync` reads at most twelve bytes through the native stream or existing target primitive. `WorkspaceTools` chooses image versus text from the shared raster signature classifier, never the filename extension; directories bypass image reads. Full image reads, text budgets, provider snapshots and canonical authorization retain their existing owners. Main regular-file, policy and opened-handle admission use the shared Linux type primitive with their original flags/error handling; native directory formatting distinguishes nonregular entries from files without following symlinks. Provider stat kinds remain target-owned.
- `WorkspaceTools` exposes repository-aware list/read/write/edit/patch operations; `WorkspacePatch` parses/apply-checks bounded patches, accepts Unicode punctuation/space-equivalent context after strict matching, and reports only the original failing hunk (anchor and context/deletion/insertion prefixes) on a context mismatch, including EOF cases. `FormatContextErrorPath`, `FormatBoundedFailedHunk`, and `FormatContextMismatch` bound the diagnostic to 1,600 characters with head/tail retention for long hunks; no guessed candidate or file preview is included. The same update engine serves ordinary patches and operation-owned compact repair.
- `LocalExecManager` owns Main's single Source-shaped active registry, native/provider starts, foreground waiting, exact-owner notification and tracking retirement. It supports Linux and Windows; other hosts keep the existing unavailable local-exec boundary. The registry is published with the shared [durable state-file helper](./dotnet-node-primitives.md#durable-state-files) (file sync, atomic replace, directory sync); the missing-status fallback uses the bare atomic replace. On Windows a reader that allows deletion (Node's `fs.readFile`, most scanners) no longer blocks a save. A save that still fails after its in-memory change (a reader that does not allow deletion) is written again by the next reconciliation, as in the CLI, so a delivered completion does not remain in the file and repeat after a restart. Once the command has started, its in-memory record is the tracking authority: a failed launch, background or foreground-retirement save stays pending rather than turning the started command's receipt into a tool error or leaving a record that neither foreground finalization nor completion delivery would retire. Native shell launch, scripts, bounded capture and output formatting are shared with CLI through [NodePrimitives](./dotnet-node-primitives.md), not a second manager. Main retains authorization, exact Session persistence, Agent cwd defaults, provider adaptation and completion authority.
- `FileDeliveryDefinitions` turns approved paths into authenticated delivery metadata; `HandoffConfirmation` requires `handoffRecall` before `message` and `handoffConfirmation` after every other argument except `currentSessionTurnAction` before enabled inter-agent handoffs, and reports all problems with a corrected argument order in one rejection.

Callers: `SessionToolExecutor`, `WebUIChannel.Files/Images`, Code services, and Node-compatible local tooling. All effects pass the unified authorization boundary first.

## Contract and side effects

Ordinary native `write(overwrite:true)`, `edit` and patch updates truncate and write the existing file in place, following symlinks and preserving its inode, hardlinks and permissions. `write(overwrite:false)` uses exclusive creation, including collisions with dangling symlinks. Patch adds retain the Source existence-check-then-write ordering. These operations are not atomic publications or rollback transactions: write failures may leave partial content, and a later patch-operation failure retains earlier completed effects. Main and CLI share the native write primitive; authorization, path resolution, parent creation and error presentation remain with their callers. Authority/configuration/Archive saves and separate file-delivery publication are unchanged.

Path/cwd checks are security and data-loss boundaries, not convenience validation. Reads/writes are bounded; patch/write retries retain artifact lifetime and do not assume a failed transport erased a successful filesystem change. Exec output is truncation-aware and process termination is explicit. Lifecycle cancellation ends a launched local exec's foreground wait with a process-shutdown receipt; explicit Stop/Run queued retain their own cause. Neither cancellation kills the independent process, reverses its effects, or replaces its actual finished result. The executor stays available until foreground turn owners settle. File delivery exposes deployment-relative/authenticated references, not local absolute paths.

## Design decisions

- [2026-09-05] Master, CLI remote, and provider-composed file reads share one byte-level LF/CRLF/bare-CR physical-line scanner and footer formatter in `fileToolCore`; wrapper-specific split/join or warning behavior is prohibited. Retained ordinary text keeps existing UTF-8 decoding, while bounded excerpts keep existing invalid-byte conversion and binary-preview safeguards.

### D-tools-write-contentref-target-reuse

[2026-08-19] A pending `contentRef` is a short-lived cached payload capability scoped to one exact session and agent, not to the path whose failed write created it. A retry may choose any `filePath` that independently passes ordinary resolution, isolation/path authorization, overwrite/createDirs policy, structural service placement, and the selected target-local file backend before any filesystem effect. A failed retry retains the ref for another attempt; only a successful write consumes it. Do not extend refs across sessions, agents, processes, or content replacement.

### D-tools-write-contentref-retry-guidance

[2026-07-24, updated 2026-08-19] Pending-write retry guidance must show a directly executable cached retry `write({ ... })` call containing the actual JSON-escaped failing `filePath`, `contentRef`, `overwrite: true`, and `createDirs: true` when required. State directly that the attempted content is already cached, that the same-session/same-agent ref may instead target another independently authorized `filePath`, and that the model must not include or pass the mutually exclusive `content` argument when using `contentRef`. If the model intentionally corrects or replaces the attempted content, instruct it to omit `contentRef` and call `write` with only the newly generated content plus the desired path and required flags. Never permit both content sources in one call, and do not rely only on indirect wording about generating or sending content again.

- [2026-07-22] Model-facing archive retrieval schemas must distinguish `target`, `vector_query`, and `contentFilter`; do not retain the old ambiguous `query` field for `recall` or `get_session_messages`.

- [2026-07-11] Keep the exec schema's minimum of 1 second but remove its hard maximum. Document 60 seconds as the maximum effective timeout, clamp larger finite requests at runtime, and keep the warning outside truncatable command output.
- [2026-06-05] Ordinary fixed-schema tools no longer expose generic `node` arguments. Session current-node routing and explicit target-bearing tools determine the execution node; special multi-node tools keep explicit source/target node arguments.
- [2026-07-02] `list_sessions` remains removed rather than compatibility-wrapped; current resource-action ownership is canonical in [D-tools-resource-action-consolidation](./tools-registry.md#d-tools-resource-action-consolidation).
- [2026-08-26] Keep the tool name `wait`, remove the model-facing `timeoutSeconds` argument without an alias, and require every new call to declare at least one valid progress source or fallback. Preserve read compatibility for legacy persisted wait state only.

### D-tools-write-parent-policy

**Selected side-effect constraint for [environment-local file operations](../behaviors/nodes-workspaces-and-permissions.md#paths-belong-to-an-environment-and-an-operation).** Parent creation and replacement must follow the requested flags. Filesystem helpers implement that behavior; a convenience retry cannot silently create directories or overwrite unrelated content.

Normal writes attempt the real filesystem operation first. Missing/non-directory parent diagnostics are fallback error enrichment, preserving normal symlink behavior while requiring explicit directory creation.

### D-tools-exec-timeout

Master and node execution use one timeout resolver. Finite values above the effective maximum are clamped with a warning kept outside truncatable command output; invalid and below-minimum values fail.

## Persistent exec storage and lifecycle

`state/running-exec.json` is the one active tracking authority: Source-shaped `execs` plus at most 1,024 `recentExecIds`. IDs are reserved against active/in-flight/recent executions and existing remote claims, not all historical artifacts. Native records without `backend` and supported historical `exec_...` IDs remain readable. Recovery opens only this registry, marks recovered foreground entries notified/recovered and observes only active entries. It does not enumerate retained exec trees or discover another runtime's live authority. No reader, importer, migration or normal-startup scan is provided for the superseded experimental C# per-exec hierarchy.

New native runs put scripts, transient paths handshake, log, cwd and exit JSON together under the actual Agent's `.temp/exec/YYYY-MM-DD`. Shell-selected log names include local time and shell PID; records retain their original absolute artifact paths. Linux uses a detached same-executable launch helper, Bash and a same-executable `--exec-paths` helper at startup rather than Node/TypeScript. After the command ends, the wrapper writes the exit JSON itself (GNU `date` millisecond `finishedAt`, falling back to seconds or an empty value that readers mark estimated; BSD `date` on macOS has no `%N`, so there it writes whole seconds and `ExecOutput.WrapperFinishedAt` takes the milliseconds from the status file's own modification time when that lies within the written second, in Main and the native CLI Node alike, so sub-second commands report a duration), so completion does not depend on the launching executable surviving [source output replacement](./source-main-entry.md#build-and-controls). Console and Desktop dispatch these private helpers before configuration/startup. Windows uses PowerShell 5.1 flags, separate BOM-encoded user source, [direct per-child capture handles](./dotnet-node-primitives.md#windows-persistent-exec-output) and shell-owned cwd/status publication. It has no foreign-process live-cwd reader. Existing native process identity facts prevent inspecting an unrelated reused PID; provider PIDs remain target metadata only.

Native commands inherit ordinary host environment, strip reserved Agent variable names (case-insensitively on Windows), then set the actual `fw_agentdir`, `fw_tmp` and wrapper fields, and finally any `secretEnv` values resolved for this launch, which reach only the process environment ([command environment](../threads/secret-references-and-redaction.md#command-environment)). POSIX unrelated uppercase names remain inherited. Native exec trims explicit and stored cwd before expanding a leading `$fw_agentdir` or `$fw_tmp` token. Whitespace-only values use the existing Session/default chain; a relative `./$fw_tmp` remains literal. Provider cwd stays target-owned under [Provider exec](#provider-exec). Agent tmp preparation and actual cwd validation precede launch. `SessionToolExecutor` preserves the native pre-exec exact-owner save and retains concrete authorization and final launch fences. The manager captures the admitted Session ID and Agent before its first asynchronous reservation/start work; native paths-handshake and provider receipt waits retain those facts even if a supported identity move commits meanwhile. Later ownership and completion resolve that original identity through the immutable lifetime graph, without relabeling original Agent or artifact facts. Cwd synchronization and ordered direct-segment replay keep their original exact-owner/Node boundaries.

Default foreground wait is 15 seconds, minimum 1, clamped above 60 with warning; native polling is 250 ms with status-before-Stop precedence. Reconciliation is every five seconds and observes executions independently. Source launch-before-registry and mutation-before-save failure ordering remains uncertain without replay, rollback or exactly-once claims. Acknowledged exact-owner completion is followed by tracking removal; delivery failure retries. Expiry is strictly older than 24 hours from `startedAt`, before queries or notification. Foreground finalization follows output/cwd work. Removal/retirement/expiry retain artifacts and never kill commands. Shutdown drains observers/persistence after foreground owners settle.

Output names the actual original log path; normal same-Node `read` consumes it. There is no `read_exec` model surface or permanent historical-ID lookup. Native and provider output use the shared Source display: 4,000-character partial and 20,000-character completed previews, token fallback, exact boundary whitespace and missing-trailing-LF information. Programmatic capture is independent raw UTF-8 within the inclusive 1 MiB bound; larger logs use 5,000-byte head/tail samples only for display. Native timeout receipts include best-effort bounded process trees; provider receipts never inspect Main processes. Process duration uses actual timestamps or measured intervals, not wait/dispatch budgets; missing-status detection and estimated finishes remain unknown.

Artifact archival is separate from active tracking and uses the actual [date-directory rotation policy](./dotnet-log-rotation.md#d-main-date-log-rotation); it does not protect long-running commands or extend notification retention.

## Listing and stopping background commands

### D-exec-list-stop

**Directly requested (2026-11-18).** A Session can see which of its commands still run in the background and end one, instead of waiting for a completion it no longer needs or finding a PID by hand. The model reaches this through `ctl exec list` and `ctl exec stop <exec-id>` (hidden builtins `exec_list` and `exec_stop`, so policy can allow listing and deny stopping), users through `/exec list` and `/exec stop`, and the WebUI through [its running-commands control](./webui-running-commands.md#running-background-commands).

- **Ownership** is the `waitExecIds` rule: `LocalExecManager.Running`/`IsOwnedActive` for native and Provider records of the Session's lifetime, `RemoteExecAuthority.Active(owner)` for CLI claims. A command whose completion was already delivered (queued, or its receipt in `acceptedExternalEventIds`) answers "already finished"; any other ID gets the same refusal, so the answer never reveals another Session's command.
- **Listing** comes from Main's own records. CLI rows use the claim's command, dispatch time and placement cwd/log; the Node is not queried. Remote claims are transient by design, so after a Main restart CLI commands are neither listed nor stoppable, as for `waitExecIds`.
- **Stop** never replaces completion delivery. `LocalExecManager.StopAsync` rechecks status and process identity (`ExecStop.Running` with the recorded start ticks), persists `stopRequestedAt` before any signal, removes the mark again when the command turns out to have finished, and triggers reconciliation. The ordinary acknowledged completion then reports `Stopped on request` with the real or unknown exit code, exactly once, also after a restart. A repeated request answers "already requested"; nothing is resent or retried.
- **Native** POSIX commands lead their own process group: `ExecStop.StopAsync` sends `SIGTERM` to the group, waits 5 seconds and sends `SIGKILL` if it is still running. The Bash wrapper traps `TERM`, `INT` and `HUP` and records 143, 130 or 129, so a stopped command no longer records exit code 0; after `SIGKILL` the missing-status fallback reports an unknown exit. Windows has no reliable soft signal for detached console-less processes and ends the process tree; the exit is unknown.
- **Provider** commands use the optional `exec-stop` operation (`docs/executable-node-provider-protocol.md`, Stop), only when the Node's descriptor declares `execStop`; otherwise the answer is unsupported. A failed or unusable reply is an unknown outcome.
- **CLI** commands use `exec_control_request` when the Node registered `features.execControl` ([remote exec](./remote-exec.md#exec-control)); older Nodes are unsupported.
- **Results** ([D-builtin-result-shapes](./tools-registry.md#d-builtin-result-shapes)): `exec list` returns `{execs}`, one `SessionManager.ExecRow` per command (`execId`, `nodeId`, `command`, `summary`, `startedAt`, `elapsedMs`, `cwd`, `logPath`, `stopRequested`), the same rows as the WebUI route. `summary` is the exec call's stated purpose as `ToolActivity.CaptionSummary` single-lines it, or null; Main records it at start (native and Provider records persist it as `summary` in `running-exec.json`, so it survives a restart; CLI claims keep it in memory like their command); `exec stop` returns `{execId, outcome, note}`, the note saying how the stop went and that the completion is reported separately. `/exec list` renders its own text from those rows (`SessionManager.ExecListText`), and `/exec stop` replies with the note.
- **Presentation**: the Session DTO's `runningExecs` count (owner DTO and the volatile catalog projection, which a Session keeps while it has background commands) tells the WebUI when to offer the list. A delivered or expired record calls `LocalExecManager.Untracked`, and a CLI completion publishes Session state, so the count drops without waiting for unrelated activity. None of this enters model requests.

### D-exec-id-first-receipts

**User-approved copy (2026-11-18).** A background receipt and its completion event begin with the execId, so a collapsed card or a quick scan of history identifies the command and its counterpart. Receipt: `[id] Still running after X, moved to background. Output so far:` (or `No output yet.`), or `[id] <cause> ended the wait after X; the command is still running in the background.` for Stop/Run queued; the output follows directly, then `---` and a footer with Node, log and the completion sentence (the external-owner variant keeps its `foxwarm_exec_result` sentence). Tests check structure only (`Tests/Tools/ExecReceipt.cs`); they do not lock the wording. The WebUI links the two leading IDs ([exec links](./webui-tool-timeline.md#exec-id-links)).

## Provider exec

`LocalExecManager.Provider` is the bridge inside the existing lifecycle owner. Records use `backend:{providerId,ref}`, actual Node, original target log path, initial/known cwd and optional target PID in the same registry. There are no provider metadata/status sidecars or Main log cache. Missing configuration never falls back to native. A shared in-flight query serves foreground/reconciliation observers; the foreground waiter consumes its outstanding query before requesting another, bounded by the remaining overall wait and cancellation. Completed observations cannot be discarded between sampling intervals. Transient errors retain tracking, while explicit loss yields unknown exit and estimated finish. Transport metadata queries retain their five-second cap.

The ephemeral foreground file view carries the original selected-Node Session cwd, not an inferred receipt cwd. One per-result observation budget covers target display and programmatic capture: remaining foreground budget after a finish, 500 ms after ordinary timeout and immediate unavailability after Stop/hard cancellation. Unavailable or short capture remains distinct from a known exit and never invents empty content. Known target cwd crosses the exact Session save lane without native whitespace trimming; deferred replay rechecks current Node and owner.

`LocalExecRegistryTests` covers synthetic Source records, acknowledged delivery, strict expiry, original paths, concurrent native effects and Linux directory-open observation proving that recovery does not traverse 20,000 retained artifacts. `MainExecLifetimeTests` covers real native effects across identity moves and retirement. `ProviderFileConsumerTests.ExecLifetime` observes the first rejected notification through periodic reconciliation, then explicitly reconciles the accepted retry; a timer interval is not a provider completion deadline. `ProviderFileConsumerTests.ExecIdentity` covers actual native/provider launches overlapping the command-routed identity move before the receipt, original tracking and log reads, exactly one effect, and completion under the renamed lifetime. `mainHostNativeExec.e2e.mjs` covers actual Main exit/restart, native Stop, original-path reads and startup rotation. Provider process restart/uncertainty coverage is mapped in [Node providers](./dotnet-node-providers.md). Synthetic record interoperability is not production Source takeover or permission to rewrite/replay existing wrappers. Windows runtime qualification remains separate from Linux tests/builds.

`HandoffConfirmation.GuidanceArgument` accepts the selected example after-send value; its default remains `finish`. Claude Code child/reminder generation supplies `continue` while retaining placeholder order, guidance and confirmation suffix. Execution validation is unchanged; the [runtime owner](./session-claude-runtime.md) applies its narrower supported controls separately.
