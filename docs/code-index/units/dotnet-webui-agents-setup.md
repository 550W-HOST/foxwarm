# Unit: WebUI Agent, setup, and model configuration routes

Files: `dotnet/Foxwarm/Channels/WebUi/WebUIChannel.Agents.cs`, `dotnet/Foxwarm/Channels/WebUi/WebUIChannel.Setup.cs`

## Purpose

Serves Agent creation/metadata/memory/knowledge and provider/model setup/configuration forms through Main-owned manager and model services.

## Stable methods and callers

Agent routes delegate catalog/AgentMemory/SessionManager Agent operations. Trusted POST restoration and DELETE retained-record cleanup are explicit modes of these same routes; their authority-preserving membership, reference checks and nonresurrection contract are owned by [retained Agent administration](./session-manager-lifecycle-identity.md#retained-agent-administration). Scoped identities remain denied for both modes. The original Architecture inspector sends `DELETE /api/agents/:agentId` with exact `confirmAgentId`; the authenticated route calls `SessionManager.DeleteAgentAsync`, returns `{success, agentId, deletedSessions}` with canonical IDs and publishes topology invalidation. Scoped identities remain denied. It preserves Source error mapping: not-found text is 404, active/busy/attachment/inheritance/mutation/deletion-stopped conflicts are 409, and other failures (including later cleanup errors) are 400. Per-Session partial cleanup is not rolled back or replaced by an Agent-wide progress promise. See [lifecycle and identity](./session-manager-lifecycle-identity.md#agent-deletion-callers) for the caller-specific selection, preflights and effects. Setup routes validate `SetupProviderRequests`, `AppConfigurationRules`, and model YAML before saving configuration or returning forms. `RegisterSetupRoutes` forwards the actual `SaveAppAsync` and `SaveAsync` installation results (`saved`, `target`, `applied`, `notApplied`, `restartRequired`) alongside existing config/reload or model payload fields. The application editor submits the entire YAML document to `/api/setup/config`; Weixin login retains its own internal section candidate builder. These routes do not make Vector fields a runtime capability.

`GET /api/setup/status` includes `capabilities.claudeCode: {available, reason}` for the shared New Session selector. This is a local launcher check from active startup configuration, not account or model health; the [Claude runtime unit](./session-claude-runtime.md#launcher-availability) owns its prerequisite, creation and retry semantics.

The same status response includes `capabilities.historySearch: {available, reason}` using the active Vector service's enabled/ready state, without probing its embedding endpoint. The [History viewer](./webui-history-search.md) uses it for an input-area hint while exact Archive message references retain their independent path.

## Contract and side effects

Setup/Agent changes are authenticated and explicit. Setup save success means the validated file was installed. Shared access identities and registered inbound MCP apply live; external-channel installation returns actual managed reload and partial results. Unsupported adapters remain unavailable rather than being reported as successfully applied. Model/settings updates are staged through manager/save-lane boundaries where they affect a Session. Agent memory selection can affect later prompts but does not rewrite active history. Unsupported remote/managed/child fields return explicit validation errors rather than being stored as accepted consumers.

The Secrets tab and `/api/setup/secrets` routes are owned by [secret store, references and redaction](./dotnet-secrets.md#setup); they never return stored values. The current Setup does not expose Authorizations. The normal host retains [outbound OAuth administrator routes](./dotnet-mcp-oauth.md), saved grants and the narrow public callback/client documents independently of this setup file; existing caller tool permissions still control MCP use.

Setup provider checks name the cause of a provider rejection without echoing credentials. A failed `/api/setup/models/test` classifies HTTP and attempt failures with the [configuration-failure classifier](../threads/model-routing.md#d-model-routing-configuration-failures) (for example "The openai provider rejected the API key. Provider response: 401: …"); other errors keep the redacted generic text. `/api/setup/models/list` reports 401/403 as a missing or rejected key. The first models save is subject to the [first-run key check](./model-configuration.md#first-run-key-check); the route's post-save behavior is unchanged.

## First-run default Session

[2026-11-03, approved first-run proposal] When `POST /api/setup/models` installs a model configuration while `state/models.yaml` did not exist before the save (the `oobe` condition reported by `/api/setup/status`), the route asks `SessionManager.EnsureFirstRunSessionAsync` to create the `main` Agent's default Session (canonical ID `main`). Creation happens only when the catalog has no Session at all and `main` is not an archived/reserved identity, under one process-local gate; otherwise nothing is created or changed. Later saves, failed saves and installations that already have Sessions never touch Sessions. The receipt carries `firstSessionId` only on a first-run save (`null` when nothing was created). A welcome failure is logged and does not turn the already-installed configuration into a failed save.

The Session receives two rows through the ordinary owned append: a user-role `<foxwarm-system kind="session-boundary" event="first-run" .../>` opening with a short notice, then a `model` row with the prepared welcome text. The user-role opening keeps provider history starting with a user turn (some providers and OpenAI-compatible chat templates reject a leading assistant message) and lets the model read the welcome as its own earlier reply. No model request is made; the welcome is visible even when the provider settings are wrong.

The welcome explains Sessions and Agents and lists advanced capabilities the user can ask for (dedicated Agents, timers, Nodes, MCP servers), each reachable through the main Agent's tools and bundled skills. The text is a packaged resource, `templates/main/welcome/{en,zh}.md` (`FirstRunWelcome.TextAsync`). `FirstRunWelcome.Language` picks it from an explicit request-body `locale` (the WebUI Setup save sends `navigator.language`; the key is removed before the YAML/form is installed) or else the weighted `Accept-Language` preference among the available languages, falling back to English. Desktop WebView2 follows the system display language for both. The WebUI places the `main` chat tab next to Setup when OOBE completes, so closing Setup lands in the conversation.

Why it lives here: the TypeScript server never created a default Session explicitly. Its WebUI opened the last-visited Session with a `main` fallback and `getSession` created missing Sessions lazily. The C# server deliberately creates no Session at startup or on history reads, and the WebUI `main` fallback was later removed, so new installations had no Session at all although the docs described one. Creating it at the first Setup save keeps startup and reads side-effect free and limits the effect to genuinely new installations.

## Tests

`FirstRunWelcomeTests.cs` covers language selection, both packaged welcomes, first-run creation through the authenticated route, unchanged Sessions on a later save and on an installation that already has a Session, explicit-locale precedence without persisting the key, and the provider request order (system, user opening, assistant welcome, user) through a scripted Completions peer.

`mainHostSetupProviders.e2e.mjs` qualifies transient listing/test requests, unchanged saved models/catalog during discovery, provider discovery from unsaved Models YAML through real editor input and completion actions, and an original-App raw `pricing` save followed by normal request cost recording, without depending on bundle module names. `mainHostModelCompact.e2e.mjs` and its controlled provider retain original creation/model/child selectors, strict setting failures, layered compaction, immutable Archive recall, cancellation and cold restart.

`ModelUsageCostTests.cs` verifies raw Setup `pricing` saves and normal request cost recording at model-object and provider-without-models placement. `AgentDeletionHttpTests.cs`; `WebUiStartupTests.cs`; `AppConfigurationRulesTests.cs`; AgentMemory/setup/model configuration tests. The original-App `mainHostAgents.e2e.mjs` and `mainHostKnowledge.e2e.mjs` retain Agent creation, owning-Agent memory, child effects and cold-restart scenarios. Knowledge checks real model-tool receipts and persisted creator metadata: a child can inherit its creator, while an unrelated memory ancestor is rejected under the [creator-ancestor constraint](./session-domain.md#agent-creator-metadata-and-admission). Rejected post-creation inheritance retains the published child without an inheritance link. `mainHostAsyncCompact.e2e.mjs` and `mainHostCompletions.e2e.mjs` install models through the real YAML editor and authenticated save route before their provider workflows; their shared save helper reloads to authenticated application readiness without requiring a selected Chat or a retired Setup modal button.

Agent creation and PUT updates accept `rules`, `defaultNode`, `defaultCwd` and `inheritable`; the retired `isolatedNode` field is rejected as unknown. Default Node changes do not move existing Sessions or create a remote environment.

PUT `/api/agents/{agentId}` also accepts a boolean `inheritable`; responses and the Agent list report `inheritable`. The list also reports `restricted` (the effective local layers end in an unconditional deny) and, for migrated legacy isolated Agents, `isolationMigration` (`migratedAt`, `automatic`, `node`, and `failClosed` while the fail-closed layer is unchanged); it no longer reports `isolated`, `isolatedNode` or a rule count. The administrator-only `GET /api/agents/isolation-migration[?agent=]` returns the read-only [isolation migration inventory](./isolation-migration.md), and `POST /api/agents/{agentId}/isolation-migration` applies the migration to one Agent (optional body `{acknowledgeDescendants: boolean}`; repeating it reruns only the placement backfill); both are absent from the scoped-browser allowlist. The WebUI has no control for them; the System view shows the startup report and the Agent badges.

The real authenticated Weixin QR start/wait routes and confirmed-owner merge use the existing Setup/HTTP boundary; [Matrix/Weixin](./dotnet-matrix-weixin.md) owns their source files, wire contract and selected-command versus reload-all distinction.

WebUI `POST /api/sessions` reads both Content-Length and chunked JSON (including the ordinary .NET `JsonContent` caller). Bodyless requests, zero-byte JSON streams and empty objects retain ordinary generated creation; nonempty malformed/non-object bodies and existing invalid fields keep their error path. The local route buffers framed bytes only to distinguish an empty stream before the existing JSON object validation; it does not alter authentication, scoped admission, name handling or committed-creation error responses. `WebUiStartupTests.SessionCreation` compares actual length-bearing/chunked requested identities, catalog/history visibility, first-root ordering and empty/malformed/access controls with the Source HTTP caller.

WebUI `POST /api/sessions` places the created root before its current root siblings through the existing catalog presentation mechanism before success acknowledgement. This caller-specific order matches Source and keeps the new Session visible in the bounded initial Sidebar window even after prior ranking/moves. It does not change general Session creation defaults or paging limits; ordinary creation and presentation failures retain their existing partial-effect boundaries. `WebUiStartupTests` covers more than 50 ranked roots, prior moves and persisted order after restart.
