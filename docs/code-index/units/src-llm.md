## Purpose

Owns provider request routing, Anthropic conversion/parsing, session snapshot consumption, provider-facing prompt-cache handling, retries/aborts, interaction logs, stream progress, unified result parsing, and one-shot requests. OpenAI conversion/stream assembly is delegated to `src/llmProviders/openai.ts`.

## Key exports

- `chat(parts, session, iteration?, options?)` — optionally append user parts, request one provider turn from current model-visible history, update stats, and append the result; eligible normal Responses turns may append completed commentary prefixes before the final suffix. [Canonical streaming contract](../threads/streaming-pipeline.md#d-streaming-early-commentary-commit).
- `readEffectiveRequestSelection`, `buildEffectiveSelectionNotice` — read the small normal-adoption baseline and compare canonical effective configurations; see [effective selection](../threads/model-routing.md#d-model-routing-live-session-selection).
- `resolveSessionToolDefinitions(session, override?)` — projects default definitions against the current Session's potential authorization, preserves explicit schema overrides, and substitutes a selected Shell Node's actual exec capability after filtering. Surviving descriptions, schemas and order are unchanged; the shared registry is not mutated. Main and Session-worker requests share this resolver. See [generic authorization](../threads/tool-dispatch-authorization.md#d-dispatch-generic-tool-authorization) and [Shell HTTP Node](./src-nodes-shell-http.md).
- `requestLlmOnce(options)` — provider request without automatic session-history orchestration.
- `deduplicateProviderRequestImages(contents, protocol)` — clones one concrete attempt's history, hashes only protocol-serializable current image bytes/MIME, removes repeated payloads, preserves descriptor/guidance context, and exposes duplicate status through a clone-local predicate rather than message fields.
- `convertToAnthropicFormat(contents, config)` — serializes the prepared clone into Anthropic-compatible messages while preserving tool-result image association and dedup guidance.
- `sanitizeProviderRequestPayload`, `isAbortError`.
- `LlmRequestError`, `isLlmRequestError`, retry event types/defaults/delay helper.
- `getOpenAIRequestApi(providerType)` — exact OpenAI surface routing.
- `DEFAULT_LLM_MAX_ATTEMPTS` plus compatibility `DEFAULT_LLM_MAX_RETRIES`; `classifyHttpFailure`.
- `fixToolCalls(contents)` — provider-safe tool-call/response history normalization.

Tool execution and local effects contracts are owned by [src-tool-executor](./src-tool-executor.md). Provider requests consume the neutral `CurrentSessionEffects` type; default Main-local composition lives separately in `session/defaultCurrentSessionEffects.ts`.

## Provider routing

| `providerType` | Request path / format |
|---|---|
| `openai`, `openai-responses` | OpenAI Responses API at `<baseUrl>/responses` |
| `openai-ws` | OpenAI Responses request/events over WebSocket at `<baseUrl>/responses` |
| `openai-completions` | OpenAI Chat Completions at `<baseUrl>/chat/completions` |
| `anthropic` | Anthropic Messages at `<baseUrl>/v1/messages` |
| `session-hash`, `failover` | Resolve a concrete leaf per outer attempt, then use that leaf's protocol |

`getOpenAIRequestApi()` returns null for non-OpenAI values; only `anthropic` then uses Anthropic-format handling. Any other type throws an `unsupported providerType` error while the plan is built, before headers, auth, or body are assembled. Config validation rejects such types earlier, so this guard covers direct entry overrides.

## Tool-response formatting

Anthropic conversion and both OpenAI serializers use `packages/shared/src/toolResponseFormatting.ts` through the built shared package. Structured tool responses remain structured internally; the shared formatter owns provider-facing text. Image parts are promoted separately and accompanied by image guidance. Canonical decision: [D-llm-shared-response-format](../modules/llm.md#d-llm-shared-response-format).

`stripRequestDisplayMeta` renders exact-target ToolScript execution responses with the shared section formatter before removing their activity metadata. This request-local text is journaled and reaches all provider serializers unchanged; native history and nested script calls retain their objects. The output guard selects the same renderer from the executor's existing exact-target activity signal. See [ToolScript execution projection](../threads/tool-dispatch-node-execution.md#d-dispatch-toolscript-execution-projection).

## Request prefix inputs

Snapshot construction and persisted cache identity are owned by [Session prompt state](./src-session-prompt.md). This module consumes those helpers for normal chat and selected-attempt prompt resolution; it does not export them.

- Provider `extraFields` and `extraHeaders` expand `${SESSION_CACHE_KEY}` from the concrete plan's effective provider key and `${TURN_ID}` from the request's ephemeral turn identity. This normally remains the resolved persisted/request key; only `openai-ws` applies the Session/scoped derivation in [D-model-routing-openai-ws-prompt-cache-key](../threads/model-routing.md#d-model-routing-openai-ws-prompt-cache-key). A low-level request without a Session ID generates one fallback identity for its retry set; the normal SessionTurnRunner supplies one turn identity for the whole session turn.
- A provider-neutral optional request effort is captured with the selected-model snapshot. Each physical concrete attempt uses the requested value when its leaf allows it, otherwise that leaf's configured default. Requests without an explicit value use the selected leaf default.

Normal owner `chat` accepts a request-only context hook. Its bounded messages are concatenated only into provider contents, not appended to history; retries re-read the context after committed retry preparation, removing stale completed/cancelled tasks. Detached/auxiliary requests do not invoke it. The canonical task contract is [D-tasks-replace-goal](src-session-task-context.md#d-tasks-replace-goal).

## Request behavior

- Provider payloads are sanitized for lone surrogates and may be gzip/brotli compressed per model config.
- `openai-ws` keeps the same complete provider-visible plan and outer retry/failover ownership, but its transport omits `stream`, owns input suffixing and `previous_response_id`, and rejects request compression or conflicting transport-owned `extraFields`, including provider-owned Conversations/context-management/background fields. The configured `max_output_tokens` remains in the logical plan/fingerprint and every full create, but the compact wire continuation with `previous_response_id` omits it; full recovery restores it. A completed chain released after canonical append is proactively closed after ten idle minutes; reuse cancels and a later release restarts that idle period, while active/pending states are never idle. A failed or ambiguous sent attempt closes only its leased socket and retries from full context without HTTP fallback.
- Each physical attempt selects a concrete model, applies the existing compatibility filter once, then hydrates and optimizes image references in an attempt-local clone immediately before one of the three provider serializers. HEIC/HEIF conversion and native generated-image replay use the same original-byte source boundary, but only ordinary vision images are optimized. The canonical journal remains pre-hydration and diagnostics redact generated provider bytes. Preparation failures occur outside the retry/failover transport catch. Canonical contract: [image blob lifecycle](../threads/image-blob-lifecycle.md).
- Each concrete physical attempt applies one provider-neutral request-local image dedup helper after history compatibility filtering. Protocol-specific eligibility determines which occurrences can seed the seen set; later identical provider-visible bytes/MIME retain descriptor or image-guidance context without base64. Tool serializers pre-associate the complete tool message so canonical response-then-image order and deduplicated orphan tool IDs remain model-visible. Canonical contract: [D-image-provider-request-dedup](../threads/image-blob-lifecycle.md#d-image-provider-request-dedup).
- OpenAI and Anthropic payloads receive current tool schemas and current Foxwarm system/source wrappers.
- Anthropic Messages payloads include the top-level `cache_control: { type: 'ephemeral' }` by default; an explicit provider/model `extraFields.cache_control` replaces it. Canonical decision: [D-llm-anthropic-default-ephemeral-cache](../modules/llm.md#d-llm-anthropic-default-ephemeral-cache).
- Memory-backed prompt snapshots filter each selected framework/inherited/current/custom source body for the chosen canonical concrete model, then add one deterministic first-line marker. Framework sources retain raw frontmatter-looking bytes; ordinary memory files parse their established Session frontmatter first. Actual-use reuse, strict owner persistence, detached mutation, and refresh are canonical in [conditional memory snapshots](../threads/conditional-memory-snapshots.md).
- The selected concrete leaf's effective `maxOutput` limit is sent as `max_output_tokens` to OpenAI Responses and as `max_tokens` to Chat Completions and Anthropic-compatible requests. Provider/model `extraFields` may override it at their existing later merge boundary; the default and canonical configuration contract are [D-config-default-max-output](./src-config.md#d-config-default-max-output).
- OpenAI Responses and Chat Completions custom function tools explicitly set `strict: false` at their protocol-defined tool locations while preserving each JSON Schema `required` array unchanged. Anthropic continues to receive the same schema through `input_schema`.
- Canonical history keeps logical queued messages separate. The Anthropic serializer coalesces adjacent same-role entries only in its outbound payload, while OpenAI serializers retain separate message entries. Queue-boundary ownership is [D-pipeline-canonical-queue-item-boundaries](../threads/message-processing-pipeline.md#d-pipeline-canonical-queue-item-boundaries).
- Streaming progress converts cumulative collector snapshots into version-2 offset deltas. Responses additionally diffs indexed summary/content/tool/image-status slices, maintaining their order in the process-local exact-owner draft and Worker-composable wire updates; other providers continue to use the flat reasoning/text reader. Reasoning/text use the fast throttle; function identity is prompt, raw partial JSON arguments are emitted at most once per second, and completion flushes before the canonical model append. The same emitter maintains a process-local exact-owner cumulative draft for subscription bootstrap and clears it on completion. Canonical transient contract: [D-streaming-delta-and-bootstrap](../threads/streaming-pipeline.md#d-streaming-delta-and-bootstrap).
- For normal Responses SSE/WS, `createResponsesPrefixCommitLane` serially parses replayable `output_item.done` prefixes, requests strict exact-owner append via `chat`, trims the owner draft after commit, and only then requests best-effort intermediate Channel delivery. Completion parses the uncommitted output suffix; one metadata-only completion row is allowed if it is empty. A partial upstream failure rebuilds the next logical/journal request from committed history without resetting the outer attempt budget. [Canonical early-commit contract](../threads/streaming-pipeline.md#d-streaming-early-commentary-commit).
- When the selected concrete model opts into error-time reasoning retention, that same lane saves only contiguous completed encrypted reasoning after an upstream stream failure and any prior committed commentary, before bounded retry builds a new request from history. This path never runs on successful completion, Stop, or local append failure. [Canonical contract](../threads/streaming-pipeline.md#d-streaming-keep-reasoning-on-error).
- Retry waits are abortable. Terminal failures move bounded diagnostics to error logs, emit a final retry event, and throw `LlmRequestError`; they do not create fake assistant `Error:` messages. Canonical boundary: [D-llm-request-errors](../modules/llm.md#d-llm-request-errors).
- Normal authoritative `chat` supplies awaited `prepareRetry`, an exact-owner selection reader and a committed-history reader independently of Responses partial commits, so Chat Completions and Anthropic also rebuild changed input. The internal loop invokes preparation after backoff, outside the transport retry catch, checks cancellation before and after it and again before dispatch, and reuses partial-prefix reconstruction for a fresh logical/journal/stream identity only when context changes. Physical budget and cache lineage remain intact; captured routing/effort changes only for [explicit model selection](../threads/model-routing.md#d-model-routing-live-session-selection), and unchanged context/selection retains identity. `onRetry` remains notification-only and swallows its own errors; preparation errors propagate without provider classification. Canonical queue ownership: [D-pipeline-retry-input-safe-point](../threads/message-processing-pipeline.md#d-pipeline-retry-input-safe-point). The per-attempt effective-selection hook runs after leaf selection and shares request-effort resolution with the actual plan. Its canonical append reuses committed-history reconstruction before the one compatibility-filter/hydration pass; it neither re-resolves an unchanged configuration snapshot nor creates another retry loop.
- Default OpenAI streaming attempts use a progress watchdog rather than a five-minute total cap: three minutes from physical dispatch/connection start to the first valid Responses output-item lifecycle event or nonempty generated reasoning, text, refusal, or function-argument increment, then three minutes by default between later activities of those kinds. Each valid activity resets the inactivity window; headers, acknowledgements, response scaffolding, hosted-search state outside output-item lifecycle events, usage, empty deltas, and text/argument done snapshots do not. A Responses `response.metadata` event whose metadata type is `safety_buffering` changes only that physical attempt to an inactivity window of max(configured normal timeout, ten minutes), restarts the window immediately, and makes later counted activity retain that extended window; each retry begins with the ordinary limits. Progressing streams may run beyond five minutes. Timeout aborts and destroys only that physical attempt so the ordinary outer retry can continue. Nonstreaming requests retain the five-minute default. An explicitly supplied low-level `timeoutMs` is an additional hard per-attempt upper bound for either mode and still wins when earlier; user Stop remains a distinct outer abort and never becomes a retryable timeout.
- A caller may supply an independent `abortSignal` to `chat`/the one-shot request path. Compaction uses this seam with ordinary Session-turn abort registration disabled, so `/stop` and `/stop compact` cannot cancel each other's provider request when both overlap.
- The historical `maxRetries` option/event field means total attempts; the default is six. Virtual attempts rebuild the complete selected concrete request, and empty/reasoning-only responses retry only when the selected concrete provider sets `disallowEmptyResponse`; otherwise the empty completion is accepted. Canonical semantics: [model routing](../threads/model-routing.md).
- First-class effort is applied after expanded `extraFields` on an attempt-local payload, overriding only known effort/thinking paths without mutating model configuration. OpenAI Responses uses `reasoning.effort`, Chat Completions uses `reasoning_effort`, and Anthropic-format providers use `output_config.effort`; `none` disables Anthropic thinking and omits its output effort. The removed global thinking-budget mechanism no longer injects `budget_tokens`.
- HTTP classification recognizes nested structured model-not-found errors and bounded common text forms without broadening ordinary HTTP 400 retries. Each selected virtual snapshot captures route activation once so unchanged-selection retries cannot replace newer configuration state.
- Successful results normalize into `ChatResult`, record the provider-qualified concrete model ID and usage, and may contain function calls for the router loop. A virtual route additionally carries its resolved configuration key through `ChatResult.virtualModelKey` into every successful provider-generated assistant message, including tool-call-only turns; canonical semantics are owned by [D-model-routing-concrete-attribution](../threads/model-routing.md#d-model-routing-concrete-attribution).
- Normal `chat` may receive an internal provider-state finalizer beside `ChatResult`. A reusable non-image WebSocket response remains unavailable until all of its canonical assistant segments have appended; their existing provider serializer must reconstruct the complete exact provider-output prefix. Append failure, an unreplayable response, and direct low-level `requestLlmOnce` calls discard pending state. Finalizer failure is diagnostic-only after a committed history append. [Canonical early-commit contract](../threads/streaming-pipeline.md#d-streaming-early-commentary-commit).
- Normal chat request history retains only a model message's canonical concrete `__meta.modelId` as provider-planning provenance; all other internal metadata remains excluded. Each physical attempt uses that identity on an attempt-local clone to remove model-specific reasoning artifacts only after a proven concrete-model mismatch, then strips all `__meta` before any of the three provider serializers. Virtual failover therefore re-evaluates compatibility for every selected leaf without mutating canonical history. Canonical contract: [D-model-routing-history-reasoning-compatibility](../threads/model-routing.md#d-model-routing-history-reasoning-compatibility).
- OpenAI Chat Completions response parsing accepts the established `message.reasoning_content` field and the compatible `message.reasoning` fallback, normalizing either into one canonical thinking part while preserving `reasoning_content` precedence when both are present. It also carries JSON-object `provider_specific_fields` into `ChatResult.providerMeta` with the producing concrete `modelId`; `chat` persists that scoped metadata on the assistant message. Later Chat Completions request plans pass their exact concrete model ID to the serializer, so the opaque fields round-trip only to the same concrete model and are omitted after model switches or on incompatible virtual targets. Outbound canonical thinking continues to use the established `reasoning_content` request field.
- Anthropic Messages parsing retains ordered `thinking` blocks with signatures, including empty thinking text when the signature is valid, and retains opaque `redacted_thinking.data` in `MessagePart.providerMeta.redactedThinking`. The Anthropic serializer re-emits those blocks unchanged for the same concrete model; existing concrete-model compatibility filtering removes them after a proven model switch without changing canonical history or block order.
- Anthropic Messages requests stream by default: an omitted `stream` or `extraFields.stream: true` sends `stream: true` and reads the SSE response through `collectAnthropicMessagesStream` (`src/llmProviders/anthropic.ts`). The collector rebuilds ordered indexed content blocks into the same non-streaming response shape the JSON path produces, so both paths share one parser. `extraFields.stream: false` selects the JSON path with a matching body and reader; any other non-boolean value is rejected before sending. Tool JSON stays raw until its `content_block_stop` and is never dispatched while streaming. A stream that ends before `message_stop`, emits an `error` event, or lacks a final `stop_reason` fails the attempt instead of succeeding. Signatures and opaque thinking never enter WebUI progress; only thinking and text deltas feed the existing model-stream draft.
- Anthropic `stop_reason` handling: `end_turn`, `tool_use`, and `stop_sequence` are normal. `max_tokens` and `model_context_window_exceeded` keep the usable text and set `ChatResult.truncatedStop`; a complete object-valued `tool_use` remains dispatchable even at a truncation stop, while incomplete or invalid tool JSON keeps its raw text, receives an argument parse error, and is never dispatched. `refusal` fails the attempt as a non-retryable response error that shows the category and explanation, with no automatic retry or model switch. `pause_turn` and Anthropic server-tool blocks (`server_tool_use`, `mcp_tool_use`, `*_tool_result`) fail explicitly as unsupported because Foxwarm neither runs server tools nor continues paused turns.
- While an Anthropic `thinking` or `redacted_thinking` block is open, the streaming watchdog widens its content-inactivity window to `REASONING_CONTENT_INACTIVITY_TIMEOUT_MS` (10 minutes) instead of 60 seconds. Keep-alive `ping` events never count as progress, and the window closes when the block stops, returning to the normal budget. The explicit call timeout and Stop still take precedence.
- OpenAI Responses can opt into the hosted `web_search` tool through concrete model `webSearch` settings. Raw provider/model config accepts the designated boolean/object form and resolves to a normalized object before inheritance/use. The tool is appended beside Foxwarm function tools for eligible Responses requests (not compact/setup-test requests); completed `web_search_call` items and URL annotations persist as ordered model-part metadata and are replayed only to the producing concrete model. They never enter `executeTools` or produce `function_call_output`. General toggle shape is canonical in [D-config-feature-toggle-shorthand](./src-config.md#d-config-feature-toggle-shorthand).
- OpenAI Responses maps only its official `usage.output_tokens_details.reasoning_tokens`, and OpenAI Chat Completions maps only its official `usage.completion_tokens_details.reasoning_tokens`. When either field is exposed, it persists as the optional `TokenUsage.reasoningTokens` component while the provider's full output/completion count remains `outputTokens`; Anthropic Messages maps its official `usage.output_tokens_details.thinking_tokens` the same way, taken from the cumulative final `message_delta` usage of a stream and never summed across events. Anthropic usage maps `cache_read_input_tokens` to `cachedTokens` and adds `cache_creation_input_tokens` to `input_tokens` for `inputTokens`; missing or invalid cache fields default to zero while missing or invalid base input/output counts remain unavailable. Cross-module accounting semantics are [D-pipeline-provider-usage-components](../threads/message-processing-pipeline.md#d-pipeline-provider-usage-components).
- Provider usage remains optional: a usable response without a usage object succeeds and simply omits token accounting, including OpenAI-compatible Chat Completions streams which ignore `stream_options.include_usage`.
- Display-only messages and internal `__meta` are excluded from provider payloads; the narrow historical concrete model provenance used during request planning remains journal-visible but is stripped before serialization.
- Request-local history also excludes top-level `Message.compaction` from provider input and canonical request journals without modifying persisted messages; see [planner diagnostics](../threads/context-compaction.md#d-context-compact-planner-debug).
- Before the first physical send, `requestLlmOnce` journals the repaired provider-neutral messages, first selected attempt's effective system prompt, and exact tool schema through content-addressed objects and a bounded manifest. Every physical attempt records concrete routing, its effective prompt when different, and a semantic-payload digest; canonical ownership is [canonical LLM request journal](../threads/llm-request-journal.md).
- The journaled request-local canonical clone first strips unsupported legacy provider-image helper keys. Caller input is unchanged, and neither those keys nor their values can affect provider serialization or reconstructed journal contents.
- Successful `ChatResult` values carry the durable request/attempt identity and logical request timing. The successful journal result retains both, and `chat` persists the identity plus `startedAt`, `completedAt`, and monotonic `durationMs` on assistant metadata. Post-response journal-result failures are logged without entering the provider retry loop. Canonical timing semantics belong to [D-pipeline-input-time](../threads/message-processing-pipeline.md#d-pipeline-input-time).
- Hosted Responses image generation is planned, executed, persisted, and reported at this layer. `buildConcreteRequestPlan` rejects an enabled config on a non-Responses protocol, appends the hosted tool beside function and hosted-search tools, and computes `usesHostedImageGeneration` plus the content-free raw-stream policy. A completed image item is externalized to a canonical blob reference before any response log or journal write, and successful images count as real content for the empty-response guard. An attempt that began a hosted image call follows the ordinary retry classification and budget like any other attempt; the only image-specific non-retryable failure is a local replay failure for stored bytes that cannot be read.

For normal turns, `chat` invokes its optional assistant-message callback only after a successful canonical append and provider history-append finalization; callback failures are logged outside provider retry/rollback control. Detached requests without the hook do not automatically publish generated media. The downstream cross-module contract is [D-image-generated-output-replay](../threads/image-blob-lifecycle.md#d-image-generated-output-replay).

## Design decisions

### D-llm-provider-router

Provider type selects one current request protocol: Responses, Chat Completions, or Anthropic Messages. Provider-specific message/stream code is separated where it has a stable boundary.

### D-llm-openai-non-strict-function-tools

[2026-08-13] Every Foxwarm custom function tool sent through OpenAI Responses or Chat Completions explicitly uses non-strict mode. The original JSON Schema `required` list remains the sole provider-facing required-key contract, so optional properties may be omitted; runtime tool validation and defaults remain authoritative. Responses places `strict: false` beside `parameters`, while Chat Completions places it inside the nested `function` object. Hosted provider tools such as Responses `web_search` and Anthropic `input_schema` are unchanged.

### D-llm-streaming-progress-timeouts

[2026-09-06; updated 2026-09-23] Streaming timeout activity is bounded model progress, not arbitrary transport traffic. Default OpenAI SSE/WS attempts receive three minutes to the first valid Responses `response.output_item.added`/`done` item or nonempty generated reasoning, text, refusal, or function-argument increment, and then three resettable minutes by default between later activities of those kinds, without an overall five-minute cap. A valid Responses `safety_buffering` metadata event enters an attempt-local inactivity mode of max(configured normal timeout, ten minutes) immediately; later counted activity retains that mode, repeated statuses replace the bounded metadata and restart it, and fresh retries return to the default. If any timeout later wins, including an explicit hard deadline, its error appends the bounded safety metadata. Chat Completions identity-only fields and non-safety metadata remain excluded. Explicit `timeoutMs` remains an additional whole-attempt deadline; nonstreaming retains the five-minute default. A streaming timeout aborts only the current physical attempt and therefore stays inside normal retry/failover ownership, while explicit user cancellation remains terminal.

`streamContentInactivityTimeoutMs` in models.yaml is a concrete provider/model setting (model override > provider > 60000 ms), validated as an integer from 1 to 2147483647. Both SSE and WebSocket use the resolved concrete model setting; virtual providers must configure their leaves. It changes neither the three-minute first-output window nor explicit caller `timeoutMs`. Safety buffering never shortens a configured timeout longer than ten minutes. Nonstreaming requests ignore this setting. Once a hosted image item is reported in an attempt, that attempt's inactivity allowance is at least ten minutes without shortening a longer configured window, every later image activity restarts it, and it does not fall back when the image item ends; a fresh attempt resumes the ordinary configured or safety-buffering window.

### D-llm-hosted-image-generation

[2026-09-19; updated 2026-09-23] OpenAI Responses models may opt into the provider-hosted `image_generation` tool through the `imageGeneration` provider/model config, which defaults off and is rejected on Chat Completions, Anthropic, and virtual providers. Output images are durable blobs referenced from canonical message parts; provider base64 never enters canonical history, the request journal, logs, WebUI transport, or error diagnostics. Raw stream content capture is disabled for every physical request that can carry or receive image bytes, keyed on the effective config and on whether the Responses input replays a native generated-image call rather than on the UI-level toggle alone.

Only the exact concrete model that produced an image may replay it natively, and only when locally verified bytes are available; another concrete model or protocol receives one bounded text note instead, while the originating model with unreadable local bytes fails the request. Unrecoverable local bytes are a non-retryable, non-countable failure: the provider was never asked to redo the work, a retry cannot restore the bytes, and a failover could pay twice for the same image. An attempt that has already begun a hosted image call is not excluded from the ordinary retry classification or budget: a regenerated image is a fresh artifact rather than a recovery of the first one, and the product accepts a normal retry window instead of an unretried failure. A successful image counts as real response content, so a text-free image turn is not retried as empty. Hosted image generation is excluded from compact-plan and setup-test purposes, like hosted web search.

The optional onAttempt hook runs after local retry/effective-selection preparation and before a prepared physical request, only when the plan is not already cancelled. Callback failures remain outside provider retry classification. Cancellation after plan preparation, including during an awaited callback, retains the established attempt-start/abort-result journal path without dispatching a provider request. Runtime consumers use the hook to clear backoff without obscuring compaction preparation. The journal boundary is canonical in [request flow](../threads/llm-request-journal.md#request-flow).
