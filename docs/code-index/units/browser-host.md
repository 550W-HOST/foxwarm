## Contract

One `browser_*` tool family serves every browser: the headless Chromium a machine manages for itself and the user's own browser through the [Browser Node extension](./browser-node-extension.md). `contract.js` is the single owner of tool names, parameter schemas, argument validation, result limits and the draft model-facing descriptions (the `COPY` table, with Chrome and Firefox variants). `toolDefinitions(profile)` derives definitions from a capability profile (`variant`, `windowed`, `keys`, `fullPage`); differences between browsers are profile entries, not separate tools. Descriptions are drafts until the coordinator approves final copy, and tests lock schemas and validation rather than wording.

The tools are `browser_tabs`, `browser_open`, `browser_close`, `browser_navigate` (URL, or history back/forward/reload), `browser_read` (snapshot, text, html), `browser_screenshot`, `browser_click` (ref, selector or coordinates with the screenshot's page identity), `browser_fill`, `browser_type`, `browser_press`, `browser_select`, `browser_scroll`, `browser_wait` and `browser_evaluate`. Mutating results report the tab's `url`, `title` and whether a navigation happened. Screenshots return the existing image carrier (`output`, `mimeType`, `inlineData`) plus tab, page identity, URL and viewport, so canonical image registration, hydration, crop, export and delivery stay in their normal owners.

## Host

`packages/browser-host` is a dependency-light ESM package bundled by esbuild into one `browser-host.bundle.cjs` (puppeteer-core included, license comments in an adjacent `.LEGAL.txt`). It is built with `npm run build:host` and runs under the machine's installed `node`; nothing is embedded in the .NET executables and no browser is bundled or downloaded.

`chromium.js` finds the executable through `PUPPETEER_EXECUTABLE_PATH`, then common installed names on `PATH`, then fixed locations. There are no other configuration keys or environment variables.

`manager.js` owns one lazily launched browser per host process. Chromium's own sandbox stays on: launch arguments are empty (pipe transport, downloads denied) and no sandbox-, site-isolation- or automation-hiding flags, spoofed user agent or webdriver override are added. Because the pipe transport reports a browser that exits during startup only as a closed target, a failed launch reruns the same executable once as a bounded headless dump to recover Chromium's own sandbox line from stderr. A launch failure that names the sandbox then adds a short hint: in Docker use the shipped seccomp profile and a non-root user; elsewhere unprivileged user namespaces are required and root cannot run the sandbox, or a suitable launcher can be selected through `PUPPETEER_EXECUTABLE_PATH`. Tabs have sequential integer IDs, a cap of ten, and an ordered per-tab lane so actions on one tab do not interleave. Navigation waits for `domcontentloaded` plus a bounded settle; auto-handled dialogs are reported in `dialogs`. A failed `browser_open` closes its page; frames that leave HTTP(S) are reset to `about:blank`. Full-page screenshots are capped. The browser exits after ten idle minutes and relaunches on demand.

`server.js` speaks line-delimited JSON on stdio: `{id, tool, args, deadlineMs}` calls, `{cancel: id}` cancellation and `{id, ok, result|error}` replies. It exits when stdin closes. `main.js --describe` prints `{tools, available, reason?}` without launching a browser, which is how callers learn whether the host can run.

## Hosting

`BrowserHost` (NodePrimitives) is the C# launcher and is the only .NET browser code. It locates the bundle (`packages/browser-host/dist/` below Main's output, or beside the CLI executable) and `node` (`PATH` first, then conventional install locations such as Homebrew, `/usr/local/bin` and the Windows Program Files `nodejs` directory, because desktop and service processes often lack the shell `PATH`), caches `Describe()` (an unavailable answer is retried after 30 seconds), spawns the child host on first call, and applies a two-minute deadline. A cancelled call sends the cancel line; a wedged host is killed by a watchdog; disposal closes stdin and kills after five seconds.

Main (`MainBrowserTools`, `MainBrowserDefinitions`) registers the described tools as discoverable, default-hidden `node` capabilities for `master`, only when the host reports itself available. Tabs belong to the Main process and are shared across Sessions; they do not survive a Main restart. The CLI Node (`NodeBrowserTools`, `NodeClient`) advertises the same tools in its registration only when its own host is available, dispatches `browser_*` calls with a cancellation controller (so `tool_call_cancel` reaches the host) and sets `features.toolCallCancellation`. A machine without `node` or Chromium advertises nothing, and a direct call fails with the host's reason.

Authorization is the generic Node-capability path: browser tools follow selection, binding and policy like other Node tools. There is no tool-specific isolated-Agent exception; persisted rules that still name the retired `browse_*` tools load and match nothing.

## Validation

`packages/browser-host/test` runs the real host against a loopback site and the installed Chromium (a test-owned launcher is used only where this environment cannot start Chromium's sandbox). `BrowserHostTests` drive the bundle through `BrowserHost`, including cancellation, and check unavailability for missing node or bundle. `MainBrowserFailureTests` pairs an unrunnable-host failure with its call and the next model request. `ToolAuthorizationEffectsTests.Browser.cs` covers generic authorization, old persisted names and discovery. `dotnetMainBrowser.e2e.mjs` runs Main dispatch, images through the canonical pipeline, policy, cancellation, isolated-Agent denial, restart and the unavailable case; `dotnetCliNodeBrowser.e2e.mjs` and `dotnetCliNodeBrowserMain.e2e.mjs` cover the C# CLI Node over the raw protocol and through Main.
