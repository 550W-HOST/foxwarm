## Contracts and rationale

<a id="d-release-prebuilt-packages"></a>
**Decision: installation uses prebuilt packages** (user, 2026-11-02). Releases are compiled once by the release workflow; installing or updating needs neither Node.js nor the .NET SDK nor compilers. The regular edition is a server package for Linux x64, macOS arm64 and Windows x64: framework-dependent everywhere, plus native on every platform ([Linux](#native-linux-package) since 0.9.4, [macOS and Windows](#native-macos-and-windows-packages) since 0.9.6). The Desktop edition is a [native Windows app](#windows-desktop-app) and a [native macOS app](#macos-desktop-app), both NativeAOT since 0.9.6 (the Windows Desktop was a self-contained managed app before). Versioning starts at 0.9; 1.0 is reserved for an improved out-of-box experience. Artifact preparation keeps running the collected compiler under an optional `node` on `PATH`; the packages neither bundle Node.js nor port that compiler. Source checkouts remain the development path with their own [build and controls](./source-main-entry.md#build-and-controls).

Release assets have version-free names (`foxwarm-linux-x64.tar.gz`, `foxwarm-linux-x64-native.tar.gz`, `foxwarm-osx-arm64.tar.gz`, `foxwarm-osx-arm64-native.tar.gz`, `foxwarm-win-x64.zip`, `foxwarm-win-x64-native.zip`, `foxwarm-desktop-win-x64.zip`, `foxwarm-desktop-osx-arm64.zip`) plus `SHA256SUMS`, so `releases/latest/download/<asset>` is stable. Each application archive has one top-level directory (`Foxwarm.app` for the macOS Desktop). The additional versioned `foxwarm-code-<version>.tar.gz` extracts directly into `packages/vscode-web/assets` with `vscode-web/` and `extensions/redhat.vscode-yaml/`; it participates in the same checksum aggregation. Every application archive except the macOS Desktop contains `release.json`, which records version, target, kind, RID, self-containment, whether it is native, asset name and source commit; installers and updates read the RID and asset from it and switch package type only as described in [the native Linux decision](#native-linux-package) and its [macOS/Windows counterpart](#native-macos-and-windows-packages). GitHub Releases host the assets because the site's static-asset download route cannot serve files of this size.

`package.mjs` publishes the existing [delivery resource graph](./core-delivery-cli.md#build-and-resource-boundary) with an explicit RID and `--self-contained` (native targets add `-p:PublishAot=true`); it adds no second resource collector. Server packages add the control script for their platform; Desktop uses the Desktop project with `FoxwarmConsoleEntry=false` and `ArtifactTargetRid` as global properties and removes the console apphost/runtimeconfig. PDB/XML files, and NativeAOT `.dbg` files and `.dSYM` bundles, are removed from delivery. The Windows Desktop then copies the complete pinned Code OSS and YAML asset subtrees, including all built-in language extensions and redistribution notices; server packages do not copy them. `validateCodeAssets`, `installCodeAssets` and `archiveCode` own pin/notice validation, Desktop layout and standalone Code packaging. `--code-only` packages already prepared assets without a managed publish. A Linux host produces the Linux server targets; the Windows job produces the Windows server targets and Desktop, the macOS job the macOS server targets and the macOS Desktop job the macOS Desktop. For a non-host RID the script extracts the locked target-native esbuild/sharp packages, after checking the lockfile integrity, beside the host packages, so the collector's no-substitution rule still holds. Tarballs use Python 3 on both GNU and BSD hosts, with sorted names, the commit timestamp, numeric root ownership and fixed gzip metadata. The macOS targets use locked darwin-arm64 esbuild/sharp natives and require an arm64 macOS build host so the shared Darwin PTY dylib and controlling-terminal helper are compiled natively. NativeAOT cannot cross-compile between operating systems, so a native target is refused on any other host RID; without `--target`, a host builds only the published targets it can build. The `qualification` target flag (built and smoke-tested, never published) remains available; no target uses it since 0.9.6. Windows targets, server and Desktop, require `--vc-runtime DIR` (see [Visual C++ runtime](#visual-c-runtime-in-windows-packages)).

### Native Linux package

<a id="d-release-native-linux"></a>
**Decision: native Linux package replaces the self-contained one** (user, 2026-11-10, Foxwarm 0.9.4). Linux x64 ships `foxwarm-linux-x64-native.tar.gz`, a NativeAOT publication of Main (`-p:PublishAot=true`, not single-file), as the package that needs no .NET; it is the default of the installer and the install documentation. The framework-dependent Linux package stays; `foxwarm-linux-x64-self-contained.tar.gz` is no longer produced. Windows x64 and macOS arm64 kept their self-contained packages for 0.9.4 and 0.9.5 and switched in 0.9.6 ([below](#native-macos-and-windows-packages)); the Windows Desktop stayed managed until its [0.9.6 switch](#windows-desktop-app). The container image is built from the native package and carries no .NET runtime.

A native package is a directory like any other server package: `Foxwarm` is the NativeAOT executable, with native libraries, resources and notices beside it and no `Foxwarm.dll`. Its `release.json` has `selfContained: true` and `native: true`. Every control script since 0.9.0 launches a self-contained package through `Foxwarm` and accepts any package of its RID in `update --package`, so an existing installation's own control script can install and start a native package. The Vector owner is the same executable started with `--foxwarm-vector-child`.

The installed control script updates within its recorded asset name, and 0.9.3 and earlier self-contained Linux installations record the retired asset. When the release lacks that asset, `update` (from 0.9.6) fails with a message naming it and the installer rerun, instead of a raw download error.

<a id="d-release-self-contained-alias"></a>
**Decision: 0.9.4 aliased the retired asset for one release; 0.9.5 dropped it** (user, 2026-11-10; dropped in 0.9.5). The 0.9.4 release also published the native Linux archive as `foxwarm-linux-x64-self-contained.tar.gz`, with its own `SHA256SUMS` line, so the unmodified `update` of 0.9.3-and-earlier installations downloaded and verified the native package. The archive's `release.json` names `foxwarm-linux-x64-native.tar.gz`, so the installation's next update requested the native asset directly. From 0.9.5 on no release publishes the retired name and the aggregate job has no alias step; the 0.9.4 release keeps its alias asset. A 0.9.3 or earlier installation therefore reaches 0.9.5 through 0.9.4 (`update 0.9.4`, which downloads the alias from that release, then `update`) or by rerunning the installer; a plain `update` fails once a later release is the newest. The Ubuntu 22.04 job upgrades from the previous release's native package (0.9.4's control script downloads its recorded `foxwarm-linux-x64-native.tar.gz` and `SHA256SUMS` from `releases/latest/download`), once by rerunning the installer and once through that release's own `update` (`smoke-upgrade.sh --via-update foxwarm-linux-x64-native.tar.gz`); the workflow's `PREVIOUS_RELEASE` moves forward with each release.

Rerunning the installer is the switch that works for every release: on an existing installation whose asset is a retired self-contained archive of its platform, or when the user chooses a package (`--native`, `--framework-dependent`, or a `--package` file whose `release.json` records another asset), the installer downloads and verifies that package itself (or uses the given file) and hands it to the installation's control script with `update --package FILE --force` (`--force` also switches between packages of one version). Data, `data_dir`, configuration and the control-script lifecycle are unchanged; the new release's upgrade inspection still runs first. Without a choice, other installations keep their package type. The retired `--self-contained` (`-SelfContained` on Windows) selects the native package with a notice. A `--package` file of another type at the installed version used to be a silent no-op reported as success; it now switches (user decision 2026-11-12), on Unix and Windows alike.

### Native macOS and Windows packages

<a id="d-release-native-macos-windows"></a>
**Decision: native macOS and Windows packages replace the self-contained ones** (user, 2026-11-12, Foxwarm 0.9.6), following [the Linux decision](#native-linux-package) after real-machine tests of both native packages. macOS arm64 ships `foxwarm-osx-arm64-native.tar.gz` and Windows x64 `foxwarm-win-x64-native.zip` as the packages that need no .NET; both installers default to them and accept `--native` / `-Native`, and `foxwarm-osx-arm64-self-contained.tar.gz` and `foxwarm-win-x64-self-contained.zip` are no longer produced. The framework-dependent packages stay. The Windows Desktop zip stayed managed under this decision; [a later decision](#windows-desktop-app) made it native for the same release. No code signing is added, and the documentation adds nothing about SmartScreen or unsigned binaries (user decision).

<a id="d-release-native-alias-096"></a>
**Decision: 0.9.6 aliases the retired macOS and Windows assets for one release** (user, 2026-11-12), exactly as [0.9.4 did for Linux](#native-linux-package). The aggregate job copies the native archives to `foxwarm-osx-arm64-self-contained.tar.gz` and `foxwarm-win-x64-self-contained.zip` before regenerating `SHA256SUMS`, so the unmodified `update` of 0.9.5-and-earlier installations reaches the native package, whose `release.json` names the native asset for later updates. The step accepts versions 0.9.5 (unreleased `testing` builds) and 0.9.6 and warns otherwise; it is to be removed in 0.9.7. The macOS and Windows jobs upgrade the previous release's self-contained package to the new native one by rerunning the installer and through that release's own update via the alias name (`smoke-upgrade.sh --via-update`, `smoke-upgrade.ps1 -ViaUpdate`), and switch a framework-dependent installation to native. The Windows via-update check runs the installed control script in the smoke's own PowerShell session, where an `Invoke-WebRequest` function (functions take precedence over cmdlets) serves the release downloads.

The Windows installer and control script write and read the `data_dir` pointer as UTF-8 without BOM, which Main reads; Windows PowerShell's default ANSI code page made a non-ASCII data path resolve differently in the scripts and in Main. The Windows smoke runs both through Windows PowerShell with non-ASCII program and data directories and checks that the pointer, Main's listener log and the control script's console logs all use the one data directory. The control script checks for the control pipe before connecting (a connect to a missing pipe waits out its timeout), polls start every 100 ms and identifies the answering process once; on the test machine start fell from about 5–6 s to about 3 s and restart to about 2.5 s. Moving a freshly extracted release into `runtime\` retries briefly, because a short-lived handle from another process was observed to deny it once.

### Visual C++ runtime in Windows packages

<a id="d-release-vc-runtime"></a>
**Decision: Windows packages ship no Visual C++ runtime; the Rust binaries link the C runtime statically** (user, 2026-11-14; replaces the app-local runtime of 2026-11-12 and 2026-11-13). The only binaries that imported `VCRUNTIME140.dll` were the official LanceDB library and the official ToolScript worker, which Windows does not provide. The [self-built libraries](#native-libraries) are linked with `-C target-feature=+crt-static`, so they import only Windows DLLs. The NativeAOT executables and the Windows App SDK and WebView2 DLLs link the C++ runtime statically and import only the Universal C runtime (`api-ms-win-crt-*`), which is part of Windows 10 and later; SQLite, SkiaSharp, esbuild, sharp/libvips and `WebView2Loader.dll` import neither. Both server packages and the Desktop package therefore contain no `vcruntime*.dll`, no `msvcp*.dll` and no `VC-RUNTIME-NOTICE.txt`, and the `--vc-runtime` option, the runtime copy step and the runtime locator in the workflow are gone. The Windows job asserts the absence directly.

`windows-imports.mjs` reads PE import and delay-import tables and fails a package whose native binaries import a DLL that is neither beside them nor a Windows system DLL (API sets and System32 names except the Visual C++ runtime, which a build machine may have installed there; Node addons' `node.exe`). `package.mjs` runs it on every Windows publication it builds, the release job runs it on both server packages and the Desktop package, and the Desktop acceptance runs it again on the extracted ZIP. A library built without the static runtime, such as the LanceDB package's or the official worker, therefore fails the build; Windows targets require `--native-libraries`.

The NativeAOT executable requires the glibc it was linked against, so the release job links it in a UBI 9 container (glibc 2.34; `scripts/release/native-linux.Dockerfile`, SDK copied from the pinned SDK image) with the delivery assets built on the runner. `check-linux-libraries.sh` rejects any ELF file in either Linux package above glibc 2.34 or needing a library outside the base C/C++ runtime. ICU and OpenSSL are loaded at run time and remain system requirements. The Rust libraries are built the way the [next section](#native-libraries) describes.

### Native libraries

<a id="native-libraries"></a>
<a id="d-release-native-libraries"></a>
**Decision: release packages ship the LanceDB library and the ToolScript worker built from pinned, patched upstream source** (user, 2026-11-14). Foxwarm opens only local-directory LanceDB tables and starts the Monty worker without type checking, so the packages do not carry what the prebuilt artifacts include for other consumers. The binding's native crate enables six object-store back ends (S3, Azure, GCS, OSS, DynamoDB, Hugging Face) that Foxwarm never uses, and its profile is optimized for speed; the worker embeds a type checker that Foxwarm never requests. Every release package ships the self-built libraries: the Linux framework-dependent and native packages and the container image (which is built from the native package), the Windows x64 server packages and Desktop, and the macOS arm64 server packages and Desktop. No other RID ships them; the standalone CLI Node packages do not include either library.

- **Sources and patches.** LanceDB: `dotnet/Foxwarm.LanceDb/source.json` (lancedb-csharp commit and archive digest, the source whose C# binding Foxwarm compiles) with `native-build.patch`, a build-configuration patch of `pinvoke/Cargo.toml`: `features = []` on the `lancedb` dependency and `opt-level = "s"`. The worker: `dotnet/Foxwarm/ToolScript/monty-source.json` pins the upstream tag, commit, archive digest and Rust toolchain; `monty-no-type-check.patch` removes the type-checking crate from the executable and replaces its two call sites with stubs that report the checker as unavailable. Both patches carry the upstream licence statement and are public. `native-source.py` downloads each archive, verifies its digest, applies the patch with `git apply` outside any enclosing checkout and selects the toolchain; after a patch that removes dependencies it prunes `Cargo.lock` with `cargo update --workspace` and fails unless every remaining package keeps its pinned name, version, source and checksum (`cargo build --locked` alone rejects a pruned lock). Upgrading a pin means moving the JSON, rechecking that the patch applies and re-running qualification.
- **Build.** `build-lancedb.sh` and `build-monty.sh` share `rust-native-common.sh` and run unchanged on Linux x64 (in `rust-native-linux.Dockerfile`, UBI 9, glibc 2.34, both pinned toolchains), on Windows x64 (Git Bash, MSVC) and macOS arm64. The LanceDB build uses the speed-to-size trade of `opt-level = "s"`; the worker keeps its upstream optimization level, because its interpreter loop is the product and size optimization slows it measurably, and aborts on panic (nothing in the worker catches an unwind). Linux builds add `-C force-unwind-tables=no` (panics abort, so unwind tables are dead weight), Windows builds add `-C target-feature=+crt-static`. `install-protoc.py` installs the pinned `protoc` on Windows and macOS (digest-checked); the Linux image installs it itself. After the build, `crate-licenses.py` writes the crate list and licence texts of the binary's linked crates (`LanceDB-native-crates.txt`, `Monty-native-crates.txt`), which ship beside the executable.
- **Workflow.** `release.yml` has one producer job per RID (`native-linux-x64`, `native-win-x64`, `native-osx-arm64`). Each restores an `actions/cache` entry keyed by the sources, patches, scripts and its platform's installer or Dockerfile, builds only on a miss, and uploads the directory as an artifact the package jobs download; a cache hit skips the Rust build. `package.mjs --native-libraries DIR` passes the directory as `FoxwarmNativeLibraries`; `Foxwarm.csproj` then substitutes the library for the LanceDB package's item of the target RID (keeping the item's metadata) and ships the worker and licence files instead of acquiring the official worker. `check-native-libraries.mjs` runs on every extracted package and requires every copy of the library and worker to be byte-identical to the build output (the macOS Desktop bundle is re-signed, so its size is compared within a tolerance) and the licence files to be present, so the qualification lanes, which run against the extracted packages, run against the self-built libraries. The Linux job also runs `check-linux-libraries.sh` on the build output.
- **Ordinary builds keep the prebuilt libraries** (the LanceDB NuGet package's and the official worker from the npm registry). Developers and the Tests workflow then need no Rust toolchain or `protoc`, builds stay fast, and tests exercise the artifacts that published upstream packages guarantee. The risk that the shipped build differs is covered by running package qualification (the native smoke, the ToolScript and Vector child qualification and Desktop acceptance) against the shipped libraries, which the release workflow does by construction. A change that touches the Vector table or the ToolScript worker protocol should therefore be exercised by a release-workflow run before it is released.
- **Not retained.** `LanceDbNativeLibrary` and `--lancedb-library`, the Linux-only substitution, are replaced by the generic directory.

### macOS packages

**Decision: macOS server packages are arm64-only** (user, 2026-11-03). Publish a framework-dependent and a no-.NET variant (self-contained until 0.9.5, [native](#native-macos-and-windows-packages) since 0.9.6), selected as on Linux. LanceDB 2.5.0 has no osx-x64 native, so Intel Mac server packages are excluded. macOS 15 is the supported minimum under the .NET 10 support policy. The [macOS Desktop](#macos-desktop-app) is arm64-only too. There is no distribution signing/notarization step. Browser-downloaded archives may carry Gatekeeper quarantine; the installation guide gives a per-package removal procedure after checksum verification. Curl installation does not add quarantine.

### macOS Desktop app

<a id="d-release-macos-desktop"></a>
**Decision: the macOS Desktop ships as an unsigned NativeAOT app in a zip** (user, 2026-11-12, Foxwarm 0.9.6), after Apple Silicon trials of the managed and NativeAOT builds. The `desktop-osx-arm64` target (`kind: 'desktop'`, `native: true`, `bundle: 'Foxwarm.app'`) publishes the [macOS host](./desktop-macos.md) with `-p:PublishAot=true` and is published like the Windows Desktop, through aggregation, `SHA256SUMS` and the GitHub release. NativeAOT was chosen over managed for its memory, helper start-up and size (on Apple Silicon, Main about 70 MB footprint against 160 MB or more for a managed Debug build, a helper re-exec 0.02 s against 0.10 s, a 224 MB bundle). The archive is `foxwarm-desktop-osx-arm64.zip`, made with `ditto -c -k --keepParent` from the bundle exactly as the Apple SDK built and ad-hoc signed it: any later change, including a `release.json` or removed debug files, would break the bundle's sealed signature, so the target writes none and the bundle's `CFBundleShortVersionString` carries the version. No Developer ID signing, notarization, dmg, installer, updater or Code workbench is provided. Without a Developer ID every format ends in the same Gatekeeper override, so a dmg would add nothing until signing exists; the install guide gives the per-archive quarantine removal used for the server packages.

The Apple SDK writes the bundle to the project's `bin/Release/net10.0-macos/osx-arm64/` and leaves the publish directory empty; `package.mjs` removes a stale bundle there before publishing and copies the new one with `ditto`. The `macos-desktop` job (`macos-15` arm64) selects Xcode 26.3 through a job-level `DEVELOPER_DIR` without changing the image default, and installs the `macos` workload pinned by rollback file to manifest 26.2.10233 (the macOS 26.2 SDK that Xcode 26.3 provides), because the SDK's current workload set selects a newer workload built for a newer Xcode. It uploads `release-packages-macos-desktop`, which aggregation and publication wait for, and runs `dotnet/scripts/qualify-desktop-mac-package.mjs` against the extracted ZIP; see [Desktop producer and qualification](#desktop-producer-and-qualification).

## Installed layout and controls

The installation root is the program directory: `data_dir`, the control script and `runtime/<version>` plus `runtime/current` (symlink on Linux/macOS, junction on Windows). Main is started with `--installation-root <program directory>`, so data selection and relative settings follow [captured installation paths](./host-runtime.md) exactly as for a source checkout. Self-contained packages run their apphost and native packages their NativeAOT executable, both named `Foxwarm`. Framework-dependent packages run `dotnet Foxwarm.dll` with the `dotnet` on `PATH`, because the apphost searches only the app directory, `DOTNET_ROOT`, the registered location and the default location; installers detect a runtime through `PATH`.

The installers select data as before: explicit parameter, `FOXWARM_DATA_DIR`, a nonempty saved pointer, then a sibling `foxwarm-data`; explicit relative paths resolve from the caller's directory and are saved as absolute paths. A fresh install runs the new release's read-only [upgrade inspection](./session-upgrade-inspection.md) before selecting it, so existing or migrated data can block installation. On Linux they choose the native package unless told; on macOS and Windows they choose the framework-dependent package only when `dotnet --list-runtimes` lists ASP.NET Core 10 and otherwise the self-contained one, unless told. They refuse a source checkout and a changed data directory for an existing installation; rerunning on an existing installation delegates to `foxwarmctl update`. The Linux installer also requires ICU and OpenSSL libraries, which .NET loads even in self-contained and native packages. It does not install system packages. The macOS installer accepts Darwin arm64, rejects Intel, uses `shasum -a 256` when `sha256sum` is absent, and skips Linux library-cache checks because macOS supplies ICU and Apple cryptography libraries. Installer and package control smoke run under system Bash 3.2 and BSD userland.

`foxwarmctl update` mirrors the [source restart](./source-main-entry.md#build-and-controls) sequence: download and verify (or use `--package`), extract into `runtime/.staging-*`, refuse another RID, skip the same version unless forced, run the staged release's upgrade inspection while Main keeps running, stop Main, move the release into `runtime/`, atomically repoint `current`, replace the root control script, start Main if it had been running and delete every other `runtime/` entry. A failed download or inspection leaves the selected release and Main untouched. There is no rollback or concurrent-update lock.

<a id="d-release-tmux-pane"></a>
**Decision: the Unix control script owns only Main's pane** (user, 2026-11-03). Users may `tmux attach` to the session and open their own windows, and another installation or a source checkout may hold the same session and window name, so `foxwarmctl` never kills a session or window. It looks only at window `foxwarm` of the exact session (`FOXWARM_TMUX_SESSION`, default `foxwarm`), listing its panes with `list-panes` (`display-message` silently reports another pane when that window is missing). A live pane is this installation's Main exactly when its `pane_current_path` equals the physical program directory: start launches Main with that working directory as the pane process through an `exec` chain, Main never changes it, and tmux reports the resolved path. This also recognizes Mains started by 0.9.0 and needs no ownership marker. A dead pane in that window, or one whose process is an unreaped zombie, is an exited Main. Accepted residual risk: a user shell whose directory is the program directory, inside that exact window, would be taken for Main.

Start reuses an exited pane with `respawn-pane`, otherwise opens the window in the existing session or creates the session, with pane-scoped `remain-on-exit` set in the same tmux command list so an early exit and its output remain inspectable; a window holding only another live program is refused with a hint to set `FOXWARM_TMUX_SESSION`. Path and runtime environment (`FOXWARM_DATA_DIR`, `MCP_CONFIG_PATH`, `DOTNET_ROOT`, `PATH`) are supplied from the invocation, as in the source controls. Stop sends SIGTERM to Main's PID, waits 60 seconds, then SIGKILLs it and fails if it survives 10 more seconds, then removes only that pane; independent exec jobs in their own sessions are unaffected. Restart and update leave the exited pane in place and respawn it, so a pane the user split into the window does not cause the restart to be refused. Another program in the window is never signalled: stop and update treat Main as not running, and `status` reports it with the hint. `status` reports running, exited (with the exit status or signal once tmux has reaped Main and recorded it) or not running, and exits 3 unless running; `attach` goes to Main's pane.

**Detached start and PID tracking** (user, 2026-11-03). Unix `start` prefers tmux and automatically uses `nohup bash -c` when tmux is absent, with stdin from `/dev/null` and stdout/stderr appended to the selected data root's `state/logs/foxwarm.stdout.log` and `foxwarm.stderr.log`. The launch chain uses `exec`, preserving Main's PID, and ignores terminal hangups without requiring `setsid`. Data selection matches Main: trimmed `FOXWARM_DATA_DIR`, then trimmed `data_dir`, then the installation root, with installation-relative paths and home expansion. `attach` in background mode reports the log paths.

Both modes write the decimal Main PID plus newline to `<installation root>/foxwarm.pid`; successful stop removes it. Pane discovery remains authoritative for tmux, including adoption of older pane-only starts. A PID recovered from the file must be non-zombie and have `ps -ww -o args=` output identifying this installation's runtime `Foxwarm` or `Foxwarm.dll` and ending with its exact `--installation-root <physical root>` argument. This rejects stale/reused PIDs and another installation whose root merely shares a prefix. Background stop repeats this check before forced termination. No `/proc` inspection is used by the control script. Status keeps `Running (PID N), release ...`, adds the mode, prints background log paths, and exits 0 for running or 3 otherwise.

The Unix script supports Bash 3.2 and BSD userland: existing directories resolve with `cd`/`pwd -P`, checksum verification falls back from `sha256sum` to `shasum -a 256`, extraction uses a directory glob, and atomic current-link replacement uses Darwin `mv -fh` or Linux `mv -fT`. No launch-mode option, concurrent-update lock or process-tree ownership machinery is added.

<a id="d-release-windows-control"></a>
**Decision: Windows package controls trust only their own Main and report success only when it serves** (user, 2026-11-10). Windows start launches Main with `--windows-background` through a hidden `cmd` that appends to the lifecycle logs, using the data-root-specific control pipe name of the [Windows source controls](./windows-service-scripts.md). The pipe name is predictable, so the control script trusts a reply only from this installation's Main: a PID reported over the pipe is this installation's Main exactly when its command line names this installation root with `--installation-root` and its program (`Foxwarm.exe`, or `Foxwarm.dll` run by `dotnet.exe`) is under `runtime\`. `status`, `start`, `stop` and `update` treat any other answerer as foreign: `status` says not running and names the process, `start`, `stop` and `update` refuse without starting or signalling anything. After the 60-second graceful wait, stop terminates the PID only if it is still verified as this installation's Main. Main claims the pipe name as its first instance and exits with a message that names the pipe when another process already holds it.

Start reports success only when Main answers on the pipe from this installation's process and its status reports `ready`, which Main sets once the host has started and its listener is up. A Main that exits while starting produces a failure with no sign-in link: a bind conflict names the port (`bot.httpPort`, default 3001) and the process holding it when Windows can tell, any other early exit shows the last line of the error log. Control replies from a Main that predates the `ready` field count as ready. The installer starts and updates through `foxwarmctl.cmd`, which runs the PowerShell control script with `-ExecutionPolicy Bypass` for that process only, so a Restricted or AllSigned machine policy does not stop it and the policy is never changed. Control failures are plain messages with exit code 1. `restart` checks that the selected release can be launched (`dotnet` on `PATH` for framework-dependent packages) before stopping the running Main. Installer reruns print the sign-in link like a fresh install.

The Unix control script applies the same rules without a pipe: tmux-pane or PID-file identity already restricts signals to this installation's Main, `start` waits for Main's listener line (`Main HTTP listening` or `Main started without HTTP`) in the pane or the log bytes appended by this start, and an `AddressInUse` failure names the port from `config.yaml`; `restart` checks the launcher before stopping.

## Workflow and image

The reusable `code-resources.yml` workflow is the single Code producer in both Tests and Release. It uses the existing `prepare-browser.mjs --code-only`/`--check-code` path and an exact input-keyed cache, then validates redistribution metadata/notices and uploads a per-run archive artifact. Tag cache visibility is not a prerequisite: an unavailable exact default-branch/tag cache falls back to one build. Consumers extract the artifact; no token is forwarded to upstream downloads. The Code source producer adds upstream LICENSE.txt and ThirdPartyNotices.txt to the untrimmed web output.

`.github/workflows/release.yml` first builds the [native libraries](#native-libraries) in one cached job per RID, then builds the Linux server packages on Ubuntu, the Windows server packages and Desktop in its Windows job (windows-2025, pinned SDK, the image's Visual Studio C++ tools and redistributable), and both macOS packages natively on the official arm64 `macos-15` runner, for pushes to `testing`/`main`, `v*` tags and manual dispatch, and keeps them as 14-day artifacts. The macOS Desktop is built in a separate `macos-desktop` job on the same runner type. Separate platform build artifacts (`release-packages-linux`, `-windows`, `-desktop`, `-macos`, `-macos-desktop`) feed one aggregation job that adds the [0.9.6 transition aliases](#native-macos-and-windows-packages), regenerates `SHA256SUMS` over every archive and uploads the final `release-packages` artifact; the tag-only release waits for aggregation and every platform qualification. `PREVIOUS_RELEASE`, set once at workflow level, names the release the upgrade checks start from. Qualification installs each server package with the real installer and control script (Linux framework-dependent on the runner, native on the runner and on Ubuntu 22.04 without .NET; both Windows packages through Windows PowerShell with non-ASCII paths; both macOS packages with and without tmux), runs Desktop validation and its WebView2 acceptance against the extracted Desktop ZIP, and starts the container image. The Linux, macOS and Windows jobs run `qualify-package.mjs` (`--vector` for the native package) and the detached-exec restart fixture against their extracted packages (Main without CoreCLR for native, file logging, the loopback listener, PTY, native ToolScript, the Vector child indexing and searching with LanceDB loaded only in the child), and switch a framework-dependent installation to native. Ubuntu 22.04 upgrades the previous release's native package to the new one, and macOS and Windows the previous release's self-contained package to native, each through the installer and that release's own control script. The Windows job also runs `windows-imports.mjs` on both server packages and the Desktop. The macOS job's dynamic-library inspection rejects accidental Homebrew dependencies. A tag must equal `package.json`'s version; after every qualification job passes it creates the GitHub release and pushes `ghcr.io/<owner>/foxwarm` tagged with the version, minor version and `latest`.

Reviewed `docs/release-notes/<tag>.md` files take precedence over generated release notes. `release-body.py` removes only an initial level-1 ATX heading and immediately following blank lines from the published body, preserving all remaining bytes and leaving the standalone document unchanged. The release name remains `Foxwarm <version>`, derived from the tag. `release-body.test.mjs` covers the filter and the publish step with a local GitHub CLI stub, including the generated-notes fallback.

The `Dockerfile` keeps the source-built default target for local and test Compose builds; it publishes native Main for the build host's architecture. Its `release` target copies the extracted native Linux package from the `package` build context onto the same runtime base (Node.js, Chromium, operator tools, ICU and OpenSSL; no .NET runtime). The release image job checks that the image has no `dotnet` or `Foxwarm.dll`, lists the image's Debian packages and checks that Main runs as `/app/Foxwarm` with uid 1000. The image runs Foxwarm as the fixed non-root `node` account: `docker/entrypoint.sh` starts as root only to check that the data directory is writable by uid 1000 (it never re-owns mounted data; the smoke job prepares a 1000:1000 volume) and drops privileges with `setpriv` (no `no_new_privs`, so the image's passwordless `sudo` for `node` works), applying to both targets. Chromium's sandbox stays on; `docker/seccomp-chromium.json` is Docker's default seccomp profile plus `clone`, `setns` and `unshare`, with no added capability. Root and test Compose reference it through `security_opt`; the install guide shows the same for `docker run`. The Docker image is validated only structurally in the Provider (entry point logic with shims, profile diff against upstream); it was not built or run there.

## Qualification boundary

Package archive normalization, Windows ZIP paths beyond the legacy path limit (including nested Code resources), aggregate checksum coverage, Darwin installer asset/variant selection (native default, `--native`, the retired `--self-contained`), the published target list, checksum verification with shasum, Intel refusal and RID refusal are covered by `package.test.mjs`. `qualify-package.mjs` runs only against an explicitly extracted payload for the host's own RID (linux-x64, osx-arm64 or win-x64; process maps from /proc, vmmap or the loaded-module list) and reuses the owned Main fixture, starting the NativeAOT executable for a native package and `Foxwarm.dll` otherwise; `mainHostNativeExec.e2e.mjs` accepts `FOXWARM_PUBLISHED_CORE` (native executable when the package has no `Foxwarm.dll`) for the actual package restart/recovery lane while retaining its ordinary source-build default. Linux package behavior is covered by `release-install.test.js` (fixture packages on private tmux servers: data selection, refusals, blocked inspection, update/restart/prune, forced kill, user windows and split panes in Main's session, a foreign program in Main's window, exited-pane respawn and removal with and without a recorded exit, a symlinked program directory, a Main started by the 0.9.0 start command, PID recording, no-tmux lifecycle and launcher-session hangup, stale/reused PID rejection, background logs, checksum-tool fallback, the native default, the installer's switch of a self-contained installation to native with later updates staying native, a same-version switch, the sign-in link for a configured listen address, and the message for a release without the recorded asset) and by `smoke-server.sh` and `smoke-upgrade.sh` against real packages. `windows-imports.test.mjs` covers PE import parsing and the runtime copy on synthetic images. Windows installer and control scripts are only parsed locally; their execution is qualified by the Windows job and was checked on a Windows Server 2022 test machine. The glibc floor of both Linux packages, semantic search included, is 2.34 since 0.9.4 (earlier releases shipped the package's LanceDB library, which needs 2.39). It is enforced by `check-linux-libraries.sh`, and the native package's smoke and `qualify-package.mjs --vector` run on Ubuntu 22.04 (glibc 2.35). HEIF decoders, signing and an installer/updater for either Desktop remain outside these packages. The Windows Desktop includes Code; servers use the separate prebuilt Code asset or source preparation. Measured archive sizes are recorded in `docs/releasing.md`.

A crashed Main can stay an unreaped zombie under a dead pane with no exit record. tmux records the exit only when SIGCHLD makes it reap the pane process, and tmux 3.4 and 3.5 built with utempter, such as the Ubuntu 24.04 package, can lose that signal: when the terminal closes before the process exits, tmux runs the utempter helper with default SIGCHLD handling, and an exit in that window is discarded until the server's next child event. tmux 3.6 sends itself SIGCHLD after the helper. The control script needs no reaping: a dead pane or zombie is exited, `status` then prints a bare `Exited.`, start/restart respawn the pane in place and stop removes it. The exited-pane fixture therefore waits until the pane is dead and the process has exited, sends SIGCHLD to its private tmux server as tmux 3.6 does, and then requires the recorded signal 9. A separate fixture starts its private server with SIGCHLD blocked, so the unreaped state is deterministic and status, restart and stop are checked there. Fixture commands clear inherited `TMUX` and use a newly owned `TMUX_TMPDIR`, including cleanup, so each fixture addresses only its own server.

## Desktop producer and qualification

### Windows Desktop app

<a id="d-release-windows-desktop-native"></a>
**Decision: the Windows Desktop ships as a NativeAOT app** (user, 2026-11-13, Foxwarm 0.9.6), as the [macOS Desktop](#macos-desktop-app) does, revising the earlier managed decision. The `desktop-win-x64` target (`kind: 'desktop'`, `native: true`) publishes the [WinUI host](./host-runtime.md#desktop-boundary) with `-p:PublishAot=true`, keeps the Code workbench and ships no Visual C++ runtime ([static C runtime](#visual-c-runtime-in-windows-packages)); it needs no .NET installation or redistributable. The asset name, layout (one `foxwarm-desktop-<version>-win-x64/` directory, `release.json` with `native: true`) and data location are unchanged, so an existing user replaces the extracted folder as before. Windows App SDK API metadata minimum is 17763; the supported Windows versions follow the .NET 10 policy.

Desktop uses the Windows App SDK WinUI component 2.6.5. Its manifest/XAML/PRI generation requires Windows tools, so the Windows job produces `desktop-win-x64` with `scripts/release/package.mjs` and the same `--vc-runtime` directory as the server packages. The Ubuntu producer builds the Linux server targets and forwards the shared `code-resources` archive. Windows extracts that same pinned archive, builds the shared assets, produces Desktop, checks the Desktop's imports with `windows-imports.mjs`, fails when the NativeAOT compiler reports a warning in the Desktop's own code (`Foxwarm.Desktop.*`; Main's warnings are gated by the Tests native lane, and release publications carry no symbols, so warnings name only the caller), and runs the extracted-ZIP acceptance. Its Desktop artifact joins the unchanged aggregate/checksum/publication path; aggregation waits for Windows qualification.

`validate-desktop-package.mjs` requires the NativeAOT layout: `release.json` with `native: true`, the native x64 executable, WinUI/Windows App SDK/WebView2 natives and resources, the shared resources and the Code workbench, and no .NET runtime, `*.runtimeconfig.json`, `*.deps.json` or managed assembly (any `.dll`/`.exe` outside `node_modules` with a CLR header). `qualify-desktop-package.mjs EXTRACTED_DIRECTORY REPORT` then launches the extracted app with a temporary data directory, configured Agent root, unrelated cwd and a local model and embedding peer. It attaches to WebView2 for native cookie sign-in, the authenticated WebSocket and Setup, executes the packaged esbuild/sharp, runs a native ToolScript turn with the exec helper, and indexes and searches through exactly one packaged Vector child (`Foxwarm.Desktop.exe --foxwarm-vector-child`), which loads `lancedb_ffi.dll` while Main does not. The process must not load `coreclr.dll`, `hostfxr.dll`, `hostpolicy.dll` or `clrjit.dll`. Window and notification-icon checks use `dotnet/scripts/desktop-window.ps1`, which touches only the Desktop process's own windows: Explorer must hold the icon (a no-op `NIM_MODIFY` succeeds only for an existing icon); closing the window (`WM_CLOSE`) hides it while Main stays ready and the icon stays; the icon's double-click notification shows it again; the icon's right-click opens the native menu (`Open`, `Exit`), whose **Exit** item is clicked with the mouse. Exit must end the process with status 0, log `Main stopped.` and end its child processes. A restart keeps origin, token, models and history, and `/admin/shutdown` ends the app with status 0. Interactive file dialogs, Windows sign-out, real-keyboard and HiDPI behavior are outside this lane.

The [macOS Desktop](#macos-desktop-app) is NativeAOT only. `qualify-desktop-mac-package.mjs EXTRACTED_APP REPORT` runs on Apple Silicon against the extracted bundle with a temporary data directory, configured Agent root, unrelated cwd and `TMPDIR`, and a local model and embedding peer. It checks the bundle identity and version, required resources and notices, the absence of managed assemblies, debug symbols, installer packages and instance data, `codesign --verify --deep --strict`, that `otool -L` of the executable names only `/usr/lib`, `/System/Library` and bundled .NET `libSystem.*.Native` libraries, and that no bundled native depends on Homebrew. It runs the bundle's esbuild and sharp. WKWebView has no remote debugging protocol, so the window is read through the Accessibility API (System Events, which the hosted runner allows for `osascript`): the signed-in application ("Open setup") must render, without "Sign in again" or the startup label. Unauthenticated `/api/auth/session` is refused. The test then exercises PTY input/output/resize/cancel, Setup save, a native ToolScript turn with the exec helper, and Vector indexing and search through exactly one packaged Vector child, which maps LanceDB, while Main maps neither LanceDB nor libvips (`lsof`). Quit Foxwarm through the menu must end the process with status 0, log `Main stopped.` and leave no child process. A restart keeps origin, token, models and history, and a second launch while the window is closed must exit 0 and reopen the window. `/admin/shutdown` must also end the app with status 0. Interactive file dialogs, quarantine handling, the WebKit profile and real-keyboard or VoiceOver behavior are outside this lane; WebKit's profile under the runner's Library is left to the disposable runner.
