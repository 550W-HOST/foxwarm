## Contracts and rationale

<a id="d-release-prebuilt-packages"></a>
**Decision: installation uses prebuilt packages** (user, 2026-11-02). Releases are compiled once by the release workflow; installing or updating needs neither Node.js nor the .NET SDK nor compilers. The regular edition is a server package for Linux x64 and Windows x64 (macOS when the server supports it), each framework-dependent and self-contained. The Desktop edition is Windows-only and self-contained. Versioning starts at 0.9; 1.0 is reserved for an improved out-of-box experience. Artifact preparation keeps running the collected compiler under an optional `node` on `PATH`; the packages neither bundle Node.js nor port that compiler. Source checkouts remain the development path with their own [build and controls](./source-main-entry.md#build-and-controls).

Release assets have version-free names (`foxwarm-linux-x64.tar.gz`, `foxwarm-linux-x64-self-contained.tar.gz`, `foxwarm-win-x64.zip`, `foxwarm-win-x64-self-contained.zip`, `foxwarm-desktop-win-x64.zip`) plus `SHA256SUMS`, so `releases/latest/download/<asset>` is stable. Each archive has one top-level directory. `release.json` records version, target, kind, RID, self-containment, asset name and source commit; installers and updates read the RID and asset from it and never switch package type implicitly. GitHub Releases host the assets because the site's static-asset download route cannot serve files of this size.

`package.mjs` publishes the existing [delivery resource graph](./core-delivery-cli.md#build-and-resource-boundary) with an explicit RID and `--self-contained`; it adds no second resource collector. Server packages add the control script for their platform; Desktop uses the Desktop project with `FoxwarmConsoleEntry=false` and `ArtifactTargetRid` as global properties and removes the console apphost/runtimeconfig. PDB/XML files are removed. A Linux host produces every target: for a non-host RID the script extracts the locked target-native esbuild/sharp packages, after checking the lockfile integrity, beside the host packages, so the collector's no-substitution rule still holds. Tarballs use sorted names, the commit timestamp and numeric root ownership.

## Installed layout and controls

The installation root is the program directory: `data_dir`, the control script and `runtime/<version>` plus `runtime/current` (symlink on Linux, junction on Windows). Main is started with `--installation-root <program directory>`, so data selection and relative settings follow [captured installation paths](./host-runtime.md) exactly as for a source checkout. Self-contained packages run their apphost. Framework-dependent packages run `dotnet Foxwarm.dll` with the `dotnet` on `PATH`, because the apphost searches only the app directory, `DOTNET_ROOT`, the registered location and the default location; installers detect a runtime through `PATH`.

The installers select data as before: explicit parameter, `FOXWARM_DATA_DIR`, a nonempty saved pointer, then a sibling `foxwarm-data`; explicit relative paths resolve from the caller's directory and are saved as absolute paths. A fresh install runs the new release's read-only [upgrade inspection](./session-upgrade-inspection.md) before selecting it, so existing or migrated data can block installation. They choose the framework-dependent package only when `dotnet --list-runtimes` lists ASP.NET Core 10 and otherwise the self-contained one, unless told. They refuse a source checkout and a changed data directory for an existing installation; rerunning on an existing installation delegates to `foxwarmctl update`. The Linux installer also requires ICU and OpenSSL libraries, which .NET loads even in self-contained packages. It does not install system packages.

`foxwarmctl update` mirrors the [source restart](./source-main-entry.md#build-and-controls) sequence: download and verify (or use `--package`), extract into `runtime/.staging-*`, refuse another RID, skip the same version unless forced, run the staged release's upgrade inspection while Main keeps running, stop Main, move the release into `runtime/`, atomically repoint `current`, replace the root control script, start Main if it had been running and delete every other `runtime/` entry. A failed download or inspection leaves the selected release and Main untouched. There is no rollback or concurrent-update lock.

<a id="d-release-tmux-pane"></a>
**Decision: the Unix control script owns only Main's pane** (user, 2026-11-03). Users may `tmux attach` to the session and open their own windows, and another installation or a source checkout may hold the same session and window name, so `foxwarmctl` never kills a session or window. It looks only at window `foxwarm` of the exact session (`FOXWARM_TMUX_SESSION`, default `foxwarm`), listing its panes with `list-panes` (`display-message` silently reports another pane when that window is missing). A live pane is this installation's Main exactly when its `pane_current_path` equals the physical program directory: start launches Main with that working directory as the pane process through an `exec` chain, Main never changes it, and tmux reports the resolved path. This also recognizes Mains started by 0.9.0 and needs no ownership marker. A dead pane in that window, or one whose process is an unreaped zombie, is an exited Main. Accepted residual risk: a user shell whose directory is the program directory, inside that exact window, would be taken for Main.

Start reuses an exited pane with `respawn-pane`, otherwise opens the window in the existing session or creates the session, with pane-scoped `remain-on-exit` set in the same tmux command list so an early exit and its output remain inspectable; a window holding only another live program is refused with a hint to set `FOXWARM_TMUX_SESSION`. Path and runtime environment (`FOXWARM_DATA_DIR`, `MCP_CONFIG_PATH`, `DOTNET_ROOT`, `PATH`) are supplied from the invocation, as in the source controls. Stop sends SIGTERM to Main's PID, waits 60 seconds, then SIGKILLs it and fails if it survives 10 more seconds, then removes only that pane; independent exec jobs in their own sessions are unaffected. Restart and update leave the exited pane in place and respawn it, so a pane the user split into the window does not cause the restart to be refused. Another program in the window is never signalled: stop and update treat Main as not running, and `status` reports it with the hint. `status` reports running, exited (with exit status or signal) or not running, and exits 3 unless running; `attach` goes to Main's pane.

**Detached start and PID tracking** (user, 2026-11-03). Unix `start` prefers tmux and automatically uses `nohup bash -c` when tmux is absent, with stdin from `/dev/null` and stdout/stderr appended to the selected data root's `state/logs/foxwarm.stdout.log` and `foxwarm.stderr.log`. The launch chain uses `exec`, preserving Main's PID, and ignores terminal hangups without requiring `setsid`. Data selection matches Main: trimmed `FOXWARM_DATA_DIR`, then trimmed `data_dir`, then the installation root, with installation-relative paths and home expansion. `attach` in background mode reports the log paths.

Both modes write the decimal Main PID plus newline to `<installation root>/foxwarm.pid`; successful stop removes it. Pane discovery remains authoritative for tmux, including adoption of older pane-only starts. A PID recovered from the file must be non-zombie and have `ps -ww -o args=` output identifying this installation's runtime `Foxwarm` or `Foxwarm.dll` and ending with its exact `--installation-root <physical root>` argument. This rejects stale/reused PIDs and another installation whose root merely shares a prefix. Background stop repeats this check before forced termination. No `/proc` inspection is used by the control script. Status keeps `Running (PID N), release ...`, adds the mode, prints background log paths, and exits 0 for running or 3 otherwise.

The Unix script supports Bash 3.2 and BSD userland: existing directories resolve with `cd`/`pwd -P`, checksum verification falls back from `sha256sum` to `shasum -a 256`, extraction uses a directory glob, and atomic current-link replacement uses Darwin `mv -fh` or Linux `mv -fT`. No launch-mode option, concurrent-update lock or process-tree ownership machinery is added.

Windows start launches Main with `--windows-background` through a hidden `cmd` that appends to the lifecycle logs, using the data-root-specific control pipe name of the [Windows source controls](./windows-service-scripts.md); stop uses the pipe's `stop`, then terminates the reported PID after 60 seconds.

## Workflow and image

`.github/workflows/release.yml` builds all packages once on Ubuntu for pushes to `testing`/`main`, `v*` tags and manual dispatch, and keeps them as a 14-day artifact. Qualification installs each server package with the real installer and control script (Linux framework-dependent on the runner, self-contained on Ubuntu 22.04 without .NET; both Windows packages on a Windows runner), runs Desktop validation and its WebView2 acceptance against the extracted self-contained ZIP, and starts the container image. A tag must equal `package.json`'s version; after every qualification job passes it creates the GitHub release and pushes `ghcr.io/<owner>/foxwarm` tagged with the version, minor version and `latest`.

The `Dockerfile` keeps the source-built default target for local and test Compose builds. Its `release` target copies an extracted framework-dependent Linux package from the `package` build context onto the same runtime base (ASP.NET Core runtime, Node.js, Chromium, operator tools). Root `docker-compose.yml` runs the published image; test Compose is unchanged.

## Qualification boundary

Linux package behavior is covered by `release-install.test.js` (fixture packages on private tmux servers: data selection, refusals, blocked inspection, update/restart/prune, forced kill, user windows and split panes in Main's session, a foreign program in Main's window, exited-pane respawn and removal, a symlinked program directory, a Main started by the 0.9.0 start command, PID recording, no-tmux lifecycle and launcher-session hangup, stale/reused PID rejection, background logs and checksum-tool fallback) and `smoke-server.sh` against real packages. Windows installer and control scripts are only parsed locally; their execution is qualified by the Windows job. The glibc floor is 2.34 for Main and 2.39 for the bundled LanceDB library used by semantic search. Code workbench assets, HEIF decoders, signing, an installer/updater for Desktop and macOS remain outside these packages.
