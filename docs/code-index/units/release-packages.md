## Contracts and rationale

<a id="d-release-prebuilt-packages"></a>
**Decision: installation uses prebuilt packages** (user, 2026-11-02). Releases are compiled once by the release workflow; installing or updating needs neither Node.js nor the .NET SDK nor compilers. The regular edition is a server package for Linux x64, macOS arm64 and Windows x64: framework-dependent everywhere, plus native on Linux (below) and self-contained on macOS and Windows. The Desktop edition is Windows-only and self-contained. Versioning starts at 0.9; 1.0 is reserved for an improved out-of-box experience. Artifact preparation keeps running the collected compiler under an optional `node` on `PATH`; the packages neither bundle Node.js nor port that compiler. Source checkouts remain the development path with their own [build and controls](./source-main-entry.md#build-and-controls).

Release assets have version-free names (`foxwarm-linux-x64.tar.gz`, `foxwarm-linux-x64-native.tar.gz`, `foxwarm-osx-arm64.tar.gz`, `foxwarm-osx-arm64-self-contained.tar.gz`, `foxwarm-win-x64.zip`, `foxwarm-win-x64-self-contained.zip`, `foxwarm-desktop-win-x64.zip`) plus `SHA256SUMS`, so `releases/latest/download/<asset>` is stable. Each application archive has one top-level directory. The additional versioned `foxwarm-code-<version>.tar.gz` extracts directly into `packages/vscode-web/assets` with `vscode-web/` and `extensions/redhat.vscode-yaml/`; it participates in the same checksum aggregation. `release.json` records version, target, kind, RID, self-containment, whether it is native, asset name and source commit; installers and updates read the RID and asset from it and switch package type only as described in [the native Linux decision](#native-linux-package). GitHub Releases host the assets because the site's static-asset download route cannot serve files of this size.

`package.mjs` publishes the existing [delivery resource graph](./core-delivery-cli.md#build-and-resource-boundary) with an explicit RID and `--self-contained` (native targets add `-p:PublishAot=true`); it adds no second resource collector. Server packages add the control script for their platform; Desktop uses the Desktop project with `FoxwarmConsoleEntry=false` and `ArtifactTargetRid` as global properties and removes the console apphost/runtimeconfig. PDB/XML files, and NativeAOT `.dbg` files and `.dSYM` bundles, are removed from delivery. Desktop then copies the complete pinned Code OSS and YAML asset subtrees, including all built-in language extensions and redistribution notices; server packages do not copy them. `validateCodeAssets`, `installCodeAssets` and `archiveCode` own pin/notice validation, Desktop layout and standalone Code packaging. `--code-only` packages already prepared assets without a managed publish. A Linux host produces the Linux and Windows server targets; the existing Windows job produces Desktop: for a non-host RID the script extracts the locked target-native esbuild/sharp packages, after checking the lockfile integrity, beside the host packages, so the collector's no-substitution rule still holds. Tarballs use Python 3 on both GNU and BSD hosts, with sorted names, the commit timestamp, numeric root ownership and fixed gzip metadata. The macOS targets use locked darwin-arm64 esbuild/sharp natives and require an arm64 macOS build host so the shared Darwin PTY dylib and controlling-terminal helper are compiled natively. NativeAOT cannot cross-compile between operating systems, so a native target is refused on any other host RID; without `--target`, a host builds only the published targets it can build. `osx-arm64-native` and `win-x64-native` are qualification targets that are never built by default or published.

### Native Linux package

<a id="d-release-native-linux"></a>
**Decision: native Linux package replaces the self-contained one** (user, 2026-11-10, Foxwarm 0.9.4). Linux x64 ships `foxwarm-linux-x64-native.tar.gz`, a NativeAOT publication of Main (`-p:PublishAot=true`, not single-file), as the package that needs no .NET; it is the default of the installer and the install documentation. The framework-dependent Linux package stays; `foxwarm-linux-x64-self-contained.tar.gz` is no longer produced. Windows x64 and macOS arm64 keep their framework-dependent and self-contained packages and the managed Desktop for 0.9.4; the release workflow builds and smoke-tests `win-x64-native` and `osx-arm64-native` so a later release can switch them, without publishing them or letting them block publication. The container image is built from the native package and carries no .NET runtime.

A native package is a directory like any other server package: `Foxwarm` is the NativeAOT executable, with native libraries, resources and notices beside it and no `Foxwarm.dll`. Its `release.json` has `selfContained: true` and `native: true`. Every control script since 0.9.0 launches a self-contained package through `Foxwarm` and accepts any package of its RID in `update --package`, so an existing installation's own control script can install and start a native package. The Vector owner is the same executable started with `--foxwarm-vector-child`.

The installed control script updates within its recorded asset name, and 0.9.3 and earlier self-contained Linux installations record the retired asset, which a 0.9.4 release does not contain. Rerunning the installer is therefore the switch: on an existing installation whose asset is the retired self-contained Linux archive, or when the user chooses a package (`--native`, `--framework-dependent`), the installer downloads and verifies that package itself and hands it to the installation's control script with `update --package FILE --force` (`--force` also switches between packages of one version). Data, `data_dir`, configuration and the control-script lifecycle are unchanged; the new release's upgrade inspection still runs first. Without a choice, other installations keep their package type. On Linux, `--self-contained` selects the native package with a notice; on macOS, `--native` is refused.

The NativeAOT executable requires the glibc it was linked against, so the release job links it in a UBI 9 container (glibc 2.34; `scripts/release/native-linux.Dockerfile`, SDK copied from the pinned SDK image) with the delivery assets built on the runner. `check-linux-libraries.sh` rejects any ELF file in the package above glibc 2.34, other than the LanceDB library (2.39), or needing a library outside the base C/C++ runtime. ICU and OpenSSL are loaded at run time and remain system requirements.

### macOS packages

**Decision: macOS server packages are arm64-only** (user, 2026-11-03). Publish framework-dependent and self-contained variants, selected automatically by the installer just like Linux/Windows. LanceDB 2.5.0 has no osx-x64 native, so Intel Mac server packages are excluded. macOS 15 is the supported minimum under the .NET 10 support policy. There is no macOS Desktop package or distribution signing/notarization step. Browser-downloaded archives may carry Gatekeeper quarantine; the installation guide gives a per-package removal procedure after checksum verification. Curl installation does not add quarantine.

## Installed layout and controls

The installation root is the program directory: `data_dir`, the control script and `runtime/<version>` plus `runtime/current` (symlink on Linux/macOS, junction on Windows). Main is started with `--installation-root <program directory>`, so data selection and relative settings follow [captured installation paths](./host-runtime.md) exactly as for a source checkout. Self-contained packages run their apphost and native packages their NativeAOT executable, both named `Foxwarm`. Framework-dependent packages run `dotnet Foxwarm.dll` with the `dotnet` on `PATH`, because the apphost searches only the app directory, `DOTNET_ROOT`, the registered location and the default location; installers detect a runtime through `PATH`.

The installers select data as before: explicit parameter, `FOXWARM_DATA_DIR`, a nonempty saved pointer, then a sibling `foxwarm-data`; explicit relative paths resolve from the caller's directory and are saved as absolute paths. A fresh install runs the new release's read-only [upgrade inspection](./session-upgrade-inspection.md) before selecting it, so existing or migrated data can block installation. On Linux they choose the native package unless told; on macOS and Windows they choose the framework-dependent package only when `dotnet --list-runtimes` lists ASP.NET Core 10 and otherwise the self-contained one, unless told. They refuse a source checkout and a changed data directory for an existing installation; rerunning on an existing installation delegates to `foxwarmctl update`. The Linux installer also requires ICU and OpenSSL libraries, which .NET loads even in self-contained and native packages. It does not install system packages. The macOS installer accepts Darwin arm64, rejects Intel, uses `shasum -a 256` when `sha256sum` is absent, and skips Linux library-cache checks because macOS supplies ICU and Apple cryptography libraries. Installer and package control smoke run under system Bash 3.2 and BSD userland.

`foxwarmctl update` mirrors the [source restart](./source-main-entry.md#build-and-controls) sequence: download and verify (or use `--package`), extract into `runtime/.staging-*`, refuse another RID, skip the same version unless forced, run the staged release's upgrade inspection while Main keeps running, stop Main, move the release into `runtime/`, atomically repoint `current`, replace the root control script, start Main if it had been running and delete every other `runtime/` entry. A failed download or inspection leaves the selected release and Main untouched. There is no rollback or concurrent-update lock.

<a id="d-release-tmux-pane"></a>
**Decision: the Unix control script owns only Main's pane** (user, 2026-11-03). Users may `tmux attach` to the session and open their own windows, and another installation or a source checkout may hold the same session and window name, so `foxwarmctl` never kills a session or window. It looks only at window `foxwarm` of the exact session (`FOXWARM_TMUX_SESSION`, default `foxwarm`), listing its panes with `list-panes` (`display-message` silently reports another pane when that window is missing). A live pane is this installation's Main exactly when its `pane_current_path` equals the physical program directory: start launches Main with that working directory as the pane process through an `exec` chain, Main never changes it, and tmux reports the resolved path. This also recognizes Mains started by 0.9.0 and needs no ownership marker. A dead pane in that window, or one whose process is an unreaped zombie, is an exited Main. Accepted residual risk: a user shell whose directory is the program directory, inside that exact window, would be taken for Main.

Start reuses an exited pane with `respawn-pane`, otherwise opens the window in the existing session or creates the session, with pane-scoped `remain-on-exit` set in the same tmux command list so an early exit and its output remain inspectable; a window holding only another live program is refused with a hint to set `FOXWARM_TMUX_SESSION`. Path and runtime environment (`FOXWARM_DATA_DIR`, `MCP_CONFIG_PATH`, `DOTNET_ROOT`, `PATH`) are supplied from the invocation, as in the source controls. Stop sends SIGTERM to Main's PID, waits 60 seconds, then SIGKILLs it and fails if it survives 10 more seconds, then removes only that pane; independent exec jobs in their own sessions are unaffected. Restart and update leave the exited pane in place and respawn it, so a pane the user split into the window does not cause the restart to be refused. Another program in the window is never signalled: stop and update treat Main as not running, and `status` reports it with the hint. `status` reports running, exited (with the exit status or signal once tmux has reaped Main and recorded it) or not running, and exits 3 unless running; `attach` goes to Main's pane.

**Detached start and PID tracking** (user, 2026-11-03). Unix `start` prefers tmux and automatically uses `nohup bash -c` when tmux is absent, with stdin from `/dev/null` and stdout/stderr appended to the selected data root's `state/logs/foxwarm.stdout.log` and `foxwarm.stderr.log`. The launch chain uses `exec`, preserving Main's PID, and ignores terminal hangups without requiring `setsid`. Data selection matches Main: trimmed `FOXWARM_DATA_DIR`, then trimmed `data_dir`, then the installation root, with installation-relative paths and home expansion. `attach` in background mode reports the log paths.

Both modes write the decimal Main PID plus newline to `<installation root>/foxwarm.pid`; successful stop removes it. Pane discovery remains authoritative for tmux, including adoption of older pane-only starts. A PID recovered from the file must be non-zombie and have `ps -ww -o args=` output identifying this installation's runtime `Foxwarm` or `Foxwarm.dll` and ending with its exact `--installation-root <physical root>` argument. This rejects stale/reused PIDs and another installation whose root merely shares a prefix. Background stop repeats this check before forced termination. No `/proc` inspection is used by the control script. Status keeps `Running (PID N), release ...`, adds the mode, prints background log paths, and exits 0 for running or 3 otherwise.

The Unix script supports Bash 3.2 and BSD userland: existing directories resolve with `cd`/`pwd -P`, checksum verification falls back from `sha256sum` to `shasum -a 256`, extraction uses a directory glob, and atomic current-link replacement uses Darwin `mv -fh` or Linux `mv -fT`. No launch-mode option, concurrent-update lock or process-tree ownership machinery is added.

<a id="d-release-windows-control"></a>
**Decision: Windows package controls trust only their own Main and report success only when it serves** (user, 2026-11-10). Windows start launches Main with `--windows-background` through a hidden `cmd` that appends to the lifecycle logs, using the data-root-specific control pipe name of the [Windows source controls](./windows-service-scripts.md). The pipe name is predictable, so the control script trusts a reply only from this installation's Main: a PID reported over the pipe is this installation's Main exactly when its command line names this installation root with `--installation-root` and its program (`Foxwarm.exe`, or `Foxwarm.dll` run by `dotnet.exe`) is under `runtime\`. `status`, `start`, `stop` and `update` treat any other answerer as foreign: `status` says not running and names the process, `start`, `stop` and `update` refuse without starting or signalling anything. After the 60-second graceful wait, stop terminates the PID only if it is still verified as this installation's Main. Main claims the pipe name as its first instance and exits with a message that names the pipe when another process already holds it.

Start reports success only when Main answers on the pipe from this installation's process and its status reports `ready`, which Main sets once the host has started and its listener is up. A Main that exits while starting produces a failure with no sign-in link: a bind conflict names the port (`bot.httpPort`, default 3001) and the process holding it when Windows can tell, any other early exit shows the last line of the error log. Control replies from a Main that predates the `ready` field count as ready. The installer starts and updates through `foxwarmctl.cmd`, which runs the PowerShell control script with `-ExecutionPolicy Bypass` for that process only, so a Restricted or AllSigned machine policy does not stop it and the policy is never changed. Control failures are plain messages with exit code 1. `restart` checks that the selected release can be launched (`dotnet` on `PATH` for framework-dependent packages) before stopping the running Main. Installer reruns print the sign-in link like a fresh install.

The Unix control script applies the same rules without a pipe: tmux-pane or PID-file identity already restricts signals to this installation's Main, `start` waits for Main's listener line (`Main HTTP listening` or `Main started without HTTP`) in the pane or the log bytes appended by this start, and an `AddressInUse` failure names the port from `config.yaml`; `restart` checks the launcher before stopping.

## Workflow and image

The reusable `code-resources.yml` workflow is the single Code producer in both Tests and Release. It uses the existing `prepare-browser.mjs --code-only`/`--check-code` path and an exact input-keyed cache, then validates redistribution metadata/notices and uploads a per-run archive artifact. Tag cache visibility is not a prerequisite: an unavailable exact default-branch/tag cache falls back to one build. Consumers extract the artifact; no token is forwarded to upstream downloads. The Code source producer adds upstream LICENSE.txt and ThirdPartyNotices.txt to the untrimmed web output.

`.github/workflows/release.yml` builds Linux/Windows server packages once on Ubuntu, Desktop in its Windows job, and both macOS variants natively on the official arm64 `macos-15` runner for pushes to `testing`/`main`, `v*` tags and manual dispatch, and keeps them as 14-day artifacts. Separate platform build artifacts feed one aggregation job that regenerates `SHA256SUMS` over every archive and uploads the final `release-packages` artifact; the tag-only release waits for aggregation and every platform qualification. Qualification installs each server package with the real installer and control script (Linux framework-dependent on the runner, native on the runner and on Ubuntu 22.04 without .NET; both Windows packages on a Windows runner), runs Desktop validation and its WebView2 acceptance against the extracted self-contained ZIP, and starts the container image. The Linux job also runs `qualify-package.mjs --vector` and the detached-exec restart fixture against the extracted native package on the runner (Main without CoreCLR, file logging, PTY, native ToolScript, the Vector child indexing and searching with LanceDB loaded only in the child), switches a framework-dependent installation to native with `smoke-upgrade.sh`, and on Ubuntu 22.04 upgrades the previous release's self-contained package to the native one through the installer and that release's own control script. Separate `windows-native` (windows-2025) and `macos-native` (macos-15) jobs build the native qualification targets with the pinned SDK, upload them as 7-day `native-qualification-*` artifacts, and run the same server smoke (and on macOS the package qualification); they use `continue-on-error`, and neither aggregation nor publication depends on them. The macOS job extracts each produced archive and qualifies Main startup/file logging, detached exec surviving a real Main restart with exactly one completion, PTY input/output/resize/cancellation and native Monty/ToolScript host calls. It also installs each archive with the real installer and exercises start/status/update/stop with tmux and without tmux. Dynamic-library inspection rejects accidental Homebrew dependencies. A tag must equal `package.json`'s version; after every qualification job passes it creates the GitHub release and pushes `ghcr.io/<owner>/foxwarm` tagged with the version, minor version and `latest`.

Reviewed `docs/release-notes/<tag>.md` files take precedence over generated release notes. `release-body.py` removes only an initial level-1 ATX heading and immediately following blank lines from the published body, preserving all remaining bytes and leaving the standalone document unchanged. The release name remains `Foxwarm <version>`, derived from the tag. `release-body.test.mjs` covers the filter and the publish step with a local GitHub CLI stub, including the generated-notes fallback.

The `Dockerfile` keeps the source-built default target for local and test Compose builds; it publishes native Main for the build host's architecture. Its `release` target copies the extracted native Linux package from the `package` build context onto the same runtime base (Node.js, Chromium, operator tools, ICU and OpenSSL; no .NET runtime). The release image job checks that the image has no `dotnet` or `Foxwarm.dll`, lists the image's Debian packages and checks that Main runs as `/app/Foxwarm` with uid 1000. The image runs Foxwarm as the fixed non-root `node` account: `docker/entrypoint.sh` starts as root only to check that the data directory is writable by uid 1000 (it never re-owns mounted data; the smoke job prepares a 1000:1000 volume) and drops privileges with `setpriv` (no `no_new_privs`, so the image's passwordless `sudo` for `node` works), applying to both targets. Chromium's sandbox stays on; `docker/seccomp-chromium.json` is Docker's default seccomp profile plus `clone`, `setns` and `unshare`, with no added capability. Root and test Compose reference it through `security_opt`; the install guide shows the same for `docker run`. The Docker image is validated only structurally in the Provider (entry point logic with shims, profile diff against upstream); it was not built or run there.

## Qualification boundary

Package archive normalization, Windows ZIP paths beyond the legacy path limit (including nested Code resources), aggregate checksum coverage, Darwin installer asset/variant selection and `--native` refusal, the published/qualification target split, checksum verification with shasum, Intel refusal and RID refusal are covered by `package.test.mjs`. `qualify-package.mjs` runs only against an explicitly extracted payload for the host's own RID (linux-x64 or osx-arm64) and reuses the owned Main fixture, starting the NativeAOT executable for a native package and `Foxwarm.dll` otherwise; `mainHostNativeExec.e2e.mjs` accepts `FOXWARM_PUBLISHED_CORE` (native executable when the package has no `Foxwarm.dll`) for the actual package restart/recovery lane while retaining its ordinary source-build default. Linux package behavior is covered by `release-install.test.js` (fixture packages on private tmux servers: data selection, refusals, blocked inspection, update/restart/prune, forced kill, user windows and split panes in Main's session, a foreign program in Main's window, exited-pane respawn and removal with and without a recorded exit, a symlinked program directory, a Main started by the 0.9.0 start command, PID recording, no-tmux lifecycle and launcher-session hangup, stale/reused PID rejection, background logs, checksum-tool fallback, the native default, the installer's switch of a self-contained installation to native with later updates staying native, and a same-version switch) and by `smoke-server.sh` and `smoke-upgrade.sh` against real packages. Windows installer and control scripts are only parsed locally; their execution is qualified by the Windows job. The glibc floor is 2.34 for Main and 2.39 for the bundled LanceDB library used by semantic search; for the native package it is enforced by `check-linux-libraries.sh` and exercised on Ubuntu 22.04 (glibc 2.35), where semantic search is unavailable. HEIF decoders, signing and an installer/updater for Desktop remain outside these packages. Desktop includes Code; servers use the separate prebuilt Code asset or source preparation. Measured archive sizes are recorded in `docs/releasing.md`.

A crashed Main can stay an unreaped zombie under a dead pane with no exit record. tmux records the exit only when SIGCHLD makes it reap the pane process, and tmux 3.4 and 3.5 built with utempter, such as the Ubuntu 24.04 package, can lose that signal: when the terminal closes before the process exits, tmux runs the utempter helper with default SIGCHLD handling, and an exit in that window is discarded until the server's next child event. tmux 3.6 sends itself SIGCHLD after the helper. The control script needs no reaping: a dead pane or zombie is exited, `status` then prints a bare `Exited.`, start/restart respawn the pane in place and stop removes it. The exited-pane fixture therefore waits until the pane is dead and the process has exited, sends SIGCHLD to its private tmux server as tmux 3.6 does, and then requires the recorded signal 9. A separate fixture starts its private server with SIGCHLD blocked, so the unreaped state is deterministic and status, restart and stop are checked there. Fixture commands clear inherited `TMUX` and use a newly owned `TMUX_TMPDIR`, including cleanup, so each fixture addresses only its own server.

## Desktop producer and qualification

Desktop uses the Windows App SDK WinUI component 2.6.5. Its manifest/XAML/PRI generation requires Windows tools, so the existing Windows job now produces the unchanged managed `desktop-win-x64` target with `scripts/release/package.mjs`. The Ubuntu producer explicitly builds the existing Linux/Windows server targets and forwards the shared `code-resources` archive. Windows extracts that same pinned archive, builds the shared assets, produces Desktop, and runs the existing complete extracted-ZIP acceptance. Its Desktop artifact joins the unchanged aggregate/checksum/publication path; aggregation waits for Windows qualification. Desktop remains managed.

NativeAOT Desktop publication remains opt-in. Its bounded direct-publish host qualification is recorded in [Host startup](./host-runtime.md#desktop-boundary); native package-layout validation and an explicit release-target decision remain necessary before offering a native release archive.
