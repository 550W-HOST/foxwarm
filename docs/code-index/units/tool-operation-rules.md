Phase 3 of [tool operation authorization](./tool-operation-authorization.md): rules with `op` in the same ordered lists as version-1 rules, the two-domain evaluator, the self exemption, the ToolScript model-request gate, unresolved rejection, operation-aware visibility and the reader marker. Decisions, derivation, explanation, the inbound adapter, adoption and phases are owned by the design unit; operations, selectors and capabilities by the [catalog](./tool-operation-catalog.md).

## Grammar

A rule is an operation rule exactly when it has `op`; every other rule keeps its version-1 meaning. Operation rules accept `id`, `enabled`, `action`, `reason`, `approval` and the [catalog selectors](./tool-operation-catalog.md#selectors); version-1 fields (`tool`, `args`, `match`, `secrets`, `targetNode`) are unsupported fields on them. `OperationRules.Normalize` stores `op` as a list, the caller selectors under `match` (as version-1 rules store them, so caller matching is shared), resource selectors under `resources` and attributes under `with`. Load-time validation, against `OperationDeclarations.Operations`:

- unknown ops and families fail;
- each explicitly listed op must declare every resource and `with` attribute the rule uses; a pattern must cover at least one op that declares them all;
- `secret.use` stands alone, and `secret` applies only to `secret.use` and `secret.manage`;
- `ask` cannot select `externalId`, and `secret.use` rules cannot select external callers (as version-1 `secrets` rules);
- Agent-local layers reject caller selectors on either kind (`AgentRulePolicy`).

A version-1 `deny` or `ask` rule whose tool selector names a builtin explicitly (a name, list, `equals` or `oneOf`) whose every declared branch is Self loads with a [load warning](./ctl-command-registry.md#d-ctl-command-registry) per rule and name (`ToolAuthorizationPolicy.SelfScopedNames`): before phase 3 such a rule decided the call, now it has no effect on that builtin, and the warning is the installation owner's only signal. Allow rules and partly Self capabilities (`run_script`, `start_toolscript_run`, `artifact`) don't warn. The rule still loads and keeps deciding everything else it matches.

The policy version stays 1 and Agent-local layers stay JSON arrays. `ToolAuthorizationPolicy.HasOperationRules` (any rule with `op`, disabled ones included) selects the evaluator.

## Evaluation

A layer without operation rules is decided by the version-1 evaluator exactly as before. A layer with one is decided by `OperationEvaluation.Evaluate`:

1. **Self.** `AssessToolAsync` does not evaluate a call whose branch is Self (`OperationPlan.SelfReason`): every layer returns allow, and the assessment carries `Self`. The global policy is still loaded and `EffectiveLayers` still reads the creator chain and every layer, so an unavailable policy, an invalid chain or an unreadable layer rejects it. Operations a host call states (a model request) are never Self.
2. **Ordinary domain.** The request's operations come from the assessment (`SessionManager.AuthorizationOperations`, derived once when some layer has operation rules) or, for inbound and visibility requests, from the request itself. Each operation is decided by the first enabled rule that is a version-1 rule without `secrets` matching the whole call (`ToolAuthorizationEvaluation.MatchesCall`), or an operation rule whose `op`, caller and resource selectors match the operation (`OperationRules.Match`). With no match, the layer's default applies (`defaultAction` for the global policy, deny for external principals; an Agent-local layer passes).
3. **Secret domain** (internal principals). Each name is decided by the first enabled rule that is a version-1 `secrets` rule whose whole-set predicate matches the original complete set (`MatchesSecrets`), or an operation rule naming `secret.use` whose `secret` selector covers the name. Otherwise an owned name is allowed, and an unowned one takes the unrestricted master exec fallback: the first version-1 rule without `args` or `path` matching exec on master, or the first `env.exec` operation rule with no `with` and no resource other than a `node` covering master; else the default.
4. **Layer effect.** The strictest over operations and names. The decision keeps `Operations` (per operation: effect, rule, `Unresolved`, later matching rules as `Unreached`), `SecretNames`, `Call`, `Secrets` and `Asking` (every asking rule once, a rule-less entry for an asking default), from which approval options are combined as before.

### Unresolved operations

Derivation keeps what it cannot establish instead of dropping it: a template whose condition or per-item facts are unknown yields its op with every resource null, and a call without a declared branch (or whose arguments fail normalization) yields one underivable stand-in. Facts operation rules read beyond the request (`AuthorizationOperation`): the resolved target and parent Sessions, Agent creator ancestry, Task owner and creator, and secret ownership, from catalog and store lookups only. In a layer with operation rules, an operation rule whose tested resource or attribute is unknown decides deny, and an operation with an unknown resource never reaches the default; a version-1 rule matching the whole call still decides it. The denial is `ToolAuthorizationUnresolvedException` (`tool_authorization_unresolved`), raised by the gate before dispatch; activity records count it as denied. Version-1-only layers never reject for unresolved facts: they keep their version-1 semantics, consistent with version 1 staying (coordinator decision, 2026-11-16). Inbound requests have no Session target fact; the adapter passes canonical Session IDs, which `target-session` then uses.

**Fact sources and handler defaults.** Every value expression of a declaration has a source (`OperationPlan.FactSource`, in `OperationPlan.Facts.cs`), and a test fails for one without. A value a handler resolves when an argument is omitted, or derives from other state, comes from one function that the handler and the plan both call; a declaration expression never reimplements it. `SessionCreationDefaults` owns the creation values: a child's Agent (the caller's unless named), the Node a creation passes (explicit, else a same-Agent parent's current Node) and the Node a new Session lands on (that, else the Agent's effective default, else master), `create_agent`'s source Session (the caller unless named) and its Agent (an existing Session's, else the Agent its ID names), the Agent whose memory a creation copies, an Agent's main Session ID, `move_session`'s target Agent and the creation runtime. `ApprovedNodeRegistry.ApprovalId` assigns a pairing approval's Node ID (`PreviewApprovalId` gives the plan the ID approval would assign now), and `AgentCatalog.MemoryCopyRoot` is the canonical memory directory a copy reads or writes. `MemoryTools.TargetAgent` selects the Agent whose memory a memory tool reads or writes (`agentName`, else the caller's) for the handler and for the path facts of `MemoryTools.AuthorizationFacts`. A name the handler normalizes comes from the handler's own function, so padding or an alias can't change what an operation names: `McpClient.ConfiguredServerName`, `SecretStore.ArgumentName`, `ChannelRegistry.FileDeliveryTarget`, `Skills.RequestedAgent`, `AgentCatalog.InheritName` (blank means none), `SessionCreationDefaults.ExplicitNode` (trimmed as execution reads a Session's Node), `SessionManager.TimerOwner` and `TimerArguments.Optional`. Where the handler resolves a Session reference (a parent, a deleted or moved Session), it uses the canonical ID that its authorization target names. A name the handler uses verbatim stays verbatim in the plan, and the handler rejects a padded form (Agent names including the memory tools' `agentName`, Session references outside target resolution, `mcp_notifications` servers, `node_create_auth_token.parentNode`, channel instances). Boolean argument defaults stay in the declaration (`default-true:createMainSession`, `arg?:fork??false`, list scopes `current-session` for Tasks and `current-agent` for Sessions, `all` for inbound lists) and the differential test below checks their omitted forms. A Session the call creates is a prospective `targetSession` carrying its Agent, its ID when the handler fixes it (an Agent's main Session, a named missing source) and whether it is the caller's child (for `create_session`, whether `parentSessionId` resolves to the caller); operations on an Agent the same call creates (`agent.create`) are on a creator descendant. An exec without cwd uses the Session working directory on master, and `.` on other Nodes and for inbound callers, where no path selector matches. Only an absence that is itself the handler's meaning stays absent (`parentSessionId`, `ownerSessionId`); a required argument that is missing is unresolved. Capabilities without a registered Session-target resolver take `targetSession` from `sessionId`, or the caller where the handler defaults to it (`CallerDefaultTargets`); version-1 target resolution is unchanged. Enforcement, explain and staging share one context (`SessionManager.OperationContext`: catalog lookups, Agent default Nodes, the pairing registry, the Node forest for `node_remove` members, the working directory), and a test checks that it supplies every member a declaration needs. `node status` views the caller's current Node (`status-node`): the calling Session's, or an inbound connection's selected Node.

**Channel targets.** A `channel.send` resource is the instance and the conversation its transport delivers to (`ChannelRegistry.CanonicalTarget` through `RegisteredChannel.Conversation`, built on the function the transport's delivery uses). Telegram names the chat ID it sends to (the leading integer: `123 `, `0123`, `+123` and `123x` are `123`). QQ Bot names `kind:id` with the ID trimmed. WeWork over the WebSocket names the conversation itself; over the webhook it names a `wok`/`wrk` chat itself and every other conversation `/default-webhook`, the configured default webhook destination (WeWork user and chat IDs never contain `/`). Other transports (Matrix, Weixin, WebUI, MCP replies) deliver to the ID verbatim. The resource is unresolved, never raw, when it can't be known before delivery: a malformed target, an unregistered instance, a conversation the transport rejects, a WeWork ID with surrounding whitespace (the server's reading is unknown), `/default-webhook` over the WebSocket, and webhook text to a non-chat conversation while streaming is enabled, which joins that conversation's stream if one is open (a file never does). Transports accept every earlier spelling.

**Differential conformance.** `OperationEffectConformance` (test project) runs representative real calls of capabilities with side effects, including omitted-argument forms, derives each call's operations under a policy with an inert operation rule, observes what the handler did from persisted state (Session rows with Agent, the Node the Session executes on, runtime and parent; moves through the kept alias; Agents, creators and Agent metadata, where an inheritance the call sets is a view of the inherited Agent that a declared `agent.view` must name; Task owners; approved Nodes; stored secrets; MCP server configuration; changed and deleted files by canonical path, written on master) and fails on:
- an effect the plan doesn't declare, a declared resource that differs from the observed value, or a declared effect that didn't happen;
- a file written outside every declared write leg on the Node it was written on, or a declared write destination left unwritten (unless the case marks it possibly empty);
- a copy whose tree write has no paired tree read, a copied file whose bytes don't come from the declared source as listed before the call, or a source file that didn't reach the destination;
- a non-canonical declared path, and a descendant or child fact that doesn't hold afterwards;
- a channel delivery, as the transport's test double received it, that differs from the declared `channel.send` target.

A case may name a resource as deferred (a timer Session's Node, decided when it fires). Operations a separate probe authorizes come from the case's own arguments, never from state the call writes. Each case also runs once per identifier argument with that argument padded with whitespace; the handler must reject the variant without effect or perform it as the variant's own plan states. Self-tests (`ToolAuthorizationEffectsTests.DifferentialSelfTests.cs`) inject known plan mistakes into real calls and require each to be reported. A padded variant whose assessment the handler's own resolution refuses (a non-canonical Agent name in a memory fact) counts as a rejection: the call must fail without effect (`OperationEffectConformance.Run`). Cases: `ToolAuthorizationEffectsTests.Differential.cs` (Agent, Session and memory capabilities including the memory tools' `agentName`, Agent metadata, Session aliases, copies, timers), `NodeAuthorizationTreeTests.Differential.cs` (pairing, removal), `AgentRulesTreeTests.Differential.cs` (secrets, MCP configuration), `ChannelConversationTests` (each transport double, both send tools, variant and padded spellings); a new capability adds a case there, a new kind of effect extends `Take` and `Diff`.

**Copy legs.** A copy is a read of its source plus a write of its target (D-auth-operation-copy-legs). Every capability whose handler copies content declares both legs as tree templates under the same condition (`OperationTemplate.Tree`): `copy_between_nodes`, `create_agent` `inheritMemory` and `move_session` `createAgent` with `createAgentInheritMemory`. Copy legs are canonical physical paths, resolved like ordinary reads and writes (`AgentCatalog.MemoryCopyRoot`, the declared paths of `copy_between_nodes`), so a symlinked memory root is its target. A tree path is the directory with everything in it: a path selector holds only when it holds for the whole tree, and when only part of the tree is inside a selector's root, a restrictive rule (deny or ask) still applies and a grant does not. A deny on one file inside the copied memory therefore denies the copy, and a grant for part of it doesn't cover it. A declaration audit test fails for a tree leg without its pair and for a listed copy capability without legs. Other content moves are internal state under `session.manage` (identity moves of Session storage) or deliveries with their own target operation (`send_file`, `artifact`).

### Prospective Sessions

`targetSession` of a Session the call creates is a prospective marker. An `id` selector covers every ID it could receive for a deny or ask and none for an allow; `self` never matches; `sameAgent` matches when its target Agent is the caller's; `relation: child` matches only a child the call creates. The timer creation-target probe evaluates `session.create(kind: timer)` with the target Agent known and Node, parent, placement and runtime unknown; an operation rule that reaches an unknown is conditional, as version-1 rules are there.

## Model requests

`request_model_without_context` resolves its catalog key (the named model, else the Session's selection when cataloged, else the default; an unknown name is authorized under that name, then fails) and is gated at the host call (`AuthorizeModelRequestAsync`) as the invocation that runs the slice (`TurnToolInvocation.Resolved`, the call the dispatch gate authorized), with the stated operation `model.request(model)`. The gate has its own approval scope with the slice as primary, keeps the run's deadline and wait accounting, and is never covered by an outer approval, except as the [ask-once decision](./tool-operation-authorization.md#d-auth-operation-script-ask-once) requires: when every asking rule is a version-1 rule, an approval of the slice's invocation (its fingerprint with the operations its dispatch gate derived: none without operation rules or for an inline script, its file read with them), or of an earlier model request of the slice, answers the ask. An operation `ask` on `model.request` asks for each request. Any deny always applies. The fingerprint binds the stated operation. Its obligation is `model-request` (retained, the same capability) in the [catalog](./tool-operation-catalog.md).

## Visibility

`ToolAuthorizationEvaluation.Visible` keeps its version-1 walk for layers without operation rules. For a layer with them, `OperationEvaluation.Visible` enumerates the declaration's branches (`OperationPlan.BranchOperations`; only the known action selects them) and shows the capability when some branch has every unconditional operation possible; a Self branch is always possible, so `ToolVisible` lists any capability that can take one when the caller's layers are valid. Version-1 rules are walked with the raw arguments the caller states; operation rules see the operation's known resources, and an unknown one leaves the rule conditional. A resource or attribute derived from an argument the caller does not state (`OperationPlan.ValueArgs`, `ConditionArgs`, `ItemArgs`) is unknown, never its default: `with.placement` without a known `node`, an MCP tool name under server discovery (the server still decides). A property test constrains each argument-derived attribute of every declaration in turn and requires the capability to stay visible. Each layer is projected separately (`ToolVisibilityContext.Policies.All`), so two layers may each admit a different branch and the capability is listed although no branch passes both. This is the contract (coordinator decision, 2026-11-16): visibility is conservative and never hides a callable command; enforcement stays at dispatch.

- **Commands.** `ctl` help passes a command's fixed arguments as known raw facts (`fixedArgs`), so a command is listed only when its capability might be allowed with them. This is the help fix and applies to version-1 policies too. Help or a parse error for a command hidden this way reports it as not available to the caller rather than unknown ([ctl errors](./ctl-command-registry.md#errors-for-guessed-forms)). Native declarations and `tool search` pass none.
- **Request-prefix stability.** In declarations, a builtin capability's `node` resources are always unknown, so a Node-scoped operation rule never hides a builtin and default declarations do not depend on the current Node, Node inventory or placement. Only a Node tool listed for an explicit Node knows its Node.
- **Probe sets.** Session, Agent and Node lists keep their tool-based probes; under operation rules those probes are decided through their operations.

## Script results

A completed script's result `parts` may carry `inlineDataRef` image references, which the outer image pipeline promotes to the next model request. `MainToolScript.AdmitResultImages` admits a reference only when its blob is referenced in the calling Session's history (`SessionManager.HistoryReferencesImage`, live context and archive) or was an image result of a nested call or model request in this run (`producedImages` on the run record, persisted across checkpoints); otherwise the run fails with an error before anything reads the blob. The admitted blob IDs are stored with the result (`resultImages`, always present on a run completed with admission, possibly empty), and projection promotes only those. Compatibility (read-old/write-new): a completed record without the field finished before admission existed, under the policy of its time, and its projection keeps promoting every reference part, so persisted Sessions project as before. Every run started with admission records `producedImages` from its start, so a checkpoint without it began before admission: it records no provenance and completes without admission (no `resultImages`), keeping the old promotion for the result it eventually produces. An image result is what the host externalized from a nested tool response (`inlineData`, `inlineDataItems`, `imageParts`) or an image part of a model answer, never reference-shaped data anywhere else in a result, and it counts only from a capability whose image results are its own (`MainToolScript.ProducesImages`): any authorized capability that is not self-exempt, a nested script or run projection (`run_script`, `start_toolscript_run`, `continue_script`, `get_toolscript_run`, whose returned images passed this same admission), and `image_crop` (a new image cropped from the caller's own history). A self call echoing a reference as data, by `call_tool`, `ctl` or a background run, proves nothing produced it. Inline bytes a script returns (`inlineData`, `inlineDataItems`) are its own data. Text, artifacts and files reach other Sessions or the user only through gated tools (`artifact`, `send_file`, `send_to_session`).

## Reader marker

`AgentCatalog.RequiredReaderLevel` is 2 when any Agent row's stored `rules` contain an operation rule, and `ReaderVersion` is 2. Every catalog index write raises `installation.json` `minimumReaderVersion` first (`EnsureReaderVersion` in `AtomicIndexWrite`), which covers `set_agent_rules`, `create_agent` with initial rules and the administrator routes. A failed marker write prevents the metadata write; a later metadata failure leaves the higher marker. Older readers reject `op`: the phase-2 C# global YAML reader with `Unknown or oversized policy mapping.`, its Agent-local reader with `Unsupported policy field.`, and the retained TypeScript reader with `unsupported field: op`, including on disabled rules.

## Generated layers

Generated layers keep generator 2 and their version-1 rules. Adding an operation rule changes the stored digest, so the layer counts as edited. `IsolationMigrationRules.EndsInDeny` never accepts an operation rule as the terminal deny, so an op rule appended after it leaves the layer without one and the existing safeguard fails it closed.
