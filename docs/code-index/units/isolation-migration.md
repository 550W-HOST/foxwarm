# Unit: Legacy isolation migration

Files: `dotnet/Foxwarm/Tools/Authorization/IsolationMigrationRules.cs`, `dotnet/Foxwarm/Sessions/SessionManager.IsolationMigration.cs`, `dotnet/Foxwarm/Sessions/AgentCatalog.Migration.cs`

R1 of the [user-decided removal of legacy Agent isolation](../modules/tools-and-permissions.md#d-tools-legacy-isolation-deprecation): generic replacements and an explicit per-Agent migration, while legacy isolation stays enforced. The generated layer is an ordinary [Agent-local layer](./tool-authorization.md#agent-local-authorization-layers).

## Contract

`IsolationMigrationRules.Generate` is the Main-owned generator: it reads the Agent's authoritative isolation metadata (bound Node or master-only, exact `toolRules`) and emits one local layer, in order: translated exact denies; structural denies (Agent/Session management, `view_session`, master `exec`, `node` select/create/ensure/destroy); the baseline (all Node tools on the bound Node; master `read`/`write`/`edit` within `${agent.dir}`; memory tools within `${agent.memoryDir}`; pairwise copies between master and the bound Node with master legs in `${agent.dir}`; bound-Node file delivery to the current Session; send to self, parent or child; same-Agent archives and exact recall; current-Session vector recall; own skills; default-self `session` status; own-Session timers with new Sessions only in the same Agent; ToolScript, wait, ask and other local tools); translated exact allows; and a final selector-free deny. Exact allows the baseline already covers, structural identities, `send_to_channel`, master `exec` and Node tools off the bound Node are reported, not emitted; master delivery builtins are emitted only for an exact allow and stay path- and self-limited; Main path builtins keep `${agent.dir}` containment. Rule IDs are `isolation-<purpose>[-n]`. Each plan carries notes (`translated`, `covered`, `dropped`, `narrowed`, `widened`) and blockers: more than 256 rules, or an isolated `main` in the retained shared-workspace layout, whose nested-Agent exclusion a local layer cannot express.

Generated rules use the local grammar only: no caller selectors, so the layer also applies to creator descendants of the Agent, which the inventory lists. Status of the current Session uses the `session` target resolver family described in [tool authorization](./tool-authorization.md#legacy-isolation-migration).

`SessionManager.IsolationMigrationInventory` is read-only and never hydrates Sessions: per isolated or migrated Agent it reports the legacy state, local rule count, `createdBy`, creator descendants, inheritors, Sessions whose catalog Node differs from the bound Node, stored timers of its Sessions, global rule IDs naming it in `agent` selectors, the candidate layer with its digest and notes, the `defaultNode` conflict and blockers; it also lists channel guest configurations and the installation reader levels. `ApplyIsolationMigrationAsync` is explicit and per Agent. One catalog write installs the layer, sets `inheritable: false`, sets `defaultNode` to the bound Node when unset (a different existing value is kept and reported), and records `legacyIsolation` (`node`, `migratedAt`, `generator`, `rulesDigest`). It refuses an already migrated Agent, existing local rules, existing inheritors and any blocker. Legacy `isolated`, `isolatedNode` and `toolRules` stay unchanged as the downgrade fence, so legacy checks keep applying in addition to the layer. Afterwards, each Session of a bound Agent without a stored `currentNode` records the bound Node (where it already ran through the binding fallback); Sessions placed elsewhere and per-Session failures are reported. Automatic migration is not enabled in R1.

## Installation reader level

`state/installation.json` may carry `minimumReaderVersion`. `AgentCatalog` refuses to load when that value exceeds its `ReaderVersion` (currently 1: local rule layers, creator metadata, `inheritable` and `legacyIsolation` markers are enforced). Before writing metadata that contains any of these, a catalog write raises the marker to its own level; it never lowers it. Binaries older than the marker ignore it, so it protects only later downgrades; Agents relying solely on local rules are not downgrade-supported. Startup does not write the marker.

## Tests

`ToolAuthorizationEffectsTests.IsolationMigration.cs` covers generator ordering and per-rule reports, authorization parity of a legacy isolated Agent with its migrated (dual) and layer-only forms, handler-local limits expressed as policy, MCP server prefiltering, inventory/apply and its refusal to repeat, `inheritable`, and the reader marker.
