## Purpose and governing contract

One administrator-selected third-party account authorizes the named server for this instance. Caller permissions and trusted Session-specific MCP contexts remain in their original owners. The canonical decision and Source contract are [outbound instance OAuth](#d-mcp-outbound-instance-oauth). This unit does not implement inbound authorization, notifications or restricted identities.

The pinned official Core SDK 2.2.0 exposes OAuth only through per-transport `HttpClientTransportOptions.OAuth`; its reusable discovery, exchange and refresh helpers are internal/private. That provider can start interactive consent and replay insufficient-scope responses, and its refresh lock belongs to a transport. The .NET service therefore implements the required standard OAuth requests through an injected `HttpClient` handler. The SDK continues to own MCP serialization, initialization, transport selection, request dispatch and remote Session termination. There is no reflection or replacement protocol implementation.

## Stable symbols and callers

- `McpOAuthService.PublicUrl` and `ClientMetadata` derive fixed callback/CIMD addresses from the startup app `url`, preserving its deployment prefix. Missing URL is harmless to normal hosting; OAuth reports an actionable error. Neither request Host nor the ordinary HTTP address fallback creates OAuth authority.
- `BeginAsync`, `DiscoverAsync` and `RegisterAsync` probe authentication without invoking MCP, validate canonical resource/issuer/S256, prefer pre-registration or retained registration, then choose advertised HTTPS CIMD or DCR. A new consent preparation merges registration/discovery into the current live grant, never an earlier token snapshot.
- `FinishAsync` binds the in-memory state, verifier, issuer, captured configuration and generation; it consumes the flow before exchanging the code. Pending flows expire after ten minutes, are bounded to 32, and do not survive restart.
- `Status`, `Disconnect` and `ConfigurationChanged` own safe account status and explicit authority removal. Disconnect retains registration, not tokens; config or new-account changes advance the generation and fence only the affected named server's bindings.
- `ResourceClient`, `AccessAsync`, `RefreshAsync` and `RenewAsync` provide one grant-aware HTTP adapter per caller transport and instance-level same-generation single-flight renewal. Stop cancels the caller's waiter, not another caller's shared refresh. All renewals, including superseded ones, remain in shutdown drain tracking.
- `GuardAsync`, `Remember`, `Credentials` and `ContainsCredential` protect ordinary discovery/results/errors using current dynamic credentials and credentials actually selected during the operation, including intermediate rotations. Shared SDK initialization has its own guard, independent of the initiating waiter's cancellation, and produces a safe error before publication to its shared completion task. Each guard becomes inactive and clears on completion; it is not a global token history. Binary image/audio data is not censored.
- `McpOAuthHttp.Endpoint`, `PinnedClientAsync`, `RequestAsync` and `ProbeAsync` separate AS requests from resource credentials, vet and pin DNS, reject redirects and unrelated private addresses, and bound discovery/token responses to 1 MiB and 15 seconds. Configured same-origin private resources and narrow loopback development peers remain supported.
- `McpOAuthRoutes.Register`, `IsPublic`, `RequireJson` and `CallbackDocument` retain the administrator OAuth service and normal token/cookie authentication. Setup does not mount the Authorizations panel; [2026-11-27] its MCP tab uses only `POST …/{server}/authorize` as the **Sign in** entry for an OAuth server ([D-mcp-setup-editing](./mcp.md#d-mcp-setup-editing)). Only the exact GET callback/client documents are public; management/completion remain authenticated JSON routes with local Origin/cross-site checks, not a restored host-wide Origin gate.

The public callback GET ignores the administrator cookie even when Lax permits it on a cross-site top-level navigation. It returns a fixed document without reading callback parameters, consuming a pending flow, exchanging a code or publishing a grant. The document removes query parameters from history and sends a first-party JSON completion POST; that POST requires administrator authentication and request-origin checks, then validates live state, issuer, configuration/generation and PKCE before publishing authorization. Forged or foreign states fail before any AS token request. This bridge also supports legacy Strict-cookie clients whose initial callback GET omits the cookie.

Authorization initiation is an administrator-only JSON POST, never a GET. Consent is shown by the external authorization server. Foxwarm does not expose inbound OAuth authorize/consent endpoints: [inbound MCP](./dotnet-inbound-mcp.md) accepts a configured MCP-surface Bearer identity and never derives an external principal from a browser cookie.

## Persistence and runtime behavior

`state/mcp-oauth.json` is a Source-compatible version-1 named-server registration/grant store, separate from ephemeral SDK transports. It uses the existing synced atomic replacement primitive with owner-only creation permissions and publishes committed authority even when a post-rename durability step fails. Token scope is reported only when supplied by the AS; same-grant renewal preserves an omitted refresh token and previously reported scope.

Ordinary calls never initiate consent or registration. A standard Bearer HTTP 401 permits one refresh/resend of the same request bytes before dispatch. Network failures, 404 and unknown-effect tool failures are not replayed. A scope 403 records a reviewable scope request without replay or loss of the still-valid remote context. Authorization failures throw before the SDK's auto fallback can mask them. Renewal retains caller contexts; a new browser grant, disconnect, invalid grant or changed configuration fences stale publication and affected bindings.

## Design decisions

### D-mcp-outbound-instance-oauth

**Selected credential-ownership design with external OAuth protocol constraints.** Outbound connection credentials belong to the configured instance/server connection, not each Session that uses [authorized MCP capabilities](../threads/tool-dispatch-mcp.md#d-dispatch-mcp-live-configuration). Callback/storage mechanics implement that ownership; they do not create an inbound identity or broaden tool grants.

[2026-10-14, initial implementation; Setup entry later withdrawn as noted above] Administrators originally configured OAuth through Setup Authorizations and explicitly share the selected named server's third-party account with the instance. Existing callers use it only through their original tool permissions; they keep independent remote MCP contexts. Use startup `config.url` for public callback and client metadata URLs. Provide outbound OAuth before any inbound consent/scopes service, keep current 2025 MCP transports, and do not add generic users, roles or a credential-vault interface.

## Tests

The owned loopback AS/official SDK fixture (`mcp-oauth-fixture.mjs`, shared with the browser scenario) qualifies pre-registration, CIMD and DCR, state/issuer/config/S256/resource rejection, private version-1 persistence and fresh-client use, distinct trusted Session contexts, native Monty/search/call consumers, rotation and stale refresh fences, consent/renewal merging, nonrotating refresh tokens, caller Stop, post-rename publication, scope status, no ambiguous replay, credential-bearing results/errors across intermediate rotations (including shared initialization after its first waiter's cancellation), bounded guard cleanup, expiry, and static/SSE/auto regressions. Existing outbound lifecycle/result tests remain applicable.

`mainHostMcpOAuth.e2e.mjs` uses the built original App and the original .NET host, with owned TLS prefix proxy and certificate request configuration, real file-token login with Lax cookies, retained legacy Strict-cookie coverage and cross-site consent documents in Chromium and Firefox. It qualifies all three registration paths, real public CIMD fetch, callback without an opener, parameter stripping, narrow auth exemptions, JSON/Origin boundaries, safe administrator status, trusted Session search/call/native consumers, rotating credentials and fresh-process saved-grant use. Management calls are authenticated same-origin browser fetches against retained real routes; actual external consent and callback documents remain browser-driven. The original App is checked for the absent Setup entry, not replaced with the separately retained component harness.

The browser security cases navigate from the real cross-site AS with forged code/state and an AS-issued code for a foreign state, verify no AS request or grant change, and then complete the original pending flow. Holding its completion POST proves that even a valid cookie-bearing callback GET has no authorization effect. Cross-site cookie-bearing inbound `/mcp` and outbound initiation GET controls remain rejected.

## Open Questions

- **Desktop authorization.** [2026-11-14] Recorded, not implemented. The Authorizations panel is not mounted, but [2026-11-27] Setup's MCP tab can start consent through **Sign in**, so a Desktop user can now reach this path. If it is mounted again, the Desktop hosts' [app-window policy](./desktop-windows.md#d-desktop-app-windows) sends the consent page to the default browser: the panel's blank popup is handed to the browser and closed when it navigates to the authorization server. The browser has no administrator cookie and no opener, so the callback document's completion POST would fail. Desktop then needs completion authenticated by the single-use pending state issued to an authenticated administrator, the panel refreshing its status when it regains focus, and `url` set to the Desktop's loopback origin, from which the callback and client metadata derive.
