# Unit: Vector owner placement and Main integration

Files: `dotnet/Foxwarm/Vector/VectorService.cs`, `dotnet/Foxwarm/Vector/VectorWire.cs`, `dotnet/Foxwarm/Vector/VectorChild.cs`, `dotnet/Foxwarm/Sessions/SessionManager.Vector.cs`

Secondary files: `dotnet/Foxwarm.Tests/Vector/VectorStartupTests.cs`, `dotnet/Foxwarm.Tests/scripts/qualify-vector-startup.mjs`

## Purpose

Provides the single enabled Vector owner and the small Main-facing facade used by committed Archive hooks, recall, history search and lifecycle. It is not Session Worker placement, a generic RPC registry, a Node provider or a second Main server.

## Placement and lifecycle

`VectorService` captures normalized configuration. Disabled operations stay lazy and create no vector/native/lexical owner. With `dbWorkers:false`, one local `VectorRuntime` owns native state. With the default `dbWorkers:true`, one supervised child owns that same runtime and communicates over a private current-user named pipe. Its opaque UUID name has no descriptive prefix: .NET adds its own prefix below the temporary directory, and the complete Unix socket path must fit the platform limit. The launcher forwards that name unchanged to the child; neither side relies on a naming prefix. Request capacity is 256 in either mode. Local operation failures pass through the same typed `VECTOR_OPERATION_FAILED` boundary as child replies, so an embedding outage remains a paired tool result and the model can continue. Existing typed disabled/unavailable codes pass through unchanged; local cancellation still propagates to the caller cancellation boundary. This adaptation surrounds only Vector operation dispatch, not foreground model requests or authoritative Session writes. Owner unavailability reports `VECTOR_UNAVAILABLE` without creating a second in-process native owner or falling back to another placement.

Main completes authoritative identity/migration work before starting the owner. `SessionManager.LoadOwnersAsync` launches the selected Vector start without awaiting its completion. `StartCoreAsync` yields before native initialization in both placements, while the service retains the initialization task for readiness and lifetime cancellation. The observing `StartVectorAsync` logs success or initialization failure; authoritative loading stays outside its catch. HTTP and Sessions can become available while the owner remains unready. The [optional startup contract](../threads/process-topology-and-rpc.md#vector-placement) retains placement/configuration, distinguishes retryable unavailability from explicit disabled mode and adds no local retry scheduler.

Required native open, source-time metadata repair and optional lexical open/recovery remain on the Vector initialization path, not the Main readiness path. Initial dense/lexical Archive-maxima enumeration, including shadow catchup, yields out of that path into retained startup tasks in both placements. Promotion becoming ready does not replace an unfinished shadow task. The child connection/first-frame handshake retains its ten-second limit. Required initialization waits for completion under service-lifetime cancellation, rather than sharing that connection deadline; readiness remains false until it succeeds. Ordinary operation deadlines are unchanged. The child keeps exactly one pipe read pending during initialization to notice parent loss, then carries that read into normal dispatch. Shutdown cancels initialization and settles the exact owned process through existing bounded termination. Native repair observes cancellation between reads/updates, not midway through unsupported native calls. Readiness does not await `WaitForStartupAsync`; both placements retain the same separate startup waits. Startup waits include enumeration/backfill, and disposal settles those tasks before stores close. Readiness does not mean historical completeness or immediate query responsiveness.

Mutating facade calls (`schedule`, `force`, `facts`, `rename`, `fork`, and failed-creation `reset`) await the existing pending initialization task before ordinary dispatch. They do not invoke the pre-placement lexical/checkpoint path while the selected owner is opening its stores. Main identity moves also await pending initialization before moving authoritative paths or Archive sources, so the repair reads stable locators. These waits use Main's admission-stop cancellation token: shutdown can settle pending publication hooks before the existing Vector disposal cancels and joins initialization. Ready-owner dispatch, completed initialization failures and final owner shutdown keep their existing behavior. Search/status remain unready rather than waiting behind repair.

Post-commit facts remain best-effort publication. If shutdown cancels a pending fact hook, or initialization/owner failure prevents it from reaching Vector, ordinary raw/block startup indexing does not reconstruct that fact. This existing recovery limitation is not changed by source-time repair; the repair remains metadata-only and adds no fact backfill or duplicate publication path.

Exits reject pending requests for that connection generation; stale connection completion cannot fail a replacement's calls. Restart uses 250 ms to 5 s backoff, and no replacement starts before the previous child confirms exit. Shutdown stops restart/admission, drains accepted requests, closes transport, then uses the existing bounded wait/TERM/KILL phases. Unconfirmed exit retains ownership and reports an error. Parent disconnect has bounded child cleanup, not durable cross-Main fencing.

Console and optional Desktop dispatch the private child branch before ordinary Main composition. Desktop dispatch precedes WinForms initialization and its single-instance guard; the same Desktop apphost can own its child without depending on a separately shipped console runtimeconfig. The child starts no HTTP listener, UI, Agent lifecycle or Session owner.

## Main caller map

- `SessionManager.LoadOwnersAsync` starts Vector after committed identity recovery; shutdown settles Session work and accepted indexing hooks before disposing Vector.
- `PersistentSessionAuthorityStore` notifies only after active authority publication, including a post-rename durability error. Precommit Archive staging/compensation does not notify. Notification is best effort and cannot change the commit result. Compaction supplies the Archive writer's owned inserted block values, not borrowed mutable proposal objects.
- `OnArchiveCommitted` computes bounded hints and schedules raw/block work, then indexes committed memory facts asynchronously. It does not replace the save lane, Archive writer, journal or projection owner.
- `ForceVectorIndexAsync` captures current authoritative sequence/block hints, awaits its queued target run (not merely an earlier background run), and only on success commits the legacy index-position compatibility fields through the ordinary save lane.
- Fork seeds progress from captured caps; same-owner identity move/recovery invokes rename, with inverse rename on existing rollback. Newly created uncommitted branches reset derived data before exact branch compensation. Clear/deletion retain committed Archive and its derived sources.
- `ResolveVectorScope` preserves isolated-current-Session and nonisolated-current-Agent model scope without hydrating searched owners. `VectorCanonicalSourceAllowed` rechecks resolved source authority before preview/fallback; [recall](./vector-recall.md) owns that contract.

## Tests and limits

`VectorStorageTests` exercises both actual placements, disabled side effects, worker loss with a held request, pending rejection and replacement. `VectorRecallTurnTests` drives ordinary Session ingress and the owner runner with real Responses HTTP/SSE and embedding HTTP peers: both placements pair a query-embedding 503 error, send it in the second model request and commit the final answer; successful recall has the same continuation and Archive pairing controls. Stop during a dispatched query settles its result without another model request or replay. `VectorMainCallerTests` invokes ordinary Main append, model tool dispatch, same/cross-Agent move, captured fork, administrator HTTP and `/session index`. `VectorCompactionTests` uses the actual Main planner/commit and verifies drained fact publication after restart.

`VectorPendingInitializationTests` gates the real local owner through its existing missing-source diagnostic, after the source lookup has disposed its Archive connections. It verifies retained mutation dispatch and fact/checkpoint results, runs actual Main move/fork before releasing initialization, and proves shutdown cancels pending hook waits before owner disposal. It does not suspend a process inside SQLite shared-memory initialization. Child handshake, repair interruption and disposal remain covered by `VectorInitializationTests`. Clear continues retaining committed sources; reset coverage uses an uncommitted derived lifetime.

`VectorInitializationTests` exercises a real 4,096-block historical child upgrade with 33 native commits (32 batches and one completion marker), post-initialization status/search dispatch, reopen without repeated metadata writes, disposal and parent disconnect during repair, and initialization failure/recovery. Both placements start real Main HTTP and serve health/Session requests while repair is pending, reject direct dense search as unavailable, and resume after interrupted host disposal. `VectorStartupTests` opens a real table, truncates its latest manifest, then checks unavailable direct operations and disposal in both placements. `qualify-vector-startup.mjs` reuses the owned Main process fixture for healthy seed, corrupt local/child startup, disabled controls, semantic API/model-tool failure, canonical message/Archive persistence across restart, admin/signal shutdown and fatal corrupt Catalog/Archive controls. Each exchange requires the marked canonical user input, its later recall response and a still-later final model answer, including after restart; earlier history cannot satisfy it. No fixture repairs the derived manifest.

These fixtures are separate disposable runtimes. They do not establish Windows Desktop runtime qualification, deployment readiness, stronger parent-loss fencing or a Session Worker platform.
