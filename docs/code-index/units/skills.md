# Unit: Skill resolution and runnable skills

Files: `dotnet/Foxwarm/Skills.cs`, `dotnet/Foxwarm/SkillRuns.cs`, `dotnet/Foxwarm/SkillResources.cs`, `dotnet/Foxwarm/Tools/SessionToolExecutor.Skills.cs`, `dotnet/Foxwarm/Sessions/SessionManager.SkillVisibility.cs`, `dotnet/Foxwarm.Tests/Tools/RunnableSkillTests.cs`, `dotnet/Foxwarm.Tests/Tools/SkillAccessTests.cs`

## Purpose

`Skills` enumerates and resolves the configured Agent skills (Agent-local, inherited and global) for the catalog, `skill load` and `skill run`, and validates a skill's optional runnable entry. The catalog text in the memory snapshot is owned by the [Session domain](./session-domain.md); running an entry is a [ToolScript](./toolscript.md#d-toolscript-skill-entry-source) run, and the `skill` commands are in the [ctl command registry](./ctl-command-registry.md).

## Runnable skills

**User decisions (2026-11-23).** A skill may declare one runnable entry, run with `ctl skill run` without loading `SKILL.md`. The entry's source is read through the skill subsystem under the `run_skill` rule, not through `read` on master (Q9), and every entry is one self-contained file (Q10; ToolScript has no local import, [D-toolscript-top-level-source](./toolscript.md#d-toolscript-top-level-source)).

**User decision (2026-11-25).** The catalog shows a runnable skill's args schema, so a model can call it without loading it or running `--help`: a skill with `run.args` gets `<args>` holding the compact JSON Schema right after its `<run>`, and the catalog's sentence says that `<args>` gives the arguments and a skill without it takes none. The compact schema may have at most 1000 characters (`Skills.MaxArgsLength`).

`SKILL.md` frontmatter `run:` holds `entry` (a path relative to the skill directory), `effect` (one line of at most 200 characters, shown in the catalog), optional `mode` (`foreground`, the default, or `background`), optional `timeoutSecs` (a positive number), and optional `args`, a JSON Schema object of at most 1000 characters as compact JSON, limited to `type`, `properties`, `required`, `enum`, `items`, `description` and `additionalProperties`. Without `args` the entry takes no arguments. Frontmatter keeps untagged scalars as strings (`FrontMatterYaml`), so `Skills.ParseRun` converts `additionalProperties` to a boolean and `enum` values to the declared type; a `required` name must be a declared property. `SkillRun.ArgsText` is that normalized schema serialized once with `JsonText.ToJsonText` (compact, declared property order, relaxed escaping, so non-ASCII stays literal); the length limit measures it, and the catalog shows it XML-escaped. It is null without `run.args`. The runner applies no defaults; the script handles absent values.

`Skills.BuildAsync` validates the block for listing and loading alike. An invalid block (unknown field, wrong type, an over-long effect or args schema, an entry that escapes or is missing) leaves the skill listed and loadable, with `SkillInfo.Run` null and `RunError` saying why; `skill run` reports that reason and the catalog omits `<run>` and `<args>`. `Skills.EntryPath` accepts only `/`-separated relative paths without empty, `.` or `..` segments, colons or backslashes, and requires each component below the skill directory to be a real directory or regular file, never a reparse point. Older Foxwarm versions read only `description` and ignore `run`.

`Skills.ReadEntryAsync` resolves the name exactly as `LoadAsync` does (Agent-local, inherited, global; the first valid match wins, so a non-runnable local skill shadows a runnable global one; nested skills are rejected), rechecks the entry path, reads it as strict UTF-8 (a leading BOM is dropped; an empty entry is an error) and returns it with the SHA-256 of its bytes. Every skill root is a Main server directory, so the entry is always read on the Main server, whatever the Session's current Node. `Skills.ValidateArgs` checks run arguments against the schema; errors name the field (`args.question`) and what it expects. The errors of `skill run` are the `skill load` error for an unknown skill, "has no runnable entry; load it with `ctl skill load <name>`", the invalid block's reason, a missing, non-UTF-8 or empty entry, argument errors, and the ordinary failures of the run itself.

## Skill access

**User decisions (2026-11-25).** Whether an Agent may use a skill is decided by the existing rules on the `skill` and `run_skill` builtins, matched by `skillName` and `agentName`; there is no separate skill configuration and no `source` (global, local, inherited) matcher (U7). A local skill that shadows a global one runs with the caller's own authority, so a name grant reaching it gives nothing new.

**Listings.** The catalog ([Session domain](./session-domain.md)) and `skill list` show a skill only when `skill load` of it might be allowed and show its run entry only when `run_skill` of it might be. `SessionManager.SkillAccessFor` probes each skill with the known-argument visibility evaluator: `skill` with `{action: load, skillName}` and `agentName` and `path` known (absent, or the listing's own `agentName`), and `run_skill` with `skillName`, `agentName` and `script` known while `mode`, `timeoutSecs` and `args` stay unknown, so a rule that denies only background runs keeps `<run>`. A conditional allow or an ask lists the skill. Visibility never authorizes: load and run are decided at dispatch, and a rule change reaches a catalog at its next snapshot rebuild (`skill list` sees it at once). `skill` and `run_skill` have no Node facts. `skill list` propagates an unavailable global policy like any call; the catalog's fallback is in the Session domain.

**Resources (user decisions 2026-11-25, U1, U5, U8).** `skill load <name> <path>` reads one resource under the existing `load` action, so every grant meaning "may use this skill" covers its references; a rule withholds them with `path: {exists: true}`. Skill files are disclosed to every Agent allowed to load the skill, so credentials never live in skill directories; an installation checks the skill directories restricted Agents can load before enabling this. Resolution is `LoadAsync`'s (`Skills.ResolveAsync`: Agent-local, inherited, global, first valid match, nested names rejected); the path is then checked inside that one skill, never falling through to a shadowed one. `Skills.ResourcePath` shares `EntryPath`'s containment (`RelativeShape`, `Contained`) and adds that no directory component may be a name the listing skips (`.git`, `build`, `dist`, `memory`, `node_modules`, `__pycache__`), so a `.git/config` remote URL stays out; a trailing `/` names a directory, a directory without listable resources is not a resource, and the listing's 200-file cap does not limit what can be read. Every refusal (missing, escaping, linked, skipped) is "`<path>` is not a resource of skill `<name>`.", so the message does not say which case applied.

`SessionToolExecutor.ReadSkillResourceAsync` reads on the Main server whatever the current Node: a file through `FileToolCore.Read` with the display name `<name>/<path>` after a `FILE: <name>/<path>` line (full content up to 1 MiB, a head-and-tail excerpt with the size above it unless a line range is given, `read`'s footers), a raster image as `read`'s `inlineData` result, and a directory as `DIRECTORY: <name>/<path>/` followed by the listing's relative paths under it and its truncation line. ToolScript callers get `read`'s structured fields with `path` (the resource path) in place of the Main `filePath`; the script data budget is charged as for a Main `read`. The result passes the ordinary output guard, which spools a large result to the current Node when the caller may not read the Main spool. Authorization is unchanged: the `skill` primary `agent.view(skill-agent)`, with no Node `read` sub-request (as for the entry, Q9). `startLine`/`endLine` without a path are refused.

**Copies (user decisions 2026-11-25, U3).** `skill copy <name> <target-path> [--path <path>] [--node <node>] [--overwrite]` (`skill` with `action: copy`) writes skill files to a Node, so a Session can run a skill's Python or shell script there with `exec`; nothing in the copy grants execution. `Skills.CopyPlan` takes the whole skill (`SKILL.md` and every listed resource) into `targetPath` as a directory, a file resource to `targetPath` itself, or a directory resource's files below `targetPath` with their layout; sources are contained as resources are, so links, skipped names and empty directories are never copied. Over 200 files (or a truncated listing) or 64 MiB the call fails before writing anything; both bounds are engineering constants. `SessionToolExecutor.CopySkillAsync` reads each file on the Main server and writes it through `WriteNodeStreamAsync`, the target leg of `copy_between_nodes` (parents created, the Session working directory for relative paths on its current Node). Authorization: the `skill` primary with a `copy` branch (`agent.view(skill-agent)`) and one `node:<node>/write` sub-request per destination file (`target-write`), all checked before the first write; an existing file without `overwrite` fails that file only. The result is `{skill, sourceType, agent, node, targetPath, files: [{path, bytes, sha256 | error}], totalBytes}`; a model sees the first 50 files and `moreFiles`, a script all of them. Copies run in the foreground; there is no background transfer for them.

**Script runs (user decision 2026-11-25, U4).** `skill run <name> --script <path>` (`run_skill` with `script`) runs another ToolScript file of a skill. `Skills.ReadScriptAsync` resolves the skill as load does (no `run` block needed, an invalid one does not matter), contains the path as a resource (a directory is refused) and reads it like the entry. Its `args` are not checked, and `mode` and `timeoutSecs` default to `foreground` and 30, not to the entry's block. The run is the entry's path (`ExecuteToolScriptAsync("run_skill", …)`); provenance `sourceSkill` carries `script` instead of `entry`. A rule allows the entry only with `script: {exists: false}`. Allowing `run_skill` lets the Agent's runs make model requests, assessed as that invocation.

**Load output (approved copy 2026-11-25).** A path-less load names the skill, description and source, then "Paths in this skill are relative to its directory. Read a resource with `ctl skill load <name> <path>`", followed by ", copy files to a Node with `ctl skill copy <name> <target-path> --path <path>`" and " and run a ToolScript file with `ctl skill run <name> --script <path>`" only when visibility (`ToolVisible` with `skillName` and `action` or nothing else known) says the caller might be allowed them, joined as one sentence (each with `--agent-name` when the load named one), then "On master, the skill directory is <path>." only when the Session's current Node is master (U8), the resource list, and `FILE: <name>/SKILL.md` with its content. The user ingress `/skill show` keeps its own output.

## Tests

`RunnableSkillTests` covers valid and invalid `run` blocks, the effect and args length limits, the compact `args` text, entry containment (`..`, absolute, backslash, missing, a linked file or directory, non-UTF-8), the entry hash, local, inherited and global resolution with shadowing and nested-skill rejection, argument validation including values built in code, the catalog's prefix guard and `<run>`/`<args>` elements, and the `skill run` command forms. `SkillAccessTests` covers the catalog and `skill list` filters (see the Session domain for the cases); `SkillAccessTests.Resources.cs` covers resource containment (`..`, `.`, absolute, backslash, colon, empty segments, linked file and directory, `.git/config`, `node_modules`, `build`, a file named as a directory, an empty directory, a nested skill's file, a file beyond the listing cap), `read` parity for line ranges, the 1 MiB excerpt, images and directory listings, shadowing and `agentName`, the shipped `restricted-worker` rules reading a global resource while `read` on master stays denied, a `path` rule withholding resources, the load header on master and elsewhere, and structured fields for scripts. `ProviderFileConsumerTests` spools a large resource read to the current Node when the Main spool is not readable. `SkillAccessTests.Copy.cs` covers whole-skill, file and directory copies with layout, hashes and skipped names, `overwrite`, containment, the bounds failing before any write (and the 50-file model view), the template worker's master write denied before anything is written, the load header clauses per rule set and with `--agent-name`, and `--script` runs (no `run` block, unchecked args, provenance, containment, an entry-only rule). `ProviderFileConsumerTests.SkillCopy.cs` copies to the current provider Node under current-Node rules and refuses master before any Node request.
