## Purpose

Owns deterministic local test discovery, classification, data isolation, process orchestration, and artifacts for the application repository. It keeps deferred or separately owned tests visible without running them in the wrong environment.

## Commands

- `npm run test:inventory` prints every tracked test classification and fails on unclassified eligible files.
- `npm test` / `npm run test:unit` run the managed solution plus maintained Node bootstrap/runtime helpers, shared, CLI Node, sandbox Node (compiled and bundle tests), browser Node, script, skill, VS Code Web, WebUI unit and Python groups.
- `npm run test:managed` restores the complete .NET solution with the caller's toolchain environment, then builds and runs it with `dotnet test --no-restore` inside the isolated test environment and with the explicit built Source oracle root. A failed restore does not start managed tests. The same managed group runs under `test:unit` and `test:local`; this preparation does not depend on a warm package cache or a workflow-only command. Restore has its own 10-minute deadline; the subsequent build and serial managed suite share a 30-minute command deadline, allowing margin beyond a measured complete CI invocation of nearly 20 minutes without changing individual test deadlines. The full suite includes optional HEIC tests requiring their pinned native prerequisite. CI builds that test-only prerequisite in owned runner-temporary storage.
- `npm run test:reference` runs only retired Main backend tests, their nested isolation regressions and the two retired standalone selftests. It uses the same runner, isolation, bounded shards and failure reporting, and requires `build:reference`.
- `npm run test:published` publishes complete managed Main into a fresh owned artifact directory, runs the packaged public Multica bin through an authenticated HTTP/SSE turn, and proves original App/Setup, Node archive/resources, native ToolScript and Main browser/image behavior, normal stop/restart and preserved data. The published fixture uses the supplied `DOTNET_ROOT` or PATH for its managed host/version calls, without changing public apphost runtime discovery.
- `npm run test:webui:e2e` prepares the Debug Main, CLI and DevTools fixture outputs used by retained native fixtures, installs the separately prepared Code workbench below the owned executable resource root, then runs local disposable WebUI browser fixtures with one explicit Chromium configuration. Missing Code assets use the existing `npm run build:code` producer; caller-prepared supported assets are reused without replacement.
- `npm run test:app:e2e` runs the real disposable application with a scripted loopback provider and Chromium.
- `npm run test:local` runs the unit, complete-publish, local-browser, and full-application groups together.

The default `unit` and `all` targets exclude historical-reference execution. Classification follows current consumers: `src/nodes/runSh.test.ts` and `runPs1.test.ts` execute still-shipped templates; the artifact runtime-helper tests exercise the validators/compiler/raster helper used by managed Main. Other Source Node tests target the retired Main owners, including its bootstrap command generator/catalog. The launcher regression may still use that generator as a fixture producer. Source artifact store/routes tests remain historical reference. Managed migration/oracle tests remain in the default managed group; their [compatibility boundary](./dotnet-tests.md#contract-boundary) does not require retired Main takeover of current installation data. Current shared/CLI/browser clients, extensions, scripts and Python tests stay maintained.

GitHub Actions uses those same public commands in separate core/unit-quality, Chromium-fixture, and real-application jobs. A separate Windows job publishes and qualifies the extracted [Desktop ZIP](./core-delivery-cli.md#build-and-resource-boundary) through the maintained Desktop scripts; it is outside the platform-independent local groups. Neither lane introduces a workflow-only test selector.

The Chromium job builds the same pinned optional HEIF prerequisite as Core and exposes its owned library prefix to fixture subprocesses. It also prepares the root-owned mode-0755 SSH privilege-separation directory before the loopback fixture starts its dedicated daemon; it does not start a system SSH service. Interactive Source CLI fixture subprocesses use `CI=false` to receive live Ink frames, including redirected stdout. Native CLI subprocesses retain the caller's CI environment.

## Behavior

- Patch parser/matcher fixtures run in the shared unit group, not as a separate root algorithm selftest.
- Inventory rules also expose managed C# source files and the separate complete-publish proof. They classify tracked Source tests and explicitly identify the full-application harness files as one browser-owned group (`appHarnessE2e`), so every `test/app-e2e/*.e2e.mjs` scenario stays visible without being run standalone by a routine unit group. Generated duplicates, asset-dependent VS Code E2E, website-owned tests, standalone smoke/regression scripts (including the explicitly provisioned [native CLI distro probe](./dotnet-cli-linux-aot.md)), live-hardware smoke drivers, and interactive skill trials are identified the same way.
- The reference runner launches retired backend files in small bounded shards. Backend test files and standalone self-tests import `src/testEnvironment.ts` before application modules; script/skill tests, shared/CLI Node filesystem tests, and browser fixtures that load the backend use the same initializer. The web-search skill test copies its module beneath owned data before importing it, because the module eagerly reads a module-relative `.env`. This owns fresh data and operating-system temporary roots before imports even under `node --test <file>` or `node <file>`, discards inherited application/MCP/model-search path overrides and provider credentials, and keeps Agent paths under owned data. Temporary roots reuse the supplied short temporary parent or a private process-root child; the existing browser keep-system-temp override remains available. Direct-run data and owned temporary roots are removed on process exit, including temporary roots under a separate short parent; runner roots remain as artifacts. The runner preload shares this process-local initialization. Ordinary subprocesses inherit the owned environment without replacing explicit child fixture paths. Backend shards default to the synchronous file logger to avoid an asynchronous transport startup race during short-lived test-process teardown. An explicit `FOXWARM_SYNC_FILE_LOG` value takes precedence; the dedicated async logger fixture clears the setting in its own child to exercise the production-default transport.
- The explicit reference isolation group runs actual retired configuration-writer tests with pre-existing checkout, pointer-selected, and inherited config/models canaries under direct and preloaded entry points, including the exact concurrent WebUI Access/config-hot-apply two-file selection. It asserts unchanged canary bytes and no added installation state such as log files.
- The maintained scripts isolation suite checks direct/preloaded Source helper imports and inherited child roots against the same installation canaries. Its coordinated two-process control imports the real WebUI module, holds a synthetic spool file while the peer imports, and proves that the peer cannot observe it or remove it on exit. Raw runtime-browser entry checks verify that a supplied listener receives no requests. The suite also checks the Source lifecycle fixture's direct race/seed/cold-reopen entries against owned sibling application/MCP overrides, with a real Source config-reader control. The browser-owned `backendIsolation.e2e.mjs` runs the ordered Responses and OAuth browser entries directly under both valid and malformed supplied installation configuration, covering in-process and ordinarily spawned backend imports without the runner preload. The reference and browser canary fixtures explicitly select TAP for child summaries whose pass/fail/skip counts they assert, independent of Node's default reporter. Home-directory exec assertions compare canonical paths so a symlinked development-Node home is supported.
- Real-app browser fixtures wait for the React root to mount and the entry splash to release pointer input before acting after navigation or reload. The shared `waitForWebUiReady` fixture helper waits on those observable states rather than a fixed delay; popup and embedded roots need no splash.
- Groups, historical backend shards, and browser files run in sorted order with bounded concurrency and finite progress/process timeouts. Workbench has a longer finite file budget for its serial full-application mounts, reloads, and navigation coverage; the Chromium job also budgets installation and builds. Output is streamed and saved with inventory, result summaries, screenshots, and disposable data in a fresh child beneath the selected artifact parent.
- Runtime-test provider credentials are cleared and proxy defaults point to closed loopback endpoints. Managed dependency restoration and browser build/resource preparation run first with the caller's standard toolchain/feed/proxy configuration; they do not run application tests or change their isolation. `managed-preparation.test.mjs` covers preparation ordering, isolated no-restore execution, failure fencing and deadline termination with a zero child exit through the real runner entry. Timeouts and interrupts terminate the active process group and produce a failing exit status, including when a child handles termination with exit zero.
- A caller-supplied artifact path is treated as a parent: the runner does not remove or replace it or unrelated prior artifacts.
- VS Code Web generated extension files are restored to their exact pre-test contents after the group, preserving pre-existing local bytes and removing only files created by the test command.
- `test-routing.test.mjs` invokes the real runner and inventory in a small tracked fixture checkout: `unit`/`all` work without retired compiled tests/selftests, reference works without maintained compiled components, and a managed failure remains a default-run failure. It records actual child execution rather than only asserting inventory labels.
- The test workflow installs the .NET 10 SDK through the official SHA-pinned setup action in each job. Its three Ubuntu jobs explicitly build managed delivery and the TS reference (still consumed by managed oracles, browser producers and App seeds); the Windows 2025 Desktop job builds only its delivery graph. Jobs share the exact Node version, read-only repository contents, ref/PR-scoped cancellation and finite job limits. Linux browser jobs use the same pinned Chrome for Testing version. Pull requests and pushes to `testing`/`main` run directly; scheduled and manual registration follows GitHub's default-branch workflow behavior.
- The Core checkout fetches full history for the managed fixtures that execute frozen ancestor source with `git show`. Local reference checkout preparation is documented in `dotnet/Foxwarm.Tests/README.md`; current shared/reference builds and historical Git objects are separate inputs.
- Linux failure/cancellation uploads select only top-level runner inventory, summary, logs and screenshots plus the full-application harness's nested logs/screenshots. Desktop uploads its bounded acceptance summary and, only on success, the distributable ZIP. Disposable process data, persisted Session state, request journals, tokens/models, browser profiles, dependencies and unrelated workspace files are excluded.

## Integration

The runner consumes managed solution tests, complete-publish/browser proof, maintained component tests and optional historical Source tests, source WebUI and browser fixtures, Python tests, standalone self-test executables, and the synthetic full-application harness. Build/install prerequisites remain separate so a single build can feed repeated focused runs. Full-application ownership, including its exact scripted provider expectations, is documented in [full-application E2E](./full-app-e2e.md).

## Full-application qualification

The required full-application Logs scenario remains enabled and exercises the [managed implementation](./dotnet-webui-logs.md) of the retained [WebUI Logs contract](./webui-logs.md). Passing solution/reference/publish or image checks alone is not complete default App/CI qualification.

The shared `mainHostFixture.mjs` starts ordinary managed Main or an explicitly selected retained Source runtime using owned config/models/token files. It observes its normal startup notification on either configured console stream before checking its own health route. Its App opener waits for the authenticated application controls and entry-splash release; a selected Chat is supplied by each scenario rather than assumed by the shared opener. The stderr host regression exercises the real managed entry.

Standalone Main drivers that read `FOXWARM_TEST_MAIN_DLL` allow an explicit built-assembly selection; it is a test-process input, not a Main runtime setting.
