# Unit: Hosted executable Provider tenancy and grants

Files: `dotnet/Foxwarm/Hosted/Providers/ProviderGrants.cs`, `dotnet/Foxwarm/Nodes/TenantProviders.cs`, `dotnet/Foxwarm.Tests/Hosted/ProviderTenancyTests.cs`, `dotnet/Foxwarm.Tests/Hosted/ProviderTenancyTests.Runtime.cs`

The deployment owns executable paths and arguments. The operator can grant a configured Provider by its exact ID; the shared `ProviderGrants.Validate` checks the deployment declaration, the tenant profile and the closed quota object, without starting a process. The operator rechecks the profile inside its grant-write transaction. Changed grants advance the tenant settings revision; ordinary generation retirement closes the previous registry and its service channels.

**Decision (2026-11-28): operator access without a grant.** An operator-profile tenant can use every available deployment Provider, including legacy drivers. An ungranted operator Provider has no grant quotas; an explicit row applies its quotas. A hosted-profile tenant sees only explicitly granted drivers that declare and implement `per-tenant`.

**Transitional single-tenant entry.** Until the forwarding cutover removes this entry, it does not apply grant rows: the hosted profile has no executable Providers and the operator profile retains available deployment Providers without quotas. A startup with any grant rows logs this limitation once. Grant management applies on the multi-tenant entry, which retires the generation when settings change.

Generation construction on the multi-tenant entry reads only that tenant’s grant rows and probes actual descriptions of selected Providers. A failed probe or mismatched declaration omits that Provider without making the tenant unavailable. The replica heartbeat lists `describe-failed`, `tenancy-mismatch` or `parent-not-granted` under that tenant's `providerProblems`, without command lines, arguments or subprocess output. A malformed description, including duplicate fields, disables only its driver. When a configured Provider parent is unavailable, its descendants are omitted before building the Node authorization forest; independent Providers remain usable. `docs/executable-node-provider-protocol.md` specifies identity echoes and driver isolation. Extended envelopes and `connect` require an exact integer `tenantId` echo. This is the immutable `tenants.tenant_id`; a recreated slug gets a new ID and cannot inherit the deleted tenant’s Provider namespace. Slugs are used only for display or logs. A service connection belongs exclusively to the tenant registry that verified its connect response; separate tenant registries never reuse streams, even for identically named Nodes. Driver startup, process and channel stderr use the tenant’s scoped log and secret masker and identify the Provider; file mode retains its original envelopes and diagnostic handling.

Each grant defaults to `nodes: 10`, `execs: 8` and `lifecycleActionsPerHour: 60`. Fields are non-negative integers; zero disables that resource. A create or potentially creating ensure checks the current tenant-scoped inventory before dispatch, under the existing topology mutation lane. Ensuring a known listed Node does not use another Node. Each admitted lifecycle invocation (including inspect) consumes an entry in the rolling hour before its effect, under the lease, so a move or failed response cannot reset the count. Core's existing running-exec registry counts this Provider's live jobs, including restored jobs, and reserves in-flight starts until tracking takes over. An unknown start receipt or retired Session follows the existing [exec tracking](./tools-local-io.md#provider-exec) contract: Core counts work it is starting or still tracks, while the driver must account for the processes it actually owns. Provider execs use only their grant's quota; the separate [resident Node RPC limit](./hosted-egress-limits.md) does not apply.
