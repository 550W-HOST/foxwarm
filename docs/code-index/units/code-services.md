# Unit: Code workbench and Git/file services

Files: `dotnet/Foxwarm/Code/CodeFileService.cs`, `dotnet/Foxwarm/Code/CodeGitService.cs`, `dotnet/Foxwarm/Code/CodeWorkbench.Routes.cs`, `dotnet/Foxwarm/Code/CodeWorkbench.Install.cs`, `dotnet/Foxwarm/Code/CodeWorkbench.cs`, `dotnet/Foxwarm/Code/workbench.html`, `dotnet/Foxwarm/Code/workbenchFrame.js`
Secondary files: `dotnet/Foxwarm.NodePrimitives/CodeNativePaths.cs`

## Purpose

Serves source files and Git metadata through the Code workbench boundary, including optional VS Code Web capability requests.

## Stable symbols and callers

`CodeWorkbench.Register`, `DownloadAsync`, `PatchWorkbench`, `PatchPre`; `CodeFileService`; `CodeGitService`. Native file/Git mechanisms now live in [shared primitives](./dotnet-node-primitives.md); these wrappers retain Main path/URI adaptation, unavailable-Git presentation and authenticated HTTP ownership.

Callers and adjacent boundaries: HttpServer; WebUI workbench components; TerminalRegistry.

## Local and remote consumers

`CodeWorkbench` keeps the existing deployment-relative workbench, static assets, capability URLs, per-Node persistent multi-root workspaces and browser bridges. Filesystem routes select Master-local `CodeFileService` or the captured Node's advertised `vscode-fs` operations through `NodeProviderRegistry`, whether the Node is a resident Node or an admitted executable Provider (see the [service channel](../threads/tool-dispatch-node-execution.md#d-dispatch-provider-service-channel)). `CodeFileService.Node` accepts one-segment resident IDs and `provider/local` qualified IDs; the Code URI authority carries the whole qualified ID as one escaped component (`node+provider%2Flocal`), so workspace files are named by its escaped form. Write/read retain the inclusive 50 MiB file boundary; oversized requests reject before dispatch. Remote binary content crosses the official base64 service envelope, not an exec command or ordinary model tool.

The read-file HTTP route is registered by the [MCP download boundary](./dotnet-inbound-mcp.md#stateless-remote-file-download), which delegates existing administrator requests to `CodeWorkbench.DownloadAsync`. Its independent external identity checks do not authorize the other Code APIs. `NodeConnectionHub.RequestServiceAsync` (resident only) accepts a final caller assertion at the existing exact-connection send gate; ordinary Code callers keep their current path.

Status/content select local `CodeGitService` or `vscode-git`; commit details require service version 2 and retain immutable commit IDs and bounded content. The HTTP response stamps the requested authenticated Node namespace for Git consumers rather than accepting a peer-supplied identity. SCM remains read-only. Local Main content normalizes the path, checks its workspace child and validates the content ref before side dispatch, including working content. The shared Node service applies the child check only to working reads and ignores their refs, so literal `..`-prefixed base names are service-only. Absolute POSIX paths and `foxwarm://node+<id>/...` preserve the concrete remote namespace; earlier URI readers remain available. Windows Main maps absolute drive paths at the [Code URI boundary](../threads/code-integration.md#d-code-real-path-uri); local filesystem/Git calls receive native paths while remote payloads retain their existing POSIX semantics. `CodeNativePaths.Native`/`Transport` own that mapping, which lives in the shared primitives so the Windows CLI Node uses it too. On Windows `/` is the synthetic drive directory: `Native` returns an internal marker only `CodeFileOperations` stat/list interpret (ready drive roots as `C:`-style directories), every mutation of it fails with ordinary file errors, and `NativeDirectory`, used for Git working directories, rejects it. Terminal creation keeps its existing native `/` handling. POSIX hosts keep `/` as the real root. Windows stat uses native file metadata/link resolution and rename uses MoveFileEx without cross-volume copy or rollback. Typed bootstrap URI components retain escaped path segments for the official URI readers' single decode, including literal percent sequences, drive colons, spaces and Unicode. Git remains an optional external executable and missing Git reports unavailable rather than borrowing a shell implementation.

The fixed workspace-root response remains Master-only and authoritative for app/data/config commands, independent of Session-selected Node/cwd. Normal instance-token authentication remains distinct from capability and exact browser bridge checks; there is no generic Origin URL gate or fabricated model caller. [Code integration](../threads/code-integration.md) owns these shared contracts.

## Installed resources and workspace defaults

Server Code assets are separately installed and survive payload replacement. Both [Desktop packages](./release-packages.md#desktop-producer-and-qualification) include them in the application [HTTP asset pack](./http-assets.md). `CodeAssets` selects payload resources when the payload pack has the workbench or an old payload `vscode-web` directory exists; otherwise it uses the stable application-root Code pack or extracted tree. Selection is checked per request, so preparation while Main runs needs only a reload. Static modules (including Code's runtime `node_modules`), built-in extension manifests/resources, optional YAML and capability webview pre resources all use the same abstraction. First-party extensions remain payload resources versioned with Main. Build tools retain their existing preparation output paths, without runtime asset environment controls.

Direct launches without a folder request open the application root. Current WebUI launches select `state/vscode-web/node-<encoded-node-id>.code-workspace` through `nodeId`, independently of the iframe-only `embedded=true` flag. `MigrateWorkspace` distributes legacy folder descriptors by URI authority and preserves settings before archiving the old file; existing per-Node target files retain their roots. Bootstrap, migration and privacy-default backfill use the existing atomic document writer through `WriteWorkspace`. Generic Code file writes retain ordinary filesystem semantics. Explicit settings and malformed current workspace files retain their existing behavior. Managed webviews retain the same-public-origin process capability. Source retains its automatic hashed localhost origin and same-origin capability fallback elsewhere. No configured-origin, default-folder or workspace-path environment branch participates.

When required workbench assets are missing, authenticated `/vscode-web` returns the original Source-style complete setup page with status 503 and `Cache-Control: no-store`. `UnavailableHtml` includes matching-version prebuilt release commands for Linux/macOS and PowerShell, plus the `npm run build:code` and `npm run download:code` source-checkout choices. `InstallCommand` uses `ProductVersion.Value`, the same release's SHA256SUMS and the selected asset base, with shell/PowerShell quoting before HTML encoding. Verification precedes replacement of `foxwarm.assets` and errors stop installation. The matching release asset is `foxwarm-code-<version>.fwassets`; no runtime extraction is needed. The page retains light/dark responsive styling and reload-only activation. The Code launcher remains available; individual missing static assets remain 404. This preserves the optional-workbench preparation path rather than adding a launch capability gate.

## Asset adaptation and version evidence

The authenticated static route adapts only `out/vs/workbench/workbench.web.main.internal.js` from the selected packed or loose Code resource store. `PatchWorkbench` matches the Source-supported webview-origin hash helper and clipboard-probe bodies, capturing current generated identifiers rather than pinning minifier names. Only the first supported helper/probe is rewritten; changed shapes fail with an explicit unavailable response. The original asset bytes are not modified. Capability bootstrap/CSP rewriting, normal auth and deployment-relative URLs keep their existing owners.

The .NET bootstrap installs `workbenchFrame.js` before Code loads. Only a top-level document with a Desktop frame provider adapts Code's Window Controls Overlay API and title-bar spacer widths to the physical left/right host reservations. The adapter also accepts the first `foxwarm-frame` event for WebView2 opener popups. It sends the existing rectangle-only frame report and active Code theme brightness, with native drag excluded over title controls and floating layers. In WebView2 the open menu’s title-bar grid cell is raised above the editor so the menu paints and receives clicks. Ordinary browsers and embedded Code keep their normal layout; the reference TypeScript route has no Desktop caller and does not install the adapter. See [the app-window decision](./host-runtime.md#d-desktop-app-windows) and [frame protocol](./webui-window-frame.md#d-window-frame).

The source preparation pin is Code-OSS 1.141.0; route-shape tests do not prove a prepared or running asset version. The owned normal-host Workbench fixture has qualified the pinned source-built 1.141.0 payload for filesystem saves, immutable SCM content/diff rendering, local terminal extension effects, embedded iframe reuse and standalone launch. This does not qualify every optional workbench feature. Optional YAML assistance requires its separately prepared vendor payload and its own browser qualification; neither asset preparation nor route registration establishes that behavior.

## Tests

`packages/webui/test/codeWindowFrame.e2e.mjs` exercises the adapter on a controlled DOM and the real workbench served by managed Main, with Windows and macOS inset providers and top-level browser and iframe controls.

`dotnet/Foxwarm.Tests/Channels/CodeRoutesTests.cs` (Windows virtual drive root over HTTP, missing-assets setup page/status/cache contract, real served files/Git, native metadata/link/error/partial-rename behavior, missing Git, renamed asset identifiers, unchanged source bytes and auth); `packages/webui/test/mainHostWorkbenchParity.e2e.mjs` (normal host/original App, optional official Code-OSS FS/SCM/PTY extensions, exact immutable Git content status/body and rendered diff within one 30-second bound rather than treating the mounted editor shell as loaded content); `NodeCodeServicesPathTests.cs` (Windows Node service mapping, virtual root, mutation refusal, mapped Git results and unchanged native/POSIX paths); `NodeServiceTransportTests.cs`; `packages/webui/test/mainHostNodeCode.e2e.mjs` (owned hosts, unchanged official CLI, original WebUI and optional official workbench/browser extensions).

`packages/webui/test/dotnetCliNodeCodeMain.e2e.mjs` exercises the .NET CLI with normal Source/.NET Main, original App and prepared official FS/SCM extensions, without claiming remote PTY support.

The remote-workspace data-folder command in `mainHostNodeCode.e2e.mjs` waits for the master frame’s Explorer root before checking master’s persisted workspace and unchanged remote roots. Keyboard dispatch alone does not settle the command.

`Workspace_migration_and_defaults_publish_complete_replacement_files` holds readers across actual bootstrap requests and checks that old handles retain the prior complete document while reopening the path yields the replacement. The original-App per-Node fixture awaits the originating frame’s request acknowledgement before reading its workspace or starting another launcher interaction; the acknowledgement includes Explorer focus completion.

The original-App Code fixture records bounded palette input, focus and result state only when its requested command-result wait fails. It rethrows the original error and avoids DOM evaluation after a native dialog has been reported, since that dialog can block CDP. This separates command-entry state from later editor-open failures without changing command selection or its timeout.
