## Purpose

A hosted replica has no `master` Node: nothing on the replica's container is an execution environment for tools. This unit owns the capability profile that says which Main-local features a runtime has, and how each feature behaves when it's absent. File mode has every feature and its behavior doesn't change.

The hosted entry and lease are in [hosted runtime](./hosted-runtime.md); the deployment/tenant configuration split, which refuses settings of absent features, is in [hosted configuration](./hosted-config.md#d-hosted-config-split).

## D-capability-profile

**Approved plan, track CP (2026-11-26).**

- **Shape.** `RuntimeCapabilities` is a record fixed when the runtime is built: `MasterNode`, `MainTerminalsAndCode`, `StdioMcp`, `ClaudeRuntime`, `ExecutableProviders`. `File` has all of them; `Hosted` has only executable Providers. Its `Egress` property is the runtime's outbound policy: unguarded for `File`, internal destinations denied for `Hosted`, and the operator profile's policy for `Operator` ([egress guard](./hosted-egress-limits.md#d-egress-policy)). `MainHost.CreateAsync` and `SessionManager` take it as a parameter, and null is `File`.
- **Profiles as data (P2 plan §6.1).** A hosted runtime's set comes from its tenant's stored profile, the operator-owned `tenants.profile` column (`TenantProfile`, plain data outside `Hosted/` so builds without hosted mode compile it): `hosted` is `RuntimeCapabilities.Hosted`, `operator` is `RuntimeCapabilities.Operator`, file mode's features over hosted stores. `HostedEntry.BuildRuntimeAsync` reads the profile (`TenantProfileStore.ReadAsync`) before it builds the runtime and passes `RuntimeCapabilities.For(profile, deployment.Egress)`, which gives each profile its egress policy (`EgressPolicy.Hosted` or `EgressPolicy.Operator`) with the deployment's `egress` rules. The profile is fixed for that runtime: a change takes effect only in the next runtime of the tenant (a move), never live. The operator profile is valid only on a master-host replica; that refusal belongs to acquisition, which reads the same row (`TenantProfileStore.Read`).
- **Refusal texts.** A call that names master, or a Main-local file, fails with `Node is not available: master` (`RuntimeCapabilities.MasterUnavailable`), the same text as for any unknown Node. A call that reaches master only through the Session's current Node, which a hosted Session without a Node still reads as `master`, fails with the coordinator-approved copy of `RuntimeCapabilities.NoCurrentNode`, which names `ctl node select` and `ctl node list`. `ToolRegistry.NamesMaster` tells the two apart: a Node tool names master only as a `call_tool` target, and a builtin is resolved again with another current Node. Both fail at resolution, before authorization effects, approvals or file access; a `skill copy` whose target is the current Node is checked when it runs, with the same choice (`RequireMasterNode(current: true)`). A file-mode Session always has a Node, so file mode never shows the second text.
- **Request-prefix stability.** Default tool declarations (`ModelDefinitions`, the runtime declarations and the registry's) are byte-identical across profiles for the same configuration. Only the Main browser tools differ, and they are never default-injected.

## D-capability-without-master

What each surface does when `MasterNode` is false.

- **Node list and status.** `master` isn't listed as a Node or a Provider. An unset Session's current Node, which file mode reads as `master`, is reported as none (`currentNode: null`, `connected: false`) by `node list`, `node status` and the Session status.
- **Session presentation.** Every Session DTO reports that none as `currentNode: null` (`SessionManager.PresentedNode`): the Session DTO and its state events, the WebUI history snapshot, catalog list and search rows, and inbound MCP's Session list. Resolution keeps reading the unset Node as `master`, so refusals and the effective request selection are unchanged. `/status` shows `current node: none` and no Agent directory, `/sessions` shows `node: none`, and the Sidebar's Node grouping labels the master group `No node`. The WebUI Execution node picker shows `Execution node: none` and lists the Session's Nodes with none selected.
- **Resolution** (`ToolRegistry.ResolveAsync`) refuses every master target: `node:master/*` tools; builtin Node effects naming master (exec, file tools, copies with a master end, file delivery, skill copy); `run_script` with a master script source; `set_config`, `node_bootstrap_info` and `node_create_auth_token` with a `filePath`; `explain_tool_authorization` with a `policyFilePath`. `node select master` and `NodeDefinitions("master")` refuse the same way. The SessionManager master file branches call `RequireMasterNode` as the last guard.
- **Secret moves.** `add_secret` with `fromConfig` is refused: no tool reads the tenant's configuration documents, so nothing could authorize a move. Approval plans have no configuration read checks. The fallback "follows the caller's unrestricted master exec" stays a pure policy computation: a default allow still allows, and a master deny still denies.
- **Session placement** (`SessionManager.StartingNode`). An explicit or inherited Node is kept. The Agent's or installation's default is kept only when it is a Node of the forest or `<provider>/<name>` of a configured Provider; anything else, `master` included, leaves the Session without a Node. File mode keeps today's order ending at `master`. A kept Provider default the Provider doesn't list fails at first use as in file mode. A Session without a Node follows the prompt's instruction: `ctl node list` shows the forest's and Providers' Nodes, `ctl node select` takes a listed one, and a Provider Node not yet listed is first created through the Provider's lifecycle (`node create`/`ensure`).
- **Main-local tools.** The Main browser tools aren't registered; `LocalExecManager` refuses launches without a Node backend; the terminal registry and Code workbench aren't built, so `GET /api/terminals` returns an empty unsupported list and the Code routes don't exist. Code downloads naming master fail as unsupported.
- **Tool output spill.** A large result is shortened in place instead of being spooled to the Agent folder.
- **Memory and skills.** `ctl memory` (read, write, edit, delete, patch, including `--agent`) works on the Agent store without a Node; it never involved one ([consumers](./hosted-agent-store.md#d-agent-store-consumers)). `ctl skill list`, `load`, resources and `run` work; `skill load` shows no master path. `foxwarm-maintenance` is hidden from the catalog, `load` and `run`: its whole content is file-mode operations (P2 hides `asr-service` too).
- **Framework prompt.** The `master-node` condition ([conditional memory](./conditional-memory.md)) selects the hosted copy in `templates/agents/00_SYSTEM.md`; the file-mode render is unchanged. `<memory_file>` blocks carry no `path=`, and the `--- DIRECTORIES ---` / `agent_folder` block is omitted.
- **Received files.** Nothing is written to the Agent folder's `.temp/channel-files`. A received image reaches the model inline only. Any other file is replaced by a text notice naming it, its type and size as not kept, so the loss is visible to the model and through it to the sender. A WebUI upload of a non-image is refused with an error naming the file.
- **MCP.** Stdio servers are refused on update and on load, with a validation error naming the server (`McpConfiguration.StdioAvailable`). HTTP and SSE servers are unchanged.
- **Claude Code runtime.** Creating a Session with it, and an external turn on it, are refused.
- **Vector** is off whenever the Archive isn't the SQLite store; the Activity index already keeps only direct records off SQLite.
- **Weixin.** Status and login output omit the configuration file path line.
- **Logs.** `MainLog` also writes every recorded line to stdout as one JSON line (`level`, `time`, `pid`, `hostname`, `tenant`, `msg`) instead of forwarding raw console output. The file log under the scratch directory stays for the operator. There is no WebUI Logs view (`RuntimeCapabilities.LogsView`): a replica's log is the operator's, not a tenant's ([logs](./dotnet-webui-logs.md)).

## D-capability-scratch-guard

**Approved plan §12 (scratch guard).** A replica's `FOXWARM_SCRATCH_DIR` may hold only `state/logs`, `state/provider-image-cache`, `foxwarm-uploads` and `.temp`. `HostedStartupTests.ScratchOutsideAllowlist` names everything else; the hosted turn scenario fails if anything is left there after a turn, a memory write and a Node-less exec.

## P1 limitations

- No Agent docs: `docs/` and other Agent-folder files beyond memory and skills can't be read or written by any tool.
- Received non-image files aren't kept; non-image WebUI uploads are refused.
- No configuration secret moves, no `set_config` or policy explanation from a candidate file, and no Node token or bootstrap files; administrators pair Nodes through the WebUI.
- No stdio MCP, Claude Code runtime, Main terminals, Code workbench, Main browser or Vector.

## Open Questions

- **Bundled skills in hosted mode (P2 plan §10, track CP2).** `foxwarm-maintenance` and `asr-service` are hidden without a master Node (`asr-service` runs a speech service beside the Main server and sets the deployment's `asrService`). The other bundled documents that state file-mode facts carry full-line `<foxwarm-if master-node="true|false">` wrappers ([skills](./skills.md#d-bundled-skill-conditions)): `about-foxwarm`, `access-control` (`SKILL.md`, `identities.md`, `policy-updates.md`), `agent-management` (`OPERATIONS.md`, including the whole legacy isolation section), `mcp-management` (`outbound.md`), `node-setup` (`SKILL.md`), `timer-automation` and `webui-markers` (the commit marker sections; a hosted tenant has no Code workbench). Their file-mode text is byte-identical to the unconditioned documents. Still open: the received-files passages (`OPERATIONS.md`, the channel-assistant template), the tool-policy editing passages of `access-control` (a tenant has no policy editor yet), the restricted worker's copy-out rule and the development workflow's master copy ends (both wait for the Agent store), and node-setup's reachable-address list.

## Tests

- **`HostedCapabilityProfileTests`** runs the hosted profile over file stores: master absent from `node list`, `ctl node list` and status; every master-targeted call refused with no file, Node registry or marker effect; no Main browser tools and no spool; stdio MCP refused on update and load while HTTP is kept; placement with no default, `master`, an unknown Node, an unknown Provider, a Provider Node and a resident Node; byte-identical default declarations of the hosted and operator profiles against the file profile; the profile-to-capabilities mapping; capability absence per stored profile (stdio MCP, `master` in `ctl node list`, Main-local exec and the Claude runtime absent for `hosted` and present for `operator`, the deployment Provider in both); skills, memory (own and another Agent) and the prompt; received files; the Claude runtime refusal. A file-profile case checks that master paths, `foxwarm-maintenance` and the file prompt remain. The presentation case checks `currentNode: null` on the Session DTO, the state event, list, catalog and administrator rows and `/status` text, the selected Provider Node once chosen, and `master` in the file profile.
- **`pickerOpenCentering.e2e.mjs`** checks the Execution node picker for a Session without a Node.
- **`HostedStartupTests.AHostedTurnUsesMemoryWithoutMasterAndLeavesNothingDurableInScratch`** runs one model turn in the hosted runtime (`HostedEntry.BuildRuntimeAsync`): `ctl node list` without master, `write_memory` into the Agent store (no Agents root appears in scratch), a refused exec; no terminals or Code routes; no Main-local path in the model request; then the scratch guard.
- **`BundledSkillProfileTests`** reads every bundled document in both modes: no wrapper left, file-mode text equal to an independent line-based reading of the true blocks (and so to the document before it was conditioned), the pinned list of conditioned documents, the hosted catalog equal to the file catalog without the hidden skills byte for byte, and Agent skills never filtered. `HostedCapabilityProfileTests.Bundled_skill_documents_and_resources_read_for_the_profile` covers `skill load`, resource reads and line ranges through the tools.
- **`HostedStartupTests.TheRuntimeCapabilitiesComeFromTheTenantsStoredProfile`** builds a runtime for a tenant stored as `operator` (terminals supported, Code routes present), changes the stored profile while it runs without effect on it, and checks that the next runtime is built as `hosted`.
- **`FrameworkPromptProfileTests`** checks both renders of the bundled template.
