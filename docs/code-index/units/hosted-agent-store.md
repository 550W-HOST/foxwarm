## Purpose

In hosted mode a tenant's Agent files (memory, docs, skills and other small durable files, plus the installation prompt files beside the Agent folders) live in the tenant's database and blob store instead of a directory (design U4(a), plan §5). This unit owns the store: its table, the write half of [`IAgentFileStore`](./storage-context.md#agent-files) on both implementations, its path rules and its limits. File mode keeps the Agent folders and doesn't change.

## D-agent-store-representation

**Approved plan §5.1, with the membership row decided by the coordinator (2026-11-27).**

- **Rows.** `agent_files(tenant_id, agent, path, kind, size, sha256, generation, inline, blob_key, mode_flags, updated_at)`, primary key `(tenant_id, agent, path)`, text keys in `COLLATE "C"`. `agent` is the Agent name, or `''` for the installation level (`IAgentFileStore`'s null Agent); no Agent name is empty.
- **Directories** are implicit in file paths. A `dir` row exists only for an empty directory, and every write keeps it that way: creating an entry below a directory removes the directory's own row, and removing the last entry of a directory adds one, so a directory stays when its contents go, as on a file system.
- **Membership.** Each existing Agent has a root row: `kind = 'dir'`, `path = ''`. An Agent exists exactly when its root row does, which is file mode's rule (an Agent exists when its directory does). The `Agents` state document stays metadata keyed by name; command deletion deliberately keeps a deleted Agent's metadata there, so its keys aren't the member list. Only the lifecycle operations (`CreateAgentAsync`, `DeleteAgentAsync`) write root rows, each in one transaction with the Agent's files.
- **Content.** Up to 256 KiB (`InlineBytes`) is inline. Larger content is a blob of the tenant's `agent-files` blob store (PostgreSQL or S3, as the deployment selects for images and artifacts) under `<agent>/<sha256>` (`.root/<sha256>` for the installation level), created before the transaction that references it. Blobs are content-addressed and created with keep-existing, so identical content shares one. Nothing deletes them: unreferenced blobs are collected in P3 with the backup window rule, as for the other blob stores ([hosted blobs](./hosted-blobs.md#d-hosted-blob-unfenced-writes)). A read verifies length and SHA-256 against the row.
- **Not representable:** symbolic links, executable bits and special files. `mode_flags` stays 0. Import reports what it can't represent.
- **Locators** are `agents/<agent>/<path>` (`agents/<path>` for the installation level), stable for unchanged rows. A hosted prompt shows no memory paths ([capability profile](./hosted-capabilities.md#d-capability-without-master)).

## D-agent-store-paths

**Derived from plan §11 (the traversal suite).** `AgentFilePaths` is the path syntax of both implementations' write half and of every hosted operation:

- relative and `/`-separated: no leading `/`, no drive prefix (`C:`) or other rooted form, no backslash, no empty, `.` or `..` segment;
- no control character, NUL included;
- valid UTF-16 (no lone surrogate), at most 255 UTF-8 bytes per segment and 4,096 in total;
- in Unicode normalization form C. A path is stored exactly as given and nothing applies compatibility normalization, so two spellings can't name two files and no later normalization can turn a stored name into `..` (fullwidth dots and the two-dot leader stay plain names).

The empty path is the Agent's own directory: it can be listed and statted, never removed or renamed. An invalid path is `AgentFilePathException` (an `ArgumentException`) and has no effect. Agent names pass `AgentCatalog.ValidateName` (the whole string; a new Agent's name is at most 128 characters in both modes, `MaxNewNameLength`, checked before a creating move has any effect; existing longer names stay readable, and a retained restoration keeps its name in both modes), so an Agent argument can't address another Agent's rows by path syntax. Authorization between Agents belongs to the consumers. `FileAgentFiles` writes through a temporary file with a fixed-size name, so a long final segment can't make it exceed the segment limit.

- **Key bound (store only).** The btree key `(tenant_id, agent, path)` must fit PostgreSQL's 2,704-byte index row limit. The store refuses a path whose UTF-8 bytes exceed `KeyBytes` (2,560) minus the Agent name's bytes with `AgentFilePathTooLongException`: "This path is too long: {bytes} bytes, and the limit here is {limit}." The margin covers the tenant key and row overhead; tests store incompressible paths at the bound with a 128-character Agent name. A tree rename or copy checks its longest resulting path before it commits. File mode keeps only the 4,096-byte rule.

## D-agent-store-writes

**Approved plan §5.1.**

- **Operations** (`IAgentFileStore`): `WriteAsync` (create or replace, parents implicit), `DeleteAsync` (a file, an empty directory, or a tree with `recursive`), `RenameAsync` (within one Agent; a file may replace a file with `overwrite`; never into itself), `MakeDirectoryAsync` (with parents; an existing directory is kept). A missing file is `FileNotFoundException`, a missing Agent `DirectoryNotFoundException`, a type clash ("Is a directory", "Not a directory", "Directory not empty") `IOException`; both implementations use the same texts (`AgentFileErrors`). Those texts are the store's. A consumer that exists in file mode (`ctl memory`, file tools) maps each condition file mode also has to file mode's own text, so a model sees the same result in both modes; only conditions file mode doesn't have (invalid store path, generation conflict, quotas, the Agent root, moving into itself) use the store's texts, which are coordinator copy.
- **Generations.** `expectedGeneration` null writes unconditionally, 0 requires the file to be absent, any other value requires that generation; otherwise `AgentFileConflictException`. In the hosted store every file write takes the next value of the tenant's counter in `agent_file_usage`, so a generation is never reused for a path, also after delete and recreate. A rename keeps the moved files' generations. `FileAgentFiles` reports a content hash (never 0) as the generation, which changes whenever the content does.
- **One write lane per Agent** (`AgentWriteLanes`) in each store instance. In the hosted store every write transaction first locks the tenant's `agent_file_usage` row, which makes the limit checks exact and also serializes all Agent-file writes of a tenant, across its Agents: there is no per-Agent write parallelism. That is accepted at Agent-file write rates; a store that needs it would have to split the usage row. Write bodies are asynchronous throughout; only `Stat`, `List`, `FileExists` and the lost-`COMMIT` checks read synchronously. Each write is one fenced `TenantDb.WriteAsync` transaction with a `Verify` for a lost `COMMIT`, retryable on serialization failure or deadlock; a write after an epoch bump fails with `TenantFencedException` and leaves no row.
- **Reads** are deterministic: listings in ordinal name order (both implementations), exact bytes, and text decoded as `File.ReadAllText` decodes it (UTF-8, a byte order mark dropped), so prompt building gets the same text from either store. Filtered listings match names as the platform matches file patterns (case-sensitive).
- **File implementation.** `FileAgentFiles`' write half writes a complete temporary file and renames it over the target, and refuses any path whose existing components below the Agent directory include a symbolic link.

## D-agent-store-limits

**Plan §7.2, defaults accepted by the coordinator (Q4).** `AgentStoreLimits(TotalBytes, Files, FileBytes)`, default 2 GiB, 20,000 and 64 MiB, is an input of the hosted store (`PostgresStorageContext.AgentStoreLimits`, read at every admission); the hosted entry applies the [operator-provided tenant limits](./hosted-operator.md#settings-and-placement) at runtime construction.

- `agent_file_usage(bytes, entries)` is maintained in each write transaction. `entries` counts files and empty-directory rows; root rows aren't counted.
- A file above `FileBytes` is refused before anything is written, its blob included. A write is refused with `AgentStoreQuotaException` (`Limit` = `fileBytes`, `totalBytes` or `files`) when it would grow a measured value past its limit. A write that doesn't grow the value is admitted, so a tenant over a lowered limit can still delete, shrink and rename.
- **Admission before blob content.** A write that needs a blob first runs the commit's checks (membership, the target's and parents' shape, the expected generation, and all three current limits) in a fenced transaction that commits nothing, then uploads, then commits and checks again; the tenant lock isn't held across the upload. Only a concurrent write that wins between the two can leave an unreferenced blob, which the no-GC rule accepts. The limits are therefore logical: they bound live files, not the physical blob storage, which also holds earlier content until collection.
- **Tree copies** (`CopyTreeAsync`) read only metadata under the lock, apply `FileBytes` to every copied file and admit the byte growth before anything moves, then copy each row's content inside the database (`INSERT … SELECT`, blobs by key); no content passes through the replica. A new Agent's creation (`AdmitCreation`) is admitted before its metadata commits, and `CreateAgentAsync` with initial blobs runs the same fenced pre-admission, root absence included, before it uploads them.
- **Reads.** `ReadAsync` reads the whole file and verifies its size and SHA-256. `ReadRangeAsync` fetches only the requested bytes: an inline slice in SQL, or `IBlobStore.ReadRangeAsync` (a byte-range GET on S3, the covered parts of the covered 1 MiB chunks in PostgreSQL). A range that covers the whole file is digest-verified; a partial read only has its length checked against the row's size, not its digest.
- File mode has no Agent store limits.

## D-agent-store-consumers

**Plan §5.2–§5.4, the authorization decision of the coordinator (2026-11-27).** A runtime uses an Agent store when it has no master Node and its storage context has one (`SessionManager.AgentStore`); a runtime with a master Node keeps Agent folders whatever its Session stores are. Over a store, Agent files have no physical path: `AgentCatalog.SourceDirectory`, `AgentDirectory` and `MemoryDirectory` throw, and each consumer uses the store instead. Hosted mode replaces the folder paths; it doesn't wrap them.

- **Catalog.** `AgentCatalog` (constructed with the store, which implies the canonical layout) takes membership from the store's root rows. Creation checks the store's admission first, so a creation over the limits leaves no authority record; if the store still refuses it for a limit (another write took the room after admission), the creation retires its metadata record again while creation is serialized, so the name stays free. It commits the metadata as in file mode, and publishes it to readers before it releases the state lock, then creates the root with `memory/`, the initial `MEMORY.md`/`SOUL.md` and, for an identity-owned creation, the `.identity-owner` proof in one store transaction; there is no preparation directory and no rename. Deletion removes the root with every row, except for `main`, which is always a member: its files go in one transaction (`ClearAgentAsync`) and its root stays, so its surviving Sessions can still write memory and startup fills the empty `memory/` with the templates, as a missing folder is filled in file mode. Retained metadata and the creator and inheritance checks are unchanged. The identity-move cleanup and completion read and delete the proof file through the store, so recovery tells an owned Agent from another as in file mode. The memory copy of `inheritMemory` and `createAgentInheritMemory` is `CopyTreeAsync` (`memory/` to `memory/`, replacing same-named files). Startup creates `main` with the packaged memory templates, or fills an empty `memory/`; the framework-copy retirement has nothing to retire. A name is reserved when its root exists (guest allocation, `move_session` creation).
- **Memory tools** (`MemoryTools.Store.cs`) resolve paths as the folder tools do (leading `/` or `memory/`, `.` and `..` inside the memory directory, a path that resolves to the memory directory itself names it, traversal refused), then apply `AgentFilePaths`. A missing parent and a missing leaf fail as they do in a folder. A delete or a patch's delete is conditional on the observed file's generation, inside the write transaction, so it never removes a replacement or a directory. Each condition file mode has returns file mode's text; .NET texts that name a physical path (`Could not find file '…'`, `Access to the path '…' is denied.`) name the memory path instead. Only store conditions use the store's texts: an invalid store path, an edit or patch update whose file changed since it was read (the write carries the read generation), and the limits. `HostedAgentStoreTests` runs one script of calls over folders and over the store and compares every result.
- **Skills.** An Agent's skill roots are `ISkillFiles` over the store, addressed by the locators `agents/<agent>/skills/...`; global skills stay on the file system. Discovery, resources, `skill load` with a path, `skill copy` and `skill run` read through the same interface, so containment, skipped names and limits are unchanged. A resource read takes the size and a bounded header first, then the script budget's charge, then the content, with ranged reads for previews (`ReadRangeAsync`).
- **Prompt.** `AgentMemory` reads the same store, so the composed prompt is byte-identical to the folder prompt for the same content (D-request-prefix-stability); `HostedAgentStoreTests` compares the persisted snapshots. `systemPromptFiles` entries resolve in the store when they name a file inside the Agent's folder: folder-relative or `$fw_agentdir/` references, reduced lexically, read and shown by their folder-relative path with the folder's checks (an existing ordinary file). Their admission is `env.read` on `@agent` with the target Agent's fact path, where file mode reads a master path (`SessionManager.PromptFileRead`). An absolute, `~`, other `$` or escaping reference fails with "`{path}` is outside this Agent's folder, so it can't be a prompt file here." In file mode a `$fw_agentdir/` reference stays a literal relative name.
- **Configuration candidates.** Without master, the candidate of `set_config` and of `explain_tool_authorization` is read in the Agent folder ([endpoint](#d-agent-folder-endpoint)) and authorized as `env.read` on `@agent`, in the Approval plan and the operation plan as well; the active-policy read of an explanation is unchanged. The checks are file mode's: a regular file, and the policy byte limit while reading.
- **Main-local file tools** get a `WorkspaceTools` over `NoAgentFolderOperations`, which refuses every effect as the missing master does; calls that target master are refused before they reach it.
- **Authorization.** A store access is an `AuthorizationPath` on the endpoint `@agent` (`AgentStorePaths.Endpoint`, never a Node ID) with the fact path `<agent>/<store path>`: `env.read`/`env.write` with `node: "@agent"`, the counterpart of file mode's `env.read`/`env.write(master, <physical path>)`. Memory tools state them per file, and the memory-copy legs take their Node from the `memory-node` fact. In the request, `${agent.dir}` and `${agent.memoryDir}` are the store roots `<agent>` and `<agent>/memory`. A legacy `allWithin`/`anyNotWithin` matcher and an operation rule's `path.within`/`notWithin` decide store facts against a root only when it is `${agent.dir}` or `${agent.memoryDir}`, optionally followed by a relative store path; any other root contains no store path, and no master path is inside a store root. So the generated isolation layer and the restricted-worker templates keep their meaning, another Agent's files stay outside `${agent.dir}`, and rules about master paths don't apply. A `node.provider` selector names the endpoint as `@agent`, never `authenticated-remote`. Equivalent suffixes (`./`, `//`, a `..` that stays inside) are canonical as in file mode (`AgentStorePaths.PolicyRoot`). A root that names an Agent root in a form the store can't decide (a variable not at the start, a suffix not after `/`, a `..` that leaves the Agent's namespace, a reduced key that isn't a store path) is refused where Agent rules are set, checked on the parsed rules as the evaluator sees them; an existing rule with one denies, whether it denies or asks (as an unknown operation-rule path does), and an allow with one doesn't match. The legacy isolation plan uses the installed layout for a store `main`.

## D-agent-folder-endpoint

**Coordinator decisions (2026-11-27), plan §5.3.** The Agent's own folder is a file endpoint without master, named `@agent` in both modes.

- **Paths.** `AgentFolderPaths` reads a path relative to the folder or starting with `$fw_agentdir/`; `.` and `..` reduce lexically, and a path that leaves the folder, an absolute, `~` or other `$` path fails with "`@agent` reaches only this Agent's own folder: <path>." `$fw_tmp` has no folder of its own there: "`$fw_tmp` isn't available here; use a path under `$fw_agentdir/`."
- **Tools.** `node:@agent/read`, `write` and `edit` are the standard file tools over the folder (`AgentFolderScope`), declared as such in both profiles (`ToolRegistry.AgentFolderDefinitions`: the standard schemas, the filePath parameter describing a folder path), so tool search and help list them. Their paths are store paths in both modes, and the folder's file owner applies the store's rules: `AgentStoreFileOperations` over the store, or over `FileAgentFiles` on the physical folder on master (`SessionManager.FolderFiles`), which refuses a link at any existing component, for reads, writes, created children and patches alike. Existence, kind, length and time come from `IAgentFileStore.Kind`, which reads no content and computes no generation (on master: file system metadata, with `other` for anything that isn't a regular file or directory); a generation is taken only by an operation that is conditional on it. Content reads open regular files only, so a read of anything else reports what master's read does. A listing shows a link as a link, from its own metadata, without following it; opening the link is refused. Errors carry a Node's codes; a write needs its parent directory as a file system's does, a write to an existing directory is refused as an existing file, a patch deletes regular files only (a conditional delete on the file's generation), and validated store keys aren't checked again as Node paths (a name may start with `$`). The call's authorization facts are store paths on `@agent`, or master's physical paths on master; the empty path names the root, as `.` does. A Session without a Node sends `read`/`write`/`edit` calls whose paths start with `$fw_agentdir` there too. The tools use the invocation's workspace, so ToolScript's structured results (a directory listing is the standard listing string) and script budget apply. A ToolScript subcall keeps the endpoint through its concrete descriptor, including one reached through `ctl tool call`, so a script's second dispatch is the same folder call and never a master file call. Top-level calls carry resolved-path receipts (master's physical path, or `$fw_agentdir/...` on `@agent`); ToolScript subcall history records no resolved paths for any tool. Results equal file mode's, with paths shown as `$fw_agentdir/...`. An ordinary master path into the folder is unchanged: it is master's file, links included. Known limitation in file mode: confinement on master is pathname-based, checks followed by separate operations rather than handle-relative ones, so it doesn't exclude a concurrent writer that changes a parent component into a link between the check and the operation; the endpoint tools can't create links. The store has no links and is unaffected.
- **Copies.** `copy_between_nodes` and `ctl node copy` accept `@agent` as either end, own Agent only, through copy's own entry points (`OpenCopySourceAsync`, `WriteCopyTargetAsync`): without master the store, with a length check against the store's limits; on master the physical folder confined as above. The generic Node stream helpers don't take it, so skill copy and `send_file` refuse `@agent` as an invalid Node.
- **Selectors (the master alias).** For the endpoint, `exact` and `provider` match its own name; a selector that names `master` also matches it (legacy `node`, `targetNode`, `provider: master`, an operation rule's `node`, and the `sourceNode`/`targetNode` argument matchers of copies). A bare legacy pattern sees only master's identity, never the literal `@agent`. `current` never matches the endpoint, and no Session can be placed on it (`StartingNode` refuses it, explicit and inherited). Path selectors still apply. On master, calls are master's with physical paths, and an explicit `@agent` copy argument is presented to policy as `master` in both the Node targets and the arguments, while the call keeps its endpoint for confinement; other copy arguments are matched as given. So the alias never changes a file-mode decision. An explanation shows the actual endpoint and marks a winning rule `masterAlias` when it matches only with the alias: the rule is evaluated again with the alias off by its own evaluator, whole-call or operation (a whole-call rule can win an operation in a layer with operation rules), and only a match that becomes no match is marked, not an undecidable match that stays undecidable. Discovery (tool search, help, ctl listings) decides an endpoint tool's visibility with dispatch's identity, master on master, while showing `@agent` IDs. The templates keep their meaning: a restricted worker's copy is denied, a channel assistant reads `.temp/channel-files` and nothing else of its folder, the generated isolation layer copies within `${agent.dir}`.
- **Explanations and staged approvals.** Explanation probes route calls through the same pure `ToolRegistry.Route` as dispatch (no live discovery), so an implicit folder call or a configuration candidate without master is explained on `@agent`, and they apply dispatch's pure availability checks (`ToolRegistry.RequireAvailable`: a master target without master, `add_secret.fromConfig` without its documents), reporting dispatch's refusal instead of a policy decision. A staged approval checks each obligation with its own resource's files: a folder read with the folder's, the active policy's read with the Session's, by the policy's locator, as the handler reads it.
- **Candidates.** A configuration candidate in the folder is read once, whole: one committed version, read through `ReadBoundedAsync`, which applies the byte limit to that version before its body is materialized; that buffer is parsed, decided and installed.
- **Clearing the Node selection.** `node select --none` targets what an unset Node is, in every projection of policy: master on master (its Node targets, `targetNode` and an `args.nodeId` of `master`), and a known absence of a Node without master (no targets, no `targetNode`, an operation `node.select` without a `node` resource, which isn't unresolved, and no default-cwd probe).

## D-agent-store-attachments

**2026-11-27.** An accepted channel file or WebUI upload is retained under `.temp/channel-files/<platform>/` in the receiving Agent. WebUI uses platform `webui`; there is no separate uploads folder in the store. All `.temp` files count toward the same store quotas as docs. The upload allowance is the smaller of the tenant upload limit (100 MiB by default) and the store per-file limit; file mode retains its 1 GiB upload limit. Hosted HTTP file bodies are bounded, including responses without a declared length. Each hosted runtime stages its WebUI uploads in its own scratch directory. The saved descriptor names `@agent` and `$fw_agentdir/...`; an inline image also keeps its image reference. Accepted uploads and channel files have no expiry. Telegram, Matrix and WeWork keep bounded downloads in the incoming message until the router resolves its receiving Session, including a first-contact guest. The routing instance identifies the conversation; the platform identifies the path segment. QQ retains its original authorized-only fetch and uses the resolved owner. A refusal at QQ's binding hosted size cap names the file and known size (or the lower bound on streamed overflow); its own size and aggregate limits retain QQ's notices. If a saved image cannot be attached inline because the image quota is full, the message carries its original saved-file descriptor and an inline-unavailable notice.

Where master would spool a tool result, hosted mode checks both read and write authorization on the Agent folder and writes `.temp/tool-output/`. The notice names `read` without a Node and `node:@agent/read` with a Node selected. A hosted runtime sweeps tool-output files at startup and hourly, deleting only generations last modified more than 24 hours ago. File mode has no sweeper. Files imported from disk and offline recovery are covered by [D-hosted-agent-folder-import](./hosted-import.md#d-hosted-agent-folder-import).
