## Purpose and consumers

A small BCL-only .NET 10 class library owns mechanisms actually used by Main and the [headless CLI Node](./dotnet-cli-node.md). Main and CLI both reference this library. Internal friend assemblies retain a narrow first-party boundary; this is not a public plugin/NuGet API or a split of Main's full runtime.

Main keeps authorization, Session/cwd policy, cached-write references, interpreter budgets, separate atomic delivery/memory publication, Provider adaptation and caller-specific filesystem effects. Ordinary native content writes use the shared in-place/exclusive primitive. CLI keeps startup roots, credential/connection ownership and its Source-native effect/publication wrapper. Native Code filesystem and read-only Git mechanisms are also shared; Main keeps HTTP/authentication, capability/URI presentation and environment ownership, while CLI keeps fixed service framing and native argument/error adaptation. Native PTY handles, ConPTY and capability-bound Code helper IPC are shared. Main keeps its registry and browser/control policy; CLI keeps its service, process records and transport generation. No exec manager, provider registry, Session runtime or image decoder is moved into this library. The agreed native process/access facts, duration formatting and petname vocabulary are shared; Main/CLI registry, caller environment, cwd defaults, ownership and notification authority remain separate. Native launch/helper mechanics, scripts and Source display/raw-capture algorithms are shared; provider output supplies only an ephemeral read-only size/read view.

The patch engine is the single canonical implementation for Main native/Provider tools, memory patches, compact-plan repair and CLI file calls. Its Source diagnostic copy, repeated-anchor cursor rule and EOF search are deliberate parity corrections, not behavior-free relocation. Parsing completes before caller effects; operations and partial-failure reporting remain caller-owned. Context mismatch feedback includes only the original failed hunk and stays within 1,600 characters.

Native directory listings classify entries without following symlinks. Linux uses the existing fixed-layout statx mode field because BCL FileAttributes does not distinguish FIFO/device/socket entries from regular files; non-Linux classification uses BCL attributes and link resolution. This is a narrow type primitive, not a general native filesystem layer. Main retains its regular-file admission, policy errno handling and opened-handle flags. Native text reads inspect file size before opening, so a zero-size entry produces the shared empty-file result without opening a FIFO. This does not impose regular-file admission on CLI ordinary reads or add an open-time race guarantee.

Code operations retain Source-native flags and result shapes. Confirmed parity corrections include owner-write permissions, broken-link listing fallback, ENOTDIR, nonrecursive directory deletion, working Git content ignoring base refs, porcelain-v2 unmerged-row omission and normalized Git paths/refs. Git base content normalizes repository-relative paths without applying the working-tree child check, so committed literal `..`-prefixed names remain readable. Working content applies that check before stat; missing paths and ENOTDIR return empty, while raw stat failures retain Git's Unknown/500 projection rather than filesystem-service permission codes. Main's Code URI adaptation, pre-dispatch content-ref validation and optional-Git unavailable response remain in its wrappers; CLI missing-Git errors follow its actual service caller, including empty failed base content. Native rename does not copy across volumes or restore an already removed overwrite destination.

## Validation

Existing Main file/Provider/image and compact-repair tests exercise the relocated implementations through their actual callers. `WorkspacePatchTests` covers bounded failed-hunk feedback and ordinary Main repeated-anchor/EOF/malformed-patch effects. `CliNodeFileTests` and the Source/new-client native corpus retain the distinct caller effect and replacement-string contracts. See the [CLI unit](./dotnet-cli-node.md#validation-and-limits) for real process interoperability.

`IsAotCompatible` enables library trim/AOT analysis. Actual native publication and platform qualification remain executable-level work, not a consequence of this managed library boundary.

Native primitives and their BrowserSupport consumer are not RID-agnostic project references: the consuming executable's target RID must flow through both paths, so a Linux cross-publish of win-x64 does not collect a build-host PTY shared object. Linux builds compile the existing C PTY shim with the installed GCC and propagate its shared object to actual executable build/publish outputs. Native CLI delivery includes that library and still needs its real libc/shell dependencies and a writable local temporary directory for helper IPC. The [Linux x64 delivery unit](./dotnet-cli-linux-aot.md) owns the measured libc floor and PTY pidfd/kernel requirements; these shared-object measurements do not qualify the separate static build or other platforms. Windows retains current-user named pipes, PowerShell/cmd wrappers and ConPTY; its runtime qualification remains separate.

`ExecNative.Launcher` binds POSIX `PWD` for Main and CLI under the shared [logical cwd contract](./shared-persistent-exec.md#d-persistent-exec-logical-cwd).

### Windows persistent exec output

Main and CLI share `ExecNative.Start` and `WindowsExecProcess` for Windows persistent exec. The caller fixes the original unique log/status/cwd paths before its final synchronous launch fence. Exclusive log creation (`CREATE_NEW`) rejects an existing path; read/write/delete sharing matches Source's `openSync(..., 'wx')`, not a no-delete lease. Stdout and stderr share that single inherited log handle; stdin is NUL. There is no transcript or output pump.

A one-shot same-executable `--exec-launch-windows` helper opens the inheritable capture handles, never the multithreaded Main/CLI process. Existing early `ExecNative.Helper` dispatch precedes Main/Desktop/CLI configuration, connection and service startup. This placement prevents unrelated ordinary BCL children, including concurrent Git service calls, from inheriting capture handles. A per-child list alone cannot provide that guarantee: the BCL's process-creation lock does not cover custom inheritable handles. The helper retains `STARTUPINFOEX` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` for only its log and NUL handles, excluding its receipt stream and any inherited caller handles. It releases parent-side handles and native attribute storage on success/failure, sends the actual PowerShell PID through its BCL-owned stdout receipt stream and exits. The tracked PID is not the helper PID.

The parent bounds receipt settlement to ten seconds. A structured helper rejection before PowerShell creation remains a definite native launch error. Missing, invalid or timed-out receipts have an uncertain outcome; they retain the known original log/status/cwd paths in the error and never retry or kill a possible command. No synthetic PID, replacement artifact namespace, durable launch record or recovery scan is introduced. Main's existing error projection preserves that message. CLI uses the existing [remote unknown-outcome representation](./remote-exec.md#contracts), rather than asserting a false prelaunch rejection. Successful launch and registry persistence retain their existing non-atomic ordering and independent command lifetime.

PowerShell user and wrapper scripts are UTF-8 with BOM for Windows PowerShell 5.1. The wrapper sets console input/output and pipeline encoding to BOM-less UTF-8 and atomically publishes BOM-less UTF-8 cwd/status files. Linux retains detached Bash launch, PID-selected paths and existing output redirection.

`WindowsExecCaptureTests` targets actual Main/CLI native stdout/stderr, formatted/direct/piped Unicode output, exit status, cwd and script/status bytes. Capture assertions use the production shared snapshot reader: status publication is not a process-exit or capture-handle-close receipt. `WindowsExecSharingTests` disposes each actual manager's observers while the PowerShell PID remains alive, checks live read/write access and rename, then confirms output continues into the renamed capture. `WindowsExecBclInheritanceTests` overlaps real manager starts with independently live ordinary `Process.Start` children; after actual owner exit and observer disposal, an exclusive capture open detects a retained read/write handle even with delete sharing. This exercises the real inheritance window but does not deterministically force the old interleaving. `WindowsExecLaunchReceiptTests` covers real missing/malformed receipt streams with once-only fixture effects, live-effect survival of the settlement deadline, definite process-creation failure and actual Windows helper exclusive-creation rejection before command effect. The receipt controls are not a substitute for native Windows capture proof. These Windows paths require a real Windows runtime; Linux compilation or a guard-returned test is not Windows qualification. Existing independent-lifetime and ConPTY proofs remain distinct.

### Static musl PTY boundary

Only the explicit static-musl CLI target compiles `FOXWARM_STATIC_MUSL`: it links the same PTY implementation into the executable and bypasses optional shared-library discovery. All glibc builds retain their existing posix_spawnp and optional-shim path. Existing IO, eventfd cancellation, mandatory pidfd_open/pidfd_send_signal, wait and release semantics remain shared and unchanged.

The musl pre-exec adaptation uses an x64 raw fork with signals blocked and a private child fd table. It does not call libc fork/atfork handlers or enter managed code in the child. Parent-prepared PATH candidates retain caller-PATH, relative-cwd and errno search semantics. The child uses only raw syscalls and copied/stack inputs: reset signal dispositions, setsid, chdir, open the slave as controlling terminal, duplicate stdio, close other descriptors, clear its mask, then execve. A CLOEXEC pipe above stdio returns setup/exec errno synchronously; the parent reaps failed children and restores its original mask. Successful exec closes the handshake pipe. Subsequent mandatory pidfd acquisition retains the existing kill/reap failure behavior.

Close-all uses close_range while excluding that pipe, or raw getdents64 over the child's own procfs fd directory when the syscall is unavailable/blocked. There is no parent-side enumeration, numeric-limit close loop, relaxed inheritance or new close_range-only kernel floor. If neither mechanism works, spawn fails before the executable runs. The [delivery unit](./dotnet-cli-linux-aot.md#explicit-static-musl-qualification) owns build/runtime qualification and the focused native probe; source support alone is not platform qualification.
