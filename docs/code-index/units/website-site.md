## Purpose

Builds and validates the public Foxwarm project website and focused user documentation without entering the main runtime package graph.

## Behavior

- `astro.config.mjs` fixes the canonical origin at `https://foxwarm.net`, enables static output and sitemap generation, and configures Starlight routes, navigation, search, branding, edit links, and documentation CSS.
- `/android` is an Astro static redirect (HTML meta refresh on GitHub Pages) to `https://github.com/550W-HOST/foxwarm/releases/latest/download/foxwarm-android-node.apk`. Both install locales link to it and show the committed `public/android-download.svg` QR, Android 11+ sideload instructions and the [release certificate fingerprint](./release-packages.md#android-node-apk). The SVG was generated with the existing WebUI `qrcode` package using that public URL, width 240, margin 4 and error correction M; no website runtime dependency is added.
- The custom homepage is bilingual: `src/pages/index.astro` (English, `/`) and `src/pages/zh/index.astro` (Simplified Chinese, `/zh/`) both render `components/Home.astro` with copy from `src/i18n/home.{en,zh}.ts`; pages declare canonical and `hreflang` alternates for each other. The homepage and the blog share `SiteHeader.astro` (brand, Docs, Download, Demo, Blog, GitHub, language menu, theme toggle), `SiteFooter.astro` and `ThemeInit.astro`; `src/i18n/home.ts` owns the `docsPath` and `blogPath` helpers. Download and GitHub leave the header at 720 px and below, and the brand text below 375 px, so the header fits a 320 px screen in both languages. The language menu (user, 2026-11-17) is a disclosure button with the docs language picker's translate and caret icons (Starlight's `Icon`) that lists English and Chinese, each named in its own language and carrying `hreflang`/`lang`: the current language links to the page itself (the `path` prop), the other to `languageHref`. It closes on Escape, an outside click or focus leaving it; without scripting, `@media (scripting: none)` shows a plain link to the other language instead. The footer keeps a text link to the other language.
- The homepage Download section ([D-website-downloads](../modules/website.md#d-website-downloads), user, 2026-11-18) renders the desktop, server and Android rows in `Home.astro` from `downloadFiles` and `latestReleaseUrl` in `src/i18n/home.ts`, with copy and installing-guide anchors per language in `home.{en,zh}.ts`. The header, the footer and a line under the hero install tabs link to `#download`. `Home.astro`'s bundled script reads the visitor's operating system with `detectPlatform` from `src/scripts/platform.mjs`, which both preselects the hero's Windows tab and marks the matching download (`data-platform`) as this device's.
- Product imagery uses real WebUI screenshots of a demo installation with fictional project data, captured at 2x in light and dark variants and swapped by the page theme (`src/assets/screens/`, rendered by `Screenshot.astro` through `astro:assets` AVIF/WebP). Conceptual visuals that are not product UI — the brain/hands Node diagram and the group-chat channel example — are drawn in HTML/CSS and labeled as illustrations in their accessible names, so they are never presented as screenshots.
- Homepage facts (platforms, install prerequisites, feature claims) must match current user documentation; capabilities that require configuration are described as configurable rather than default behavior.
- `src/content/docs/docs/` owns English user guides, grouped in the Starlight sidebar as Get started (overview, quick start, install, model setup), Concepts (how it works, Agents/Sessions/memory, long conversations), Use (delegation, Nodes, Channels and group chats, tools/Skills/MCP, timers, WebUI), Control and security (access control incl. per-Agent rules, Node trees and credential-isolation configuration; inbound MCP) and Operate (data/backups, model options, TypeScript migration, FAQ). Existing slugs are kept stable. Detailed implementation references remain in the repository.
- Docs use Starlight i18n with English at the root locale and Simplified Chinese at `/zh/docs/`. Only core pages are translated under `src/content/docs/zh/docs/` (overview, quick start, install, model setup, model options, how it works, channels, FAQ); other `/zh/docs/` routes are Starlight fallbacks showing English with a notice from `src/content/i18n/zh-CN.json`. The homepage links each language to its docs locale and shares Starlight's `starlight-theme` storage key so the theme carries across.
- The docs palette and type in `docs.css` match the homepage; `HandsDiagram.astro` and its `diagram.css` are shared by the homepage and the how-it-works pages.
- The tools/Skills and inbound MCP guides navigate to the bundled access-control, agent-management, and mcp-management workflows. The inbound guide distinguishes separately permitted history reads from explicit online text replies; detailed reply setup remains in the MCP skill reference.
- `scripts/sync-assets.mjs` copies both repository-root installers, Chromium's Docker seccomp profile (`docker/seccomp-chromium.json`, served as `/seccomp-chromium.json`) and the existing WebUI favicon assets into ignored `website/public/` build inputs before development or production build. The installing guide owns the Docker install steps, which download that profile from the site; both quick starts and the homepage Docker tab repeat them verbatim, in lines short enough to show whole beside the homepage copy button, which sits in its own column so it never covers a command.
- `scripts/build-demo.mjs` runs after asset sync in `prebuild`. It builds the static [WebUI demo](./webui-demo.md) into ignored `website/public/demo/`, installing `packages/webui` dependencies from that package's lockfile when absent, so the site serves it at `/demo/`. Every demo page is `noindex, nofollow` and the sitemap excludes the demo; `robots.txt` lets crawlers fetch it so they can read that rule. It is linked publicly from the homepage ([D-website-public-demo](../modules/website.md#d-website-public-demo), user, 2026-11-15): a Demo item in the header navigation opens `/demo/`; the hero screenshot caption adds an "Open the interactive demo" button with a one-sentence read-only description and opens the Session shown in the screenshot; the compaction/recall, Nodes and delegation feature sections add "Open in the demo" next to their docs link. `src/i18n/home.ts` owns the demo URL helper and the linked Session IDs; the English and Chinese copy files own the labels.
- The blog ([D-website-blog](../modules/website.md#d-website-blog), user, 2026-11-15) is an Astro content collection (`blog` in `src/content.config.ts`, glob loader) rendered outside Starlight by `BlogLayout.astro`, which supplies the canonical, `hreflang`, Open Graph and RSS-discovery metadata. `src/blog/posts.ts` groups the language versions of each post by slug; `BlogIndex.astro` and `BlogPost.astro` render the indexes and articles from `src/pages/blog/` and `src/pages/zh/blog/`, and `src/blog/feed.ts` writes each language's RSS 2.0 feed with the same entries as its index. Labels and date formats are in `src/i18n/blog.ts`. `blog.css` sets the long-form type on the homepage palette; tables and code blocks scroll inside the column on narrow screens. Starlight's Expressive Code processes all Markdown, so blog code blocks get the docs' frames; `blog.css` supplies the Starlight palette variables they read. Their copy-button labels stay English on Chinese articles, because Starlight derives the code-block language from the docs content path.
- **Adding a post.** Write `src/content/blog/<slug>/zh.md` or `en.md` (lowercase hyphenated slug). Frontmatter: `title`, `description` (also the index summary and meta description), `date` (`YYYY-MM-DD`), optional `series` and `version` (for example `Foxwarm 0.9.5`). A translation is the sibling file with the other language code under the same slug; nothing else links them. Routes, both indexes, the feeds and the sitemap pick posts up automatically. Point in-site links at the article's locale and demo links at recorded Sessions; `npm run check` verifies both.
- The test suite validates the Android redirect, QR asset and certificate in both install locales, required routes, canonical URLs, indexability, the unindexed demo and its homepage links, recorded Session IDs in every demo link outside the demo, the blog indexes (every post listed, other-language entries marked), article canonical, sitemap, Open Graph, translation and `hreflang` rules, the header language menu targets on every homepage and blog page, the homepage downloads (latest-release targets that the release workflow builds, the `/android` redirect, no emphasis in the HTML, header, footer and hero entries), visitor platform detection, feeds, homepage navigation and footer entries, local links/assets on every page including the blog, installer and seccomp-profile byte parity and file identity, the Docker steps matching the installing guide in both quick starts and on the homepage, robots/sitemap output, Pagefind search output, and absence of unresolved installer-host placeholders.
- The Pages workflow uses immutable revisions of official checkout, Node setup, Pages artifact upload, and deploy actions. It runs for website, installer, Docker seccomp profile, WebUI and shared-source changes (the profile is served by the site; the WebUI paths feed the demo), installs the website with `npm ci`, runs the standalone check, and uploads `website/dist`. Pull requests are checked but only a successful `main` push or a manual run explicitly selected on `main` can deploy; permissions are job-scoped and deployment is serialized.

- `wrangler.jsonc` provides a separate Cloudflare Workers Static Assets preview target named `foxwarm-preview`, serving only `dist/` with the custom 404 page. Its production `workers.dev` URL is disabled (`workers_dev: false`) so only version and branch-alias preview URLs serve the site. Workers Builds uses `website` as its root and `npm ci && npm run check` as its build command. Production-branch deployment uses `npx wrangler deploy`; non-production branches use `npx wrangler preview`, which creates a per-branch Worker Preview from the `previews` block (empty, because the static site has no bindings or variables). Worker Previews replace the earlier `wrangler versions upload` branch aliases (`<branch>-<worker>.<subdomain>.workers.dev`); `preview_urls` still enables those version URLs. `public/_headers` adds `X-Robots-Tag: noindex` to everything this Worker serves, so preview hosts, including custom preview domains without Cloudflare's automatic preview noindex, stay out of search indexes. Only Workers Static Assets applies the file; GitHub Pages serves it as an ordinary unlinked file and adds no header, so foxwarm.net remains indexable. This target does not replace the canonical GitHub Pages deployment or configure its domain.

## Tests

From `website/`:

```bash
npm ci
npm run check
```

`npm run check` creates the static `dist/` output and runs `node:test` assertions against it. Browser sanity checks use the built preview for desktop/mobile layouts, both color modes, keyboard navigation, docs search presence, and horizontal overflow.

## Integration

README and the main installation guide address new C# users: prerequisites, installation, first model setup and ordinary controls. Commands target the normal public `main` branch. TypeScript-to-C# cutover details belong in the dedicated migration guide, reached by short links rather than repeated in the main entry. The data/update guide owns data-root selection, backups and platform update ordering; optional Vector native requirements belong beside search setup. User setup examples belong in the website guides; the Channels guide owns its starter configuration rather than linking back to README. README installation commands and documentation links use the canonical public domain. The PowerShell installer's header example uses the same URL, and both source installers check the WebUI build requirement (`^20.19.0 || >=22.12.0`) before cloning or installing dependencies. Source prerequisites and support limits link to [source Main entry](./source-main-entry.md); installer downloads remain generated copies, not a separate implementation. Canonical architecture and deployment ownership are recorded in [D-website-independent-static-site](../modules/website.md#d-website-independent-static-site).
