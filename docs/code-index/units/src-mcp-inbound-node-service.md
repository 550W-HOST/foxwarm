## Purpose

Main-local entry from an HTTP-verified external principal and a generated live external context to a compatible authenticated CLI Node or an already-ready first-party resident Docker-worktree Node. It does not create a Foxwarm internal Session, Agent or synthetic sourceSessionId. The inbound catalog uses this service for `node` discovery/calls, Node selection and scoped command results.

## Exports and behavior

- `listExternalNodeTools` walks the authoritative provider registry and lists potentially visible read/write/edit/patch/exec capabilities only on ready authenticated CLI Nodes with negotiated v3 and `externalToolOwner:1`, or ready first-party resident Docker-worktree Nodes with their derived primitive tools. A first-party provider marker is verified after discovery rather than trusting descriptor text alone. Master, executable-provider and browser-tool external effects remain unsupported.
- `callExternalNodeTool` binds the verified identity and immutable context UUID, authorizes exact source `node`, target Node, full arguments and execution-derived file/patch/cwd path facts, then dispatches to the actual advertised capability. A disposed context fails after async authorization/lookup and again before the remote final send or each resident Docker primitive/process launch. An attempted multi-step file mutation is never reported as wholly pre-effect. Exec reserves one real persistent exec ID and Main-signed capability before dispatch; the resident Docker adapter uses the record locally without a new wire/HMAC protocol and binds the actual provider generation before launch. Error/timeout paths do not retry effects. Foreground and background results stay scoped to the original context, including after current-Node changes.
- `externalExecResult` lists at most 20 Main-owned records per context or inspects one exact real ID, rechecking the original `node:.../exec` rule and retained bounded arguments on each call. Completed output is bounded; running output is queried from the authenticated CLI Node or the exact active Docker generation's resident runtime. Destroy/recreate cannot route an old running ID to a new generation. Offline/expired/unavailable results do not switch providers or reconstruct authority from Node files.
- `externalNodeAction` authorizes the concrete `builtin:node` action with its normalized action arguments: list has no target Node fact, status uses the actually selected current Node, and select uses the validated requested Node rather than a synthetic `master` target. It then checks actual compatible capabilities. A new selection uses the Node-supplied default cwd rather than another Node's working directory. Completed commands update cwd only if the selection generation is unchanged.
- `releaseExternalNodeContext` synchronously fences its context and discards Main's live ownership records on DELETE/expiry/shutdown; it sends best-effort release to authenticated CLI Nodes used by that context, including commands whose completed record has since been evicted. Docker's local completion callback silently retires an unclaimable finished record. Neither path kills an already-running process.

## Tests and ownership

`mcpInboundNodeService.test.ts` pairs a real CLI Node and connects two real MCP SDK clients to Main: exact file capabilities, foreground/background commands with partial/final output and cwd, identity isolation, policy revocation, reconnect and interrupted POST recovery, DELETE without command termination, exited-artifact cleanup, and a negotiated-v2 Node rejected before tool dispatch. No shared Testing service is modified.

`mcpInboundNodeOwnership.test.ts` deterministically holds the capability and post-reservation provider lookups across release, asserts no late Node effects or records, and tests completed-record eviction versus all-active saturation. The real paired fixture separately proves that an already-started background process survives DELETE. The Docker provider's own FakeDocker/local-process fixture tests the same external identity through shared file tools, foreground/background output, owner-only results, policy revocation, artifact denial, disposal at readiness and prelaunch gates, partial patch error honesty, DELETE process survival, and exact generation binding; it does not require a shared Docker service.
