# Unit: Model configuration, concrete hosts, and routing

Files: `dotnet/Foxwarm/Models/AppConfigurationRules.cs`, `dotnet/Foxwarm/Models/ConfiguredModelRequests.cs`, `dotnet/Foxwarm/Models/EffectiveRequestSelection.cs`, `dotnet/Foxwarm/Models/HostModels.Resolve.cs`, `dotnet/Foxwarm/Models/HostModels.cs`, `dotnet/Foxwarm/Models/ModelAttemptFailure.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.Form.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.Install.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.cs`, `dotnet/Foxwarm/Models/ModelRequestOwner.cs`, `dotnet/Foxwarm/Models/RequestSizeDiagnostics.cs`, `dotnet/Foxwarm/Models/ModelHistoryCompatibility.cs`, `dotnet/Foxwarm/Models/ModelRequestScope.cs`, `dotnet/Foxwarm/Models/ModelUsageCost.cs`, `dotnet/Foxwarm/Models/ModelRouting.cs`, `dotnet/Foxwarm/Models/ModelRoutingFingerprint.cs`, `dotnet/Foxwarm/Models/SessionModelSettings.cs`, `dotnet/Foxwarm/Models/SetupProviderRequests.cs`, `dotnet/Foxwarm/Models/ModelApiKeys.cs`

## Purpose

Captures model YAML, derives concrete and virtual hosts, selects failover targets, tracks request owner/scope, and validates setup/configuration forms before a request reaches a provider. Key fields may use [`${secret:NAME}`](./dotnet-secrets.md).

## Stable methods and callers

- `ModelConfiguration` loads/reloads captured config/model paths from `HostPaths` and exposes provider/model limits and setup data. Configured startup locations do not change under a live owner when saved YAML changes its `paths` section.
- `HostModels` resolves configured concrete hosts and virtual aliases; `ConfiguredModelRequests` prepares a request owner and concrete client settings. Native hosted-tool purpose selection is owned by [Responses](./model-responses.md#d-responses-hosted-tool-purpose); [separate image generation](./session-image-generation.md) owns its reasoning-free request policy and compatible mode naming.
- `ModelRouting.Select/RecordFailure/Health` applies deterministic target order, cooldown, and attempt attribution; `ModelRoutingFingerprint` identifies routing prefixes. `Select` accepts an optional failover eligibility filter, also applied to its all-cooling fallback; the owner uses it so a request that started on a redacting leaf, and every request on a failover route whose first target redacts, never uses one without [text redaction](./model-text-redaction.md).
- `ModelUsageCost.ValidatePrices/Complete/FormatUsd` validates concrete-leaf rates, settles owned normalized completion usage and formats saved USD estimates under [D-model-usage-cost](../threads/model-request-and-streaming.md#d-model-usage-cost).
- `ModelRequestOwner`, `ModelRequestScope`, and `ModelAttemptFailure` carry owner/attempt lifecycle into retries, streaming, journal, and Session messages. Terminal `ModelRequestException.Scope` retains the failed request origin, including errors propagated through a different request's preparation. Caller cancellation is rechecked after awaited retry-notice delivery before throwing a terminal provider failure.
- `SetupProviderRequests` and `AppConfigurationRules` validate WebUI setup fields without changing active Session authority.
- `ModelApiKeys` recognizes template placeholder keys and hosted services that always require a key; `ModelConfiguration.InstallAsync` applies it to the first models installation ([first-run key check](#first-run-key-check)).

Callers: `SessionChatService`, provider adapters, `SessionModelSettings`, `HttpServer` startup, and WebUI setup routes.

## Contract and side effects

Concrete model objects may set `upstreamModelId` to a nonempty string (trimmed during resolution); omitted values use the internal `id`. Only the final request's `RequestModel` changes. Selection/routing keys, model options/prices, canonical history and journal attribution, model-memory identity and WebSocket connection ownership keep the internal provider-qualified ID. Equal upstream values do not declare history compatibility. The effective upstream ID participates in the resolved route fingerprint, and ordinary provider `extraFields.model` retains its existing final wire precedence. Provider entries, including virtual providers, reject `upstreamModelId`; string model entries and concrete no-model leaves retain their existing behavior. Raw Setup saves publish this configuration, while structured saves preserve the overrides of retained model objects. The ad-hoc Setup provider test still builds a transient string model from its submitted upstream test name; CLI and ToolScript one-shot calls use the captured configured model through `ConfiguredModelRequests.Plan`.


Concrete `textRedaction` inherits individual fields from models defaults, provider and model, with explicit lower-level disablement; a lower-level `excludeLabels` list replaces the inherited one, and `apiKey` accepts `${secret:NAME}` at each level. The captured leaf controls detection and output restoration through `ConfiguredModelRequests`; the [text redaction unit](./model-text-redaction.md) owns its settings, service contract and failure behavior.

### Native-history compatibility

**Derived design; the model/provider declarations were proposed and approved after an explicit upstream-identity request.** They implement [compatible history projection](../threads/model-routing.md#d-model-routing-history-reasoning-compatibility) while preserving internal IDs for routing, attribution and configuration. Resolution rules below describe the chosen catalog mechanism; a matching wire model name alone is not approval to replay provider-native state.

Model-only `sameModelAs` names a compatible concrete model by its whole local internal ID or whole provider-qualified key. Resolution tries the local ID first, preserving slash-containing IDs, then the qualified key. Provider-only `sameProviderAs` names a concrete provider and maps each internal model ID to the corresponding ID there, including IDs absent from that provider's configured model list. An existing target model's own override is followed; a missing target model has only its provider mapping to follow. Explicit model references take precedence over provider mapping. Chains terminate at one compatibility identity; declared unknown/non-concrete references, empty/non-string values, provider cycles and model/mixed cycles are configuration errors. Neither field is a root default or virtual routing option.

`ModelHistoryCompatibility` resolves this projection once per captured catalog and attaches it to its concrete leaves. `ConfiguredModelRequests.Plan` carries it through request filtering, Completions provider fields, Responses native items/annotations, generated-image hydration and WS append finalization. Existing history keeps its original canonical and provider metadata source IDs. New requests use the captured current mapping, so a saved declaration applies to old history without rewriting it; retries keep their captured catalog unless the normal explicit-selection recapture occurs. Unknown/deleted historical IDs retain exact-ID fallback, without inferring a provider mapping for an absent source model. An inferred target ID may still match that exact historical ID.

These declarations affect only existing native-history admission gates. Selection, options, tool declarations, prices, journal/canonical attribution, memory identity, route keys, prompt-cache keys and live WS connection/previous-response ownership retain internal identity. Equal `upstreamModelId` values alone do not establish compatibility; no configuration inheritance or cross-protocol conversion is introduced.

### Setup model listing

`SetupProviderRequests.ListAsync` returns `SetupListedModel` entries (`{ id, contextLimit?, maxOutput?, imageInput? }` on the wire) with metadata only when the provider declares it: Anthropic `max_input_tokens`, `max_tokens` and `capabilities.image_input.supported`; OpenRouter-style gateways `context_length`, `top_provider.max_completion_tokens` and `architecture.input_modalities` (image support only from a complete string list). Limits must be positive integers. OpenAI's list has identifiers only. `SetupProviderModelListTests` covers the three shapes. The YAML completion caller uses only `id`; the form's use, including writing `imageInput: false` for models declared text-only, is [D-setup-models-declared-limits](./webui-setup-view.md#d-setup-models-declared-limits).

### First-run key check

**Derived design for the approved first-run proposal ([D-setup-model-oobe](./webui-setup-view.md#d-setup-model-oobe)).** When the active models file does not exist yet, a models installation is rejected with an `InvalidDataException` (shown as the Save error) if any concrete leaf's effective token, after the legacy app-level fallback, matches the placeholder pattern (`your-…`, `…-here`, `replace-me`, `replace-with-…`, `changeme`, `placeholder`, `sk-...`, `sk-xxx`, `xxx`, `<…>`) or is empty while its base URL host is a known hosted service (`api.openai.com`, `api.anthropic.com`, `openrouter.ai`, `api.deepseek.com`, `generativelanguage.googleapis.com`, `api.x.ai`, `api.mistral.ai`, `api.groq.com`, or their subdomains). The file is not written and first-run Setup stays open. Local and unknown endpoints may stay keyless. Once the file exists, saves are not blocked; `Diagnostics()` reports `hasPlaceholderSecrets` / `placeholderProviders` for concrete providers with the same pattern. The WebUI form mirrors both lists in `setupModels.ts`. `ModelConfigurationFailureTests` covers both outcomes and the legacy fallback key.

### Connection, routing and installation

Concrete connection settings retain Source's string fallback: an empty provider `baseUrl` or `apiKey` falls through to the startup app `llm.openaiBaseUrl` / `openaiApiKey` or `llm.anthropicBaseUrl` / `anthropicApiKey`. Empty legacy URLs fall through to the built-in family endpoint; with neither a provider nor a legacy key, the request remains unauthenticated. Nonempty provider strings win without trimming. These are application defaults, not automatic provider-SDK environment readers. Saving app YAML does not replace the captured legacy fallback, even when a later models installation publishes a new catalog; reopening the configuration adopts the saved app settings.

Concrete `contextLimit`, `maxOutput`, and `providerImageOutputFormat` resolve in order from model override, concrete provider, root `defaults`, startup app `llm`, and built-ins (200000, 32768, and `webp`). Every supplied scope validates even when masked. Virtual providers forbid these three fields, and virtual context is the minimum resolved leaf window. Root defaults additionally accept `imageInput`, `retryIntervalsMs` and `textRedaction` under their separate contracts. Unknown provider types are rejected during installation and concrete dispatch; existing OpenAI aliases and empty-type fallback remain supported. Routing fingerprints include effective output and image settings. Physical requests use the selected leaf's max output and input-image format, while provider `extraFields` retain their established wire override precedence.

Concrete `imageInput` resolves from model override, concrete provider, root `defaults`, then built-in `true` (no app `llm` layer); explicit values must be booleans at every scope, and virtual providers and the structured concrete-to-virtual conversion reject/remove it. `ConcreteHostModel.ImageInput` is passed to provider image hydration for each attempt, participates in the routing fingerprint, and is exposed per option in the WebUI model list (`WebUiContract.Models`; virtual options report `true` only when every target does). Request behavior is owned by [D-image-provider-image-input](../threads/image-blob-lifecycle.md#d-image-provider-image-input).

Concrete `asyncCompact` and `disallowEmptyResponse` resolve from model object override, then provider default, then built-in `true` / `false`. Explicit `false` overrides an enabled provider; string model entries and concrete providers without a model list keep provider inheritance. The resolved flags participate in routing fingerprints. Virtual entries cannot set either flag: background compaction eligibility is conservative across all reachable resolved leaves, while each physical request uses its selected leaf's empty-response policy. Ordinary request capture retains those resolved options across a configuration reload; existing explicit selection recapture and compact planning boundaries remain unchanged. The [compaction lifecycle](../threads/compaction-lifecycle.md) owns background admission versus awaited planning and busy rejection.

Virtual selection resolves to a concrete provider before network I/O; failures are attributed to the selected attempt and can enter cooldown. Configuration validation rejects unsupported provider shapes early. Model/effort setters remain ordinary save-lane operations, without notices or actor attribution. At each normal authoritative attempt, after owner retry preparation and concrete routing, `SessionChatService` adopts concrete model, effective Node and normalized effort through `SessionSaveLane.AdoptEffectiveSelectionAsync`. Initial adoption is silent except a missing-model fallback warning. Canonical model/Node changes and changed missing keys create one timestamped settings notice; same-effective aliases, effort-only changes and unattempted away-and-back placement do not. Automatic failover retains its reason. Metadata and any notice share the existing canonical commit/publication boundary; failed preparation cannot become a provider-health failure.

Between eligible retries, an explicitly changed raw model recaptures the live configuration, route generation and effort pair, even for a same-leaf alias. An effort-only edit or ordinary configuration reload does not replace the captured pair. The existing six-physical-attempt loop retains its remaining budget, prompt-cache lineage and committed history; a recapture or newly appended adoption notice refreshes request-owned history and journal/stream identity before serialization. Compact, background-compact and low-level/detached requests have no normal adoption callback. `ModelRequestOwner.RequestAsync` accepts an optional `maxAttempts` (default six); [automatic Session titles](./session-auto-title.md) pass one so a failed title costs a single attempt. Immutable history provenance and per-record journal preparation remain unchanged.

### Retry interval configuration

`models.yaml` `retryIntervalsMs` accepts a nonempty array of integers from 0 through 2147483647 milliseconds. Concrete requests resolve model → provider → root `defaults` → built-in `[2000, 5000, 10000, 20000, 40000, 60000]`. Virtual providers (including shorthand aliases) resolve only their own setting → root `defaults` → built-in; selected leaf intervals never participate, including after failover. Arrays replace the inherited sequence, and retries beyond their length reuse the final entry. Zero retries immediately. Every declared scope validates even when masked. The field is not an app `llm` setting.

The runtime request owner receives `HostModels.GetRetryIntervals` from its live configuration owner. Each eligible failure resolves the selected route key's current interval before publishing its retry notice; that same value drives the cancellable wait. Models saves therefore apply to the next retry wait without restart, including in-flight requests. An already announced wait keeps its deadline. Missing route keys in a subsequently installed catalog fall back to current root defaults rather than another selected model. Requests retain captured provider parameters, route health/generation, attempt budgets and preparation semantics; interval-only changes do not change routing fingerprints. Explicit model recapture changes the lookup key at its existing safe point. Normal, compact, BTW, ToolScript and CLI request owners share this behavior.

`ModelRetryIntervalsTests` covers scope precedence, alias/virtual isolation, validation and live save/rejection, and a real Session retry/failover with live interval adoption while preserving captured leaf options. `RoutingAttemptsTests` covers custom/default sequences, last-entry reuse, notice parity and cancellation.

### Request timing and configuration installation

An adoption-only history refresh preserves the running monotonic response timer across retry backoffs and concrete failover, even when the canonical notice requires a new journal manifest. The successful assistant and journal result share that logical duration; the turn host copies it to only the first tool response. Physical start/failure records remain attempt-local, and `llmAttempt` indexes attempts within the successful manifest rather than counting all sends in the outer loop. Explicit selection recapture and changed retry history (including retained prefixes) retain their existing new-logical-request timer boundary. Tool continuations and later turns invoke a fresh request owner call. The timing consumer contract is [D-pipeline-input-time](../threads/message-processing-pipeline.md#d-pipeline-input-time).

`ModelConfiguration.InstallAsync` serializes native `set_config` and WebUI full-document, structured Models and Weixin login saves in one lane. A structured save reads the latest installed document inside that lane. App candidates additionally share the narrow `PersistAppAsync` section with Weixin command confirmation: candidate read/merge, validation and atomic replacement are ordered in the same owner, then that section is released before access/listener/runtime application. The ordinary install/apply lane remains held for Setup and `set_config`; direct command saves do not acquire it. Validated UTF-8 candidates retain their exact bytes, are installed through a private same-directory atomic replacement, and report committed durability failures separately from validation failures. Models publish the validated live catalog; app access, `sessionAutoTitle` and `agentDefaultNode` publish live after persistence. Other app configuration remains startup-captured. A models save at the first-run transition (no active models file before the save) also seeds a missing `state/config.yaml` from `templates/config.example.yaml`; see [automatic Session titles](./session-auto-title.md#configuration). Result fields distinguish applied models/tool rules/access, unavailable channel runtime work, post-publication connection cleanup failures, and changed startup settings that require restart. With a registered HTTP/MCP owner, MCP identity changes apply live. An all-HTTP-disabled or configuration-only host saves a newly declared MCP surface but reports it not applied and requiring restart; normal startup can then provide the existing transport. The [access unit](./dotnet-access-identities.md) owns this outcome. Before app persistence, access candidates are checked against both active access authority and the current existing administrator token file, including all-HTTP-disabled hosts. Reading that file does not create a missing token or listener. Candidate validation failure leaves the active bytes/catalog unchanged.

Structured Models saves accept a `providers` array or the retained single-provider body. Array drafts choose the first JavaScript-truthy `id`, `providerKey`, or `provider`, then the positional `providerN` fallback, before trimming the chosen key. Single-provider bodies use `providerKey`, `provider`, or `openai` (not top-level `id`), and normalize `models || model` plus the connection/routing fields through the same draft builder. The submitted provider set replaces the old set; each retained provider and model inherits its prior overrides, while top-level extension fields survive. Converting a retained concrete provider to `session-hash` or `failover` removes its concrete-only settings, including `sameProviderAs`, before candidate validation. Single-provider normalization includes omitted connection fields as empty values, matching the TypeScript setup builder's clearing behavior; array drafts retain omitted connection fields. Structured defaults choose the first JavaScript-truthy `defaultModel` or `default`, convert it to a string and trim it, then fall back to the first submitted provider/model if the result is empty. Generated candidates use the ordinary validation/install lane. Raw-YAML saves bypass draft normalization and remain byte-preserving.
