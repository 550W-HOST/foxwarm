# Unit: Model configuration, concrete hosts, and routing

Files: `dotnet/Foxwarm/Models/AppConfigurationRules.cs`, `dotnet/Foxwarm/Models/ConfiguredModelRequests.cs`, `dotnet/Foxwarm/Models/EffectiveRequestSelection.cs`, `dotnet/Foxwarm/Models/HostModels.Resolve.cs`, `dotnet/Foxwarm/Models/HostModels.cs`, `dotnet/Foxwarm/Models/ModelAttemptFailure.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.Form.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.Install.cs`, `dotnet/Foxwarm/Models/ModelConfiguration.cs`, `dotnet/Foxwarm/Models/ModelRequestOwner.cs`, `dotnet/Foxwarm/Models/ModelRequestScope.cs`, `dotnet/Foxwarm/Models/ModelUsageCost.cs`, `dotnet/Foxwarm/Models/ModelRouting.cs`, `dotnet/Foxwarm/Models/ModelRoutingFingerprint.cs`, `dotnet/Foxwarm/Models/SessionModelSettings.cs`, `dotnet/Foxwarm/Models/SetupProviderRequests.cs`

## Purpose

Captures model YAML, derives concrete and virtual hosts, selects failover targets, tracks request owner/scope, and validates setup/configuration forms before a request reaches a provider.

## Stable methods and callers

- `ModelConfiguration` loads/reloads captured config/model paths from `HostPaths` and exposes provider/model limits and setup data. Configured startup locations do not change under a live owner when saved YAML changes its `paths` section.
- `HostModels` resolves configured concrete hosts and virtual aliases; `ConfiguredModelRequests` prepares a request owner and concrete client settings.
- `ModelRouting.Select/RecordFailure/Health` applies deterministic target order, cooldown, and attempt attribution; `ModelRoutingFingerprint` identifies routing prefixes.
- `ModelUsageCost.ValidatePrices/Complete/FormatUsd` validates concrete-leaf rates, settles owned normalized completion usage and formats saved USD estimates under [D-model-usage-cost](../threads/model-request-and-streaming.md#d-model-usage-cost).
- `ModelRequestOwner`, `ModelRequestScope`, and `ModelAttemptFailure` carry owner/attempt lifecycle into retries, streaming, journal, and Session messages. Terminal `ModelRequestException.Scope` retains the failed request origin, including errors propagated through a different request's preparation. Caller cancellation is rechecked after awaited retry-notice delivery before throwing a terminal provider failure.
- `SetupProviderRequests` and `AppConfigurationRules` validate WebUI setup fields without changing active Session authority.

Callers: `SessionChatService`, provider adapters, `SessionModelSettings`, `HttpServer` startup, and WebUI setup routes.

## Contract and side effects

Concrete connection settings retain Source's string fallback: an empty provider `baseUrl` or `apiKey` falls through to the startup app `llm.openaiBaseUrl` / `openaiApiKey` or `llm.anthropicBaseUrl` / `anthropicApiKey`. Empty legacy URLs fall through to the built-in family endpoint; with neither a provider nor a legacy key, the request remains unauthenticated. Nonempty provider strings win without trimming. These are application defaults, not automatic provider-SDK environment readers. Saving app YAML does not replace the captured legacy fallback, even when a later models installation publishes a new catalog; reopening the configuration adopts the saved app settings.

Concrete `contextLimit`, `maxOutput`, and `providerImageOutputFormat` resolve in order from model override, concrete provider, root `defaults`, startup app `llm`, and built-ins (200000, 32768, and `webp`). Every supplied scope validates even when masked; root defaults allow only these fields, virtual providers forbid them, and virtual context is the minimum resolved leaf window. Unknown provider types are rejected during installation and concrete dispatch; existing OpenAI aliases and empty-type fallback remain supported. Routing fingerprints include effective output and image settings. Physical requests use the selected leaf's max output and input-image format, while provider `extraFields` retain their established wire override precedence.

Virtual selection resolves to a concrete provider before network I/O; failures are attributed to the selected attempt and can enter cooldown. Configuration validation rejects unsupported provider shapes early. Model/effort setters remain ordinary save-lane operations, without notices or actor attribution. At each normal authoritative attempt, after owner retry preparation and concrete routing, `SessionChatService` adopts concrete model, effective Node and normalized effort through `SessionSaveLane.AdoptEffectiveSelectionAsync`. Initial adoption is silent except a missing-model fallback warning. Canonical model/Node changes and changed missing keys create one timestamped settings notice; same-effective aliases, effort-only changes and unattempted away-and-back placement do not. Automatic failover retains its reason. Metadata and any notice share the existing canonical commit/publication boundary; failed preparation cannot become a provider-health failure.

Between eligible retries, an explicitly changed raw model recaptures the live configuration, route generation and effort pair, even for a same-leaf alias. An effort-only edit or ordinary configuration reload does not replace the captured pair. The existing six-physical-attempt loop retains its remaining budget, prompt-cache lineage and committed history; a recapture or newly appended adoption notice refreshes request-owned history and journal/stream identity before serialization. Compact, background-compact and low-level/detached requests have no normal adoption callback. Immutable history provenance and per-record journal preparation remain unchanged.

An adoption-only history refresh preserves the running monotonic response timer across retry backoffs and concrete failover, even when the canonical notice requires a new journal manifest. The successful assistant and journal result share that logical duration; the turn host copies it to only the first tool response. Physical start/failure records remain attempt-local, and `llmAttempt` indexes attempts within the successful manifest rather than counting all sends in the outer loop. Explicit selection recapture, changed retry history (including retained prefixes), and changed request-only Task context retain their existing new-logical-request timer boundary. Tool continuations and later turns invoke a fresh request owner call. The timing consumer contract is [D-pipeline-input-time](../threads/message-processing-pipeline.md#d-pipeline-input-time).

`ModelConfiguration.InstallAsync` serializes native `set_config` and WebUI full-document, structured Models and Weixin login saves in one lane. A structured save reads the latest installed document inside that lane. App candidates additionally share the narrow `PersistAppAsync` section with Weixin command confirmation: candidate read/merge, validation and atomic replacement are ordered in the same owner, then that section is released before access/listener/runtime application. The ordinary install/apply lane remains held for Setup and `set_config`; direct command saves do not acquire it. Validated UTF-8 candidates retain their exact bytes, are installed through a private same-directory atomic replacement, and report committed durability failures separately from validation failures. Models publish the validated live catalog; app access publishes the shared live snapshot after persistence. Other app configuration remains startup-captured. Result fields distinguish applied models/tool rules/access, unavailable channel runtime work, post-publication connection cleanup failures, and changed startup settings that require restart. With a registered HTTP/MCP owner, MCP identity changes apply live. An all-HTTP-disabled or configuration-only host saves a newly declared MCP surface but reports it not applied and requiring restart; normal startup can then provide the existing transport. The [access unit](./dotnet-access-identities.md) owns this outcome. Before app persistence, access candidates are checked against both active access authority and the current existing administrator token file, including all-HTTP-disabled hosts. Reading that file does not create a missing token or listener. Candidate validation failure leaves the active bytes/catalog unchanged.

Structured Models saves accept a `providers` array or the retained single-provider body. Array drafts choose the first JavaScript-truthy `id`, `providerKey`, or `provider`, then the positional `providerN` fallback, before trimming the chosen key. Single-provider bodies use `providerKey`, `provider`, or `openai` (not top-level `id`), and normalize `models || model` plus the connection/routing fields through the same draft builder. The submitted provider set replaces the old set; each retained provider and model inherits its prior overrides, while top-level extension fields survive. Single-provider normalization includes omitted connection fields as empty values, matching the TypeScript setup builder's clearing behavior; array drafts retain omitted connection fields. Structured defaults choose the first JavaScript-truthy `defaultModel` or `default`, convert it to a string and trim it, then fall back to the first submitted provider/model if the result is empty. Generated candidates use the ordinary validation/install lane. Raw-YAML saves bypass draft normalization and remain byte-preserving.
