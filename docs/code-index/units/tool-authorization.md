# Unit: Tool authorization and isolation compatibility

Files: `dotnet/Foxwarm/Tools/Authorization/AgentRulePolicy.cs`, `dotnet/Foxwarm/Tools/Authorization/IsolatedToolCompatibility.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationAuthority.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationEvaluation.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationExplain.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationPolicy.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationToolDefinition.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationYaml.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolAuthorizationYamlGraph.cs`, `dotnet/Foxwarm/Sessions/SessionManager.AuthorizationExplain.cs`, `dotnet/Foxwarm/Tools/Authorization/ToolApprovalScope.cs`, `dotnet/Foxwarm/Sessions/SessionManager.Approvals.cs`

## Purpose

Loads the authority YAML/graph, evaluates allow/ask/deny effects and path scopes, gates ask outcomes on an approval, emits authorization tool definitions, and preserves compatibility with isolated Node/tool policies.

## Stable methods and callers

`ToolAuthorizationAuthority.Load/Reload` parses the canonical authority graph; `ToolAuthorizationPolicy` resolves tool/path/effect matches; `ToolAuthorizationEvaluation` returns the decision, matched rule, scope, and explanation used by `ToolRegistry`/`SessionToolExecutor`; YAML graph types preserve inheritance/agent/tool rule edges. `IsolatedToolCompatibility` translates only the supported remote/isolation shape.

## Contract and side effects

Every executable local/MCP/Node capability enters authorization before dispatch. Rules provide tool authorization, not OS/network sandboxing; a remote Node's protocol capability still requires an allowed Main-side boundary. Deny/ambiguous/invalid graphs fail closed, while read-only definition discovery may report unavailable tools without invoking them.

File transfer consumers retain their actual builtin identities. Copy supplies separate `sourcePath`/`targetPath` facts with each endpoint's Node; Main paths resolve from that Agent directory and remote facts stay unresolved. Copy/image/send do not require additional ordinary Node read/write grants. Remote ToolScript source retains its existing concrete Node read authorization. Isolated copy permits only Main own-Agent paths and its bound/current Node; explicit builtin grants do not bypass Main path, unrelated-Node or destination-Session checks. Canonical consumer contract: [External Node files](./external-node-files.md).

The hidden `node_create_auth_token` builtin uses absolute Main `filePath` facts, including when execution placement is remote. Existing generic path policy and the independent isolated-Agent own-directory boundary apply; an exact builtin grant does not authorize unrelated Main paths or require a remote write grant.

The non-default setter is `set_config` with required `target` (`config`, `models`, or `tool-rules`) and `filePath`. There is no obsolete `set_tool_rules` command alias. Persisted generic policies that explicitly name that removed builtin fail validation with migration guidance toward deliberate `set_config` target restrictions; exact isolated metadata receives explicit migration guidance rather than an unconstrained replacement. The new setter retains the independent isolation/path/authority boundaries.

The captured `${workspace}` base is the configured Agents directory for canonical installs. Retained main-at-workspace callers keep their original policy scope. The isolated-main nested `agents` exclusion applies only to that retained layout, where it protects sibling Agent directories; a canonical main Agent may use an ordinary `main/agents` subdirectory. Generic path rules, physical resolution and isolated own-directory checks remain independent of membership and startup layout.

`browser_*` tools have no tool-specific authorization: master's browser capabilities follow the ordinary bound-Node fence, generic policy and caller-current versus explicit Node facts like any other Node tool. Persisted exact rules that name the retired `browse_*` tools still load and no longer match anything. See the [managed browser host](./browser-host.md#hosting).

The hidden Archive message and block tools retain an independent same-Agent read guard for isolated callers, in addition to generic policy. The shared handler resolves live catalog identity and aliases first; absent live membership uses Source's requested-ID Agent fallback. It checks before reading retained Archive data, without hydrating a target owner or requiring its Node to be online. Clear/deletion retain Archive records and do not relax this boundary; an exact capability allow cannot bypass it. Nonisolated callers retain selected-target reads, and missing permitted targets remain pure empty reads.

## Ask outcome and approvals

Governing decision: [D-dispatch-approval-ask](../threads/tool-dispatch-authorization.md#d-dispatch-approval-ask).

**Grammar.** `action` and `defaultAction` accept `ask`. A rule may add `approval: {timeoutSeconds, approvers}`, valid only with ask: `timeoutSeconds` is an integer from 30 to 604800, `approvers` holds 1–64 access identity IDs (duplicates removed). Ask combined with an `externalId` selector is a parse error, because external principals cannot wait. Agent layers accept the same action and `approval` shape.

**Decision.** `AuthorizationDecision.Effect` is `Allow`, `Ask` or `Deny`; `Allowed` means `Effect == Allow`, so every consumer that only reads `Allowed` fails closed on ask. Layers combine deny over ask over allow. The combined approval options use the shortest timeout and the approvers named by every asking layer. For external principals a matching ask rule and an ask default are deny. Discovery (`Visible`) treats ask as a possible allow for internal callers. `EvaluateCreationTarget` reports `Ask` when ask is the only possible outcome and indeterminate when ask mixes with allow; timer registration rejects both.

**Enforcement order.** `AuthorizeToolAsync` throws for a denying layer, then applies legacy isolation, and only then throws `ToolApprovalRequiredException` for ask unless the current `ToolApprovalScope` covers the request. Only `SessionToolExecutor.AuthorizeAsync`, the dispatch gate of the call's own invocation, turns that exception into a request; every other check (effect-owner rechecks, sub-capability reads, nested steps) fails closed with `tool_approval_unavailable`.

**Grant.** Each invocation has its own AsyncLocal `ToolApprovalScope`. After approval the gate stores a grant bound to a fingerprint of the approved call (source, name, MCP server, execution Node, arguments, path facts, Node targets, Session target and Task owner; not the Session ID) and authorizes again against the current policy, so a deny installed during the wait wins. A recheck of the primary call compares the fingerprint; internal steps of that invocation are covered without comparison. If the facts no longer match, the gate requests approval again, at most three times in total, then fails. Nested ToolScript calls are separate invocations and never inherit an outer grant. Effect work that leaves the invocation's flow (the detached transfer task of `copy_between_nodes`, MCP notification reception callbacks) must carry the grant explicitly: it captures `ToolApprovalScope.Detach(owner)` while still in the invocation and enters that scope itself, where every check is an internal step of the approved call. The ambient value never reaches suppressed-flow or later-scheduled work, so such work without the explicit scope fails closed. MCP notification reception continues under ask only when the reception start was approved.

**Records and waiting.** `SessionManager.BeginToolApprovalAsync` registers a live waiter and commits a pending record through the questions save lane; `AwaitToolApprovalAsync` settles it on decision, deadline or cancellation with one first-wins transition; `DecideToolApprovalAsync` is the approver entry. Record shape, limits and routes belong to [Session questions](./session-questions.md#tool-approvals). Rejected and expired calls return `tool_approval_rejected` / `tool_approval_expired` with `approvalId` (and the note on rejection); an approved call's result carries `approvalNote` beside the model-facing value. Stop returns the existing not-started cancellation receipt. The record ends with what happened to the call: an approved call that never dispatches (Stop or shutdown after the decision, a deny installed during the wait, a skipped exec segment member) moves from `approved` to `cancelled`, keeping the approver as `approvedBy`. A cancellation that loses the race to an approval settles the same way. Model-facing wording is coordinator-owned copy.

## Agent-local authorization layers

The requested Agent rules tree adds ordered local v1 rule arrays to the global policy, using the approved creator-chain/intersection design. `AgentRulePolicy.Parse` reuses the v1 normalizer and rejects caller `agent`, `session`, `sessionPattern` and `externalId` selectors in both authored selector styles. Registered target Session/Task matchers remain available. An unmatched local layer passes; an explicit selector-free final deny expresses an allowlist. A local allow passes only its own layer.

`SessionManager.Authorization` captures the initiating Agent's complete root-to-initiator layers from one current catalog snapshot, evaluates the global policy first, then requires every local layer to pass. It retains the same initiating Session, Agent directories, current Node, request and canonical relationship facts across all layers. Target and Task-owner facts are populated when any effective layer needs them. Missing/cyclic creator chains and invalid local rules reject execution and discovery; configured admission limits never truncate an existing chain. The catalog setter publishes immediately, independently of memory snapshots and the global YAML loader's timed cache.

Default injection and `search_tools` use the same conservative per-layer visibility projection. Notification reception reuses the effective internal policy and current facts on each reception check; ordinary inbound MCP principals remain Agent-less and global-policy-only. Legacy isolation and handler-local guards continue after effective generic authorization. See [creator metadata and lifecycle](./session-domain.md#agent-creator-metadata-and-admission) for persistence and management authority.

Existing global caller `agent: A` selectors continue matching the actual initiator only; they do not begin matching creator descendants. Migration must deliberately move subtree restrictions into A's local layer rather than rewriting global first-match order automatically. The existing isolated-rule generator produces a review candidate, not parity or an automatic installation: exact grants, stored timer targets, incoming relationships, attachment placement and default Node routing require separate inventory. New/old checks coexist; no installation migration or isolation retirement is implicit. Older Main versions that ignore Agent layers are unsafe readers of an installation using them; deployment or downgrade requires an explicit compatible-version/state decision.

## Renamed Session observation policy identity

The executable builtin is `view_session`. Persisted generic selectors naming `get_session_messages` still match the new builtin through `ToolMatches`, including scalar/list and name equals/oneOf forms. Ordered rules, argument/actor scopes and target-resolver families remain intact; MCP/Node tools with the old name retain their own identities. This read compatibility does not register an executable alias or rewrite authored automation. Exact Agent metadata reads normalize the old builtin rule identity to the new one; duplicate identities fail closed. Independent structural isolation continues to deny Session observation even with an exact allow. The stable inbound `foxwarm_session(action:read)` uses this policy identity with its external principal and canonical target, while sharing active-history page selection with the internal reader. Its retained response fields and additive version/navigation contract belong to [ordinary inbound MCP](./dotnet-inbound-mcp.md#concrete-catalog-and-retained-effects). Maintained scripts must call the new builtin; stored executable scripts need deliberate owner updates rather than source substitution.

## Policy selectors and authoritative facts

Main path facts name physical destinations: home expansion is followed by real symlink resolution through the nearest existing ancestor before any missing suffix is appended. Path-policy expectations use filesystem evidence for a symlinked home rather than its lexical profile alias.

Version-1 rules accept either legacy `match` or top-level selectors, never both. Omitted IDs become position-based `rule-N` diagnostics. Top-level Session/Node identity selectors use bounded literal `*` patterns; legacy `match.session`, scalar/argument matchers, ordered first-match evaluation and external-default-deny remain unchanged. Node selectors use the [authorization forest contract](../behaviors/nodes-workspaces-and-permissions.md#node-authorization-forests): bare IDs/patterns cover matching ancestors, `{exact}` covers the endpoint only, and caller-current or exact Provider IDs retain their meanings: native Main is `master`, authenticated native remotes are `authenticated-remote`. The matcher syntax does not create a Provider backend or widen native Node registration.

`ToolAuthorizationNodeEffects.Resolve` registers actual Node effects separately from legacy `TargetNode` and exact caller `CurrentNode`. Node capabilities and file/image delivery contribute one endpoint; copy contributes both; concrete builtin Node select/inspect/destroy and native removal contribute their argument targets. Native credential creation contributes its explicit parent; Session-owned executable create/fresh ensure uses the configured parent and existing ensure uses its existing identity. Registry ancestry snapshots accompany both internal effective-policy and ordinary external-global requests.

Concrete Session policy evaluation resolves any missing executable endpoint inventory before taking the effective snapshot, including compound builtin files and their separately authorized source reads. A provider identity left unadmitted cannot pass this stage; the original capability, caller, arguments, paths and complete endpoint list remain the authorization facts. Read-only Node metadata inspection keeps its nonblocking exception; [provider admission](./dotnet-node-providers.md#ancestry-admission-and-lifecycle) still fences unadmitted executable capabilities. Explicit ensure resolves its requested identity through the existing provider admission path before the first decisive Node policy check, and its effect owner repeats authorization with the final existing/fresh facts.

Unrelated Main/MCP tools, arbitrary `nodeId` arguments and the ToolScript VM/source placement do not acquire Node facts. Allow requires all actual endpoints; deny matches any. Unknown builtin endpoint selectors remain conditional in discovery without inventory enumeration. Session and inbound external MCP callers construct facts through their existing authority owners; external contexts never become internal/current-Node principals.

Session-target matchers use the builtin/argument pairs registered by `ToolAuthorizationPolicy.TargetResolvers`. Existing Session tools retain their `sessionId` resolver families; builtin `task` additionally accepts `args.ownerSessionId: {session: {relation: parent}}` and the existing self/same-Agent/child conditions. `SessionManager.PopulateAuthorizationTargets` resolves canonical identities, aliases and relationships from the live catalog without hydrating a target owner. The Task resolver supplies no Session fact for omitted, null, blank, non-string or unknown owner targets. Rules must select registered builtin tools with the same argument and resolver family; same-name MCP/Node tools and other Task fields cannot use this matcher. External principals never match internal Session relationships. Combining `args.action: create` with the parent matcher expresses a narrow parent-assignment grant; no permission is enabled by the framework itself.

The exact builtin `task` selector may use `args.taskId: {task: {owned: true}}`. `SessionManager.AuthorizeToolAsync` resolves current canonical ownership through `TaskService.OwnerSessionId`/`TaskStore.OwnerSessionId`, then the Session catalog, on each real evaluation. Proposed owner arguments never establish ownership. Missing/unowned/other-owned Tasks and external principals do not match. This optional policy fact does not change shared Task get/description/note authority or introduce a new mutation transaction.

### Session creation Agent targets

Exact builtin `create_session` rules accept `args.agentName: {agent: {sameAgent: true | false}}`. The comparison uses a nonempty string target and the internal caller's authoritative Agent, not the owner of a timer, creator ancestry or a Session-ID prefix. Missing/non-string targets and external principals match neither value. Existing scalar arguments and Session relationship matchers retain their meanings; other builtins and same-name MCP/Node tools cannot use this Agent matcher.

`EvaluateCreationTarget` is a timer-only precheck of the same ordered generic policy. Caller/tool/Agent facts are known; other creation arguments are unknown, not supplied as absent or invented values. Each unknown condition retains its possible first-match effect until a decisive rule or default. All possible effects must allow in each global/Agent layer; any definite denial rejects, and mixed outcomes report indeterminate authorization. Ordinary `Evaluate` and discovery keep their existing semantics. The caller-facing boundary and persistence exclusions belong to [scheduled work](../behaviors/automation-and-scheduled-work.md#schedule-a-message-or-execute-a-quiet-script).

## Authorization explanation

`SessionManager.AssessToolAsync` is the single fact-construction and per-layer evaluation path. `AuthorizeToolAsync` enforces its first denying layer, then legacy isolation, then an uncovered ask outcome; nothing else re-evaluates policy. The governing decision is [D-dispatch-authorization-explanation](../threads/tool-dispatch-authorization.md#d-dispatch-authorization-explanation).

Hidden builtin `explain_tool_authorization` accepts 1–32 probes. Each probe names an existing caller Session and a `call_tool`-shaped target; the target is resolved by `ToolRegistry.Resolve("call_tool", …)` at that Session's current Node and evaluated with its own Agent, cwd workspace and catalog relations. There is no Agent-only hypothetical caller. Each probe variant reports `decision` (`allow`, `ask`, `deny`); `allowed` is true only for allow, and ask adds `askedBy: "policy"` and the combined `approval` options. A probe reports pre-policy Node/path boundary denials as `precheck` with decision deny; otherwise every layer's `decision` with rule position, ID, action, reason and normalized match (or the default), the isolation result, and the request facts. Handler-local validation, external-runtime support and service availability are not evaluated. Per-probe resolution errors are returned inside that probe.

The caller needs the generic grant for the builtin plus `node:master/read` of the active policy path, and of `policyFilePath` when supplied; a probe of another Session additionally requires the caller’s `view_session` authorization against that concrete Session, while a probe of the caller’s own Session does not. Unauthorized, unavailable and nonexistent Session probes return the same error, including when policy becomes unavailable during the foreign-Session view check; this fails the probe closed. Self references follow the catalog's exact-ID-before-alias resolution. The candidate is captured like a `set_config` candidate and parsed strictly, but never installed. The candidate replaces only the global layer; Agent layers and isolation stay current. With `compare`, each probe carries `active`, `candidate` and `changed` (final decision differs), and `ruleDiff` compares normalized rules by ID: `added`, `removed`, `changed`, and `moved` (common IDs outside a longest common subsequence of the two orders), plus a changed `defaultAction`. Position IDs (`rule-N`) of rules without explicit IDs are not stable across insertions.
