## Contract and decision

### D-node-android-on-device

[2026-11-15, user decision] Android Node runs as an on-phone app, replacing the unpublished host-side ADB/Python implementation. The first deliverable is a sideloadable APK for physical-phone testing. Release distribution and signing follow the [Android release contract](./release-packages.md#android-node-apk). The app uses the existing per-Node trust and ordinary tool protocol, with an accessibility service and a persistent foreground connection service.

The app requires API 30 (Android 11), targets API 35 and uses `AccessibilityService.takeScreenshot`; there is no MediaProjection consent flow. QR scanning uses ZXing without Google Play Services. It advertises core protocol 1–3 and no backend services or external-owner features. The existing [protocol negotiation](../threads/node-communication.md#d-node-thread-core-protocol-compatibility) remains authoritative.

## Pairing and lifecycle

The administrator's existing explicit `onboarding/create` response carries `androidPairing`: `{type:"foxwarm-node", version:1, baseUrl, nodeId, authToken}`. This serializes the same one-time per-Node credential used by the other clients; it introduces no authentication scheme. WebUI renders the JSON as a QR code and displays the equivalent manual fields. The app validates the address and payload, saves the three fields in private preferences with backup/transfer disabled, and builds a deployment-prefixed `/node_ws?id=…&auth=…` URL. The setup Activity blocks screenshots and never saves credential fields in Activity instance state.

`MainActivity` owns scanning, manual entry, connection controls and links to accessibility, App info/restricted settings and battery optimisation. User-started `NodeService` owns the `specialUse` foreground notification and Stop action, saved desired-running state and sticky process restart. Connection controls reflect the live service rather than the persisted desire to run, so reopening after force-stop or reboot permits Connect. There is no boot receiver.

`NodeClient` is Android-independent production Kotlin using OkHttp. A serial scheduled lane owns connection generation, registration, exponential one-to-sixty-second retry and status. A separate serial tool executor prevents device calls from blocking heartbeat. Native WebSocket ping/pong and server JSON ping are supported. Work waits for valid registration; stale sockets cannot start queued work or send successor replies. Incompatible/malformed registration quarantines application work while retaining heartbeat, and does not reconnect after closure. Rejected credentials require operator action. Status strings omit socket URLs, credentials and raw transport exceptions.

## Device actions and image result

`DeviceAccessibilityService` dispatches actions on the Android main thread and waits on the tool lane for gesture/screenshot completion. It reads the active window, recycles acquired nodes and returns bounded tree/list results with truncation indicators. Password text is omitted. Exact text/resource-ID selectors require one visible match; exceeding the traversal bound fails selection instead of using an incomplete uniqueness check.

The 14 base `android_*` tools cover tree/list, coordinate or element tap, long press, double tap, swipe, focused/resource-ID text replacement, navigation, active package, package launch, screenshot, wake, lock and device state. Bounds and gesture coordinates are screen pixels. `NodeProtocol.tools` is the declared tool schema; `execute` supplies the same actions. `ScreenGestures` gives double taps two non-overlapping strokes in one gesture with a configurable end-to-start interval. No arbitrary shell, force-stop or install tool is exposed.

`WakeActivity` is a private, transparent Activity using `setShowWhenLocked`, `setTurnScreenOn` and `requestDismissKeyguard`. Android supplies dismissed/cancelled/error callbacks; the bridge reports `bouncer_shown` only after finding a numeric pad, otherwise a pending request is `dismissal_requested`. The Activity expires after 20 seconds. An off-screen fallback uses a timeout-bounded wake lock. `android_device_state` reads `PowerManager.isInteractive`, `KeyguardManager.isKeyguardLocked`/`isDeviceSecure` and the active package without needing a screenshot. `android_lock` uses `GLOBAL_ACTION_LOCK_SCREEN`. See `packages/android-node/LOCKSCREEN.md` for the API 30–35 background-launch permission chain.

### D-android-local-pin-unlock

[2026-11-16, user decision] Numeric PIN unlock is an explicit on-device opt-in, off by default. The PIN never leaves the phone. `PinSettingsActivity` requires Android screen-lock confirmation before exposing settings and suspends this app's remote device tools throughout confirmation and editing. PIN entry is `FLAG_SECURE`, excluded from saved state/autofill/accessibility and never displays the stored PIN. Patterns, passwords and biometrics are unsupported.

`PinStore` encrypts the PIN using an Android Keystore AES-GCM key and private, backup-excluded preferences. `PinUnlocker` consumes the persisted attempt permission before device effects, wakes the phone, waits for the pad, clicks digit accessibility nodes, confirms if needed, and checks keyguard disappearance. `KeyguardPinPad` searches only `com.android.systemui`, preferring resource IDs to text/content-description matches, requiring unique clickable targets and refusing prefilled password input and known SIM PIN/PUK challenges. It never returns input text. After any unsuccessful/interrupted attempt, further calls refuse until the PIN is re-entered through protected settings; there is no retry loop. Successful verification restores attempt permission.

`android_unlock` is declared only while enabled. `NodeService` observes private setting changes, and `NodeClient.setUnlockEnabled` reconnects only when the enabled boolean changes, because Main ignores repeated registration frames on an existing socket. PIN edits, attempt state and periodic UI refreshes do not change capabilities. Execution separately checks enabled/refusal state.

Screenshots close the hardware buffer, copy into a software bitmap, JPEG-encode at quality 80 and recycle both bitmaps. `NodeProtocol.screenshot` emits the current `{output, width, height, inlineData:{mimeType,data}}` image result. The output preserves original screen dimensions for coordinate mapping after Main's vision resizing. Protected screens and unsupported accessibility actions report errors. The app's own credential setup screen is protected.

## Build and evidence owners

The Gradle wrapper pins 8.11.1; AGP 8.9.2 and Kotlin 2.1.10 build with JDK 17 and SDK 35. `app:assembleDebug` uses the committed public debug-only keystore in `packages/android-node/signing/`, the application ID `io.foxwarm.android.debug`, and the label Foxwarm Node (Debug). Debug builds from different workspaces upgrade the same debug installation; the unsuffixed release identity remains separate. The public debug key must never sign releases. Version names and monotonic version codes come from the root release version through `app/build.gradle.kts`; signing and non-tag qualification are owned by the [release workflow](./release-packages.md#android-node-apk). The Android CI job runs core JVM tests, Robolectric lifecycle tests, lint, APK assembly and the owned Main integration driver; it uploads the APK and test reports without release secrets.

Robolectric runs offline. Left alone, it downloads `android-all-instrumented` runtime jars over HTTP from inside the test JVM, outside Gradle's retries and dependency cache, and one failed download fails every test on that SDK. Instead, `app/build.gradle.kts` resolves the jars as Gradle dependencies, each in its own configuration so conflict resolution can't merge the two versions of the module. It syncs them into `app/build/robolectric-android-all` and gives `Test` tasks `robolectric.offline=true` with that `robolectric.dependency.dir`. Each sandbox needs two jars: the runtime SDK from `@Config` (30) and Robolectric's newest SDK supported by the test JDK (35), which serves as the compile-time resource SDK. The jar versions come from Robolectric's `DefaultSdkProvider` table. Update them with the Robolectric version, and add a jar whenever a test uses another SDK level. A missing jar fails with `Path is not a file` and doesn't fall back to a download.
