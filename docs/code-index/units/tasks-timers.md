# Unit: Task service and timer scheduler

Files: `dotnet/Foxwarm/Sessions/TaskProgress.cs`, `dotnet/Foxwarm/Sessions/TaskService.cs`, `dotnet/Foxwarm/Sessions/TaskStore.cs`, `dotnet/Foxwarm/Timers/CronFields.cs`, `dotnet/Foxwarm/Timers/CronLocalDate.cs`, `dotnet/Foxwarm/Timers/CronSchedule.cs`, `dotnet/Foxwarm/Timers/MainTimers.Crud.cs`, `dotnet/Foxwarm/Timers/MainTimers.Scheduler.cs`, `dotnet/Foxwarm/Timers/MainTimers.Store.cs`, `dotnet/Foxwarm/Timers/TimerArguments.cs`

## Purpose

Persists current task authority/notifications and progress checkpoints, parses cron schedules, and schedules Main timers with explicit CRUD and restart behavior.

## Stable methods and callers

- `TaskProgress.Sequences` and `TaskProgress.IsOrdinaryVisible` define the ordinary-visible sequence input used by model requests and compaction checkpoints. `TaskStore.Execute` owns task records, owner/assignee, parent linkage, status/result/description, notification state, and durable CRUD. `TaskStore.MigrateLegacyGoal` creates/updates one legacy Goal task; `TaskStore.TaskContext` checkpoints reminder progress and returns due task context without appending Session history or queue rows. The method accepts an optional live `anchorSeq` to create/claim/self-assignment/open/active/reset updates so reminder progress is anchored to the source Session message sequence.
- `TaskService.ExecuteAsync` resolves a live actor anchor when available; tool execution passes `source.Entry.Snapshot().NextMessageSeq - 1`, while the HTTP/API path reads the persisted Session authority anchor and does not hydrate a cold catalog member. `ExecuteAsUserAsync` handles authenticated WebUI create/comment/assign actions without inventing a Session actor. The service keeps the full mutation result for trusted completion/assignment facts while model-facing task mutations expose only the short receipt; task notification delivery remains service-owned.
- `MainTimers.CreateAsync`, `UpdateAsync`, `MainTimers.Store.LoadAsync`, and the scheduler’s `RunClockAsync` create/update/load and deliver timer records; delivery enqueues the declared Session operation after due-time/schedule validation.
- `RunClockAsync` starts with suppressed execution-context flow, before synchronous or delayed delivery. Independently fired timers cannot borrow the registering model turn, cancellation, mutation admission or Agent-command settlement scope. Normal message queue delivery and clock/completion tracking retain their owners.
- `CronFields`, `CronLocalDate`, `CronSchedule`, and `TimerArguments.Normalize` own parsing/next-occurrence semantics and argument validation.

Callers: `SessionManager.Tasks/Timers`, `WebUIChannel.Tasks`, timer/task tools, process startup, and WebUI TasksView.

## Contract and side effects

The turn host also marks a terminal tool batch in `ChatResult`; `LocalSessionTurnHost` returns `Terminal=true` and `SessionTurnRunner` exits the outer provider loop before later passive-only follow-up admission can start another provider turn. Runnable/release boundaries still decide whether a later active item should run.

Task authority/service/API/UI work includes legacy Goal migration on owner saves, request-only Task progress, compaction checkpoints, task-linked child creation, and `TaskStore.AttachChild` attachment after owner assignment. Task IDs created by current writers use the `task_` plus 12 lowercase hexadecimal character form; older IDs remain readable. Task records and notes retain explicit `createdByKind`/`authorKind` provenance, with nullable Session IDs for authenticated user actions. `TaskStore.Validate` requires explicit `ownerSessionId` on assign (with explicit null for release) and a boolean `notifySession` whenever supplied; WebUI user mutations accept bounded 20,000-character descriptions/results and 1,000-character notes. `create_child_session.taskId` preflights creator/current-owner authority, creates and assigns the child under the TaskService mutation lane, attaches it, then delivers one full assignment notice outside that lane; failed delivery preserves the committed child/task and does not arm wait/finish postactions. Full assignment descriptions bypass the bounded list/get preview. Completion notices deliver the full accepted stored result, without a separate notification-result cap; list previews and previous-owner summaries remain bounded. Completion commits before notification status is recorded, and reopening does not replay completion or permit another terminal completion. Model-facing values and trusted completion identity remain separate, as described below. Task notices use task metadata wrappers without creating peer-report relations or child-handoff boundaries; user notices carry explicit user provenance. Persisted child-handoff boundaries resolve only from consumed canonical queue items or trusted parent-send/attached-task receipts; arbitrary tool/script output is not a receipt. Timer admission and internal wait clocks remain Main-owned for external placement, even offline. New timer-created Sessions preserve captured/bound Node placement, including explicit master. Legacy persisted timers with no Node use the same omitted-selection Agent-main fallback as named creation; actual remote effects still require that Node. Timer due calculation is persisted and restart-aware; a timer enqueue still follows queue admission semantics and must not be represented as a completed model turn.

The service mutation lane coordinates Task mutations with child preflight, creation and attachment. Reads query the store without this lane. Awaited notification delivery and outcome recording run after its release, so a held recipient save cannot block unrelated Task operations. Assignment notices use the captured mutation fields and full stored description captured inside the lane; completion notices use the captured completion result. A later mutation may overtake delivery, while the existing store revision fence prevents an older assignment receipt from settling the newer revision. Post-delivery response refreshes retain current Task detail and do not supply notification bodies. Store monitor/transaction ownership remains independent.

An authorized other Session may replace description, add a note, or combine both on an open/active task only when the update has no status property. Status, ownership, terminal and tool-policy rules retain the existing TaskStore/TaskService owners; a status property does not become shared authority even when its value is unchanged.

Model `task.list` defaults to creator-or-owner `current-session`; `owned` filters only canonical current ownership, including aliases and moved Session references, without enumerating the Agent. `current-agent` matches tasks created by or assigned to any Session in the actor's Agent, while `all` preserves global listing. Scope resolution uses catalog identities/aliases without admitting semantic owners. HTTP/user task listing remains global by default. Non-owner update notes notify only with `notifySession:true`; omission/false still saves the note silently. Service-owned notification receipts increment `sentNotifications` only after actual accepted delivery, including linked child assignment/previous-owner and completion notices. Native task output and send/child receipts support merged Activity parsing; arbitrary nested script/tool values do not create trusted counts.

### Native model-facing Task results

`SessionToolExecutor.ExecuteTaskAsync` returns native model-facing JSON: mutations expose `taskId`, `status`, `ownerSessionId`, `sentNotifications` and only an actual postcommit warning; get/list preserve their detail/summary objects. Direct, unified and ordinary nested ToolScript calls receive those values without an output-string envelope or JSON decoding. Trusted completion identity still comes separately from the full service result through `TurnToolReceipt`, never from visible return fields. Generic tool/provider formatting presents these objects without task-specific rendering.

## Owner-bound ToolScript timers

Records without `action` remain message timers. `action: toolscript` stores the complete normal starter specification, normalized by `MainToolScript.NormalizeStartArgs` without file I/O. `TimerArguments.PutAction` shares that parser with ordinary run startup. A supplied `script` replaces the whole specification; changing actions requires the new payload and clears incompatible message/script and new-Session settings. Create resolves the caller's canonical owner; update trims the timer ID before both lookup and ownership checks, including inherited script actions. A permitted message target cannot grant authority to configure code for another Session.

At fire, `SessionManager.DeliverTimerAsync` resolves the current existing exact owner and uses an independent `SessionToolExecutor` with unattended caller control. It runs the ordinary authorized `run_script` path, including the current source Node/cwd capture, full file reread and independent read authorization. The source Node supplies input, not VM placement or nested-tool defaults. Monty, nested dispatch and run persistence are the ordinary Main-local implementations; no script queue item, ordinary tool/history row, foreground abort slot, foreground ToolScript progress, automatic notification or paused-run resumption is added. Explicit tool effects, one-shot model requests and exec completion remain ordinary. Deferred waits and send post-actions have no caller model turn to control; a saved timeout wait intent remains available to an explicit manual continuation.

The scheduler reserves one script invocation per timer ID before owner admission. Overlapping cron ticks skip without backlog, and the next recurrence is calculated from the current clock rather than replaying missed ticks. Completion, failure or pause ends an initial slice. Cron retains its record and attempted `lastTriggeredAt`; once removes only the captured record. Updates/deletes cannot reverse accepted effects or let an old successful/failed delivery consume a replacement. An overdue once script replacement waits for the previous invocation's release. Message delivery retains successful-delivery timestamp semantics and the same captured-record guard on success and failure.

`StopFuture` closes admission and cancels future clocks; disposal drains accepted slices before ToolScript/services close. Only an already accepted scheduler delivery can request the narrow closing-time owner admission path; it does not borrow a foreground settlement scope or reopen runner admission. A cold accepted owner can finish admission and publish a fenced runner during this drain. The exact-owner mutation admission covers only initial identity/deletion validation, not native execution: a surviving child may use ordinary nested deletion to remove its parent without waiting on its own slice. Accepted-slice shutdown drain belongs to the scheduler, while nested effects retain their ordinary owner admissions. Existing best-effort restart semantics remain: overdue once fires, cron waits for its next tick, and there is no journal, missed-tick replay or exactly-once guarantee. Paused snapshots use ordinary owner-scoped manual continuation.

At normal scheduler start, the existing loaded timer snapshot supplies aggregate loaded/scheduled/inactive counts. An unavailable store reports scheduling disabled. No timer content or new persistence/statistics scan is needed for this diagnostic.
