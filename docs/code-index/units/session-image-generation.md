# Unit: Separate image generation

Secondary files: `dotnet/Foxwarm/Models/SessionChatService.cs`, `dotnet/Foxwarm/Models/ConfiguredModelRequests.cs`, `dotnet/Foxwarm/Models/HostModels.Resolve.cs`, `dotnet/Foxwarm/Sessions/SessionOwner.cs`, `dotnet/Foxwarm/Tools/MainLocalToolDefinitions.cs`, `dotnet/Foxwarm/Tools/SessionToolExecutor.cs`, `dotnet/Foxwarm/Sessions/SessionManager.Authorization.cs`, `dotnet/Foxwarm.Tests/Models/SeparateImageGenerationTests.cs`, `dotnet/Foxwarm.Tests/Models/ImagesApiImageGenerationTests.cs`, `dotnet/Foxwarm.Tests/Models/ImagesApiImageGenerationTests.Usage.cs`, `dotnet/Foxwarm/Models/ModelUsageCost.cs`, `dotnet/Foxwarm/Models/ModelRequestOwner.cs`, `dotnet/Foxwarm/Models/ModelRoutingFingerprint.cs`

`imageGeneration.mode: separate` exposes `generate_image` instead of the native conversation image tool. Omitted mode and `hosted` keep native hosted generation. The earlier `isolated` spelling remains accepted as a compatibility alias; new configurations should use `separate`, avoiding confusion with legacy Agent isolation metadata. No file rewrite is required to keep existing configurations working.

`SessionChatService` captures the concrete model and catalog before each attempt's declarations. During its tool loop, declarations, discovery and dispatch use that captured leaf, including failover and session-hash routes. The separate request retains that leaf rather than rerouting with a fresh image cache key. A changed explicit model selection invalidates the previous selection. Outside an active model turn, only a directly selected concrete model can supply this capability; a virtual route has no adopted tool-producing leaf yet. Hosted and disabled models neither declare nor discover this builtin, and guessed direct/unified calls are rejected before dispatch. Normal tool authorization still applies to an enabled capability.

The Session boundary validates a bounded visual prompt and at most eight same-Session image IDs. IDs resolve against current and archived caller history before any provider request; credentials and filesystem paths are not accepted. Successful images return through the existing `imageParts` reference carrier and normal tool-image persistence/delivery. Missing images become a normal tool error.

`ImageGenerationRequests` owns the dedicated request policy: prompt/reference-only history, fixed image instructions, no functions or search, one attempt, cancellation propagation and no reasoning. The separate request never changes Session reasoning effort or appends a detached assistant message into canonical history. Both backends run through `ModelRequestOwner` with journal purpose `image-generation`, retaining secret masking, text redaction, diagnostics and request journal handling.

## Request backends

`imageGeneration.api` selects the backend of the separate request ([D-image-generation-images-api](#d-image-generation-images-api)):

- `responses` (default when omitted): a Responses request with a single forced native image tool. Its wire builder is selected before ordinary Responses planning; reserved `extraFields` cannot restore reasoning, ordinary conversation state, functions or cache continuation. Image options use the same native image-tool builder as hosted generation. Other provider extensions retain their established behavior. HTTP and WebSocket providers use their normal transport.
- `images`: `ImagesApiChatService` calls the OpenAI Images API on the leaf's `baseUrl` with its `apiKey` and `extraHeaders`. Without reference images it POSTs JSON to `{baseUrl}/images/generations`; with reference images it POSTs multipart to `{baseUrl}/images/edits`, one `image[]` part per reference (hydrated through the normal provider image path) plus `model`, `prompt` and options. It is always plain HTTP; an `openai-ws` provider's `ws`/`wss` base URL maps to `http`/`https`. `size`, `quality`, `background`, `outputFormat` and `outputCompression` map to `size`, `quality`, `background`, `output_format` and `output_compression`; `action` has no Images API form, since the endpoint follows from the references. `response_format` is not sent (GPT image models always return `b64_json`).

Images API configuration is validated after provider → model inheritance: the effective settings need `mode: separate` (or `isolated`) and a nonempty `model`; there is no default image model.

Images API results are accepted only as `b64_json`. Each image is strictly decoded, recognized by raster signature, checked against the response `output_format`, bounded by the hosted-image per-image, cumulative and count limits, and stored as a content-addressed blob with `imageMeta.origin = "generated"`; it has no native replay metadata, so later requests use the existing generated-image placeholder rules. URL-only or rejected items become a tool error. The journal and diagnostics record form fields plus a digest per uploaded image and omit `b64_json`. Response `usage` is recorded with the attempt, attributed to the image model and priced only by `imageGeneration.pricing` ([Attribution and cost](#attribution-and-cost)); the conversation model's `pricing` is never applied to image tokens (`ChatResult.UsagePricedByService`). Non-2xx responses become a non-retryable, non-countable failure whose concise message carries the provider's `error.message`. The non-streaming response uses the ten-minute image inactivity floor.

Text redaction applies to the prompt as on the Responses path. Image output has no text to restore, and original values are never sent.

## Attribution and cost

An Images API request calls the configured image model over the Images API, not the conversation leaf, so the rows that name a request's model say so ([D-image-generation-images-api-attribution](#d-image-generation-images-api-attribution)). `ImageGenerationRequests.Attribution(leaf, purpose)` returns the model key and provider type for one attempt: `<providerKey>/<imageGeneration.model>` (the key form of catalog models, so `provider_key` is still the leaf's provider) and `openai-images`, the wire API as `openai-completions` names one, when the purpose is `image-generation` and the effective `api` is `images`; otherwise the leaf's own key and type. `ModelRequestOwner` computes it once per attempt and uses it for the journal attempt start (`concrete_model_id`, `provider_type`), which the usage ledger's live and backfilled rows read, for the text-redaction record (the redacted prompt is what the image model receives) and for the result's `modelId` metadata. The key need not exist in the catalog: usage, ledger, redaction and journal readers treat model keys as text. Diagnostics (`ModelInteractionDiagnostics`) still name the selected leaf. The caller's conversation model remains the request's `requested_model_key`, and `virtual_model_key` stays empty because it names a virtual route. The Responses backend calls the conversation model and keeps the leaf attribution.

`imageGeneration.pricing` is `{input, imageInput, output}`, USD per million tokens, all three required, no other key; it is valid only when the effective settings use `api: images` and it is replaced as a whole by a model-level value. There is no cached rate: Images API usage reports no cached count. `ModelUsageCost.ImageCost` computes `(text_tokens * input + image_tokens * imageInput + output_tokens * output) / 1e6` from the raw response usage and returns no cost, never a guess, when counts are missing or fractional, `text_tokens + image_tokens` differs from `input_tokens`, or a nonzero cached count is reported. Without `input_tokens_details`, the input of a generation is all text and an edit's is unpriced. All output tokens use `output`. `ImagesApiChatService` stores the cost in the normalized usage and marks the result `UsagePricedByService`, so `ModelUsageCost.Complete` keeps it and never applies the conversation model's rates. Without pricing the cost stays empty. The pricing is not part of the routing fingerprint, like model pricing.

## Tool failures

A failed separate request, local preparation failure or journal preparation failure is the tool's own result: `GenerateImageAsync` converts every non-cancellation exception from the request owner into a tool error `Image generation failed: <reason>` ([D-image-generation-failure-is-tool-result](#d-image-generation-failure-is-tool-result)). Cancellation and turn shutdown keep their existing tool-cancellation handling.

## Design decisions

### D-image-generation-images-api

[2026-11-16, user] Separate image generation gets an Images API backend for OpenAI-compatible routes that cannot force hosted `image_generation` on a Responses request. It is selected with `imageGeneration.api: images` and requires an explicit `imageGeneration.model`; the Responses backend remains the default and keeps its behavior. The request uses the provider's connection settings over plain HTTP even for `openai-ws`, because the Images API has no WebSocket form.

### D-image-generation-images-api-attribution

[2026-11-16, user] Journal, usage and text-redaction rows of an Images API request name the image model and wire API actually called: model key `<providerKey>/<imageModel>`, provider type `openai-images`. The conversation model stays in `requested_model_key`, so no column is added and `virtual_model_key` keeps meaning a virtual route. Image requests are priced only by optional `imageGeneration.pricing` with `input`, `imageInput` and `output` rates and no cached rate; unmatched counts leave the cost empty.

### D-image-generation-failure-is-tool-result

[2026-11-16, user] A failed `generate_image` always yields a persisted tool error and the turn continues like any other tool error. Previously a `ModelRequestException` from the one-attempt image request escaped tool dispatch (neither the tool executor nor the turn host maps that type), ended the turn as a model failure and left the function call without a function response. Among tool handlers, only `generate_image` awaits a `ModelRequestOwner` request inside dispatch: ToolScript `request_model_without_context` failures become a script `RuntimeError`, and compaction, BTW and automatic titles are scheduled or user-command paths.

### D-llm-image-generation-tool-declaration

[2026-09-19] Hosted image generation is declared as a Responses tool object built only from the effective normalized config. Foxwarm does not hardcode a default hosted image model, size, or enablement field, so provider defaults stay authoritative and a future provider field can be adopted without a schema migration.

### D-llm-image-generation-binary-boundary

[2026-09-19] Provider image base64 is accepted only inside generated-image normalization (`GeneratedImageNormalization` in `HostedResponsesTools`), which validates the bytes, writes a content-addressed blob, and reduces the item to a reference plus safe metadata. Replay needs the same concrete model and locally verified bytes; a missing or unreadable blob is an explicit failure, never a dangling native call id or a silent regeneration.

### D-llm-image-replay-local-failure

[2026-09-19] A generated image that cannot be replayed from local storage raises a dedicated local replay failure rather than a generic error. The failure is local, so it is reported as non-retryable and non-countable against model health: the provider was not asked for anything, retrying cannot restore the bytes, and a failover could pay twice for the same image. Canonical history is never rewritten to work around it.

### D-openai-generated-image-replay

[2026-09-19] Assistant history may carry a hosted generated image as a reference-only part with safe native metadata. Responses request conversion replays it as one complete `image_generation_call` only when the part's source concrete model matches the destination model and the local blob bytes are readable; that replay runs before the generic inline-image branch and consumes the part. Any other destination model or protocol receives one bounded text note instead of native metadata or a dangling call id, and canonical history is never mutated. Only final images are represented; `partial_images` stays at 0 and preview payloads are never persisted.

### D-llm-hosted-image-generation

[2026-09-19; updated 2026-09-23] OpenAI Responses models may opt into the provider-hosted `image_generation` tool through the `imageGeneration` provider/model config, which defaults off and is rejected on Chat Completions, Anthropic, and virtual providers. Output images are durable blobs referenced from canonical message parts; provider base64 never enters canonical history, the request journal, logs, WebUI transport, or error diagnostics. Raw stream content capture is disabled for every physical request that can carry or receive image bytes, keyed on the effective config and on whether the Responses input replays a native generated-image call rather than on the UI-level toggle alone.

Only the exact concrete model that produced an image may replay it natively, and only when locally verified bytes are available; another concrete model or protocol receives one bounded text note instead, while the originating model with unreadable local bytes fails the request. Unrecoverable local bytes are a non-retryable, non-countable failure: the provider was never asked to redo the work, a retry cannot restore the bytes, and a failover could pay twice for the same image. An attempt that has already begun a hosted image call is not excluded from the ordinary retry classification or budget: a regenerated image is a fresh artifact rather than a recovery of the first one, and the product accepts a normal retry window instead of an unretried failure. A successful image counts as real response content, so a text-free image turn is not retried as empty. Hosted image generation is excluded from compact-plan and setup-test purposes, like hosted web search.

The optional onAttempt hook runs after local retry/effective-selection preparation and before a prepared physical request, only when the plan is not already cancelled. Callback failures remain outside provider retry classification. Cancellation after plan preparation, including during an awaited callback, retains the established attempt-start/abort-result journal path without dispatching a provider request. Runtime consumers use the hook to clear backoff without obscuring compaction preparation. The journal boundary is canonical in [request flow](../threads/llm-request-journal.md#request-flow).
