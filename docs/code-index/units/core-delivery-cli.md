# Unit: Core delivery resources and public one-shot CLI

Secondary/integration references: the [public CLI frontends](./model-cli.md), `package.json`, `dotnet/Foxwarm/Foxwarm.csproj`, `dotnet/Foxwarm.Desktop/Foxwarm.Desktop.csproj`, `dotnet/scripts/publish-desktop.sh`.

## Purpose and stable callers

- Root `foxwarm` remains a JavaScript command dispatcher: no arguments/help show usage, version reads the package version, and only `model` and `archive` select operations. It does not start Main. Independent Multica remains a JavaScript HTTP/JSONL client.
- `coreExecutable` is shared with the [Main entry](./source-main-entry.md) without sharing its drain policy. `parseArgs` in each public frontend is the only flag parser. `runCoreCli` launches the published Core apphost (or `dotnet Foxwarm.dll` when no apphost exists), or the selected source Core output through `runtime/current`, resolved to its stable real directory. Missing builds/runtime fail without a TypeScript backend fallback. One parsed-options JSON header and optional raw prompt stdin feed the child; this is not a Main controller/RPC service.
- `CliCommands.RunAsync` handles the private one-shot entry before ordinary Main construction, but after private Vector/native-helper dispatch. `ModelAsync` uses `ModelConfiguration`, `HostModels`, `ModelRequestOwner`, provider transports, routing and the journal. `ArchiveAsync` uses the fixed [Archive migration/export owners](./archive-message-store.md#legacy-migration-and-jsonl-export).
- `CliFrontendLifetime.ConnectAsync` adopts the frontend's lifetime connection before consuming input or starting work. Unix uses an inherited pipe at fd 3, as with the Main launcher, without a filesystem socket address or a restriction on the caller's `TMPDIR`; Windows retains its named pipe. The frontend keeps this pipe open independently of prompt stdin. Frontend termination, including a hard kill by an outer consumer timeout, closes it and exits the one-shot child; prompt EOF does not. This does not change independent exec lifetimes or Main's process-tree policy.
- `Directory.Build.props` reads the product version from root `package.json`; assembly identification, Core `--version`, MCP server information and ordinary provider user agents use `ProductVersion.Value`. Protocol versions and native dependency pins are independent.

## CLI behavior

Model supports existing long/short options, list aliases, configured default/virtual keys, prompt or non-TTY stdin, explicit system text, per-attempt timeout (also replacing the nonstream transport idle default), text and `{text,modelId,usage}` JSON. Model-list and unknown-key checks precede prompt consumption. Missing/blank prompts and unknown keys return usage exit 2; operational/provider/empty-result failures return 1, and successful operations return 0. Frontend help/usage/version do not require Core/configuration. The request is tool-free `purpose:cli`, iteration zero, without a Session ID, Session engine, Main prompt, HTTP listener, timer or Vector startup. Low-level WebSocket history finalizers discard reusable provider state.

Archive preserves `export-jsonl --output/-o DIR`, the `sessions/` JSONL tree and `llm-request-journal.jsonl`, with `{output,sessions:{files,records},llm:{records}}` stdout. Output paths resolve from the caller's cwd; settings/data still use captured installation-relative paths. Diagnostics go to stderr, not JSON/text stdout. Export does not start Main or recover a Session lifetime.

## Build and resource boundary

`npm run build:assets` uses the independent Shared and CLI Node builds, the Main-only `build:artifacts` data helpers, original WebUI and four tracked Code extension builds. `build:delivery` collects those assets into Core using the [source staging/promotion owner](./source-main-entry.md#build-and-controls); `publish:core` prepares them then performs framework-dependent publish. Direct Core publish also rejects missing required built inputs. Ordinary `dotnet build`/tests never invoke npm or rebuild the frontend. Root `npm run build` selects that complete delivery graph; `build-all` installs root/WebUI dependencies first. `build:reference` and `test:reference` retain the TS Main oracle explicitly. Default unit/CI tests include managed solution execution alongside the retained reference; full-application E2E selects managed Main. Shared/TS CLI `build:node` is independent of .NET and root Main dependencies, including `Dockerfile.node` and bootstrap source fallback. `build:artifacts` uses root Main esbuild/sharp dependencies without adding them to the Node package closure. Package/Main control entry is owned by [managed source startup](./source-main-entry.md); the [shared production/test Docker recipe](./public-main-docker.md) publishes this graph without another asset copier.

`Delivery.targets` is the shared resource graph: original WebUI, public global skills/resources, templates, tracked Code manifests/bundles/media, Node bootstrap source/manifests/locks/build inputs/bundles, root/native notices and pinned runtime dependencies. The [artifact compiler closure](./dotnet-artifacts.md#delivery) is collected from installed production dependencies with target-native selection and the actual fixed WebUI React resolver tree. Ordinary compilation may omit an unavailable target closure; complete delivery/publish rejects that omission rather than copying a host-platform executable. Public Multica includes its HTTP, setup and mandatory readiness-handshaken watchdog helpers alongside the bin. It excludes dependency caches and never collects installed Agent/state/token trees or optional operator Code/HEIF installations. Core-only JavaScript CLI entries/package metadata are omitted from Desktop's project-reference resource collection; Desktop intentionally removes Core apphost/runtimeconfig and consumes the same assembly/resources through its own entry. It uses the same `webui-dist` directory, not a second WebUI copy.

Build prerequisites remain .NET 10 SDK, restored pinned NuGet packages, Node/npm asset dependencies, Python for fresh pinned Monty acquisition, and GCC/libutil for the Linux PTY helper. Root Linux npm installation also requires Python/make/G++ for node-pty; no optional image decoder is required. A complete published Core runs outside the checkout without experiment-root overrides or an extra frontend copy. Runtime/qualified-platform limits are described in [managed source startup](./source-main-entry.md#supported-candidate-boundary); cross-publishing is not Windows runtime qualification.

## Tests

`scripts/model.test.js` drives the real public child against controlled Responses and nonstream Anthropic providers, including settings precedence, stdin/system/default/virtual/list behavior, per-attempt timeout/retry, frontend hard/ordinary termination, clean stdout/exit distinctions, tool-free journal export and no TypeScript backend loading. These model, Archive and frontend-lifetime paths use an existing long temporary-directory path, including spaces, while prompt EOF remains independent of the lifetime connection. The timeout peer deliberately holds the first response and checks its disconnection before exactly one successful retry; its one-second attempt budget does not require cold transport preparation and immediate SSE collection to finish within 100 ms. `CliArchiveMigrationTests.cs` and `dotnet/Foxwarm.Tests/Fixtures/cli-archive-fixture-ts.mjs` use real Source-produced storage and real Source export consumers. The maintained complete-publish lane invokes the public Multica bin from the actual payload through the existing authenticated HTTP/SSE fixture, proving startup, watchdog readiness, task POST and one successful result from an unrelated cwd. `packages/webui/test/publishedCore.e2e.mjs` accepts an explicitly owned publish directory and exercises original login/no-model Setup, packaged templates/global skill/resource, Node source archive/bundled client, extension consumers and ordinary native ToolScript with disabled Vector. Its managed host/version calls use `DOTNET_ROOT` when supplied or the ordinary PATH-resolved `dotnet` otherwise; public CLI apphosts retain normal runtime discovery. Readiness checks the owned child's exact wildcard listener address at the configured port, then uses loopback for HTTP/browser access. Failure output includes captured child diagnostics, including startup-wait timeouts. Multi-stage turn failures additionally report the request count and last provider reply, Main browser fixture reachability and fixed-executable presence/version, bounded tool/failure summaries, and minimal runtime state before owned cleanup. The bounded failure projection excludes installation state, request bodies, image bytes, tokens and browser profiles.
