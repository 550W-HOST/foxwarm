## Purpose

Implementation of the [secret references and redaction](../threads/secret-references-and-redaction.md) thread, which owns the cross-module contract, sinks, failure rules, redaction points, model-facing restrictions and the decision `D-secrets-store-references-redaction`. This unit owns the store and key formats, the matcher, exposure records, the Setup surface and tests.

## Store and key

`InstanceKeys` owns `<data root>/keys/secrets.key`: a versioned JSON document with a key ID and 32 random bytes, created once at Main start in an owner-only directory (0700) and file (0600) through a temporary file and a no-overwrite move. Purpose keys are derived with HKDF-SHA256 (`foxwarm/<purpose>/v1`); `secret-store` encrypts the store and `text-redaction-placeholder` is reserved for reversible text redaction. The key directory is outside `state/` so state backups and Git-backed copies do not carry it; restores must carry the key separately. When `state/secrets.json` exists and the key file does not, Main never creates a replacement key.

`SecretStore` keeps `state/secrets.json` (owner-only, atomic writes). Each name has a description and versions; each version is AES-256-GCM sealed with AAD `name\0version\0keyId`. Names are 1-64 lowercase letters, digits, `.`, `_` or `-`. Values are at most 64 KiB without NUL. Replacing or deleting a value retires the current version; retired values are pruned after 90 days. Values shorter than 12 characters are accepted and resolved but are not redactable, and Setup says so. A file that cannot be read, is malformed or has a newer `version` raises `SecretStoreLockedException`, the same as a missing or foreign key; the read is retried on next use and the file is never rewritten while unreadable. `InstanceSecrets.LockError` reports the reason. `Generation` changes on every mutation; the model catalog cache, MCP pooled-connection comparison and the redactor rebuild from it, and a catalog resolved while locked is rebuilt once the store is usable.

## Matcher and sources

`InstanceSecrets` builds one `SecretRedactor` from the store's current and retained values plus literal sources registered with `AddSource` (models, app configuration, access and instance tokens, Node secrets, MCP static credentials and OAuth tokens). `InstanceSecrets.Literals` applies the per-sink literal rules from the thread (`SecretSinkKind` `Credential`, `Url`, `Environment`, `Header`, `Argument`). Sources are re-read at most every five seconds, immediately after configuration installation, or when the store generation changes; a change also schedules a background rebuild, because log writes use the last built matcher and never rebuild it themselves. Other readers wait for an in-progress rebuild instead of masking with an older matcher.

The matcher covers raw text, JSON string escapes, upper/lower percent-encoding, upper/lower hex and the stable core of base64/base64url at every byte alignment, using leftmost-longest matching. Values below the minimum length produce no patterns and are not known values. `SecretMessageRedaction` applies it to canonical messages, skipping `__meta` except `questionAnswer`, `providerMeta`, inline data and reasoning parts, which are reported instead. `SessionSaveLane.RedactStagedHistory` (`SessionSaveLane.Redaction.cs`) is the single history point described in the thread.

`SecretExposures` records label, count, first/last time, last redaction point and last Session ID in `state/secret-exposures.json` (debounced, at most 512 labels). Writes are serialized and an older snapshot never replaces a newer one. Content is never recorded. The count is the number of times a value was masked at a redaction point, not the number of distinct occurrences: a value in instructions is counted on every request. Setup shows these as rotation hints and can dismiss them.

## Setup

`/api/setup/secrets` (administrator-only like all Setup routes) lists metadata, usages by provider/channel/setting/MCP server, referenced-but-missing names, exposures, the lock state and the key file path. `InstanceSecrets.LockError` is always a `SecretStoreLockedException` whose message is one of the fixed user-facing locked-store sentences (other key-loading or store-read failures are wrapped as "the instance key is unavailable" or "its file cannot be read"), and `lockMessage` is that message alone, without the exception type. `PUT /api/setup/secrets/{name}` sets a value and/or description, `DELETE` retires the current value, `POST .../forget-retired` drops retained values and `POST /api/setup/secrets/exposures/clear` dismisses one exposure label. Responses never contain values. The WebUI Secrets tab offers add/replace/describe/delete, prefill for missing names and exposure dismissal; value inputs are password fields cleared after save.

## Tests

`SecretStoreTests` covers key/file modes, encryption at rest, reopen with the same key, locked behaviour for a missing or foreign key without key replacement, retention and pruning, short values and exposure persistence without content. `SecretReferenceTests` covers sink resolution and validation, literal sources and the marker guard. `SecretRedactionTests` covers encodings, leftmost-longest and copy-on-write matching, byte-identical reasoning with exposure reporting, request-stage masking of instructions, tools and history copies, and that a reader arriving during a rebuild waits for the rebuilt matcher. `SecretHostTests` runs real Sessions against a loopback provider: the provider key resolves into the Authorization header while user input and `read` output reach history and both requests only as markers; a missing provider secret fails the turn without provider contact; model-initiated configuration writes cannot redirect referencing entries. `SecretBoundaryTests` covers inherited `llm` base URLs, credential-shaped literal rules, unreadable or newer stores, key restoration without restart, OAuth with referenced client secrets, and a real Session where a structured answer, the question record, a retry notice and a memory write never keep a known value in history, meta or data files. `SecretSetupRouteTests` exercises the Setup routes on a real Main host, the locked-store `lockMessage` text and the wrapping of other lock failure types, the owner-only `node_bootstrap_info` file, and Setup provider drafts (model listing and testing) with literal and referenced keys. `IndependentProcessEnvironmentTests` covers the master exec environment drop. The Setup tab is covered by `packages/webui/test/setupModels.e2e.mjs`.
