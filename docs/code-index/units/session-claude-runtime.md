# Unit: Claude Code Session runtime

Files: `dotnet/Foxwarm/Sessions/External/ClaudeRuntimeConfiguration.cs`, `dotnet/Foxwarm/Sessions/External/ClaudeRuntimeState.cs`, `dotnet/Foxwarm/Sessions/External/SessionRuntimeCredentialStore.cs`, `dotnet/Foxwarm/Sessions/External/ClaudeRuntimeToolSupport.cs`, `dotnet/Foxwarm/Sessions/External/ClaudeSessionDriver.cs`, `dotnet/Foxwarm/Sessions/External/RuntimeMcpService.cs`, `dotnet/Foxwarm/Sessions/External/LocalSessionTurnHost.Claude.cs`

## Goals and decision provenance

- **User goal:** connect an external Agent through `claude -p` or the Agent SDK and provide Foxwarm tools. Use Claude Code's own configured model, login and subscription; Foxwarm supplies neither the model nor an LLM key.
- **Approved derived design:** keep an ordinary internal Session and replace only its model loop. Use separate exact-run credentials rather than entry identities. Disable CLI-native business tools and route business operations through Foxwarm authorization.
- **Review-selected, subject to user revision:** run the CLI only on Main, use a private cwd with `--setting-sources user`, default credentials to one hour with renewal, and initially omit wait/batch/compaction/fork support. The current implementation supports Linux only. These are implementation choices, not permanent limits on the user goal.

## Runtime and trust contract

The external runtime is one ordinary Main-owned internal Session and foreground processor. It replaces the model loop inside `LocalSessionTurnHost.ChatAsync`; it does not introduce an ordinary inbound MCP identity, another Session, a second model loop, or a generic runtime platform. Runtime selection is creation-only, defaults to `foxwarm` even for children of an external parent, and accepts `claude-code` through the two creation tools and the human Session creation API. The CLI owns its model/login configuration. Foxwarm does not supply a model flag, account key, LLM proxy, `--bare`, or an authentication-directory override.

The host account, executable, and effective administrator-controlled configuration are trusted prerequisites. Linux/`setsid` hosting uses a stable Main-owned mode-0700 context directory under `state/claude-runtime/<external-UUID>`, not the Agent workspace. The directory follows the existing external checkpoint across identity moves; Clear creates a fresh context, and old/custom cwd checkpoints refuse rather than migrate or replay. The startup `workingDirectory` option is removed. `--setting-sources user` enforces project/local settings exclusion while retaining user/managed configuration. Mode 0700 does not override same-account unrestricted native-write/Main-exec grants; existing scoped file/exec policy remains the boundary, and no user policy is installed automatically. Configured automatic effects outside the bridge are not controlled by Foxwarm tool policy. The settings overlay suppresses hooks only in the CLI's documented ordinary-settings scope; administrator-managed hooks and force-enabled managed plugin hooks may run. Initialization checks refuse observable tool/plugin/MCP/permission mismatches (any reported tool other than `mcp__foxwarm__*` and `EndConversation`), but successful init cannot establish that no managed hooks ran. The user guide is `docs/claude-code-sessions.md`; its custom-wrapper section is the executable contract for `claudeCode.executable`. A wrapper may host the CLI elsewhere, but it owns endpoint forwarding, file and transcript synchronization and remote cleanup; Main keeps its local endpoint, local transcript precondition and process-group control unchanged. Controlled tests establish bridge/lifecycle behavior, not installation-account qualification or host isolation.

## Input and persistence

The CLI receives the committed instruction snapshot without a Foxwarm current-model identity. Before the first run there is no observed CLI model; a later explicit snapshot refresh may use the last observed model for model-conditional memory.

`ClaudeRuntimeState` validates the creation selector and version-2 external checkpoint. Version 1 remains the Foxwarm authority format; older version-1 readers already refuse version 2. The checkpoint contains the external UUID, Main-local cwd/transcript reference, input frontier/latest-user high-water, run status, observed model/auth-source metadata, and latest CLI usage estimate. It contains no run credential.

`SessionTurnRunner` commits one ordinary queued input unit before invoking the driver. New input remains queued until that run settles. The driver resumes the recorded UUID and sends only user rows beyond the committed input frontier, not a replay of Main history. It records that frontier before writing NDJSON to stdin. Known pre-submission failure restores the previous checkpoint/frontier; unknown input outcomes are never automatically replayed. A recovered initialized run becomes interrupted without the ordinary recovery-trigger synthesis. A valid pre-first-launch Busy checkpoint remains `new`, without invented CLI identity or paths. Both first-launch and initialized recovery wait for explicit continuation; queued known input remains queued, and Continue commits that unit before invoking the CLI. Continue capability includes known queued input as well as the interrupted checkpoint or unsubmitted user sequence, including completed CLI runs with no text response. Missing transcripts refuse resume; Clear creates a new external context through the existing lifecycle owner. Clear removes Main history and the external checkpoint, not the CLI account's transcript files.

Checkpoint changes share the existing canonical save lane and publication boundary. Complete assistant rows and known partial text on interruption use canonical history append. CLI tool echoes, compact boundaries, and result metadata do not execute business tools or change Main's history version/Archive. The latest result usage is source-labeled; its possibly cumulative CLI cost is not added to Foxwarm API totals. Hot metadata, cold catalog projections, history DTOs and the composer expose the CLI model/source and Continue capability without substituting a Foxwarm provider default or inventing an LLM journal request.

## Exact-run bridge

`SessionRuntimeCredentialStore` is Main-process-local and separate from ordinary access identities. A cryptographically random credential binds the exact owner, Session ID, Agent, foreground run, expiry, and callback. Renewal requires that same live run; expiry/revocation cannot be revived. Process exit removes tool admission even while already buffered CLI output is settled. Stop, failure/result, move, deletion and shutdown revoke credentials; no credential authority survives restart. Per-run mode-0700 directories and mode-0600 MCP/settings/prompt files are removed after drain, and stale run files are removed when a new manager starts.

`RuntimeMcpService` serves `/runtime/mcp` through the actual MCP SDK's stateless Streamable HTTP transport. The route has independent bearer authentication and does not use ordinary inbound identity promotion. `tools/list` returns `SessionManager.RuntimeModelDefinitions`: the same default-injected and current-Node definitions, with the same global/Agent-layer/legacy-isolation visibility, that an internal Session's model request receives. It omits response-wide cancellation fields because each MCP request is one call, and applies the runtime-only handoff projection below. Concrete names dispatch directly; `search_tools` and `call_tool` remain in that set for tools that are not default-injected. The list is captured when the CLI connects, while every call is authorized again. Tool calls and CLI observations share a per-run lane. The driver callback uses `ExecuteRuntimeToolAsync`, which reuses the normal attributed executor, canonical call/result rows, receipt consumption, complete-row settlement, output guards and image hydration. Fatal policy unavailability at normal batch settlement retires the run and propagates the existing exception to the foreground runner, so CLI success and automatic queued successors cannot overwrite that terminal outcome. Ordinary denials and business errors remain nonfatal. Raw tool identity arguments cannot select an actor. Policy and runtime support are checked again at resolved concrete dispatch, including unified aliases and `argsJson`.

`ClaudeRuntimeToolSupport` filters unsupported tools from normal discovery, narrows runtime-only handoff schemas, and rejects unsupported concrete effects. It refuses wait, ToolScript run/resume controls, Foxwarm compaction, response-wide batch controls, non-continue handoffs and current-Session identity/Stop controls. Forks, current-Session Foxwarm model/effort changes, BTW requests and cross-Node external-process resume are also unsupported. Ordinary canonical definitions and independent unattended work keep their normal semantics. Claude Code's `EndConversation` is an accepted driver control observation, not a business tool.

## Process and lifecycle owners

`ClaudeSessionDriver.Command` uses Linux `setsid` with structured arguments, bounded UTF-8 NDJSON records, a single strict MCP config, native-tool removal, and a tool-surface-only overlay. Root exit is observed independently of pipe EOF; it drains the same CLI-owned group so inherited pipes cannot strand the reader, while already buffered final records remain readable. A result fences tool admission before canonical completion. Failure/Stop joins admitted tool work before processor release; cancellation interrupts the owned process group and escalates to termination, including descendants that outlive the root. The existing `SessionControl`, identity move, deletion, shutdown and Clear owners retain their admission/drain responsibilities. Independent Main-owned background Exec and ToolScript lifetimes are not moved into the CLI process group.

Empty successful native completion still applies the existing child-report decision without fabricating an assistant row. Child creation and reminder guidance select continue-valued examples for Claude Code, including confirmation framing; ordinary Foxwarm guidance and task/send/no-action receipts retain their existing behavior.

The driver never spawns a model subprocess in automated tests. The controlled executable is selected through normal configuration, not a production test branch. No extra provider/model settings are used.

## Tests

`dotnet/Foxwarm.Tests/Sessions/ClaudeRuntimeTests*.cs` and `ClaudeRuntimeFixture.cs` use owned state/configuration, a controlled NDJSON child and the installed JavaScript/C# MCP SDKs. They cover parity between the listed tools and internal model definitions under Agent rules, direct concrete dispatch, actual registry file effects, output spooling and image results, reporting receipts, pre-effect unsupported controls and live policy changes, actor-argument rejection, runtime selection, hot/cold projection, duplicate/late events, crash/partial/malformed/configuration failure, transcript loss, Stop/move/delete/shutdown revocation, renewal/expiry, startup recovery, Clear, process descendants and independent background Exec lifetime. The settings regression plants helper/hook fixture files in both old and private cwd, verifies actual cwd/argv/user-only selection, and exercises real scoped file/exec denial. The delegation scenario creates a human-root planner through HTTP, onboards `c1` beneath `box1` through normal token tools and actual Node clients, applies the documented allowlist recipes with final denies, rejects ancestor management and `mcp_config`, and verifies allowed child-Node versus denied parent-Node command effects through the controlled CLI and real MCP. The fixture never invokes a real Claude model or copies account credentials.
