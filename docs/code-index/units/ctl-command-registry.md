# Unit: `ctl` command registry and model front end

Files: `dotnet/Foxwarm/Tools/Ctl/CtlCommands.json`, `dotnet/Foxwarm/Tools/Ctl/CtlRegistry.cs`, `dotnet/Foxwarm/Tools/Ctl/CtlLexer.cs`, `dotnet/Foxwarm/Tools/Ctl/CtlParser.cs`, `dotnet/Foxwarm/Tools/Ctl/CtlHelp.cs`, `dotnet/Foxwarm/Tools/Ctl/CtlCommandText.cs`, `dotnet/Foxwarm/Tools/SessionToolExecutor.Ctl.cs`, `packages/webui/src/ctlCall.ts`, `packages/webui/build/ctlRegistry.ts`

## Purpose

`ctl` is one CLI-like model tool backed by one declarative command registry. Each command (noun and verb, typed parameters, help) resolves to an existing canonical capability (`builtin:*`, `node:*`, `mcp:*`) and runs through the ordinary resolved-tool path. It replaces the former `search_tools`/`call_tool` pair and the default declarations of rarely used builtins. `ctl` is a front end, not a capability: authorization, ask approvals, Node selectors, activity records and tool-local validation are those of the target.

### D-ctl-command-registry

**Directly requested interface (2026-11-14).** User decisions:

- The tool is named `ctl`. Arguments are `command` (one command line), `values` and `valuesJson` (the same object-or-string fallback as `args`/`argsJson`).
- Long text and JSON are passed as a whole-token `@name` bound to `values.name`; `@@` writes a literal leading `@`.
- The command table was drafted once from the builtin schemas by a one-off generator; the checked-in registry, not the old schemas, is the source afterwards. There is no runtime derivation.
- `search_tools` and `call_tool` are removed without an alias period. ToolScript's `call_tool` host function is unrelated and stays.
- Later phases reuse the same registry and grammar for user `/commands`, inbound MCP and a ToolScript host function; only authority and presentation differ. Commands carry an ingress list (`model` now) for that purpose.

Coordinator decisions:

- `task` keeps its native declaration; the registry has no `task` noun (proposed in implementation, accepted by the coordinator).
- Persisted policy rules naming `search_tools` (or the never-valid `call_tool`, or `ctl`) still load, match nothing and are reported once as a load warning; they never make a policy unavailable. Discovery is filtered by target policy instead.
- Newly generated isolation-migration layers no longer list `search_tools`. A stored generated layer that differs from the current generation only by that name is still current and is kept as stored (`IsolationMigrationRules.CurrentDigest`); the name matches nothing there.
- Model-facing hints in tool output name the `ctl` command, built from the registry (see Command hints).

## Registry

`CtlCommands.json` is an embedded resource loaded and validated once by `CtlRegistry`. Each command records its noun/verb path, aliases, summary and help, ingress availability, parameters and target. A parameter has a name, an optional target argument path `arg` (a dotted path such as `model.modelId` fills a field of an object argument, so `session create --model sonnet --effort high` builds `model: {modelId, effort}`), optional flag spelling, type (`string`, `integer`, `number`, `boolean`, `enum` with `values`, `array` with `items`, `object`, `json`, `null`, or a `|` union), kind (`flag`, `positional` or `rest`), `required`, `variadic` and help. A target is either a fixed capability (`source`, `name`, optional fixed arguments such as `action`) or a local front-end operation (`tool-search`, `tool-call`). Loading rejects duplicate nouns, commands and parameters, invalid types, kinds and ingress, enums without values, arrays without items, more than one rest parameter, a variadic parameter that is not the last positional, and targets that are neither local nor a source and name. Tests check that every fixed target is a registered tool whose schema has each mapped property (and nested property for dotted paths) and whose required properties stay required. A parameter is `integer` only when its target rejects non-integers (`session view` positions, counts and history versions, `history recall --before-seq`, `image crop` geometry, artifact revisions). Parameters whose targets truncate, floor or accept fractional values (`previewLength`, limits, `session list` offsets, Archive ranges, memory line numbers) stay `number`, so any accepted target argument can be written as a command.

Registry copy uses ctl spellings: options as `--kebab-case`, positionals as `<kebab-case>`, other commands as `` `ctl noun verb` ``, and Foxwarm concept names capitalized (Session, Agent, Task, Node, Provider). A command's help adds to its summary rather than repeating it.

Every registered builtin is reachable through a specific command or through `tool call`. Nouns: `session`, `history`, `agent`, `node`, `memory`, `skill`, `file`, `image`, `artifact`, `channel`, `timer`, `script`, `config`, `secret`, `mcp`, `tool`.

## Grammar

`CtlLexer` tokenizes POSIX-style: single quotes, double quotes with `\"` and `\\`, backslash escapes outside quotes, no expansion. Unquoted `|`, `;`, `&`, `<`, `>`, `$(` and backticks are rejected with an error stating that `ctl` is not a shell and pointing to `run_script`. An optional leading `ctl` word is ignored.

`CtlParser` binds tokens to the command's parameters: kebab-case flags with the camelCase spelling also accepted, `--flag value` and `--flag=value` (an option needs its `--name=` prefix unquoted; quoting only the value, as in `--content="a b"`, keeps it an option, while a quoted `"--content=x"` is text), `--flag`/`--no-flag`/`--flag=true|false` for booleans, repeated flags or one JSON token for arrays, `@name` or one JSON token for objects, registry positionals, `--` to end flags, and one optional trailing rest parameter taking the remaining raw text once every positional is filled, including positionals given as options (`channel send --channel-target-id x @m`). `@name` matches `[A-Za-z_][A-Za-z0-9_-]*` as a whole token; a missing name and unused `values` keys are errors, and `values`/`valuesJson` are mutually exclusive. Literal tokens are converted to the parameter type; bound values are type-checked, never coerced. Errors are `CtlUsageException`s carrying the command's usage; unknown nouns and verbs get suggestions from `CtlHelp.Suggestions`, computed from the commands visible to the caller (the same predicate as help), so a hidden command is never suggested.

`help`, `<noun>`, `<noun> --help` and `<noun> <verb> --help` return help from `CtlHelp`, bounded to 16,000 characters and filtered by a visibility predicate.

## Resolution and dispatch

`ToolRegistry.Unwrap` turns a `ctl` call (and ToolScript `call_tool("ctl", …)`) into the target invocation, and `Resolve` records `InvocationName = "ctl"` on the resolved target. `tool call` takes a tool ID or `--source`/`--name`/`--server`/`--node-id` and `--args @args`, and resolves exactly as the former `call_tool` did, including Node placement selectors and `argsJson`-style input. `tool call builtin:ctl` is rejected as not concrete. Help, `tool search` and parse errors resolve to the `ctl` front end itself, which `SessionToolExecutor` handles without generic authorization: help filters each command by `SessionManager.ToolVisible` for its target, and `tool search` runs `UnifiedTools.SearchAsync` with the existing visibility, MCP server prefilter, budgets and structured descriptors for programmatic callers. A model parse error is an ordinary tool error of type `invalid_command`; a programmatic one throws to the script.

Node selection is a batch prerequisite: when it fails, later calls in the same model batch are skipped. `CtlParser.SelectsNode` keeps that guarantee for calls that fail to parse (malformed `valuesJson`, non-object `values`, extra envelope keys, unused values, bad options). Any `node select …` counts. For `tool call` it re-reads the lexer tokens with the parser's rules: only an option whose `--name` prefix is unquoted is an option, the first other token is the tool ID, and `@name`/`@@` resolve against the call's values for the identity fields and `--args`. A known `builtin:node` identity counts when its arguments select or can't be read; a known other identity never counts; an identity that can't be determined (an `@name` without a value) counts only when the arguments are known to select. When the words can't be lexed at all, only a literal `node select` counts.

`CtlParser.Describe` and `DescribeCall` map stored `ctl` arguments to the target descriptor without executing them. Consumers use it wherever the former `call_tool` wrapper was unwrapped: activity targets, sequence projection, compaction skill-load recognition and pruning exemptions, archive tool effects, Node-selection batch prerequisites, compaction submission detection and approval presentation.

`call_tool` is no longer a model tool; a model call to it is `Unknown tool`. The ToolScript `call_tool` host function remains.

## Default declarations

`SessionToolExecutor.DefaultBuiltins` lists the natively declared builtins: `read`, `write`, `edit`, `exec`, `run_script`, `continue_script`, `wait`, `ask_user`, `send_to_session`, `create_child_session`, `task`, `submit_compact_plan` and `ctl`, plus the conditional `generate_image` and provider-native tools. `node`, `recall`, `copy_between_nodes`, `cancel_transfer`, `send_file`, `image_write_to_file`, the memory tools, `image_crop`, `list_agents`, `skill`, `session`, `view_session` and `send_to_channel` remain registered concrete identities reached through `ctl`. The `ctl` declaration is fixed and Node-independent ([D-tools-node-independent-default-declarations](./tools-registry.md#d-tools-node-independent-default-declarations)).

## Command hints

Tool output that suggests a follow-up call (Archive drill-downs, literal-search continuations, prune markers, Vector raw-window sources, `session view` page links and stale-range hints, hosted image placeholders) writes it as a `ctl` command through `CtlCommandText.For(builtin, args)`. The command path and the option and positional spellings come from the registry entry targeting that builtin, and values are quoted so `CtlLexer` reads them back unchanged. Arrays of scalars become repeated options, while an empty array or one with structured or `[`-leading items becomes one JSON token, so an explicit `[]` stays distinct from omission. Rest text is written raw only when every positional before it is given as a word and the text has no leading whitespace; otherwise it is a quoted option. `CtlCommandTests` checks the round trip for every argument shape of every builtin a hint names, and follows a generated `session view` page link with a fractional budget and an empty `--parts`. Text detection that looks for such hints (preview navigation budgeting) recognizes both the new commands and the former `recall(`/`view_session(` call forms, which persisted history keeps. External MCP reads keep their own `foxwarm_session(...)` form and JSON spellings, such as `previewLength:20000` in the preview-budget notice; the same notice for model callers names `--preview-length 20000` through `CtlCommandText.Option`.

Other model-facing text that names an operation without a native declaration uses the `ctl` form as well: native declaration copy (`run_script`, `continue_script`, `wait`), channel boundary hints (`ctl channel send`, with the full command for send-only channels), the inbound MCP reply hint, background ToolScript receipts, memory-write conflicts, saved-image results (`ctl file send`), image placeholders and the resized-image coordinate note (`ctl image crop`, `ctl image save`). Policy messages, rule selectors and tool IDs keep concrete builtin names, because rules match those identities.

## WebUI

`ctlCall.ts` reads the same registry for display only. `ctlConcrete` turns a stored `ctl` call into the call it runs (builtin and Node tools under their own name and arguments, MCP tools as a unified descriptor), and the tool card renders that call with all capability-specific behavior (argument views, diff controls, file download) while showing `ctl <command>` as secondary context and keeping the stored call in the JSON view. Activity, communication and question cards, artifacts, reply files and approval labels use the same resolution. The production bundle carries a slim projection of the registry (paths, parameters, targets; no help) through the Vite plugin in `packages/webui/build/ctlRegistry.ts`.
