## Purpose

Shows what [reversible text redaction](./model-text-redaction.md) did without recording private values: per-attempt counts recorded with the request journal, a per-turn summary in the usage details, an installation-wide section in System › Usage, and an on-demand view of which ranges of a message were replaced when it was last sent.

## D-model-text-redaction-observability

[2026-11-09, user-selected scope] Statistics are counts and timings only; no surface records or returns placeholders, and only the sent-version view returns originals, for one message the viewer can already read. No detector call or provider attempt is added for observability. A separate store of span offsets and labels for the sent-version view, and a detector health counter, were not chosen; since 2026-11-10 the view also reads the [persisted slot results](./model-text-redaction-persistence.md) that keep requests prefix-stable.

**Per-attempt statistics.** `ModelRequestOwner` gives each attempt on a redacting leaf a `TextRedactionStats` through `ResponsesClientOptions.TextRedactionStats`; `TextRedactionChatService` clears it from the inner options so it never reaches serializers. The collector counts:

- replaced ranges per label, split into detected and literal-masked; a range with several labels counts under its first;
- non-empty slots: total, sent for detection, and served from the detection cache, including slots whose literal result was memoized;
- detector calls, including prefetch calls;
- the wall time of the whole redaction pass, including waiting for the per-endpoint queue;
- whether an oversized slot was omitted for compaction.

The collector reads counts the pass already computes: a few integer increments per slot and one dictionary update per replaced range. It adds no work proportional to text length.

**Failure representation.** Detection failures happen before provider contact and keep their existing semantics: they consume the request retry budget, write no attempt start or result, do not touch provider health and claim no send. They are recorded in a separate additive journal table, `llm_redaction`, keyed like attempts by `(request_id, attempt)`. A row with a NULL `failure_kind` describes a sent attempt. It is written in the same journal transaction as a successful result, under its own savepoint, so a missing table never fails the result. A sent attempt that fails or is stopped gets its row as a separate write. A row with a `failure_kind` describes a detection failure that consumed that attempt number with nothing sent. `TextRedactionException.Kind` gives the kind: `busy` (429/503), `timeout` (408 or the client timeout), `connection`, `too-large` (413), `invalid-response`, `config` (401/403/404/405 or an unreadable instance key), `service-error` (other 5xx) or `other`. An omitted oversized compaction slot is a successful attempt with `omitted=1`. The table is not a provider-attempt ledger: reconstruction, the usage ledger, provider health and raw diagnostics never read it. A failure row's partial counts are kept but are not aggregated. The Session, purpose, model, provider, protocol and virtual route are copied onto each row, so the existing usage dimensions apply without joins. Old databases without the table keep loading. Readers check for the table, the next journal start creates it, and nothing is backfilled.

**Per-turn summary.** A successful assistant message's `__meta.textRedaction` holds `{replaced, labels: {label: {detected, literal}}, slots, cachedSlots, detectorCalls, detectionMs[, omitted]}` when its request redacted; otherwise the key is absent. The WebUI usage details (badge and conversation statistics) sum the samples of the requests they already cover and add two rows, `Redacted` (total and per-label counts) and `Detection` (time and cached share of slots). They show nothing when no covered request redacted.

**Installation usage.** `UsageOverview` aggregates `llm_redaction` with the same buckets, groups and Session attribution as the usage ledger. Total and group `usage` objects then carry `redaction: {attempts, replacements, detected, literal, labels, slots, cachedSlots, detectorCalls, detectionMs, failures: {kind: count}, omitted}`; per-bucket rows do not. Counts and times cover sent attempts only; `failures` counts detection failures by kind and never adds to `requests` or `attempts`. A group whose only rows are failures can appear with zero requests. System › Usage shows the section only when the period has statistics.

**Sent-version view.** `GET /api/sessions/{id}/messages/{seq}/redaction` resolves the Session through the normal route binding (`FindRouteAsync`; the route is on the scoped-identity allowlist, so scoped WebUI identities reach only their own Sessions) and reads the message with that `seq` from the Session's active history. `TextRedactionView` rebuilds that message's slot texts the way a request to each redacting target of the Session's current route builds them: stage-S secret masking, concrete history preparation, then `TextRedactionProjection.RedactSlotsAsync`, which walks the same slots as the request and also reports each slot's kind, argument path, tool name and call ID. For each slot it reads the redactor's detection cache entry for the slot's exact text under that target's current options with `Peek`, which does not refresh LRU order; on a memory miss it reads the slot's persisted record without caching it or touching its use. Only an entry with a memoized literal result counts, because only that slot finished both passes. Detected offsets are in the slot text; literal offsets are mapped back from the detected form. The response returns the slot texts with `{start, length, label, source: detected|literal}` ranges, or `available: false`. When no slot is cached (store eviction or deletion, a settings change, or a message that was never sent) the state is `unavailable` and the UI says so; nothing is recomputed or guessed. The view never calls the detector and writes nothing. It returns no placeholders and no other message's text. Detection scores are not retained by the cache and are not shown; keeping them would need a cache-entry format change for presentation only.

The WebUI entry point is a `Sent version` message action, shown only when the Session's current model redacts (`session.textRedaction`). It appears on user messages (hover row), assistant replies (action buttons) and tool cards. A tool card filters to its call ID across the call message and the result message. Ranges are `<mark>` elements with a title and a screen-reader suffix naming the label and source.

## Tests

- `TextRedactionObservabilityTests` uses an owned journal, a local detector and a loopback provider. It covers detected versus literal counts, slot and cache counts, the absence of originals and placeholders in rows, the failure kinds without attempt starts, results committing when the table is missing, and old journals without the table.
- `TextRedactionObservabilityTests.View` covers ranges from the cache after two turns, literal offset mapping, no detector calls, unavailable states (never sent, changed options, empty redactor) and slot descriptors for arguments and tool results.
- `TextRedactionHttpTests` runs over a real Main with a scoped identity. It covers the persisted turn summary, the view's ranges and access (own Session, other Session forbidden, unknown or invalid seq), the usage `redaction` object and the `textRedaction` Session flag.
- `textRedaction.test.mjs` covers summary parsing and rows, usage validation, range segmentation and response validation. `mainHostTextRedaction.e2e.mjs` exercises the real UI against an owned Main with a fake detector and provider: popover rows, the System › Usage section with a failure, both range kinds in the dialog, the dialog still available after a restart, and the unavailable message after a settings change.
