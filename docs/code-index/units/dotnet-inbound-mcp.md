## HTTP and context lifetime

`HttpServer` registers `/mcp` outside its administrator/browser token middleware, including headless startup and an empty identity map. `MainHost` owns shutdown ordering; the service is also registered with the HTTP host lifetime. A normal live configuration save reports `access.surfaces.mcp` applied. First/last identity activation needs no restart while a listener exists. If all HTTP features were disabled at startup, enabling the first MCP surface reports restart required instead of creating a listener during configuration installation. MCP identity comparison uses only token plus the MCP surface, so WebUI-only edits do not retire its contexts.

Each request independently accepts only the configured surface's strict Bearer credential. Instance tokens/cookies, client metadata, tool arguments and the transport ID cannot issue an external principal. Origin, when supplied, must be the same HTTP(S) authority with no additional path/query/fragment. Content/Accept/protocol headers, bounded JSON syntax and exact context ownership are checked before SDK dispatch. Unknown/cross-owner/stale contexts return 404; reinitializing an existing context is rejected.

The production budgets are 8 MiB request JSON, 32 live/retiring contexts, 32 concurrent non-GET HTTP requests per context (the single physical GET has its own attachment slot), a 65-minute POST deadline, 15-minute POST-idle lifetime, 64 catalog entries/256 KiB, and 16 MiB serialized tool results. Active POSTs hold the idle lifetime; an idle GET does not. Oversized completed output is withheld with an uncertain-outcome error, never replayed. Errors replace only an unstarted response; an already-started failed SSE body is aborted rather than rewritten as successful JSON.

A per-POST `CancellationToken` flows through the public SDK request execution context; handlers capture/link that token with the context lifetime without retaining `HttpContext`. A request disconnect can cancel that wait or downstream request without retiring an initialized owner. Context disposal synchronously fences new effects, stops/drains physical GET writes, disposes both SDK objects, releases selected outbound MCP bindings and all used CLI execution namespaces, and awaits actual GET scope exit. DELETE sends its response only after this selected asynchronous cleanup, including the downstream SDK DELETE. There is no effect replay or transport retry after initialization/output failure.

## D-dotnet-inbound-mcp-pinned-sdk

**Engineering integration design using the official MCP SDK for the [supported external bridge](../threads/tool-dispatch-mcp.md#d-dispatch-mcp-inbound-bridge).** The version pin and adapter seams are engineering choices within real protocol compatibility. SDK convenience behavior must not redefine Foxwarm identity, authorization or retained-effect semantics.

[2026-10-18] Keep the already-qualified official MCP 2.2.0 packages and initialize revision `2025-11-25`. Public `StreamableHttpServerTransport` plus `McpServer` own framing and protocol dispatch. A public outgoing-message filter replaces the typed tool-result placeholder with that POST's bounded raw result; a typed `CallToolResult` round trip would discard opaque extension fields. Its mutable per-POST scope contains only a token/result, never an HTTP context, and is neither an offline record nor a replay store. Before raw publication, the external outbound call validates Source-known result fields and its five content discriminators using public SDK subtypes plus the confirmed Source null/shape constraints. Validation-only field copies exclude SDK-only fields and accommodate Source base64/union semantics. Accepted Base64 is decoded and re-encoded canonically only in the discarded SDK validation copy, including omitted padding and nonzero unused pad bits; the original result and its exact binary spellings remain unchanged. Malformed post-effect results become valid uncertain-outcome tool errors without automatic retry. SSE POST is a permitted representation and is exercised by unmodified official JavaScript and C# clients. This integration contract is qualified against those exact packages.

`McpAttachedResponseStream` is a small public-API attachment seam for the SDK's one logical unsolicited GET writer. A real GET attaches its response body, flushes headers and only then becomes physically ready. A disconnected physical GET does not end the SDK task or initialized context; the same context can attach a successor without `Last-Event-ID` or initialize. Resumption headers are rejected because there is no event store. The application must distinguish this physical attachment from the existence of the SDK GET task.

The seam intentionally depends on SDK 2.2.0 writing each complete SSE event in one `WriteAsync`. Attachment generation is captured before waiting on the SDK writer, so a stale queued send cannot acquire a successor response. Detachment clears body references immediately and tracks genuine in-flight write drain; write/flush/cancellation failure detaches only that physical attachment without poisoning the SDK writer. Sends with no ready attachment are dropped. It does not parse frames, retain an offline queue/event store, offer replay/retry, patch/fork/reflect into the SDK or create a general relay. `McpAttachmentTests` qualifies complete Unicode frames, held partial failures, stale sends and actual retirement drain against the real official SDK and the framework SSE reader; rerun it for SDK upgrades.

## Concrete catalog and retained effects

`foxwarm_discover`, `foxwarm_call`, `foxwarm_node`, `foxwarm_exec_result` and `foxwarm_session` are transport wrappers, not blanket grants. Discovery exposes only permitted configured MCP tools, compatible external Node tools and the two existing pairing builtins. Node list returns deduplicated permitted Node ID strings, never raw capability descriptors. Execution reconstructs concrete builtin/MCP/Node policy facts, including the real external identity/context, original arguments and remote path facts. It never grants local workspace/Agent/path ancestry to an external principal.

Discovery also lists bounded JSON-quoted tool IDs in its text content for clients that do not render `structuredContent`; the existing structured catalog and result budgets remain authoritative. External Node descriptors replace Agent-specific path/environment guidance with connection-local cwd and process-environment semantics. Calls accept the fixed file/exec parameter names; unknown fields and malformed patch envelopes fail before dispatch with safe, actionable errors. Already-dispatched failures retain unknown-outcome/partial-effect semantics. External exec timeout results direct callers to `foxwarm_exec_result` in the same MCP context rather than promising an internal Session notification; both retained TypeScript and managed CLI Nodes keep their actual completion owners.

`McpInboundSessions.ListAsync` reuses the existing bounded catalog page query, not the unbounded legacy Session listing. Read shares `SessionOwner.ViewPage` and `ContextPreviewRenderer.RenderLive` with internal `view_session`: newest 10 eligible records by default, chronological display, structural `parts` selection before count, then page-local literal/regex filters. Explicit `start` reads forward (negative indices count from the end); exclusive `before` reads backward, and the two cannot be combined. Counts are nonnegative safe integers without a separate read ceiling; count 0 returns only runtime/page information. Preview length uses the shared default/zero/clamping behavior, independently of record count. The page reader materializes only the traversed active-history rows, without `owner.History()` or an unrelated full-history projection.

Read preserves `sessionId/start/count/total/executionState/preview`, adds exclusive `end` and `historyVersion`, and returns actual selected source-record count before text filters or preview truncation. A structurally stale explicit boundary returns MCP `isError: true` while retaining the structured page payload and its text representation: `error: stale_history_boundary`, the current version, zero selected records and a fresh callable read instruction. Successful pages retain their ordinary success envelope; invalid-input errors retain their existing error envelope. Append preserves existing boundaries. Older/newer navigation uses callable `foxwarm_session(action:read)` arguments retaining page options and version. External previews do not generate internal `view_session` or `recall` instructions; folded/truncated content reports that Archive originals are unavailable through this endpoint. Authored content is not rewritten. No raw history, queue, prompts or Archive reconstruction is exposed. Read-only options reject on list/send; list retains its 1–50 count bound. Authentication, exact canonical-target resolution, concrete `builtin:view_session` authorization and final context/policy/owner assertions remain external-specific. Send resolves an exact canonical target, preserves the external-input wrapper and enqueues a real User item without internal intersession source authority. `SubmitExternalAsync` uses a strict save-lane admission; its final context, canonical-target and policy check runs after awaited input/goal preparation and before durable admission. It returns `accepted` only after strict persistence. A pre-rename failure does not publish hot queue state; committed/unsynced failure retains its actual committed input and reports uncertainty rather than accepted success. Ordinary WebUI/internal best-effort admission is unchanged.

False/omitted `allowReply` creates no reply destination; legacy `reply` remains read-compatible and conflicting booleans reject before effect. True uses the negotiated version-1 capability, real physical GET and temporary registered text channel supplied by [Session notifications/replies](./dotnet-mcp-notifications.md). The five ordinary wrappers and external policy identities are unchanged.

## CLI effects and bounded ownership

Only an authenticated, live, compatible Node wire connection with negotiated protocol 3 and `features.externalToolOwner: 1` can receive the external owner envelope. Master execution and excluded resident Providers are unavailable, with no Main fallback. Supported remote file/patch/exec definitions come from actual advertised capabilities. Pairing uses the existing persistent trust owner and omits returned authentication credentials from the external result.

Exec reserves a unique identity before dispatch, captures the selected Node/cwd generation and carries `{kind: external, externalId, contextId}` with the Source-compatible signed v2 completion capability. The final assertion runs after the connection send gate and before the authenticated socket effect. Results/completions require the same owner, Node, execution ID and capability. There are at most 20 retained executions per context, original arguments are at most 64 KiB, and output is at most 256 KiB. Completed records can be evicted; active saturation rejects before dispatch. Used Nodes are tracked independently of record eviction and all receive context release. New contexts do not recover authority from artifacts.

Result access reauthorizes the original exec arguments under current policy, including retained completed output. Query failures report unavailable/unknown state without retry. A late old-selection completion can retain its own cwd but cannot overwrite a successor selection. Started CLI processes survive caller/context loss; release retires their namespace after active work settles, not by killing effects or replaying commands. Internal Session claims, internal completion ownership and normal Node execution remain separate.

## Stateless remote file download

`McpNodeFileDownload` registers only `GET /api/vscode-web/fs/read-file` independently of the optional WebUI/Code workbench. It authenticates the same strict MCP Bearer identity, requires an explicit remote CLI Node and Node-native absolute path, rejects Main, and evaluates the concrete external Node `read` policy with the original `filePath` and no Agent/Session context. A supplied MCP context header grants no Session fact. Compatible protocol/owner/read capabilities and the existing fixed `vscode-fs` service are required; identity, policy and connection authority are checked at the service send gate and before publishing bytes. Other Code routes keep their original authentication.

The existing service transfers whole-file base64 within its 30-second deadline; the HTTP result is the original bytes up to the inclusive 50 MiB limit, with no-store and nosniff headers. Errors expose safe status/text rather than private backend details. There is no streaming/Range/ticket protocol or automatic retry. Administrator callers retain the existing local/default-Main and remote download behavior through `CodeWorkbench.DownloadAsync`, including headless operation without mounting the other Code routes.
