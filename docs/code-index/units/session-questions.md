# Unit: Structured user questions (`ask_user`)

Files: `dotnet/Foxwarm/Sessions/SessionQuestions.cs`, `dotnet/Foxwarm/Sessions/SessionManager.Questions.cs`, `dotnet/Foxwarm/Tools/AskUserToolDefinitions.cs`, `dotnet/Foxwarm/Channels/WebUi/WebUIChannel.Questions.cs`, `packages/webui/src/sessionQuestions.ts`, `packages/webui/src/sessionQuestionsState.ts`, `packages/webui/src/questionAnswerDrafts.ts`, `packages/webui/src/components/QuestionCard.tsx`, `packages/webui/src/components/QuestionContent.tsx`, `packages/webui/src/questionContent.ts`, `dotnet/Foxwarm/Sessions/SessionApprovals.cs`, `dotnet/Foxwarm/Channels/WebUi/WebUIChannel.Approvals.cs`, `packages/webui/src/sessionApprovals.ts`, `packages/webui/src/components/ApprovalCard.tsx`

## Purpose

Lets an Agent ask the user one to four questions, optionally with choices, and either end its turn until the user answers or keep working and receive the answer later as user input. The Session owns the question records, so the WebUI can render an answerable card or dock after the originating tool call has been compacted, and the records survive restart.

## Key contracts

- **Tool.** `ask_user` is available in every Session. `questions` (1-4; each with up to 6 options, `multiSelect`, per-option `description`/`recommended`) and `close` are mutually exclusive; `closeNote` accompanies `close`. The result is `{ questionId, status }`. `afterAsk:"wait"` (the default) is a terminal control with exactly the `wait` semantics: it takes effect after the tool batch, a sibling tool error suppresses it, and inside a ToolScript it follows the nested-wait rule. The Claude Code runtime projects the enum to `continue` only. The tool and parameter wording is coordinator-owned model-facing copy.
- **Wait source.** `wait.waitQuestionIds` names open questions of the calling Session. It is a real progress source like `waitForInput` (no automatic fallback deadline). `ask_user` with `afterAsk:"wait"` is equivalent to asking and then waiting on that ID. The runtime presentation reports `waitingFor:"question"`.
- **Authority.** `meta.questions = { revision, items[] }` in Session JSON. Each record holds `id` (`q-` plus 10 hex), `status` (`open`, `answered`, `skipped`, `closed`), the full question payload, `toolCallId`, `afterAsk`, and the resolution (`answer`, `closeNote`, `resolvedAt`). At most 32 open records; the 20 most recent resolved records are retained. `SessionAuthorityDocument` validates the shape on load and save.
- **Answers are user input.** The WebUI card/dock answer (`POST .../questions/{id}/answer`, body `{answers:[{selected[],text}], note, skip}`) becomes an ordinary user queue item from the WebUI channel with `questionAnswer` metadata and a model-facing rendering that names the question ID and pairs each question with its answer. It is admitted through the normal user-input path: it joins at a safe point while busy and starts a turn while idle, whether or not the question was waited on. Skipping produces the same kind of message, marked skipped.
- **Plain messages answer waited questions.** While the current wait lists `waitQuestionIds`, an ordinary user message (WebUI composer or external channel, `OpenFields.userInput`) answers those questions with its text and carries a `question-answer` system part. Messages from other Sessions, timers, task notices and system events never answer questions. Attachments remain ordinary message attachments.
- **First answer wins.** `SessionQuestions.ApplyAdmission` runs inside the save lane before `SessionWait.Apply`; a structured answer to a question that is no longer open fails with `QUESTION_NOT_OPEN` (HTTP 409). Answers cannot be edited.
- **Reminder.** While questions are open, each normal provider request receives request-only `question-reminder` context listing them (ID, short text, waited-on or not), after the Task reminder, so the Agent can close stale asynchronous questions. It is not persisted history.
- **Projection.** The catalog row carries `questions: { open, revision, waiting? }`; the partial index `idx_session_catalog_question_presence` serves the `questionSessions` rows of the first Sidebar page without hydrating Sessions. Session state and `session-state` events carry the same projection.
- **External channels.** Asking broadcasts a plain-text rendering (numbered questions, numbered options with descriptions and a recommended marker, "Reply to answer.") to the Session's attached normal-mode channels, excluding the WebUI. Closing sends nothing. A reply is an ordinary message; with a waited question it is the answer.
- **Known secrets.** Question records are masked on each ask or close, a structured answer's open fields at admission, and `__meta.questionAnswer` as history content, through the Session's [history masking point](../threads/secret-references-and-redaction.md#redaction-points).
- **No defaults.** There is no automatic default answer or timeout choice.

## WebUI

- `QuestionCard.tsx` renders `ask_user` calls in the timeline (`AskUserToolCard`). [2026-11-06, coordinator decision] The dock is the only interactive answering surface: while a question is open the card shows the question text and option labels (descriptions on demand) with a waiting or pending state, and clicking it expands the dock on that question and focuses its form. Resolved records collapse to their outcome (answered with the answer, skipped, or closed with the note). The record comes from Session state, not from the tool result.
- `QuestionDock` sits above the composer in every history view, driven by `GET /api/sessions/{id}/questions`, refetched when the Session state's `questions.revision` changes. It is expanded by default while the Session waits on a question; the composer placeholder then says that a reply answers it. There is no separate hint line: the dock header and placeholder already state it.
- The answering user message is rendered from `__meta.questionAnswer`, not from its model-facing text: a card or dock answer shows question/answer pairs (selected labels, free text, note) without the question ID, or a skipped notice. The metadata carries the question texts, so this survives pruning of the record. A plain message that answered a waited question stays an ordinary bubble with an "Answered the question" label; its `question-answer` system marker is lightweight metadata (the message remains user input in Conversation) and is not shown in the bubble.
- The dock form supports number keys to select options and Enter to advance or submit; several questions are stepped through and submitted together.
- **Answer drafts.** The unsent answer (selected options, free text, current step, note text and whether the note is open) is a browser-local draft keyed by Session and question ID (`questionAnswerDrafts.ts`, localStorage `foxwarm_question_drafts_v1`, like the composer draft), not form state. Every answer form for the question shares it, so it survives collapsing the dock, switching dock items or Sessions, and page reloads. A successful answer or skip clears it; a failed submit keeps it; each questions-view load drops that Session's drafts for questions that are no longer open (answered elsewhere, skipped, closed). At most 50 drafts younger than 30 days are kept across Sessions, newest first; an empty draft is not stored. Restored drafts are fitted to the question set (unknown options dropped, step clamped). The draft never reaches the backend; the answer protocol is unchanged.
- The Session list adds a "Needs your answer" section above Pinned for Sessions with open questions (waiting first) without changing the pin flag, and marks rows; waiting is visually stronger than asynchronous-open. A "Question for you" notification is raised when a Session gains an open question while it is not visible. The browser-local Setup choice decides which Sessions qualify: all Sessions (default), only those with the per-session idle notification turned on, or none. Questions already open when the page loads do not notify; a Session first seen later with an open question does. Baselines continue while notifications are off.

## Tool approvals

A call whose authorization outcome is `ask` waits for a decision ([D-dispatch-approval-ask](../threads/tool-dispatch-authorization.md#d-dispatch-approval-ask), [gate and grant](./tool-authorization.md#ask-outcome-and-approvals)). Its request lives beside the questions so it shares their revision, projection, dock and catalog index.

- **Authority.** `meta.questions.approvals[]`, validated with the questions. A record holds `id` (`ap-` plus 10 hex), `status` (`pending`, `approved`, `rejected`, `expired`, `cancelled`), `createdAt`, `origin` (`turn`, `script`, `timer`, `webhook`, `runtime`), `tool` (source, name, server, execution Node, invocation name), a one-line `summary`, `workingDirectory` for `exec` (resolved on master; the declared or Session cwd forwarded to another Node, absent when that Node uses its default), `toolCallId`/`runId` when known, the arguments (`args` up to 16 KB; otherwise `argsPreview` plus `argsTruncated`, while the live waiter keeps the full arguments), resolved `facts` (paths, Node targets, Session target), the asking `rules` (layer, ID, reason), `approvers`, and `timeoutSeconds`/`expiresAt` when there is a deadline. Settlement adds `decidedAt`, `decidedBy` (`administrator`, `identity` with its ID, or `system` with reason timeout, stop, shutdown, restart or notStarted) and the trimmed `note` (up to 2000 characters). An approved call that never starts ends `cancelled` with `approvedBy`/`approvedAt` holding the approval ([gate](./tool-authorization.md#ask-outcome-and-approvals)). At most 32 records are pending; 20 settled records are retained. Records, including arguments and notes, are masked on every write and the decision on the paired tool result is masked as history content; see [secret masking](../threads/secret-references-and-redaction.md#redaction-points). The live waiter's arguments shown to approvers are not persisted and are not masked.
- **First transition wins.** Decision, deadline and cancellation use the same pending-only transition inside the save lane; a later decision fails with `APPROVAL_NOT_PENDING` (HTTP 409).
- **Restart.** No pending approval survives a Main restart. A pending record found when the Session loads becomes `expired` with reason restart; the call is not replayed. Startup loads every Session whose catalog projection announces pending approvals (`SessionCatalog.PendingApprovalIds`, beside the busy/queued restart set), so background script and timer waits that did not make the Session busy are settled and their projection cleared too. A busy Session's resumed-turn notice names each such call as not executed.
- **Projection.** `questions.open` counts open questions plus pending approvals, `questions.approvals` counts pending approvals, and any pending approval sets `waiting`. The questions view (`GET .../questions`) adds `approvals[]` with `canDecide` for the requester.
- **Routes.** `POST /api/sessions/{id}/approvals/{approvalId}` with `{decision: approve|reject, note?}` decides. The administrator decides every request. A scoped WebUI identity needs scope for the Session (the ordinary route check) and must be listed in the record's `approvers`, which hold the identities named by every asking rule; otherwise the route answers 403 `APPROVAL_NOT_ALLOWED`. `GET` on the same path returns the record with the full arguments to those who may decide; it is a convenience for reviewing a shortened preview, not a confidentiality boundary. Anyone with Session scope already sees each record with its stored arguments and resolved facts in the questions view, and the call itself in the Session history; `approvers` controls who decides, not who reads.
- **External channels.** Asking broadcasts a one-line notice that a tool call is waiting for approval in the WebUI. Channels cannot decide.
- **WebUI.** The dock lists pending approvals before open questions and expands while any is pending. The approval form shows the tool, Node, origin, summary, the exec working directory, resolved targets, asking rules with reasons, remaining time and the arguments, with a full-argument load when shortened, then an optional note and Reject/Approve; an identity that cannot decide sees the request without controls. A waiting tool call in the timeline shows its approval state with a shortcut to the dock; settled calls show the outcome and note from `__meta.approval` on the result. The runtime status reads "Waiting for approval", the Session list badge and label name pending approvals, and the question notification is titled "Approval needed" when the Session has pending approvals.

## Answer content presentation

Resolved question outcomes and structured answer bubbles render their question text and answers with the shared sanitized Markdown renderer. Open question cards and the answering dock retain plain-text question presentation. Legacy via-message answers project transport attachment descriptors into attachment controls without rewriting stored records. Code spans, fences, nested code examples and pasted literals remain literal. Master-local raster attachments open the shared image preview; downloads retain existing authorization and errors. Remote descriptors remain non-actionable rather than being interpreted as local paths. User-bubble prose and links use the user foreground token. Regression coverage: questionContent unit/browser tests.
