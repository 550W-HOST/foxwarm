# Unit: Main ToolScript runtime

Files: `dotnet/Foxwarm/ToolScript/MainToolScript.Detach.cs`, `dotnet/Foxwarm/ToolScript/MainToolScript.Execution.cs`, `dotnet/Foxwarm/ToolScript/MainToolScript.HostCalls.cs`, `dotnet/Foxwarm/ToolScript/MainToolScript.cs`, `dotnet/Foxwarm/ToolScript/MontyFrameBudget.cs`, `dotnet/Foxwarm/ToolScript/MontyValues.cs`, `dotnet/Foxwarm/ToolScript/MontyWorker.cs`, `dotnet/Foxwarm/ToolScript/ToolScriptBudgetBuffer.cs`, `dotnet/Foxwarm/ToolScript/ToolScriptContext.cs`, `dotnet/Foxwarm/ToolScript/ToolScriptDataBudget.cs`, `dotnet/Foxwarm/ToolScript/ToolScriptRecordJson.cs`, `dotnet/Foxwarm/ToolScript/ToolScriptRunStore.cs`

## Purpose

Runs Main-local Monty ToolScript slices, routes the supported host calls, persists run records and opaque waiting snapshots, and resumes or cancels owner-scoped runs without bypassing normal tool/Session boundaries.

## Stable methods and callers

- `MainToolScript.NormalizeStartArgs` validates and normalizes starter intent without source I/O for ordinary starts and [script timer registration](./tasks-timers.md#owner-bound-toolscript-timers).
- `MainToolScript.ExecuteAsync` admits one operation while shutdown is open; `StartAsync`, `ContinueAsync`, `RequiredAsync`, `CancelAsync`, `CancelForegroundForShutdown`, `BeginShutdown`, `DrainAsync`, and `DisposeAsync` own start/continue/read/cancel/process-lifecycle behavior.
- `MainToolScript.RunAsync` and its `ProjectSlice` closure (the Execution partial) drive one configured worker or snapshot continuation and publish trusted current-slice subcalls, including an empty list, with the lean outer execution result; `MainToolScript.HostCallAsync` (the HostCalls partial) admits `call_tool`, `ask_agent`, and `request_model_without_context`, records subcalls, and returns progress/results through `ToolScriptContext`.
- `MontyWorker.ConfigureAsync`, `TurnAsync`, `Kill`, and `DisposeAsync` own the native Linux/Windows x64 and macOS x64/ARM64 Monty 0.0.19 subprocess protocol and watchdog; waiting runs retain snapshots rather than a live worker. `IsSupported` gates Main ToolScript discovery on Linux/Windows x64 and macOS x64/ARM64. Worker creation is lazy; startup does not launch Monty. Standard build/publish acquires the exact official standalone worker for the [delivery target RID](./core-delivery-cli.md#build-and-resource-boundary), defaulting to the SDK's portable RID, into build-only intermediate output and ships it under `ToolScript/native/`, with the existing notices. Normal runtime selects the packaged worker only; isolated in-process callers may pass the existing binary constructor argument. There is no experiment environment selection or historical private-prefix fallback. Windows retains only SystemRoot in the otherwise empty worker environment. macOS acquisition selects the exact official Darwin package for the target architecture and applies the same registry-integrity, version, protocol and resource-limit checks.
- `MontyFrameBudget.Parse`/`Preflight` inspect the fixed protobuf envelope before generated materialization: each frame is capped at 256 MiB and protocol nesting at depth 100.
- `ToolScriptDataBudget.Charge`, `Retain`, `JsonPreflight`, `ParseJson`, `JsonValue`, and `ReadRecordAsync` charge conservative per-activity materialization; `ToolScriptStdout.Append` enforces the cumulative 64 MiB UTF-8 stdout limit. `ToolScriptBudgetBuffer` charges incremental JSON tokens while serializing opaque values.
- `ToolScriptRecordJson.Write` streams bounded record JSON; `ToolScriptRunStore.AcquireAsync`, `ReadAsync`, `ListAsync`, `WriteAsync`, `RequireOwned`, and `RequireUnmanaged` serialize per-run access, owner checks, durable record writes, and managed-run refusal.

Callers: `SessionToolExecutor.ToolScript`, `ToolScriptToolDefinitions`, `SessionManager.ToolScript`, and WebUI/tool timeline consumers. The interpreter is Main-local even when source is fetched from a selected external Node through the [whole-file consumer](./external-node-files.md). Managed child-session host functions are explicitly unsupported in this host.

## Budget and worker contract

`MontyFrameBudget` is a fixed-protocol preflight, not an instruction budget, global RSS limit, or process sandbox. `MontyWorker.ConfigureAsync` passes Monty limits of 64 MiB native memory, recursion depth 200, and the requested duration; `TurnAsync` uses a watchdog and kills the worker on timeout/protocol failure. `ToolScriptDataBudget` is a conservative programmatic materialization budget (default 1 GiB) covering JSON values, frame/request bytes, retained stdout/snapshot representations, and record serialization. `ToolScriptStdout` separately caps cumulative host output at 64 MiB.

These budgets account for allocations Foxwarm materializes or retains; they do not claim to bound the whole OS process. Completed host effects and durable records remain when a later budget/cancellation failure occurs.

## Record numbers and timings

[2026-11-12] ToolScript JSON values carry the [Archive number contract](./session-authority-json.md): integers that fit Int64 stay integers, and every other number is a finite binary64 value, as `JSON.parse` reads it. `ToolScriptDataBudget.ParseJson`/`ReadRecordAsync` therefore never produce CLR decimals. Stored run records reach tool results through `get_toolscript_run`, `list_toolscript_runs`, cancellation of a finished run and timer run inspection, and `argsJson` reaches script timer rows, so a decimal there would make the Session's canonical tool-row append fail.

Recorded durations are whole milliseconds (rounded half away from zero) where they are produced: `subCalls[].durationMs`, `lastHostCall.durationMs` and `waiting.timeout.elapsedMs`, matching the integer timings of the retained TypeScript runtime. Existing stored records keep their earlier fractional values; they are read as binary64.

## Detached background runs

Contract: [background mode](../behaviors/automation-and-scheduled-work.md#pause-and-resume-the-run) (user, 2026-11-12). `SessionToolExecutor.ExecuteToolScriptAsync` supplies a `ToolScriptDetach` only for a top-level attended `run_script`/`continue_script`; timer and webhook dispatchers and nested calls get none, so they keep the slice contract. `StartAsync` marks such a background record `detachable` and records the wait (`DetachWait`: default 15 s, capped at 60 s with a warning) as its `timeoutSecs`; `continue_script` of a `detachable` record reuses the contract.

`RunDetachableAsync` takes ownership of the run's store lane, starts `RunAsync` on its own task with no caller token, and waits for it, the wait limit or the caller's token. If the segment has settled, its ordinary result is returned. Otherwise, under `ToolScriptDetach.Gate`, it records the hand-off, snapshots the segment's printed output and returns `status: running`. From then on the progress hook no longer updates the outer tool row, Task receipts, handoff targets and finish requests no longer reach the outer turn, nested deliveries use `ts:runId.n`, and nested calls are recorded directly in the activity index with origin `model` and the run ID. Approval requests keep origin `script` and the ordinary deadline. A detachable segment is configured without a Monty duration limit and skips the timeout checkpoint; an absent `max_duration_micros` also disables the parent watchdog.

`ObserveDetachedAsync` passes a handed-off segment's lean outcome to `SessionManager.DeliverToolScriptRunEventAsync`, which formats `ToolScriptRunEvent` and commits it once through the shared background-event path used by copies, keyed by the run ID as `execId` and by a per-segment event ID. `IsDetached` makes the run ID a `waitExecIds` source. `cancel_toolscript_run` cancels through the existing active-run path. `SessionManager.BeginShutdown` calls `CancelDetached`, so detached runs end `cancelled` with `ShutdownCancellation` and no event; startup `ClearLostBackgroundWaitsAsync` drops waits on `tsr_` IDs without a queued event, as for copies. Session retirement calls `RetireDetachedAsync`. An abrupt process exit leaves the record `running`, like an interrupted foreground run; `cancel_toolscript_run` settles it.

## Waiting, restart, and cancellation

`ask_agent` and timeout-safe host-call suspension write `waiting`, `snapshotBase64`, continuation metadata, and VM identity into the owner record. `ContinueAsync` requires the exact owner, continuation ID, `@pydantic/monty` version `0.0.19`, and snapshot format `monty-pool-snapshot-v0.0.19`; it loads the snapshot into a fresh worker and retains incompatible historical record/snapshot instead of converting it. Completed/current-runtime failed/cancelled records remove resumable snapshot state. Main-managed wait records are rejected by `RequireUnmanaged`, while unsupported managed-session functions fail without importing child state.

Foreground caller cancellation fences subsequent host admission and reaches active tools through their linked host token, but does not cancel delivery of an already-settled result or its next native resume. `ActiveRun` keeps explicit run/shutdown cancellation separate for the VM lifetime. Explicit cancellation requests that run token and lets started host work settle. Neither path rolls back already committed tool, Session, file, or process effects. `BeginShutdown` rejects new operations; `DrainAsync` waits for admitted activity and worker disposal while leaving persisted records intact.

Normal manager shutdown invokes `CancelForegroundForShutdown` during the [runner cancellation phase](./session-turns.md), before waiting for foreground settlement. It requests VM cancellation only for active runs belonging to that exact entry whose caller token is already cancelled, including a preceding Stop or Run queued that took the foreground handle. Independent timer slices carry no foreground cancellation token and are not selected. Global `BeginShutdown` remains after admitted foreground and timer settlement; this hook does not close dependencies or change ordinary Stop's settled-result delivery.

A nested call that waits for [tool approval](./tool-authorization.md#ask-outcome-and-approvals) holds its host call open. `ToolApprovalWaitMeter` records that wait per slice, and the slice compares `timeoutSecs` and reports `elapsedMs` without it, so a decision taken after the slice budget does not pause the run. Unattended timer slices use the one-hour default deadline when the rule sets none. Rejection and expiry reach the script as ordinary host-call errors that it may catch; Stop follows the ordinary foreground interruption; an approved nested call does not grant later nested calls.

## Host-call boundary

`HostCallAsync` accepts only the supported names and normalizes `call_tool` descriptors into the unified tool path. [2026-11-14] `ctl(command, values=None)` (user-approved phase D of [D-ctl-command-registry](./ctl-command-registry.md#d-ctl-command-registry)) builds exactly the `call_tool("ctl", {"command": …, "values": …})` wrapper and shares that branch: native target value, parse errors raise, and the target's authorization, approvals and placement apply. Filesystem, exec, terminal, MCP, Node, Session, and authorization effects remain behind their ordinary tools/owners; Monty OS functions and mounts are not exposed. `request_model_without_context` uses the current owner’s prompt-cache/effort boundary and returns normalized text/parts, while ToolScript records keep run metadata separate from outer Session history. `ToolScriptContext.CallTool` carries nullable JSON source values through the ordinary Session executor; [MCP values and trusted control](../threads/tools-permissions-and-exec.md#outbound-mcp-values-and-trusted-control) govern the projection boundary.

`run_script` and the existing compatibility starter accept independent `node` source selection only for file source; any node property with inline code is rejected. File paths are trimmed. Source Node/cwd is captured before awaited starter/read authorization and recorded as `sourceNode` diagnostics, while the VM stays Main-local. Source-capable starter discovery treats the optional source target as unknown rather than hiding it because the current Node is denied. Windows source selection does not relocate the VM or change the pinned native protocol. `filePath` source uses complete programmatic content or whole-file bytes with strict UTF-8/source-budget checks through the [file consumer boundary](./external-node-files.md). A snapshot continuation does not refetch a changed source file; nested calls retain current-owner dispatch and authorization after Node selection changes.

Short `call_tool` strings containing a qualified ID, such as `node:master/read` or `builtin:task`, use the same concrete registry path as descriptor calls. Cancellation is checked before host-call/tool admission and again after asynchronous authorization. Stop settles a launched exec wait without killing its shell. `NormalizeToolScriptResultAsync` externalizes the already-returned payload without a late foreground cancellation check; the completed subcall and actual receipt reach Monty before the next host-admission fence. Pure script output and return can retain that receipt, while later host work receives an unstarted interruption error. Lean outer results do not invent a dump of earlier nested results. Foreground runs, unattended slices, nested runs and the compatibility starter execute a segment before returning and pause at the time budget for explicit continuation; an attended background run follows [Detached background runs](#detached-background-runs).

Ordinary builtin `wait` is validated and authorized through the canonical Session dispatcher but records a cloned intent in the current `ToolScriptWaitScope` instead of registering a Session wait. Nested run/continue calls share that scope. Each actual host invocation clears its previous intent before argument processing, including failed/unknown functions, OS rejection and `ask_agent`; computation, print and ordinary return do not. Inner completion cannot arm the caller. Only normally completed outer execution re-enters `builtin:wait` resolution, authorization and live source validation. The existing exact wait-ID list, save lane, timer/liveness services and batch-error/Stop cleanup own the effect; returned dictionaries and diagnostics never supply control. Actual Task-completion receipts propagate through nested execution independently of wait intent.

Timeout checkpoints persist `pendingSessionWait` only in `waiting.timeout`, beside the actual pending VM return/exception. Continuation restores that explicit field before delivering the saved VM outcome; a later host invocation clears it. Paused/failed slices cannot arm a wait. Older checkpoints without the field remain valid and infer no intent. No managed controller or new scheduler is involved.

Final result objects promote top-level `inlineData`, nonempty `inlineDataItems` and canonical image-reference `parts` through the existing outer image pipeline. Only promoted entries receive bounded text placeholders; other result data and persisted native results remain intact. Nested normal reads/MCP image normalization still externalize bytes to canonical parts before returning them to the VM. Blob validation, Session-visible image IDs and provider hydration retain the image owner.

The per-context delivery capture and actual run ID are installed only around the real native unified host call and restored afterward. The run ID reaches `SessionToolExecutor.ScriptScope` and the canonical send handler separately from arguments/results, permitting self-notification from real run/continue/scheduled execution only. Direct model self-send and argument/result forgeries remain denied; ordinary authorization, isolation and configured handoff validation remain authoritative. Self-origin messages use a `type="toolscript"` wrapper with the actual run ID and no self reply route. Other-Session wrappers and typed receipt handling are unchanged. See the canonical [self-notification contract](./src-session-misc.md#d-script-self-notification).

The per-context delivery capture is installed only around the actual unified host call and restored afterward. A successful builtin send attaches bounded canonical destination/body to that completed subcall; a started exec attaches its [placement record](../threads/tools-permissions-and-exec.md#d-exec-placement-record) as `exec` through the same scoped capture. Nested run contexts cannot overwrite outer captures; current-slice projection retains the existing start/continuation boundaries. No send is inferred from source, stdout or result fields.

Calls of unattended slices (timer and webhook runs) have no Session tool row, so each is recorded directly in the [activity index](./activity-index.md) with its origin, run ID and target; attended subcalls are indexed from their `toolScriptSubCalls` record.
