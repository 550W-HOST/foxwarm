# Unit: External Node file consumers

Files: `dotnet/Foxwarm/Nodes/NodeConnectionHub.Files.cs`, `dotnet/Foxwarm/Sessions/SessionManager.NodeFiles.cs`

## Purpose

Connects whole-file transfer to actual copy, remote ToolScript source, image export/delivery, and administrator attachment ingress. The generic registry selects executable primitives or the existing resident Node connection for remote filesystem effects; Session history, Archive, canonical images, the Monty interpreter, and authenticated WebUI delivery remain Main-owned.

## Stable symbols and callers

- `NodeConnectionHub.ReadFileAsync` and `WriteFileAsync` send the official CLI `file_read_request`/`file_write_request` envelopes with the real Session and Agent. `HandleFileReply` settles only the corresponding response type and exact authenticated connection/transfer ID; replacement, removal, disconnect and shutdown fail that connection's pending transfers.
- `ReadNodeFileAsync`/`WriteNodeFileAsync` connect actual whole-file reads/writes to the existing Main filesystem implementation or remote transfer. Main uses regular-file/handle checks, native path resolution and atomic no-overwrite publication. Remote namespaces are never canonicalized by Main.
- `CopyBetweenNodesAsync` implements one read followed by one write. Relative Main/resident paths use the Agent directory independently on each endpoint; executable transfer paths use the adapter default. Neither uses Session cwd.
- `SessionToolExecutor.ToolScript` loads trimmed `filePath` from an independently selected source Node and captured cwd; the complete source is materialized under the existing source budget and strict UTF-8 decoding, not reconstructed from an ordinary read preview. Execution and continuation stay in the existing Main-owned Monty host; nested tools use their current real owner and ordinary dispatch.
- `SessionManager.ExportImageAsync` resolves only the sender's current history or effective Archive and canonical image store, then writes the target Node once. `SendFileAsync` reads remote bytes into unique Main delivery staging and uses the existing attached-channel checks and authenticated download route. Delivery failure does not delete an exported remote image or report successful delivery.
- `WebUiUploadedFiles.PrepareAsync` transfers staged attachments to an isolated Agent's bound Node and records the actual destination/Node in descriptors and partial saved-file results. Non-isolated uploads retain Main storage even when their Session selects a remote execution Node. Administrator ingress is not a model-tool invocation.

## Authorization and path contract

Copy/image/send use their real builtin identities, not additional ordinary `node:read`/`node:write` grants. Their actual endpoint facts and all/any Node-policy semantics are canonical in [authorization](./tool-authorization.md#policy-selectors-and-authoritative-facts). Copy supplies independent source and target path facts before read and again before write: Main resolves from the caller's Agent directory and remote paths remain unresolved. Isolated copy permits Main own-Agent paths and the bound/current Node, but neither unrelated Nodes nor other Main directories. File builtin targeting preserves Main path and attached-destination restrictions. ToolScript captures source Node/cwd before starter authorization, and binds starter paths, source-read authorization and the actual read to that capture. Omitted/current uses the invocation Node/cwd; another remote Node uses its own default, with authoritative absent cwd remaining absent. Explicit master uses Main path rules and the captured applicable owner cwd. Remote source first executes canonical programmatic `read` so official CLI approval or rejection settles before transfer; the approved resolved path sidecar supplies the complete-read target, with captured-cwd fallback for older peers. The complete byte transfer retains strict UTF-8 and source budgets rather than using a truncated preview. Source selection does not freeze nested tools' live-owner routing. Main source retains ordinary read policy and isolated own-Agent path restrictions; unrelated isolated remote sources are rejected. Administrator attachment ingress uses the actual target owner and staging/path checks, not a fabricated model caller.

## Transport and failure contract

Generic whole-file transfer has no WebUI-derived 50 MiB ceiling. Main and resident transfers retain their complete-file materialization; executable transfers retain bounded 1 MiB primitive reads and initial-create/append writes, with initial-stat equality and failed-prefix/no-replay behavior unchanged. Real resource and transport budgets still apply: resident Node messages retain the Source `ws` default 100 MiB envelope budget, including base64 and metadata, and the existing 30-second transfer timeout. Upload, Code and source-materialization budgets remain at their respective callers rather than becoming generic copy limits. Path metadata accepts up to 128 KiB of UTF-8, including extended remote Windows namespaces. `TransferFile` retains the remote payload MIME alongside bytes/path/name; successful delivery receipts preserve that MIME, falling back to the ordinary Main extension map only when absent or empty. Receipt MIME does not authorize inline previews. Reads validate decoded size and the existing wire SHA-256 before use; write receipts validate size/SHA-256 against the bytes sent. No local staging/report hashes or secondary verification protocol are introduced. Source materialization is charged before base64 decoding rather than trusting a peer-reported size.

The CLI transfer write contract creates missing parents and defaults to no overwrite. This is separate from ordinary `write.createDirs`. Cancellation, timeout, disconnect and uncertain writes are never replayed; an already-started effect may remain. Unavailable Nodes/capabilities never fall back to Main. The existing post-write image partial result retains `fileWritten` and the actual path. A successful upload or file delivery does not commit a model turn or create destination Session history.

Executable primitive file consumers are mapped in [.NET providers](./dotnet-node-providers.md). Code/PTY services, Shell HTTP, Worker ownership and external-owner execution retain separate owners.
