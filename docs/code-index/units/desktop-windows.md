## Purpose

The Windows Desktop app: a WinUI 3 window and notification icon around the complete same-process [Main host](./host-runtime.md), its native login, navigation and app windows, Desktop data, and the acceptance of its extracted package. [D-desktop-app-windows](#d-desktop-app-windows) is the app-window policy of both Desktop hosts; the [macOS host](./desktop-macos.md) follows it. Instance switching is owned by [Desktop instances](./desktop-instances.md), packaging and the installer by [Desktop packages](./desktop-packages.md).

## Stable methods and callers

- `Foxwarm.Desktop` is a `net10.0-windows10.0.19041.0`/`win-x64` WinUI 3 host using the Windows App SDK WinUI component 2.6.5 and WebView2 SDK 1.0.4258.31. It owns a per-user named mutex across login sessions (`NamedWaitHandleOptions` with `CurrentUserOnly=true`, `CurrentSessionOnly=false`), one window/tray, one embedded Main host and one WebView2 profile. Close hides; Open restores; Exit drains/disposes; Windows shutdown is not hide-to-tray. While the tray adapter is live, the registered `TaskbarCreated` message re-adds its icon after Explorer recreates the taskbar, preserving the previous NotifyIcon recovery behavior.

## Desktop boundary

Desktop references `Microsoft.WindowsAppSDK.WinUI` rather than the umbrella package. Its supported Base/Foundation/InteractiveExperiences dependency closure owns the app-local manifest, rendering/input resources and payload copy; unused ML/AI/Search/Widgets/DWrite component packages are not selected. The common component license and Base's complete common notice (including WinUI's notice) accompany the retained WebView2/Main dependency notices; the explicit Base reference for that notice adds no component to WinUI's transitive closure. The WinUI host keeps the actual Desktop entry and same-process MainHost. `App.xaml` supplies the standard application/control resources and application PRI through the SDK XAML pipeline; the window itself remains C#-constructed and hosts the original WebUI. Direct resource access from the code-only Application failed Windows startup with `Application.Resources` returning `0x8000FFFF`; standard `InitializeComponent` resource initialization passed the managed GUI lane. `DesktopNative` supplies the native tray menu, minimum window size and Windows session-end messages without a WindowsDesktop/WinForms dependency. The SDK auto-initializer is disabled; the included self-contained WinRT initializer is called explicitly after exec/Vector/Code helper dispatch and single-instance acquisition. `PrepareDesktopWinRtInitializer` includes that SDK source before XAML's temporary assembly compilation, which also compiles the custom Program entry. The WinRT WebView2 projection represents cookie expiry as Unix seconds, unlike the previous managed wrapper's `DateTime`. Desktop authentication uses the existing Main JSON source context so that this call does not require reflection serialization under NativeAOT.

The release package is a NativeAOT publication ([decision](./desktop-packages.md#windows-desktop-app)): `PublishAot=true` with the WinRT AOT optimizer compiles Main, Desktop and the WinRT projections into `Foxwarm.Desktop.exe`; a build without it remains a managed development build. Desktop code must stay free of trim/AOT warnings, because reflection-based JSON fails only in the native build: `JsonArray.Add<string>` in `DesktopFrame.StateJson` threw on the first window deactivation, which WinUI turned into a stowed-exception exit (0xC000027B) during a ToolScript turn; the items are now `JsonNode` values. Windows App SDK API metadata minimum is 17763, with the separate .NET 10 supported-OS policy unchanged. Self-contained WinUI publication invokes Windows manifest/XAML/PRI tooling, so the Windows release job produces Desktop; Linux C# compilation alone is not a complete Desktop build. The release acceptance of the extracted native ZIP is described in [Desktop producer and qualification](./desktop-packages.md#desktop-producer-and-qualification). Real Explorer recreation has also been exercised; cross-login-session ownership, Windows session-end and external-channel paths remain outside it.

`DesktopInstance` owns the per-user single-instance mutex (`Foxwarm.Desktop.<user SID>`) and, for the lock holder, two auto-reset events: `Foxwarm.Desktop.Open.<user SID>` enqueues the tray's **Open** (`OpenWindow`), and `Foxwarm.Desktop.Exit.<user SID>` the tray's **Exit** (`ExitApplication`), so Main shuts down normally. A further ordinary start that finds the lock held allows the running copy to take the foreground, signals the open event (waiting up to 10 seconds for a copy that is still starting to create it) and exits; there is no already-running message. The lock is per user, not per directory, so starting an installed copy while a portable one runs shows the portable one's window. Two arguments exist for the [Windows installer](./desktop-packages.md#windows-desktop-installer) and nothing else. `--exit` takes no lock: it finds this user's processes whose image path equals its own executable (the Desktop and its helper children), signals the event if any exist, and waits up to 60 seconds until none remains, returning 0, or 1 on timeout; a copy started from another path is not touched. `--tray`, the sign-in start, starts Main (when the local instance is selected) with only the notification icon; the window is activated, and WebView2 created, when it is first opened (`shown` gates the WebView step of startup), and a `--tray` start that finds the lock held exits without signaling anything.

`CaptureDesktopAsync` retains file-token validation, enables WebUI and selects IPv4 loopback independently of configured server port/bind/public URL. It reads the last successfully bound port from `state/desktop-port`, defaulting to zero. The desktop saves the actual successful port after startup so ordinary restarts retain the WebUI origin and browser preferences. Kestrel's normal socket factory first binds that remembered endpoint; only `AddressAlreadyInUse` retries the socket bind at port zero. This does not recreate Main, replay Session startup, probe/adopt the occupant, or migrate browser preferences across origins. The startup callback updates the shared public address before the desktop consumes it. Console port/public-prefix validation remains unchanged. [2026-11-23] Local Main starts at launch only when the local instance is selected, and otherwise when it is selected; the menu can stop it again ([D-desktop-instances](./desktop-instances.md#d-desktop-instances)). The native host posts the token only to that owned endpoint's existing `/api/auth`, then creates an HttpOnly/Strict cookie directly through its owned WebView2 CookieManager, scoped to that actual local endpoint with a 365-day UTC expiry and Secure only for HTTPS, and never includes the token in navigation or arbitrary requests. Navigation and new windows follow [D-desktop-app-windows](#d-desktop-app-windows); HTTP resource loads outside the selected instance's scope are blocked in every window. There is no host object and no general message bridge. [2026-11-13] User decision: the only page-to-host channel is the custom window frame's one-way `frame-regions` message and, since 2026-11-23, the brand row's one-way `instance-menu` message (`IsWebMessageEnabled` with `WebMessageReceived`), accepted only from the selected instance's scope and only when they match the exact schemas, with no replies or other capabilities; contract in [D-window-frame](./webui-window-frame.md#d-window-frame). The window extends its content into the tall (48 px) caption, so the WebUI's title row and the caption buttons share one row, keeps `Window.Title` synced to `document.title`, and sets explicit caption rectangles from each report (`DesktopFrame`).

### D-desktop-app-windows

[2026-11-14] User decision: same-origin new windows open in the app on both Desktop hosts; other web pages open in the default browser. The policy is shared (`DesktopNavigation`, unit-tested) and applies to every window. [2026-11-23] "The app's origin" is the selected instance's scope, its origin plus its base path ([D-desktop-instances](./desktop-instances.md#scope)); for the local instance that is the owned endpoint with base `/`, so its behaviour is unchanged. Switching instances closes the app windows first.

- **Targets.** `Classify` sorts a top-level navigation or new-window request into the app's scope (scheme, host and port of the selected instance, and a path within its base path), `about:blank`, another HTTP(S) page, or anything else. The app's origin and `about:blank` stay in the app; other HTTP(S) pages go to the default browser; everything else is refused. A new-window request for another origin opens the browser and no app window.
- **App windows.** A same-origin or blank new-window request opens an app window whose web view is the opener's new web contents: WebView2's `NewWindowRequested` gets a new `CoreWebView2` in a new WinUI window on the same environment and profile (`e.NewWindow` under a deferral), and WKWebView's `createWebViewWith` returns a web view built from WebKit's configuration in a new `NSWindow`. Cookies, storage and `window.opener`/postMessage carry over; callers that null `opener` keep doing so. Scripts, filters and handlers are installed before the contents attach. WebView2 doesn't run document-created scripts in the first document of such a window, so the Windows frame state is also delivered on `DOMContentLoaded` (when absent) with a `foxwarm-frame` event, which the page already listens for. `window.close()` closes the window.
- **Size and place.** window.open's `width`/`height` (CSS px) set the content size, clamped between 480 × 360 and the work area; without them the window is 1100 × 760. The whole window, including a system title bar, stays within the work area. It cascades 32 px from its opener inside the work area.
- **Frame.** The WebUI document at the app root (the base path, with or without its trailing slash) uses the existing custom frame. [2026-11-18] User decision: a window opened at the Code workbench route (`/vscode-web` with or without the trailing slash) also uses the [frame protocol](./webui-window-frame.md#d-window-frame). Code OSS's own menu bar, command center and layout actions share one row with native window buttons, removing the second title bar. Setup and error documents without a frame report have a blank native drag strip above the page, clear of the native buttons. Files, other same-origin routes and blank windows keep their system title bar and have no page-to-host channel. The decision is made once, from the requested URL; the frame channel gains no commands.
- **Blank windows.** A blank window whose first top-level navigation leaves the origin is handed to the default browser and closed. This is the generic `window.open('')` then `location = url` pattern; there is no OAuth-specific handling ([open question](./dotnet-mcp-oauth.md#open-questions)).
- **Lifecycle.** App windows close normally; only the main window hides to the tray. Exit, Windows session end and macOS Quit close every app window, and no new one opens after that starts. macOS gives each app window its own user content controller (WebKit's configuration otherwise shares the opener's), with the same off-origin content rules.

## Desktop data and Windows Main

Default desktop data is `%LOCALAPPDATA%\Foxwarm\Desktop\data`, including host authority and the owned `webview2` profile. Desktop passes the ordinary `ModelConfiguration(HostPaths.ForDataRoot(...))` into the canonical `MainHost` overload and uses `MainHost.StartAsync`. `FOXWARM_DATA_DIR` selects data; captured `paths.agentsDir` selects the Agent root, defaulting to `<data>/agents`. Every Agent, including main, owns `<Agents root>/<name>`. The former sibling-workspace caller is retired; Desktop does not detect, retain or migrate it, and existing user files are not moved or deleted. Generic retained-data readers remain independently supported. The ZIP consumes Core's shared resource graph (`webui-dist`, skills, templates, Node and extension resources, native dependencies/notices) and embeds the .NET 10 NETCore and AspNetCore frameworks, not state/credentials. Core-only CLI scripts/package metadata and its console apphost/runtimeconfig are omitted. WebView2 Evergreen is required. The repository's Linux PTY target is skipped for Windows RIDs even when built on Linux.

Windows Main includes native PowerShell exec, ConPTY terminals/Code helper entry and the pinned ordinary native Monty worker; see their local-IO, terminal and ToolScript units. Optional official Code workbench/HEIF/external-service assets are not supplied. Vector dependencies follow the existing optional owner contract. The identity ledger retains flush-to-disk and atomic replacement on Windows; directory synchronization uses the pre-existing `Unsupported` result. Successful normal restart tests do not qualify power-loss durability.

## Tests

Native WebView2 CookieManager execution requires Windows; HTTP tests and cross-builds do not qualify it. The Windows job of `.github/workflows/release.yml` runs `qualify-desktop-package.mjs` against the extracted distributable ZIP, using a fresh temporary data directory, canonical Agent directories and unrelated cwd. Its ordinary executable entry creates the loopback host and native WebView2 cookie; the test also checks the configured canonical Agent root and cookie-authenticated WebSocket handshake, and attaches through WebView2's debugging option (child environment for non-elevated execution, app-specific HKLM policy on the disposable elevated runner) and checks authenticated original WebUI/Setup, protected HTTP, extension resources, packaged esbuild/sharp execution, a real native ToolScript write and exec-helper invocation through a local mock provider, the Vector child, the absence of CoreCLR, close-to-tray, notification-icon reopen and Exit, graceful admin shutdown and persisted origin/token/models/history after restart ([details](./desktop-packages.md#desktop-producer-and-qualification)). Cleanup (`desktop-cleanup.mjs`) runs every step, treats a Desktop process that already exited (`taskkill` status 128) as ended, and never replaces a failed acceptance's error with a cleanup failure; cleanup failures are reported on stderr and thrown only after a passed acceptance. It never signs in by injecting a browser cookie. Windows shutdown, HiDPI rendering and power-loss durability remain outside this lane. Original browser login qualification is described in [WebUI sign-in](./webui-login.md#verification).
