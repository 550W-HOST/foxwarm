Phase 2 of [tool operation authorization](./tool-operation-authorization.md#delivery-phases): every call builds its plan and is approved in stages under version-1 rules. That unit owns the design, its decisions and the delivery phases; the user decision governing ask and its phase-2 replacement of internal-step coverage is [D-dispatch-approval-ask](../threads/tool-dispatch-authorization.md#d-dispatch-approval-ask). The ask outcome, records and waiting are owned by [tool authorization](./tool-authorization.md#ask-outcome-and-approvals) and [Session questions](./session-questions.md#tool-approvals).

## Stages

- **A. Protected inputs.** These are inputs whose content decides facts of the call before it can be assessed: today the `set_config` candidate of `config` and `models`. They are assessed as their concrete sub-requests. Other inputs read before the effect (explain policy and candidate files, `add_secret` sources, compaction plan files) are concrete sub-requests of stage B.
  - A deny stops the call.
  - Asks produce one input approval.
  - Admitted bytes are captured, and the effect consumes them; they are never re-read.
- **B. Plan assessment.** The plan is derived from normalized arguments, prospective facts and admitted inputs. Every obligation with known facts is assessed: the primary request, concrete sub-requests, policy probes, and retained final requests such as each cascade member.
  - One call approval lists every asking obligation and operation.
  - Its fingerprints bind each request's identity, raw arguments and facts; from phase 3 also normalized arguments and operations. Admitted input bytes are consumed, never re-read.
- **C. Final requests.** Each owner boundary re-evaluates its retained requests against **current policy and current facts**, inside the existing registry, configuration and timer lanes. The grant is consulted only when that evaluation asks. It covers the ask only if B approved an identical request: same identity, raw arguments and facts.
  - A deny always stops, including a deny installed while the call waited.
  - A new or changed ask fails closed with `tool_approval_unavailable`, before the protected effect.
  - An unchanged operation never short-cuts current-policy evaluation. Effects that already completed are not rolled back.

Nested calls keep their own gates, and external principals cannot be asked, as today. Answer-time storage of an `ask_user` secret happens after the invocation, carries no tool approval scope, and keeps the existing rules for filling configured names.

## Implementation

`SessionManager.AuthorizeCallAsync` (`SessionManager.ApprovalPlan.cs`) is the gate's assessment; `SessionToolExecutor.AuthorizeAsync` turns its `ToolApprovalRequiredException` into one approval request per stage and adds the grant to the invocation's `ToolApprovalScope`.

- **Staging only where an ask is possible.** When no effective layer of the caller's Agent holds an enabled ask rule or an asking default (`PolicyCanAsk`), the gate assesses only the call's own request, exactly as before, and every other request is decided by its owner. With an ask possible, a call whose own request and planned checks all allow or deny still dispatches as before: a denied sub-request is left to its owner, which reports it in the existing form. A deny among the checks stops the call at the gate only when the call asks or already holds an approval, so it is never offered for approval or dispatched after one. `Calls_without_asks_decide_as_at_the_base_revision` (fixture `approval-staging-equality.json`, recorded at the base revision) checks this for real calls under no-ask and unrelated-ask policies.
- **A today.** Stage A covers the `set_config` candidate of `config` and `models`, the only input whose content decides authorization facts under version-1 rules (its secret facts). Its read is assessed first; a deny stops derivation: a call that asks is denied at the gate and never offered for approval, and a call without any other ask is left to its owner, which reports the denial as before; asks become one input approval (`stage: input`). After admission, the gate captures the candidate bytes once (`ToolApprovalScope.Inputs`); `SecretFactsAsync` and `InstallConfigAsync` consume them, so the installed candidate is the one whose facts were approved and no re-read happens. The other inputs read before the effect are stage-B sub-requests.
- **B today.** `CallChecks` takes the requests of `OperationPlan.Derive` that can be built from the arguments and current facts (sub-requests, retained final requests such as each cascade member with its own `nodeId`, and the optional default-cwd probe), plus `create_session` prompt-file reads and `add_secret` `fromConfig` reads, built as their owners build them. Each is assessed as its owner will assess it; one whose assessment fails (invalid arguments, an unresolvable path) is left to its owner. Asking checks join one call approval with the call; the record lists them as `checks`, and the grant lists the fingerprint of each. Options combine across every asking check: shortest timeout, approver intersection. The optional default-cwd probe joins an approval the call needs anyway and never causes one; an explain probe view is skipped for the caller itself (aliases included) and for a missing Session, and its deny does not stop the call because the owner reports it as that probe's error. A new-Session timer that will ask is checked for its creation target before approval, which an ask or indeterminate outcome rejects, so it is never offered for approval.
- **C today.** Every owner check runs `AuthorizeToolAsync` against current policy and facts; deny throws first; an ask passes only when a grant lists the request's fingerprint (`SessionManager.ApprovalFingerprint`: identity, raw arguments, path facts, Node targets, Session target and Task owner, resolved even when no rule needs them, and secret facts). The gate's re-check after each approval re-runs A and B: a deny installed during the wait stops the call before dispatch with its record `cancelled`/`notStarted`; a changed request asks again at most three times per stage. Changes after dispatch (a cascade member added before the registry mutation, changed destination secrets inside the configuration lane, a timer creation target that started asking) fail closed at that owner before its effect.

## Catalog notes

Phase 1 found these in the code; they are not decisions. Phase 2's resolution follows each note.

- **Non-string actions.** The `session` handler reads a non-string `action` (for example `["list"]`) as absent and runs `status`, while `node` and `skill` reject it. A version-1 `action` rule never matches that spelling. The phase-1 normalizer mirrors each handler, and the phase-3 normalizer parity corpus needs the case. *Phase 2:* out of scope. Staging evaluates version-1 rules against the original raw arguments and adds no normalizer, so the spelling decides exactly as before; the handler behavior is unchanged.
- **Call-level identity for stage C.** One call site can check several obligations, and one obligation can be checked at several sites: the timer primary is checked outside and inside the timer lane, `set_config`'s local check runs before install and again inside the configuration lane, and the `add_secret` store recheck runs in two members. Stage C needs an identity per assessed call, not per site. *Phase 2:* resolved. A grant lists request fingerprints (`SessionManager.ApprovalFingerprint`), independent of the site: every site that checks the same request computes the same fingerprint, so one approval covers all of them, and a site whose request differs is not covered.
- **Checks without a primary call.** Checks entered through `ToolApprovalScope.Detach` (the detached copy transfer) or after the invocation (answer-time `ask_user` storage) have no current primary request, so phase 1 attributes them as their own capability. Stage C should carry the admitted plan's obligation ID into these paths. *Phase 2:* resolved for `Detach`: the detached scope carries the call's grants and its primary request, so the transfer's checks are attributed to the call and pass an ask only for a listed request. Answer-time `ask_user` storage stays out of scope: it runs after the invocation with no tool approval scope and keeps the existing rules for filling configured names.
