## Contracts and rationale

The root package `main` remains a JavaScript execution boundary. Directory/package execution starts managed Main; it is not a newly defined import API, and no restrictive exports map is added. The public `foxwarm` bin remains the [one-shot dispatcher](./core-delivery-cli.md), with help on no arguments and no new start subcommand. Missing managed output/runtime never selects TypeScript Main.

`coreExecutable` selects a published apphost or DLL, otherwise the selected source `runtime/current/Foxwarm.dll`, resolved to its stable real path. Main and one-shot JS frontends share this selector. It unconditionally supplies the known package installation identity as a leading internal `--installation-root <root>` entry pair; Program consumes that metadata before helper/CLI/Main dispatch and forwards explicit paths only to owners needing them. This recognized internal argument is callable directly but is not an advertised public CLI configuration option. No environment application-root selection, root search or cwd adoption participates. Direct DLL/apphost defaults to its executable/resource directory. Configuration follows [captured installation paths](./host-runtime.md); source launch must not move data into the binary output or discover another installation from cwd. Main preserves caller arguments, cwd and stdio.

Foreground package execution replaces an earlier in-process Main. A spawn without parent ownership would leave Main alive when an outer operator or consumer terminates that JS entry. The foreground launcher therefore keeps one local connection independent of stdin. Unix passes an already-connected extra stdio pipe at fd 3, without creating a filesystem socket address or changing `TMPDIR` for ordinary temporary files. Windows retains its UUID-named pipe. Signals request stop over the connection; connection loss, including hard parent termination, requests the ordinary Main host lifetime stop and ordered Session drain. Parent stop is connected before host startup, including the interval while an external channel initializes after HTTP starts. Main retains and stops that initializer before dependency teardown; see [host startup](./host-runtime.md). Windows spawning avoids libuv's kill-on-parent-exit child job so pipe-driven shutdown can finish an accepted canonical publication after hard launcher loss. The launcher still inherits stdio and references/awaits Main; this Windows process flag does not make the foreground entry a background service. Linux process-group behavior is unchanged. This is not the CLI's abrupt one-shot exit policy, does not kill independent exec jobs, and is not a daemon manager. [Windows background startup](./windows-service-scripts.md) launches managed Main directly and intentionally survives the completed start client.

## Build and controls

`scripts/build-source.js` owns source output preparation and promotion for complete and backend-only npm builds. Every build clears and compiles into `build/core`, never into the runnable output. Before selection, the staged Core runs [read-only Session upgrade inspection](./session-upgrade-inspection.md); local warnings allow selection while global/active-Worker blockers leave the previous selection and staging intact. Success moves the directory into a unique `runtime/` child and selects it with `runtime/current` (Linux directory symlink, Windows junction). `--stage-only` defers promotion; `--promote` performs the move/selection after the controls stop Main. Failed builds remove partial staging and leave the selected payload alone. Both top-level output directories are Git-ignored. Existing processes keep their resolved real paths. Older directories are retained because independent Unix exec wrappers invoke their original DLL again for `--exec-status`; cleanup is operator-owned after all consumers finish. The first upgrade also leaves pre-existing Debug output untouched for those consumers. No concurrent-build coordination, rollback or automatic retention service is introduced.

Default `build` prepares [complete delivery resources](./core-delivery-cli.md#build-and-resource-boundary); `build-all` installs root/WebUI lockfiles first. `build:core` uses the same staging/selection without preparing assets. Plain .NET builds remain independent of npm and do not change package/CLI runtime selection. A standalone npm build selects the next launch output without restarting an existing Main. `build:reference` retains the TS Main oracle explicitly. Broad reference/package tests and Source Archive seeding still require that explicit build; default unit tests also run the managed solution, and the full-application harness starts managed Main. `build:node`, `node`, `cli-node` and `Dockerfile.node` use Shared/TS CLI builds without .NET or a native CLI replacement.

Tmux start refuses an exact existing session. Restart chooses the exact dedicated window/active pane or creates it; stable pane IDs survive renaming. Input is literal with Enter separate. Relevant path/config/runtime environment (not host port or bind overrides) is supplied from the invocation rather than inherited from a stale tmux server. Bash start/restart always launch their own package installation, ignoring inherited retired application-root controls; relative data/config settings remain installation-relative. Bash start/restart build with `--stage-only`, including first startup. Restart sends Ctrl+C and waits for the foreground process group to return the terminal to its shell before promoting and sending startup, with a bounded failure instead of overlapping Main. Stop also uses exact session/window selection. Tests use only private sockets/servers.

Both source installers preserve checkout/branch selection, external data directories, the `data_dir` pointer and OOBE URL flow. They diagnose a net10.0-capable selected SDK and ASP.NET Core 10 runtime without pinning a local patch SDK or installing host tools. Linux source installation needs Python 3/make/G++ for the retained node-pty npm build and GCC/pty.h/libutil for the managed PTY helper. Fresh pinned Monty acquisition uses Python 3; Windows can reuse its cached native output. No optional image decoder is required. Website installer copies are generated byte-exactly by the existing website build.

## Supported candidate boundary

This entry and the shared production/test Docker delivery remain a candidate, not a public promotion or deployment. Managed/default CI and application-lane ownership are mapped in [test runner](./test-runner.md) and [full-application E2E](./full-app-e2e.md). Linux x64 and Windows x64 are candidate targets; cross-publish is not Windows execution qualification and macOS Main is not qualified here. Other-platform TS Node clients and retained reference code remain supported boundaries. Main TUI is not implemented: explicit `--tui` fails before startup, while persisted `bot.enableTUI` logs an ignored/unsupported diagnostic. Worker/controller configuration and records are retained without implementing those hosts. The source promotion inspection classifies existing Worker lifecycle/mailbox evidence before selection; ordinary startup does not add a Worker scan or replay. Native Source exec adoption remains a separate drain-versus-adopt decision before a real cutover.

## Evidence

`scripts/main.test.js` uses owned application/data/cwd trees and the actual managed output, checks directory/resolved-package startup, settings precedence, missing output/runtime, TUI response, no TS backend loading, signal exit, parent loss, and a held accepted canonical publication owner during drain. Held production Matrix startup controls send real SIGTERM/SIGKILL and check Main exit, refused new admission and no restart after the response is released. Their Linux process check treats `ENOENT` and `ESRCH` from `/proc/<pid>/stat` as process disappearance, counts zombies as stopped and propagates other errors. Long-`TMPDIR` controls retain the caller's cwd, standard streams and temporary-file environment, deliver a stop queued before managed entry, and preserve an independent native exec helper through hard launcher loss and Main drain; the helper allocates its ordinary temporary file in the selected long directory. `scripts/main.test.js` also executes real managed Main through Bash start/restart on a private tmux server, checking installation-relative data/config, previous Main exit and stop-before-restart ordering. Only the fixture build command is stubbed. `scripts/tmux-scripts.test.js` checks exact targeting and failure propagation on private servers. `scripts/source-installer.test.js` executes the Bash installer with fixture-owned Git/build/start boundaries to check prerequisite failures, compatible SDK selection, branch/path/data and OOBE behavior. Its compiler stub consumes the piped PTY probe source before returning the selected success/failure status, so an early stub exit cannot break the producer under the installer's `pipefail`. Its private bin selects the invoking test process's real Node executable, so the isolated PATH does not fall back to an older system Node in CI. The missing-SDK scenario exposes only that private bin after removing its SDK stub, so a system dotnet cannot satisfy an intentionally absent prerequisite. Windows actual launcher/installer qualification is independently required.

The opt-in `FOXWARM_TEST_SOURCE_UPDATE=1 node --test scripts/source-update.test.js` lane owns a disposable source/dependency/data tree and private tmux server. It performs real complete builds for first start, deliberate compiler failure and changed-version restart; verifies old output/process preservation, new resolved assembly execution, retained configuration/Session data and the delayed original `--exec-status` helper; and exercises source one-shot selection plus published apphost/DLL Main startup and drain. Only npm dependency installation is replaced with the fixture's installed locked dependencies. It does not qualify clean dependency acquisition or Windows execution.
