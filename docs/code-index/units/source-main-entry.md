## Contracts and rationale

The root package `main` remains a JavaScript execution boundary. Directory/package execution starts managed Main; it is not a newly defined import API, and no restrictive exports map is added. The public `foxwarm` bin remains the [one-shot dispatcher](./core-delivery-cli.md), with help on no arguments and no new start subcommand. Missing managed output/runtime never selects TypeScript Main.

`coreExecutable` selects a published apphost or DLL, otherwise the explicit source Debug DLL. Main and one-shot JS frontends use that single location selector and `coreEnvironment`. The latter supplies the checkout installation identity unless `FOXWARM_APP_ROOT` is explicit. Configuration follows [captured installation paths](./host-runtime.md); source launch must not move data into the binary output or discover another installation from cwd. Main preserves caller arguments, cwd and stdio.

Foreground package execution replaces an earlier in-process Main. A spawn without parent ownership would leave Main alive when an outer operator or consumer terminates that JS entry. The foreground launcher therefore keeps one local connection independent of stdin. Signals request stop over it; connection loss, including hard parent termination, requests the ordinary Main host lifetime stop and ordered Session drain. This is not the CLI's abrupt one-shot exit policy, does not kill independent exec jobs, and is not a daemon manager. [Windows background startup](./windows-service-scripts.md) launches managed Main directly and intentionally survives the completed start client.

## Build and controls

Default `build` prepares [complete delivery resources](./core-delivery-cli.md#build-and-resource-boundary); `build-all` installs root/WebUI lockfiles first. Plain .NET builds remain independent of npm. `build:reference` retains the TS Main oracle explicitly. Existing broad unit/app runners and default CI still need that lane until their separate conversion. `build:node`, `node`, `cli-node` and `Dockerfile.node` use Shared/TS CLI builds without .NET or a native CLI replacement.

Tmux start refuses an exact existing session. Restart chooses the exact dedicated window/active pane or creates it; stable pane IDs survive renaming. Input is literal with Enter separate. Relevant path/config/runtime environment is supplied from the invocation rather than inherited from a stale tmux server. Restart sends Ctrl+C and waits for the foreground process group to return the terminal to its shell before sending startup, with a bounded failure instead of overlapping Main. Stop also uses exact session/window selection. Tests use only private sockets/servers.

Both source installers preserve checkout/branch selection, external data directories, the `data_dir` pointer and OOBE URL flow. They diagnose a net10.0-capable selected SDK and ASP.NET Core 10 runtime without pinning a local patch SDK or installing host tools. Linux source installation needs Python 3/make/G++ for the retained node-pty npm build and GCC/pty.h/libutil for the managed PTY helper. Fresh pinned Monty acquisition uses Python 3; Windows can reuse its cached native output. No optional image decoder is required. Website installer copies are generated byte-exactly by the existing website build.

## Supported candidate boundary

This source entry is not a public promotion, deployment, production/test Docker migration or full CI/test-lane cutover. Linux x64 and Windows x64 are candidate targets; cross-publish is not Windows execution qualification and macOS Main is not qualified here. Other-platform TS Node clients and retained reference code remain supported boundaries. Main TUI is not implemented: explicit `--tui` fails before startup, while persisted `bot.enableTUI` logs an ignored/unsupported diagnostic. Worker/controller configuration and records are retained without new global rejection/migration or claims that those hosts exist. Native Source exec adoption remains a separate drain-versus-adopt decision before a real cutover.

## Evidence

`scripts/main.test.js` uses owned application/data/cwd trees and the actual managed output, checks directory/resolved-package startup, settings precedence, missing output/runtime, TUI response, no TS backend loading, signal exit, parent loss, and a held accepted canonical publication owner during drain. `scripts/tmux-scripts.test.js` checks exact targeting and failure propagation on private servers. `scripts/source-installer.test.js` executes the Bash installer with fixture-owned Git/build/start boundaries to check prerequisite failures, compatible SDK selection, branch/path/data and OOBE behavior. Windows actual launcher/installer qualification is independently required.
