# Unit: Managed source Main entry

## Contracts and rationale

The root package `main` remains a JavaScript execution boundary. Directory/package execution starts managed Main; it is not a newly defined import API, and no restrictive exports map is added. The public `foxwarm` bin remains the [one-shot dispatcher](./core-delivery-cli.md), with help on no arguments and no new start subcommand. Missing managed output/runtime never selects TypeScript Main.

`coreExecutable` selects a published apphost or DLL, otherwise the explicit source Debug DLL. Main and one-shot JS frontends share this selector. It unconditionally supplies the known package installation identity as a leading internal `--installation-root <root>` entry pair; Program consumes that metadata before helper/CLI/Main dispatch and forwards explicit paths only to owners needing them. This recognized internal argument is callable directly but is not an advertised public CLI configuration option. No environment application-root selection, root search or cwd adoption participates. Direct DLL/apphost defaults to its executable/resource directory. Configuration follows [captured installation paths](./host-runtime.md); source launch must not move data into the binary output or discover another installation from cwd. Main preserves caller arguments, cwd and stdio.

Foreground package execution replaces an earlier in-process Main. A spawn without parent ownership would leave Main alive when an outer operator or consumer terminates that JS entry. The foreground launcher therefore keeps one local connection independent of stdin. Unix passes an already-connected extra stdio pipe at fd 3, without creating a filesystem socket address or changing `TMPDIR` for ordinary temporary files. Windows retains its UUID-named pipe. Signals request stop over the connection; connection loss, including hard parent termination, requests the ordinary Main host lifetime stop and ordered Session drain. Parent stop is connected before host startup, including the interval while an external channel initializes after HTTP starts. Main retains and stops that initializer before dependency teardown; see [host startup](./host-runtime.md). Windows spawning avoids libuv's kill-on-parent-exit child job so pipe-driven shutdown can finish an accepted canonical publication after hard launcher loss. The launcher still inherits stdio and references/awaits Main; this Windows process flag does not make the foreground entry a background service. Linux process-group behavior is unchanged. This is not the CLI's abrupt one-shot exit policy, does not kill independent exec jobs, and is not a daemon manager. [Windows background startup](./windows-service-scripts.md) launches managed Main directly and intentionally survives the completed start client.

## Build and controls

Default `build` prepares [complete delivery resources](./core-delivery-cli.md#build-and-resource-boundary); `build-all` installs root/WebUI lockfiles first. Plain .NET builds remain independent of npm. `build:reference` retains the TS Main oracle explicitly. Broad reference/package tests and Source Archive seeding still require that explicit build; default unit tests also run the managed solution, and the full-application harness starts managed Main. `build:node`, `node`, `cli-node` and `Dockerfile.node` use Shared/TS CLI builds without .NET or a native CLI replacement.

Tmux start refuses an exact existing session. Restart chooses the exact dedicated window/active pane or creates it; stable pane IDs survive renaming. Input is literal with Enter separate. Relevant path/config/runtime environment (not host port or bind overrides) is supplied from the invocation rather than inherited from a stale tmux server. Bash start/restart always launch their own package installation, ignoring inherited retired application-root controls; relative data/config settings remain installation-relative. Restart sends Ctrl+C and waits for the foreground process group to return the terminal to its shell before sending startup, with a bounded failure instead of overlapping Main. Stop also uses exact session/window selection. Tests use only private sockets/servers.

Both source installers preserve checkout/branch selection, external data directories, the `data_dir` pointer and OOBE URL flow. They diagnose a net10.0-capable selected SDK and ASP.NET Core 10 runtime without pinning a local patch SDK or installing host tools. Linux source installation needs Python 3/make/G++ for the retained node-pty npm build and GCC/pty.h/libutil for the managed PTY helper. Fresh pinned Monty acquisition uses Python 3; Windows can reuse its cached native output. No optional image decoder is required. Website installer copies are generated byte-exactly by the existing website build.

## Supported candidate boundary

This entry and the shared production/test Docker delivery remain a candidate, not a public promotion or deployment. Managed/default CI and application-lane ownership are mapped in [test runner](./test-runner.md) and [full-application E2E](./full-app-e2e.md). Linux x64 and Windows x64 are candidate targets; cross-publish is not Windows execution qualification and macOS Main is not qualified here. Other-platform TS Node clients and retained reference code remain supported boundaries. Main TUI is not implemented: explicit `--tui` fails before startup, while persisted `bot.enableTUI` logs an ignored/unsupported diagnostic. Worker/controller configuration and records are retained without new global rejection/migration or claims that those hosts exist. Native Source exec adoption remains a separate drain-versus-adopt decision before a real cutover.

## Evidence

`scripts/main.test.js` uses owned application/data/cwd trees and the actual managed output, checks directory/resolved-package startup, settings precedence, missing output/runtime, TUI response, no TS backend loading, signal exit, parent loss, and a held accepted canonical publication owner during drain. Long-`TMPDIR` controls retain the caller's cwd, standard streams and temporary-file environment, deliver a stop queued before managed entry, and preserve an independent native exec helper through hard launcher loss and Main drain; the helper allocates its ordinary temporary file in the selected long directory. `scripts/main.test.js` also executes real managed Main through Bash start/restart on private tmux servers, checking fixed package installation selection with spaces despite relative/absolute/stale retired settings, installation-relative data/config and stop-before-restart. Only the fixture build command is stubbed; two valid installation candidates expose wrong-root startup. `scripts/tmux-scripts.test.js` checks exact targeting and failure propagation on private servers. `scripts/source-installer.test.js` executes the Bash installer with fixture-owned Git/build/start boundaries to check prerequisite failures, compatible SDK selection, branch/path/data and OOBE behavior. Windows actual launcher/installer qualification is independently required.
