## Process and authorization

The operator provisions tenants. Each tenant receives a subdomain of a shared base domain. Third-party tenants require the external security review (2026-11-27).

`foxwarm operator serve` is a separate process in the hosted image. It opens no tenant runtime, serves only `/operator/v1`, checks the schema and the actual connection role against `schema_info.operator_role`, and loads the KEK. Its Kestrel listener binds `bot.httpHost` and `operator.port`; `operator.url` is its externally visible origin. Requests must address that host and port. A browser that sends an Origin must match it. TLS termination belongs to the ingress. Replicas do not expose the operator API, even to a tenant administrator. The [packaging](./hosted-packaging.md) gives the two roles separate services and separate database secrets.

`operator token create` uses the **migration** URL and checks the connected role owns `operator_credentials`. It prints a random 256-bit bearer token once; the table stores its SHA-256 digest and a digest prefix for lookup. The operator checks the digest and revocation on every API call. It neither accepts nor sets an authentication cookie. The remote CLI takes `--url ORIGIN --token-file FILE`, sends the bearer only to that origin, and disables redirects. It writes successful JSON to stdout and failures to stderr. Neither remote CLI nor operator API receives the migration credential.

## Tenant lifecycle and login

- `POST /tenants` requires `slug`, `profile` and `primaryHostname`. The immutable slug is a DNS label (`TenantSlugs`); the profile is `hosted` or `operator`. The hostname must match the deployment's `url` expansion for that slug, and must differ from the operator hostname. Custom domains are outside this release. `GET /tenants` and `GET /tenants/{slug}` return settings, never credential material.
- Creation is one cluster transaction: tenant record, storage identity, bootstrap lease, DEK wrapped under the KEK with the tenant ID as associated data, and primary hostname. A schema-owner function inserts only the wrapped key, with RLS and the normal epoch trigger under that bootstrap lease. The transaction releases the lease before committing. A unique-key conflict rolls back the entire creation. Empty configuration is represented by **absent** config and models rows, so first-run Setup can install them.
- The operator returns a setup token on creation and on `POST /tenants/{slug}/rotate`. Only its digest, expiration (24 hours) and redemption time are persisted. Rotation replaces any earlier setup token and increments `credential_version`. On the tenant's origin `POST /api/auth` exchanges a valid setup token for its reusable access token; the browser stores the latter, displays it for copying and waits for Continue. No other API accepts the setup token. Redemption checks the runtime token against the current version and spends the matching digest once under the tenant-row lock and lease fence. Competing exchanges cannot both succeed. A lost success response cannot be replayed; rotation supplies a fresh setup token. Expired and already-redeemed tokens receive distinct responses only when the digest matches. Successful exchanges use `Cache-Control: no-store`.
- A positive credential version selects a purpose-specific key derived from the DEK and version. Possession of the previous access token does not reveal the new one. Version zero preserves imported and previously created tenants' encrypted `http-token` credential. Other instance credentials are unchanged. The operator API never returns a reusable tenant access token; the legacy `hosted token` CLI refuses versioned credentials.
- **Object identity.** Newly provisioned tenants get `t/<tenant_id>-<UTC creation timestamp>/`. Existing/imported tenants whose `object_identity` is null retain `t/<slug>/`; all three blob stores and the conditional-write probe use the same identity. A later deletion must sweep the identity of the deleted row. A reused slug created by this API gets a new identity. `tenant_leases.deletion_epoch` already exists; the deletion boundary and sweeps are separate work.

## Settings and placement

`PATCH /tenants/{slug}` accepts `limits`, `journal`, `profile`, `ceiling` and `primaryHostname`. Each supplied field replaces that field; omitted fields remain unchanged. `journal` accepts `enabled` and `retentionDays`. An empty limits or journal object restores its defaults. A null `ceiling` removes the tenant override. `GET`/`PUT /profiles/{profile}/ceiling` read and replace a global profile ceiling, also nullable. Validation uses the same limits, journal and ceiling parsers as the runtime. All changes in a patch commit together. See [limits and journal policy](./hosted-egress-limits.md) and [ceiling precedence](./hosted-config.md#d-hosted-operator-ceiling).

**Live application** does not require a replica restart. Hostname changes invalidate the directory; a ceiling edit invalidates the running owner's policy cache. A changed profile, limit, journal setting or credential version retires the affected tenant's generation. Acquisition captures the tenant's settings revision. On `foxwarm_tenants` and on subscription or reconnect, the owner compares the stored settings and placement with its published grants. Each successful periodic renewal independently compares the revision: an edit missed by the listener is discovered by the next successful renewal (normally within 5 seconds). A locked or unreachable database still has the ordinary grant-proof and fence deadlines. There is no per-request database check. From commit until observation, the old settings or credential may still be accepted. Once observed, the gate latches, admitted work gets the usual bounded placement drain and a new request activates with current settings. Rotation also aborts open WebSocket and SSE streams authenticated with the old instance token. See [retirement and fencing](./hosted-runtime.md), including the hard stop when a drain cannot be confirmed.

`GET /placement` returns tenants with active, unexpired owner, epoch, lease age in seconds, hot and busy Session counts, and registered replica boots with role, product version, binary and reader levels, capacity, drain state and heartbeat time. Counts come from each published runtime's resident owners at heartbeat, keyed by tenant and epoch inside `replicas.capacity`. Unobserved and epoch-mismatched counts are null; an observed zero is zero. Ranking and eligibility use the existing [placement rules](./hosted-runtimes-host.md#d-hosted-placement).

## Tests

`OperatorProcessTests` provisions through the CLI against a separately launched operator process, then activates the tenant on a replica process and exercises authorization, role/origin separation, setup, settings, placement, expiry and rotation (including open streams). `TenantReplicaTests.SettingsRevisionDrainsOnlyTheChangedGeneration` separates notification, reconnect and renewal-only refresh and checks a sibling remains available. `PlacementRankTests` includes diagnostic capacity observations in the candidate inputs. `packages/webui/test/login.e2e.mjs` checks the browser stores and displays only the returned credential and continues on demand.
