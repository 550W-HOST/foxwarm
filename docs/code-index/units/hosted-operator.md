## Process and authorization

The operator provisions tenants. Each tenant receives a subdomain of a shared base domain. Third-party tenants require the external security review (2026-11-27).

`foxwarm operator serve` is a separate process in the hosted image. It opens no tenant runtime, serves only `/operator/v1`, checks the schema and the actual connection role against `schema_info.operator_role`, and loads the KEK. Its Kestrel listener binds `bot.httpHost` and `operator.port`; `operator.url` is its externally visible origin. Requests must address that host and port. A browser that sends an Origin must match it. TLS termination belongs to the ingress. The operator refuses to start if its hostname is assigned to a tenant. Unknown routes return an empty 404 before authentication. The replica front rejects the reserved hostname and path before tenant resolution, admission or rate limits. The [packaging](./hosted-packaging.md) gives the two roles separate services and separate database secrets.

`operator token create` uses the **migration** URL and checks the connected role owns `operator_credentials`. The operator role can read this table but cannot insert, update or delete rows. The command prints a random 256-bit bearer token once; the table stores its SHA-256 digest and a digest prefix for lookup. The operator checks the digest and revocation on every API call. It neither accepts nor sets an authentication cookie. The remote CLI takes `--url ORIGIN --token-file FILE`, sends the bearer only to that origin, and disables redirects. It writes successful JSON to stdout and failures to stderr. Neither remote CLI nor operator API receives the migration credential.

## Tenant lifecycle and login

- `POST /tenants` requires `slug`, `profile` and `primaryHostname`. The immutable slug is a DNS label (`TenantSlugs`); the profile is `hosted` or `operator`. The hostname must match the deployment's `url` expansion for that slug, and must differ from the operator hostname. Custom domains are outside this release. `GET /tenants` and `GET /tenants/{slug}` return settings, never credential material.
- Creation is one cluster transaction: tenant record, storage identity, bootstrap lease, DEK wrapped under the KEK with the tenant ID as associated data, and primary hostname. A schema-owner function inserts only the wrapped key, with RLS and the normal epoch trigger under that bootstrap lease. The transaction releases the lease before committing. A unique-key conflict rolls back the entire creation. Empty configuration is represented by **absent** config and models rows, so first-run Setup can install them.
- Creation and rotation issue a fresh random 256-bit setup token. `tenant_auth` stores its SHA-256 digest, 24-hour expiry and credential version. The app role has no table privileges. On the tenant origin, `POST /api/auth` can exchange the setup token whenever HTTP is enabled, including without a WebUI. Redemption takes the lease fence and locks the credential row; a matching unused, unexpired token is spent by installing the digest of a **new random 256-bit access token**. The successful response alone returns its plaintext, with `Cache-Control: no-store`. The browser displays the access token for copying before Continue. A lost response requires rotation. Matching spent or expired tokens receive distinct diagnoses.
- The owner loads its access verifier through a fenced snapshot and checks submitted tokens in constant time. After redemption the same owner installs the verifier locally. Downloads use a separate random signing key for that version. No reusable credential is derived from an imported key. Version zero preserves an existing installation's encrypted HTTP credential until rotation. `hosted token` refuses versioned credentials.
- **Object identity.** Migration 1200 installs an insert trigger on `tenants`. Every row created afterwards (by `db migrate`, import or the API) gets `t/<tenant_id>-<UTC creation timestamp>/`. Only rows already present when 1200 ran retain `t/<slug>/`. All three blob stores and the conditional-write probe use the resolved identity.
- **Rollout.** Finish upgrading the replicas before provisioning or rotating. The operator rejects both while a live registry heartbeat has binary level below 1200. A reader floor is checked at startup; applying a migration does not evict an already-running reader.

## Settings and placement

`PATCH /tenants/{slug}` accepts `limits`, `journal`, `profile`, `ceiling` and `primaryHostname`. Each supplied field replaces that field; omitted fields remain unchanged. `journal` accepts `enabled` and `retentionDays`. An empty limits or journal object restores its defaults. A null `ceiling` removes the tenant override. `GET`/`PUT /profiles/{profile}/ceiling` read and replace a global profile ceiling, also nullable. Validation uses the same limits, journal and ceiling parsers as the runtime. All changes in a patch commit together. See [limits and journal policy](./hosted-egress-limits.md) and [ceiling precedence](./hosted-config.md#d-hosted-operator-ceiling).

**Multi-tenant replicas.** Live application does not require a restart. Hostname changes invalidate the directory; a ceiling edit invalidates the running owner's policy cache. A changed profile, limit, journal setting or credential version retires the affected tenant's generation. Acquisition captures the tenant's settings revision. On `foxwarm_tenants` and on subscription or reconnect, the owner compares the stored settings and placement with its held grants, including starting and retiring generations. Each successful periodic renewal independently compares the revision: an edit missed by the listener is discovered by the next successful renewal (normally within 5 seconds). A locked or unreachable database still has the ordinary grant-proof and fence deadlines. There is no per-request database check. From commit until observation, the old settings or credential may still be accepted. Once observed, the gate latches, admitted work gets the usual bounded placement drain and a new request activates with current settings. A generation whose settings changed during startup cannot publish. Rotation also aborts WebSocket and SSE streams authenticated with the old token, including during an existing graceful drain. See [retirement and fencing](./hosted-runtime.md), including the hard stop when a drain cannot be confirmed.

**Single-tenant (P1) replicas.** Per-tenant settings apply at the next start. On P1, a rotation takes effect only after a replica restart. A settings revision does not fence a P1 lease.

`GET /placement` returns tenants with active, unexpired owner, epoch, lease age in seconds, hot and busy Session counts, and registered replica boots with role, product version, binary and reader levels, capacity, drain state and heartbeat time. Counts come from each published runtime's resident owners at heartbeat, keyed by tenant and epoch inside `replicas.capacity`. Unobserved and epoch-mismatched counts are null; an observed zero is zero. Ranking and eligibility use the existing [placement rules](./hosted-runtimes-host.md#d-hosted-placement).

## Tests

`OperatorBoundaryTests` covers independent rotated credentials after importing the same source, pre-1200 rollout, SQL contracts, headless exchange and reserved routing. `OperatorProcessTests` provisions through the CLI against a separately launched operator process, then activates the tenant on a replica process and exercises authorization, role/origin separation, setup, settings, placement, expiry and rotation (including open streams). `TenantReplicaTests.SettingsRevisionDrainsOnlyTheChangedGeneration` separates notification, reconnect and renewal-only refresh and checks a sibling remains available. `PlacementRankTests` includes diagnostic capacity observations in the candidate inputs. `packages/webui/test/login.e2e.mjs` checks the browser stores and displays only the returned credential and continues on demand.
