## Process and authorization

The operator provisions tenants. Each tenant receives a subdomain of a shared base domain. Third-party tenants require the external security review (2026-11-27).

`foxwarm operator serve` is a separate process in the hosted image. It opens no tenant runtime, serves the console at its origin root and the API at `/operator/v1`, checks the schema and the actual connection role against `schema_info.operator_role`, and loads the KEK. Its Kestrel listener binds `bot.httpHost` and `operator.port`; `operator.url` is its externally visible origin. Requests must address that host and port. A browser that sends an Origin must match it. TLS termination belongs to the ingress. The operator refuses to start if its canonical hostname is assigned to a tenant, including P1’s configured public hostname. Host comparisons ignore case and the terminal DNS dot. Unknown routes return an empty 404 before authentication. The replica front rejects the reserved hostname and both root and deployment-mounted operator paths before tenant resolution, admission or rate limits. The [packaging](./hosted-packaging.md) gives the two roles separate services and separate database secrets.

`operator token create` uses the **migration** URL and checks the connected role owns `operator_credentials`. The operator role can read this table but cannot insert, update or delete rows. The command prints a random 256-bit bearer token once; the table stores its SHA-256 digest and a digest prefix for lookup. The operator checks the digest and revocation on every API call. It neither accepts nor sets an authentication cookie. The remote CLI takes `--url ORIGIN --token-file FILE`, sends the bearer only to that origin, and disables redirects. It writes successful JSON to stdout and failures to stderr. Neither remote CLI nor operator API receives the migration credential.

The operator serves three fixed console resources from the packaged or loose WebUI distribution. Its sign-in shell contains no deployment data. The browser sends the bearer only on same-origin API requests, keeps it in memory and discards it on sign-out or reload. Tenant listeners do not serve the console. It shows tenant state, lease owners, Session counts and replica heartbeats; operators can edit limits and journal settings, suspend a tenant or resume it. Provisioning, grant edits and permanent deletion remain API and CLI operations.

## Tenant lifecycle and login

- `POST /tenants` requires `slug`, `profile` and `primaryHostname`. The immutable slug is a DNS label (`TenantSlugs`); the profile is `hosted` or `operator`. Creation and allowed profile edits set `pinned_role` in the same statement: `master-host` for the operator profile and null for hosted. The deployment-wide operator-tenant uniqueness conflict returns 409. The hostname must match the deployment's `url` expansion for that slug, and must differ from the operator hostname. Custom domains are outside this release. `GET /tenants` and `GET /tenants/{slug}` return settings, never credential material.
- Creation is one cluster transaction: tenant record, storage identity, bootstrap lease, DEK wrapped under the KEK with the tenant ID as associated data, and primary hostname. A schema-owner function inserts only the wrapped key, with RLS and the normal epoch trigger under that bootstrap lease. The transaction releases the lease before committing. A unique-key conflict rolls back the entire creation. Empty configuration is represented by **absent** config and models rows, so first-run Setup can install them.
- Creation and rotation issue a fresh random 256-bit setup token. `tenant_auth` stores its SHA-256 digest, 24-hour expiry and credential version. The app role has no table privileges. On the tenant origin, `POST /api/auth` can exchange the setup token whenever HTTP is enabled, including without a WebUI. Redemption takes the lease fence and locks the credential row; a matching unused, unexpired token is spent by installing the digest of a **new random 256-bit access token**. The successful response alone returns its plaintext, with `Cache-Control: no-store`. The browser displays the access token for copying before Continue. A lost response requires rotation. Matching spent or expired tokens receive distinct diagnoses.
- The owner loads its access verifier through a fenced snapshot and checks submitted tokens in constant time. After redemption the same owner installs the verifier locally. Downloads use a separate random signing key for that version. No reusable credential is derived from an imported key. Version zero preserves an existing installation's encrypted HTTP credential until rotation. `hosted token` refuses versioned credentials.
- **Object identity.** Migration 1200 installs an insert trigger on `tenants`. Every row created afterwards (by `db migrate`, import or the API) gets `t/<tenant_id>-<UTC creation timestamp>/`. Only rows already present when 1200 ran retain `t/<slug>/`. All three blob stores and the conditional-write probe use the resolved identity.
- **Rollout.** Finish upgrading the replicas before provisioning or rotating. The operator rejects both while any unexpired serving lease has an unregistered owner or a boot below binary level 1200, even if its heartbeat is stale. Rotation takes the target lease lock before this check. New-style tenants (non-null storage identity or positive credential version) require a registered 1200-or-newer boot on serving acquisition; the acquisition trigger applies even to old standby binaries. Legacy lease renewals continue through rollout. A reader floor is checked at startup; applying a migration does not evict an already-running reader.

## Suspension and deletion

`tenant suspend`, `resume` and `delete` use the same tenant-then-lease lock order as placement changes. Suspend commits `suspended` and the routing drain timestamp together. Owners stop admitting new work on state notification or failed renewal. Suspend and delete require level 1201 (the serving-state renewal check) from every replica with a heartbeat within one lease TTL, including standbys, and every unexpired serving lease owner, even when the heartbeat is stale. An unknown serving owner is refused. Full and Agent-only import leases are excluded: their unregistered migration-role owners serve no traffic. The stored drain deadline ends an outstanding epoch even if the request disconnects or the operator restarts; the continuous suspension worker runs independently of S3. The lifecycle API addresses tenants by DNS slug. Retiring a pre-0003 non-DNS P1 name through this surface is unsupported. Resume retires any remaining old epoch before permitting acquisition. Neither suspension nor deletion interrupts an import. Delete accepts only suspended or already-deleting tenants, records one terminal epoch and releases the lease with no owner. The REST operations are `POST /tenants/{slug}/suspend`, `POST /tenants/{slug}/resume` and `DELETE /tenants/{slug}`. A 202 acknowledges the durable deletion; GET eventually returns 404.

Deletion acknowledgement covers the operator’s SQL and object-storage work. Each replica independently removes its local `t/<tenant_id>` scratch when it sees the terminal state or the absence of that ID, after its generation has released the directory. The replica reconciles on notification, on subscription (including reconnect) and on the periodic directory refresh. An offline replica cleans a retained scratch volume when it returns. The operator does not wait for acknowledgements from individual pods. These scratch files include model interaction diagnostics only when the tenant’s journal policy permits recording them.

Every operator worker scans `deleting` tenants, including a migration-role import abandonment that has no progress row yet. The operator-only `operator_deletions` table records SQL completion, pending objects and the earliest final listing. Pages and chunks are bounded. A schema-owner function checks the terminal state and deletion epoch under the lease lock before each SQL chunk. It opens an ownerless lease only inside that transaction, runs through forced RLS and the ordinary write fence, and closes it before commit. An error rolls back the chunk and lease together. Key provisioning shares the maintenance helper. The final transaction checks all fenced tables and cluster dependencies before removing the lease, key and tombstone. A reappearing dependency returns the job to SQL cleanup with its key intact. A newly tracked serving grant clears the preceding stale observation even when a recreated tenant reuses the slug and epoch number.

The operator’s separate S3 identity lists and deletes one page of the old namespace at a time. Versioned and versioning-suspended listings advance using both markers, even when Object Lock retains an early page. An empty trailing page never proves the whole namespace empty: a new pass must start at the beginning. After an empty listing past one TTL plus the bounded PUT timeout, the SQL job may retire the tenant row and free its slug. A receipt for the numeric tenant ID, endpoint, bucket and object namespace survives this retirement. Client cancellation does not withdraw a PUT already accepted by the gateway. `LateWriteRecheck` therefore schedules an independent pass 24 hours later, giving asynchronous storage work a day to settle without delaying slug reuse. This is a reconciliation interval, not a storage-side write fence or guarantee of permanent erasure.

`GET /operator/v1/deletions` (CLI `deletions`) lists only pending late checks: numeric `tenantId`, old `slug`, `status: lateWriteCheckPending`, `observedEmptyAt`, `recheckAfter` and `foundLateObjects`. Recovery removes late versions and markers, then requires a fresh empty listing; a refused delete, an unreachable endpoint or a missing bucket at the same destination keeps the receipt. When the configured destination changes, the operator discards the receipt without contacting either destination, warning with the old namespace, endpoint and bucket. The operator who moved the storage is responsible for checking the former destination. The worker logs the namespace and observed result on completion and forgets the receipt, with no completed-check history. A new tenant never opens the old namespace. See [deployment configuration](./hosted-packaging.md) and the S3 permissions in `deploy/hosted/README.md`.

## Settings and placement

`PATCH /tenants/{slug}` accepts `limits`, `journal`, `profile`, `ceiling` and `primaryHostname`. A profile edit that would move a tenant between hosted SQL Agent files and the operator’s master-host directories returns 409, even when the tenant is suspended, being imported or being deleted. The check uses the stored profile under the tenant row lock, before applying any other fields in the patch. The API provides no implicit store transfer. Each supplied field replaces that field; omitted fields remain unchanged. `journal` accepts `enabled` and `retentionDays`. An empty limits or journal object restores its defaults. A null `ceiling` removes the tenant override. `GET`/`PUT /profiles/{profile}/ceiling` read and replace a global profile ceiling, also nullable. Validation uses the same limits, journal and ceiling parsers as the runtime. All changes in a patch commit together. See [limits and journal policy](./hosted-egress-limits.md) and [ceiling precedence](./hosted-config.md#d-hosted-operator-ceiling).

`GET /tenants/{slug}/provider-grants` returns the tenant's explicit grants as an object keyed by exact Provider ID, including defaults for missing quota fields. Other stored fields are omitted; a malformed known field returns 409 without including the stored value. `PUT` to that path with `?providerId=ID` sets or replaces an explicit grant using the quota object as its body; `DELETE` with the same query removes it. The CLI verbs are `grants list`, `grants set` and `grants remove`. They do not enumerate implicit operator access. The write locks the tenant and uses the stored profile for [Provider validation](./hosted-provider-tenancy.md), without starting a driver. Removal also works when its Provider is no longer configured. In the same transaction an actual change increments `settings_revision` and notifies `foxwarm_tenants`; an equivalent write or absent removal does neither. Removal of an operator-profile grant restores that profile's implicit access without quotas.

**Multi-tenant replicas.** Live application does not require a restart. Hostname changes invalidate the directory; a ceiling edit invalidates the running owner's policy cache. A changed profile, limit, journal setting or credential version retires the affected tenant's generation. Acquisition captures the tenant's settings revision. On `foxwarm_tenants` and on subscription or reconnect, the owner compares the stored settings and placement with its held grants, including starting and retiring generations. Each successful periodic renewal independently compares the revision: an edit missed by the listener is discovered by the next successful renewal (normally within 5 seconds). A locked or unreachable database still has the ordinary grant-proof and fence deadlines. There is no per-request database check. From commit until observation, the old settings or credential may still be accepted. Once observed, the gate latches, admitted work gets the usual bounded placement drain and a new request activates with current settings. Grant tracking and slot ownership are installed under the same lock. A generation whose settings changed during startup cannot publish; the first such observation starts one drain bound for its start and disposal, followed by normal fencing and supervision on overrun. Rotation also aborts WebSocket and SSE streams authenticated with the old token, including during an existing graceful drain. The revocation callback uses the front’s transport features: a bodyless HTTP response may start after its tenant context has been disposed. See [retirement and fencing](./hosted-runtime.md), including the hard stop when a drain cannot be confirmed.

`GET /placement` returns tenants with active, unexpired owner, epoch, lease age in seconds, hot and busy Session counts, and registered replica boots with role, product version, binary and reader levels, capacity, drain state and heartbeat time. Counts come from each published runtime's resident owners at heartbeat, with the immutable tenant ID and lease epoch inside `replicas.capacity`. All three sample fields require a live lease, a matching tenant ID and epoch, and a heartbeat newer than one default lease TTL (30 seconds). Replicas heartbeat every five seconds: this tolerates missed intervals and uses the same freshness window as the operator’s live-registration check. A stale heartbeat suppresses the sample without hiding the independently renewing owner. The same sample supplies `providerProblems`, an object keyed by exact Provider ID with diagnostic codes from the [generation’s Provider checks](./hosted-provider-tenancy.md). The console lists each Provider separately and shows unfamiliar codes verbatim. `{}` is a healthy observation and null means no current observation. The replica view does not expose the underlying tenant samples. Unobserved and epoch-mismatched counts are null; an observed zero is zero. Ranking and eligibility use the existing [placement rules](./hosted-runtimes-host.md#d-hosted-placement).

## Placement actions

Use these actions after all participating replicas run the multi-tenant topology with placement-action support. `POST /tenants/{slug}/move` and `/release` require `{tenantId, owner, epoch}` from `GET /placement`. The CLI takes the same observation: `tenant move|release SLUG TENANT-ID BOOT EPOCH`. An old observation cannot change the new grant, even when a boot serves a recreated slug at the previous tenant's epoch. `POST /replicas/drain` takes `{boot}` (`replica drain BOOT`); the boot ID includes the startup suffix so a restarted process cannot inherit the request.

The operator calls [`ReplicaPlacementRequests`](./hosted-forwarding.md) on its own database connection. That service owns request validation, locking and notification. A new or identical pending action returns 202. A conflict, stale grant or move without another eligible target returns 409; the operator does not pick another grant and retry. An unknown or expired replica boot returns 404. Suspension and deletion supersede the one-shot request under the existing lifecycle locks. A move needs an eligible destination; release asks the tenant to sleep until demand. An administrative drain moves residents only to eligible non-draining replicas. New public or autonomous activations prefer eligible non-draining boots; a healthy drained boot remains a fallback if none is available. Shutdown removes the boot from consideration entirely.

Placement is a current observation, not a job log. Tenant `requestedAction` records the accepted action; `drainingSince` records the separate per-lease routing latch. During a move the old boot can be excluded even after release; the next acquisition clears the one-shot request. Replica `draining` is the boot-wide placement flag, and `heldGrants` counts only active, unexpired leases held by that boot. The console submits the observed identities and shows current progress on refresh.

## Tests

`OperatorDeletionTests` covers an acquisition blocked by deletion, transactional rollback under an injected error, a restarted worker and concurrent deleters. `OperatorObjectDeletionTests` uses an opt-in versioned S3 gateway, delays an actual HTTP PUT past the first empty listing and checks Object Lock and suspended versioning. `OperatorBoundaryTests` covers independent rotated credentials after importing the same source, pre-1200 rollout, SQL contracts, headless exchange and reserved routing. `OperatorProcessTests` provisions through the CLI against a separately launched operator process, then activates the tenant on a replica process and exercises authorization, role/origin separation, setup, settings, placement, expiry and rotation (including open streams). `TenantReplicaTests.SettingsRevisionDrainsOnlyTheChangedGeneration` separates notification, reconnect and renewal-only refresh and checks a sibling remains available. `PlacementRankTests` includes diagnostic capacity observations in the candidate inputs. `packages/webui/test/login.e2e.mjs` checks the browser stores and displays only the returned credential and continues on demand.
