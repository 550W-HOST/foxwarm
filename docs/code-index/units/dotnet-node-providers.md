## Purpose and current boundary

Main owns startup executable-provider configuration, qualified identities, discovery, lifecycle dispatch and canonical file capabilities. Fixed Main/native resident adapters keep their existing path, credential, protocol, completion and service owners. The external executable implements the existing public primitive protocol in `docs/executable-node-provider-protocol.md`, not model tools or a new resident Node protocol.

Native credential IDs contain no slash; executable IDs are qualified by their validated configured provider name. These owner namespaces are disjoint. Executable discovery validates duplicates within that provider; slash-qualified and native identities remain disjoint. Main records trusted parent metadata and referenced offline provider identities in the existing native registry owner; see the [authorization forest contract](../behaviors/nodes-workspaces-and-permissions.md#node-authorization-forests).

The registry connects files, process primitives, selection, Agent binding and their actual consumers. A ready descriptor with `exec:true` derives the existing approved exec definition. Provider exec uses the existing persistent `LocalExecManager`; native resident exec retains its authenticated completion/protocol owner. Bounded provider discovery and optional lifecycle use the existing Main builtin and native ToolScript path. [Provider lifecycle authority](../threads/tool-dispatch-node-execution.md#d-dispatch-node-provider-lifecycle) owns the shared decisions and their reasons. Native/provider jobs share the [Source-shaped bounded active registry](./tools-local-io.md#persistent-exec-storage-and-lifecycle); synthetic record interoperability is not live cross-runtime takeover. The project scope is canonical in [delivery scope](../overview.md#d-dotnet-delivery-scope).

## File and caller ownership

`ITargetFileOperations` supplies target-owned parent/stat/ranged-read/readdir/write/mkdir/remove primitives. The existing `WorkspaceTools` workflow owns argument handling, write references, exact replacement, parsed patch sequencing and partial-effect summaries for both native and executable files. `FileToolCore.ReadContent` and `FormatDirectory` share the existing scanner, byte/line budget, text formatting and programmatic data. `WorkspacePatch` and `ExactReplacement` remain the sole grammar/matcher owners. Native regular-file/path/publication checks and atomic writes stay in native branches; executable mutations use target `w`/`wx`/`a` rather than host temporary paths or rename.

Provider paths, home handling, separators, cwd and parent resolution remain opaque on Main. Leading native Agent variables are rejected before filesystem effects. Provider definitions override only the approved target-path descriptions; Main/CLI descriptions remain unchanged. Generic copy, delivery and image-export descriptions distinguish native Agent defaults from executable environment defaults. The registry does not fabricate a target Agent directory or Code/PTY/browser service capability.

`ToolRegistry.ResolveAsync` refreshes only actual Node capability targets, so a broken selected provider cannot block an explicitly Main-local builtin. Qualified tool IDs separate the tool name at the last slash. `SessionManager.SelectNodeAsync`, generic Agent binding and persisted selection admission accept Core IDs, while pairing/token/rename/removal validators remain native. The directory and Session picker use async generic discovery; the shared directory parser accepts the 193-character qualified bound without granting services.

Full-file consumers retain their actual authorization owners. Copy checks both endpoints; image and file delivery use builtin endpoint policy rather than synthetic primitive tool calls. Complete ToolScript source separately authorizes `read`, passes its captured target cwd directly and remains Main-local execution; nested calls resolve the live owner. Primitive ingress uses environment-default relative storage, not an Agent-specific root. Main retains image storage, delivery staging and receipts, including the full qualified source identity. The [structured output guard](../threads/tools-permissions-and-exec.md#structured-output-guard) also uses these file operations for provider storage, under existing read/write policy and the captured exact-Node Session cwd; its relative locator names that basis instead of pretending to be an absolute path.

Provider descriptors never supply `parentNode`. The registry adds parent presentation from trusted metadata. Create inventories existing provider identities before effects, including generated-ID calls; returning an existing identity from create is an error after that one external effect, without retry or rollback. Explicit-ID ensure authorizes the known identity after discovery or admits a fresh configured-parent child. The reviewed top-level omitted-ID compatibility path cannot establish a subtree target before effects; delegated callers must give an ID. Discovery absence prunes only unreferenced provider metadata; retained referenced identities are presented offline. Startup configuration can reparent existing provider records, subject to forest validity and changed-edge admission limits.

## Failure and partial-effect contracts

Transport request/operation/stdio limits and errors follow the public protocol. Direct-child termination is graceful-first and bounded; direct-child exit and closure of owned stdio are observed separately. Malformed/multiple/oversized stdout, unsafe envelopes, abnormal exit, timeout and cancellation fail without exposing launcher arguments or raw stderr. Provider-reported filesystem codes are preserved; only `ENOENT` is missing. Patch deletion checks target existence before remove, including for idempotent adapters; a missing delete retains earlier operations and prevents later effects without imposing native regular-file restrictions. The executable remains trusted administrator code, not an OS sandbox.

Primitive transfer requests contain at most 1 MiB of bytes. The initial write uses `w` or `wx`, including empty files; subsequent requests append. A failed later append retains the prefix without rollback, retry or a successful receipt. Complete source/transfer reads request the fixed chunk size until the first short/empty result and require the returned byte count to equal the initial stat size. A short final snapshot is not probed again for later appends; an exact chunk multiple requires the normal next read. Premature short data and bytes exceeding the initial size fail. This is not a whole-file stability or atomic-snapshot guarantee. Native CLI SHA-256 transfer receipts and correlation are unchanged. A lost ordinary write receipt can leave the actual effect; Core does not replay it.

## Persistent process boundary

`ToolRegistry` sends direct, unified and native ToolScript provider exec calls through `SessionToolExecutor.ExecuteProviderExecAsync`. Authorization remains concrete; the last prelaunch fence checks foreground cancellation and the exact owner/runner. Once dispatched, the launcher receives only independent owner-loss cancellation and its transport deadline, not ordinary foreground Stop. A missing or invalid receipt has an unknown outcome and is never retried. Provider PID is target metadata, never Main process authority.

The existing [persistent exec owner](./tools-local-io.md#provider-exec) persists exact provider ID, qualified Node ID, private reference, original log path, start/known cwd and target PID in its single active registry. Recovered jobs query that exact configured backend even when discovery is unavailable or the Session now selects another Node. Missing provider configuration and transient query errors retain tracking; explicit lost status has unknown exit and estimated duration. No native fallback, Source-registry migration, target cleanup or command replay is introduced.
