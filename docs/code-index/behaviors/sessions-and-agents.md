# Behavior: Sessions and Agents

For developers and Agents changing how work starts, is organized, or is retired. An Agent supplies a workspace and instruction sources; a Session owns a conversation and its work/settings. Opening a Chat, creating a Session, and creating an Agent are different actions. Neither Agent membership nor a parent link grants tool or environment authority.

## Use an existing lifetime, start fresh, or fork

Opening an existing Session selects its browser conversation; it does not allocate another Session or submit model work. Several Chats can observe the same backend lifetime. Browser tab/component behavior belongs to [Workbench and Chat](workbench-and-chat.md#tabs-select-surfaces-panes-arrange-them).

| Supported choice | Starting conversation and instructions | What starts work? |
| --- | --- | --- |
| New Session under an existing Agent | Fresh history and cache lineage, with that Agent's default memory sources unless an explicit source list is supplied. Recording a parent does not copy its history. | Creation alone does not submit an instruction. |
| Fresh child | Fresh history/cache lineage with the caller as actual parent. A same-Agent child retains the parent's custom memory-source selection, if any; a cross-Agent child uses the target Agent's default sources. | An initial message or Task assignment enters the child's queue; an unassigned child is not started by its creation receipt. |
| Fork | Copies the source's history and prompt snapshot at a point in time, with bounded Archive lineage and shared prefix/cache lineage. It does not share mutable history or receive later parent messages. | A manual fork without initial input is not a work assignment. A model-created child's supplied message/Task has its separate handoff effect. |
| New Agent with a main Session | Creates an independent Agent directory and, normally, a fresh main Session. Optional conversion instead moves an existing lifetime. One-time memory copying and ongoing inheritance are separate choices. | A newly created main Session does not run merely because its directory or creation receipt exists. |

Fresh means no copied transcript, not an absence of structured creation/identity notices. Those notices record the initial placement the model starts with: a new top-level Session's first input begins with `<foxwarm-system kind="session" currentSessionId="…" currentNode="…" cwd="…" />`, and fresh children and forks carry the same `currentNode`/`cwd` attributes on their `session-boundary` identity notice. `cwd` is omitted while unset, meaning the Node's default directory. Attribute escaping preserves the exact Node ID and path, including repeated whitespace; it does not apply the Session-ID text normalization. They describe the start only; later selections are reported by the operations that change them. Fresh Agent creation with `createMainSession:false` creates no main Session lifetime; the directory is not evidence that such a target exists.

Cross-Agent forks are rejected. A fresh cross-Agent child requires an existing target Agent and retains its actual caller as parent. Creator-scoped model callers may select only their own Agent or creator descendants; [management admission](../units/session-manager-lifecycle-identity.md#creator-scoped-model-management) also covers timers, parent changes and selected-source conversion/copy. A user-created fork records context provenance, not a standing obligation to report to that parent. A later real handoff can establish that obligation normally. No creation path fabricates an assistant acknowledgement of understanding. Exact inherited tool-pair completion and manual-fork notices remain in [creation provenance](../threads/session-lifecycle.md#d-lifecycle-creation-origin).

[Collaboration and Tasks](collaboration-and-tasks.md) owns initial assignment delivery, reporting, and Task linkage. [Conversation and history](conversation-and-history.md#which-instructions-are-in-the-working-context) owns which instruction sources are selected and when they become the model's working context.

## Omitted creation settings do not have one universal source

The entry point matters where it changes actual defaults:

| Entry | Initial model/effort source | Initial execution Node source |
| --- | --- | --- |
| WebUI New Session | No current-Chat model/child policy is passed; unresolved selection uses the global model default. | Target isolation binding, target Agent default, installation default, then master; the selected Chat is not its Node source. A WebUI child created under a parent follows the fresh-child row. |
| Model `create_session` or `/session create` | Resolves the caller's prospective child model/effort policy, with supported explicit overrides (`forceModel` and, for the model tool, `model`). | Target isolation binding, explicit Node (`create_session`), target Agent default, installation default, then master. Neither the caller nor a recorded `parentSessionId` supplies a Node; the parent records a relation only (user decision 2026-11-08). |
| Fresh child or fork | Resolves the source's prospective child model/effort policy, not necessarily its current displayed model. | Target isolation binding, explicit Node, the parent's current Node when the child is in the parent's Agent (always for forks), target Agent default, installation default, then master. |
| New-Session timer | Captured at registration and revalidated when firing. | Target isolation binding, the stored owner Node when the target is the owner's Agent, target Agent default, installation default, then master. |
| Source-based Agent-main creation | Explicit values over the source's current raw pair; it also retains the source's future-child defaults. A model tool's omitted source is its caller; WebUI creation does not supply that caller source. | Target isolation binding, the new Agent's `defaultNode`, installation default, then master; neither the caller's nor the source's Node. |

The C# Main has no caller or Agent-main-Session Node fallback. The frozen Source still looks up the Agent's main Session; see [named-session defaults](../units/src-session-agent-ops.md#named-session-node-defaults). Do not infer a universal “inherit the selected Chat” rule from the UI's current selection.

**User decision (2026-11-01): Agents carry optional workspace defaults instead of a separate Project concept.** An Agent may record `defaultCwd` next to `defaultNode`. The directory belongs to the effective default Node: the Agent's own `defaultNode`, otherwise the installation `agentDefaultNode`, otherwise master. It becomes a new Session's initial cwd only when its resolved initial Node is that Node. [2026-11-08] Enabling or changing the installation default changes that association for Agents with a `defaultCwd` and no `defaultNode`; existing Sessions do not move. An explicit other Node, an isolation binding to another Node and a same-Agent parent or timer owner on another Node start without it. New Sessions, children, forks, timer Sessions and Agent main Sessions follow the same rule. Like the Node default it chooses placement only: it grants no access, is validated as an absolute path but not checked on a possibly offline Node, and changing it leaves existing Sessions where they are. Session cwd remains mutable afterwards; the default is not a membership or containment boundary.

**User decision (2026-11-06): placement follows explicit choice, then a same-Agent parent, then defaults.** The order is isolation binding (a hard constraint), explicit Node, the current Node of a parent Session in the same Agent, the target Agent's `defaultNode`, the installation default, then master; the table above applies it per entry. A timer's stored owner Node counts as a parent. For `create_session`, an optional recorded parent establishes a relationship but does not affect placement (user decision 2026-11-08); Agent creation has no parent, and the earlier caller and Agent-main-Session fallbacks are removed. This reverses the 2026-10-29 placement of the Agent default above child, fork and timer source placement. Top-level app config `agentDefaultNode` is the installation default; it applies live from Setup/`set_config` saves and is used only when the Agent has no `defaultNode`. It does not travel through memory `inherit`, is not written into Agent metadata, and the Agent API reports only each Agent's own value; `GET /api/nodes` reports the installation value for the WebUI. Like the Agent default it is placement only and grants no access. An Agent that must stay independent of it records an explicit default, including `master`.

### Prospective model and effort are a pair

[2026-08-13, extended 2026-11-08] Spawned children/forks resolve model from `forceModel`, source future-child model default, the model tool's `model` suggestion, source current model, then global default. Effort resolves from `forceModel`, source future-child effort default, the `model` suggestion's effort, source raw effort, then unset. Unset stays unset so the selected concrete model or virtual leaf uses its own configured default; it is not frozen to the parent's current effective effort.

**Directly selected (2026-11-08): `model` beside `forceModel`.** `create_child_session` and `create_session` accept `model: { modelId?, effort? }` with the same shape as `forceModel`. The two differ in authority: `forceModel` is for a user's explicit request and outranks everything, including the user's own child-model settings; `model` is the Agent's suggestion, advised by the [model catalog](../threads/conditional-memory-snapshots.md#d-memory-model-catalog), and ranks below those settings so it never overrides what the user chose per Session. Each field resolves independently, with one pair rule: when `model.modelId` is superseded by a higher-precedence model (`forceModel` or the child-model default), `model.effort` is ignored too, because it was chosen for that model; an effort-only `model` applies unless a higher-precedence effort exists. An unknown `model.modelId` is always rejected, even when superseded, and the error lists the catalog keys when a catalog exists. When `model` takes effect it is validated like `forceModel` (effort capability included). Claude Code Sessions manage their own model: `model` is accepted and key-checked but not applied. Other creation paths (WebUI, timers, forks without these tools) have no `model` argument and are unchanged. `PlanCreationModel` owns the resolution for both tools; the creation result then states `Model: <key> (<source>); effort: <level> (<source>).` with sources `forceModel`, `child setting`, `model`, `inherited` and `global default` (`effort: default.` when unset).

The resolved pair becomes the spawned Session's current settings. Its own future-child overrides start unset, so grandchildren normally follow that child's current pair. A one-time creation override therefore does not pin every later descendant. Existing stored future-child overrides remain effective until explicitly changed; equality with current settings does not implicitly clear them.

Newly explicit effort is validated against concrete capability or a virtual route's supported union. Stale inherited effort that no longer fits clears to unset instead of blocking creation. Source-based Agent creation is the distinct case above: it retains source future-child defaults. New-Session timers capture a prospective pair at registration and revalidate it when firing; [scheduled work](automation-and-scheduled-work.md#schedule-a-message-or-execute-a-quiet-script) owns that later-use boundary.

Creation sets prospective configuration, not the identity of a successful provider attempt. [Models and requests](models-and-requests.md#selection-is-not-execution-identity) owns selected versus attempted/adopted configuration, virtual routes, provider defaults, and later switching.

## Change a label, an identity, or a relationship

| Action | What changes | What does not follow from it |
| --- | --- | --- |
| Display-name update, WebUI Rename, `/session rename` | Human-readable label; clearing it retains the internal ID. | No new lifetime, Archive rename, Agent move, or parent change. |
| Automatic title after the first completed user turn, when `sessionAutoTitle` is enabled | Sets a generated label only on an unnamed Session whose first input came directly from the user. | No change to an existing or concurrently set label, no history row, and no retry. |
| Reorder a Session in the sidebar | Browser-facing sibling order recorded in the catalog. | No history move, new context, or execution placement change. |
| Reparent, including a tree drag to another parent | Actual Session parent relation. Sidebar ordering may be changed separately. | No Agent membership, inherited memory, Task creator/owner, or copied conversation change. |
| `move_session` or `/session move` | Internal ID, optionally Agent membership, retained aliases, and associated history/attachment identity. Direct child references follow the new canonical ID. | Not the WebUI sidebar `/move` operation, a recursive tree move, or a copy of every Agent-owned file. |
| Change Agent memory inheritance | Sources used by later prompt materialization/refresh. | No parent/Task relation, permission inheritance, or default immediate rewrite of every Session snapshot. |

Automatic titles use one detached background model request and the ordinary rename publication; qualification, request and commit rules belong to [automatic Session titles](../units/session-auto-title.md).

An identity move preserves the incoming parent when no parent override is supplied. An explicit parent override is a separate post-move relation update: failure can leave the identity move committed while the requested parent change is unconfirmed. The technical owner retains [identity-move relation and recovery rules](../threads/session-lifecycle.md#d-lifecycle-identity-move-relations).

[Creator-scoped model admission](../units/session-manager-lifecycle-identity.md#creator-scoped-model-management) additionally restricts membership changes and both sides of parent changes. Cross-Agent identity moves also retain the isolated-source/target checks; the model move tool rejects an isolated source. Internal-ID moves are unavailable under Session-worker placement. Do not infer these restrictions for ordinary display-name updates or administrator sidebar operations. [Node and permission boundaries](nodes-workspaces-and-permissions.md#authority-has-several-independent-boundaries) remain independent.

**Current implementation:** an identity move does not itself rebuild the retained prompt snapshot. Immediate adoption of the target Agent's memory is not an established guarantee; the normal [instruction adoption boundaries](conversation-and-history.md#when-do-changed-instructions-reach-the-model) still apply. History text and old file locators are not rewritten into new Agent-owned resources merely because membership changed.

An internal ID identifies one lifetime while its retained historical identity remains reserved. Explicit creation/move cannot reuse a deleted lifetime's retained ID; automatic allocation skips reserved IDs. Old committed move aliases resolve to the current live lifetime while it exists, and remain historical references after deletion. Display names are not reserved identities. Allocation serialization, exact legacy IDs, alias recovery, and failed unpublished creation compensation remain in [identity reservations](../threads/session-lifecycle.md#d-lifecycle-archived-id-reservation).

## Put work aside, clear the conversation, or retire the lifetime

| Action | Observable consequence | Work/history that is not erased by that action |
| --- | --- | --- |
| Close Chat | Removes that browser view. | Backend Session, running turn, tools, timers, and background exec. |
| Archive a Session | Changes its list/presentation flag. Optional descendant archive is explicit and defaults off; unarchive is single-Session. | Active history and running work; this is not the immutable Archive store or a pause command. |
| Clear the Session | On successful clear, starts an empty active conversation within the existing Session identity. | Agent memory and retained historical originals. Busy admission and exact clear effects belong to [history actions](conversation-and-history.md#actions-and-consequences). |
| Delete the Session | Removes live access, detaches Channels, and retires current Session authority. Nonrecursive deletion detaches surviving direct children rather than deleting them. | Retained Archive/identity reservations and independent durable work records are not a global erasure target. |

Delete is coordinated, not an unconditional immediate UI removal. Non-WebUI Channel attachments can block it. A busy local target receives the existing stop/queue-clear retry outcome; a Worker target uses its owner teardown path. Recursive WebUI deletion is explicit and defaults off, derives the full descendant selection on the backend, and deletes deepest-first only after preparation. Unexpected failure reports partial progress, not invented rollback. Exact claim/revalidation and retained-store boundaries remain at [Session deletion](../threads/session-lifecycle.md#archive-and-deletion).

Neither archive nor closing a tab establishes that work completed. Returning to Chat reads the retained lifetime; it does not recreate its last browser component or replay an uncertain command. Restart recovery reassesses recorded busy/queued/waiting work rather than resuming the last machine instruction or regenerating a completed answer. Keep those consequences at [Workbench lifetimes](workbench-and-chat.md#mounted-visible-and-running-are-independent) and [persistence and recovery](persistence-and-recovery.md#restart-resumes-recorded-work-not-the-last-machine-instruction).
