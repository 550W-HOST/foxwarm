# Module: WebUI timeline

## Responsibility

Owns the browser's Timeline modes, pane-local Chat Search, Reasoning presentation, Conversation projection, and Activity accounting across the WebUI rendering units. The [WebUI module](./webui.md) owns the surrounding application and server surface.

This is a render-only boundary. Provider data and persisted request timing remain in the [message processing pipeline](../threads/message-processing-pipeline.md#d-pipeline-input-time), live transport and draft reconciliation in the [streaming pipeline](../threads/streaming-pipeline.md), and archive retrieval in [archive and recall](../threads/archive-and-recall.md). Runtime controls and queue geometry follow [Chat's bottom status layout](../units/webui-chat.md#d-chat-bottom-status-layout); decorative captions and stable accessible labels follow [fox loaders](../units/webui-fox-loaders.md#behavior).

## Units and integration

- [Image preview](../units/webui-image-preview.md) — shared full-viewport attachment viewer across composer, history/tools and reply files.
- [Timeline renderer](../units/webui-chat-timeline.md) — maps derived rows to ordinary and nested surfaces.
- [Timeline rows](../units/webui-timeline-rows.md) — grouping, Reasoning ownership, Conversation projection and Search disclosure.
- [Usage and timing](../units/webui-timeline-usage-timing.md) — request attribution, Activity intervals and time markers.
- [Thread cards](../units/webui-timeline-thread-cards.md) and [tool timeline](../units/webui-tool-timeline.md) — native disclosure, headers and tool output.
- [Shared rendering](../units/webui-chat-shared.md) and [pasted text](../units/webui-pasted-text.md) — sanitized readable content and Search projections.
- [Chat](../units/webui-chat.md) — committed-history and runtime inputs, pane Search controller and viewport ownership.
- [Small components](../units/webui-small-components.md) — Reasoning cards and the live status component; [fox loaders](../units/webui-fox-loaders.md) owns caption presentation.

## Design decisions

### D-webui-timeline-time-separators

[2026-09-27; updated 2026-10-11] In Detailed and Grouped, a quiet centered timeline text row compares the next ordinary committed message’s valid `__meta.llmRequestTiming.startedAt`, falling back to `__meta.timestamp`, against the preceding message’s persisted `__meta.timestamp`. The marker displays that same selected next-message time, so a long request does not become an idle gap; the preceding baseline never uses its request start or substitutes `completedAt`. Structured CTX-BLOCKs still use only `__meta.contextBlock.rawStartTimestamp` for both their time and the following comparison, never their creation time or request timing. No ingress wrappers, reconstructed intervals, tool execution timing, or render time are read. The first eligible visible row shows its clock; other eligible rows show only their clock when the selected time differs from the preceding baseline by at least 60 seconds or crosses the browser’s local calendar date. A CTX-BLOCK without a valid range-start timestamp shows no time row and breaks adjacent comparison instead of falling back to its creation timestamp; missing or invalid predecessors can show only the next valid clock, without estimating a gap. English 24-hour `HH:mm` applies today, `MMM d, HH:mm` otherwise (year across years); the tooltip includes full date, seconds, and time zone. No elapsed suffix or countdown is shown. Tool responses and whole Event wrappers contribute their adjacent persisted timestamp but have no independent divider; an eligible next model call can safely split a historical group only without separating a paired call/result. A divider is a keyed sibling outside collapsed content with no viewport anchor; nested CTX, queued previews, and temporary/synthetic stream or optimistic rows add none. API/token/Seq badge behavior and stored backend timing data remain unchanged.

In Conversation, an Activity disclosure and its immediately following reply form one time-separator display unit. No divider appears between them, whether the Activity is collapsed or expanded. Only the unit's first source can own its clock, with the same validity, minute-gap, and local-date rules. For segmented logical requests, the first prefix uses validated request timing from the same request anywhere in already-loaded history within the current CTX scope, rather than treating its generation time as idle. A later unit after a visible surface of that request (or an intervening user input while the request is already present) starts at that committed visible boundary, not the whole request's earlier origin. Unknown segment origins or boundary timestamps omit the clock; they do not borrow a later final body's time. Linking never crosses CTX, mutates persisted metadata, or fetches Archive. Other sources retain their own request-start/timestamp rule. A standalone Activity can also own its clock without waiting for a model body: a leading unit uses its first real input or trustworthy execution origin from already-loaded, CTX-local evidence, not Session creation or maintenance. Current requesting-model work can use its reliable live origin before the first provider part exists. A tool/event-first Activity can therefore own a unit clock even when its raw message was not independently eligible; an unknown start omits the unit clock rather than moving the later body's time before it. All raw persisted timestamps still contribute the adjacent comparison baseline. User rows, CTX cards, and independent image surfaces interrupt the pairing and retain their source rules; repeated surfaces from one source do not duplicate its clock. This does not merge, hide, or reorder body parts, change anchors/Search/stream identity, or alter the separate visible-text boundaries used for Activity elapsed/busy/waiting and counts. Actual nested CTX and queue timelines still have no dividers.

### D-webui-contiguous-reasoning-cards

[2026-10-01; updated 2026-10-20] Consecutive reasoning parts in one model message share one Reasoning card. All Reasoning tags omit the word Reasoning while retaining their Brain icon and any existing `×n` count; a single card without a count does not invent `×1`. Their full label/count remains in the tooltip and accessible image name, including Grouped summaries and processing cards. Real-tool labels are excluded by explicit tool identity. Grouping follows original part adjacency, not the filtered visible list: text, system, tool, image, hosted activity, and unknown parts are barriers, and mixed-field parts retain their other visible output. Recognize a string `thinking` field (including empty), a typed reasoning-summary array, or known encrypted-reasoning metadata; generic provider metadata is not reasoning. Empty summaries count as real parts without invented summary or visible encrypted content.

A reasoning run without readable summary content gives up its standalone card when a later model-text part or tool invocation can receive its information. Render the Brain icon and its existing reasoning-token value at that next item's upper right. In assistant prose it floats right, with text naturally wrapping beside and below it rather than reserving a metadata header row. Ordinary assistant hover controls keep their original absolute upper-right position and overlay the badge without moving or reserving room; Conversation keeps its original bottom action row. Tool badge placement, duration/disclosure, and readable body content remain unchanged. Derive ownership from ordered messages and parts, never from Session busy state or merely the presence of earlier text in a message. Direct input and existing CTX/turn boundaries stop the handoff. Metadata-classified LLM retry notices neither receive the information nor block handoff to later real model prose or a tool invocation. Without an eligible successor, retain the original empty Reasoning card, including active thinking, stopped/Continue, and other tail states; arriving output applies the same rule naturally. Detailed, Grouped, and expanded Conversation share one render-only ownership plan, including when the receiving reply is outside its Activity disclosure. Nested CTX expansion derives its own plan.

The message's actual `reasoningTokens` belongs to its first run and appears once as `N tokens`, either at the trailing edge of that Reasoning header or at its recipient. Each receiving position shows exactly one Brain icon and at most one number: sum all existing reasoning-token values assigned to that recipient for display only, including when hosted activity separates multiple empty runs. All-unknown handoffs show only the icon; mixed known/unknown handoffs show the known sum without an extra icon. Zero is valid; absence adds no estimate. Independent recipients remain separate. Reasoning tokens are already included in output usage and are never added to totals again. Do not borrow completion-suffix usage for an earlier committed prefix. Content-bearing Reasoning, grouped summary counts, disclosure/anchor ownership, manual card height transitions, and exact per-part Search markers remain unchanged. This is presentation-only: canonical parts, replay, provider output order, history segmentation, and usage badges remain authoritative and unchanged.

### D-webui-chat-session-search

[2026-09-29; updated 2026-10-07] Chat offers pane-local Search over the current Session’s already-loaded committed top-level messages. Search opens from the Chat header or Ctrl/Cmd+F with a literal case-insensitive query, one current match counter, previous/next, and close; Enter, Shift+Enter, and Escape work inside its input. Before focusing Search, Ctrl/Cmd+F captures a non-empty selection from ordinary text, contenteditable, input, or textarea controls and uses it as the query; without a selection it retains the existing query. The active Search input supports ArrowUp/ArrowDown history navigation with a bounded, deduplicated browser-local history: entering history saves the current draft, returning past the newest item restores that draft, and entries are committed only at search navigation/close boundaries rather than on every keystroke. History is local to the browser context and does not add backend state. The browser Find shortcut is intercepted only when an actual Chat is active: in a split workbench only the focused active Chat registers the listener, while a standalone popup or embedded single Chat is active by default. It does not intercept Ctrl/Cmd+Shift+F, Alt combinations, composition, or a non-Chat active tab; repeating the shortcut focuses/selects the current query without duplicating Search. Opening Search builds a display-text projection once per history change and query edits only filter that projection; it performs no additional history or Archive requests and never counts queue previews, optimistic/streaming drafts, nested CTX archive content, image bytes, opaque reasoning, internal metadata, or non-text visual blocks. Ordinary Markdown is searched as rendered readable text; Tool arguments and complete expanded result text use the corresponding display formatters, not truncated preview content or a serialized card payload. An explicit jump temporarily reveals only the owning group/card (a CTX summary unclamps without fetching its archive), mounts an already-loaded older row only when that match or its needed group/call falls outside the current timeline window, detaches bottom-follow, and scrolls once with an exact-character browser text Range highlight. Forced disclosure does not alter manual expanded state or start the normal card-height animation; close/session replacement clears the instance’s highlight and never scrolls to the bottom. This pane-local feature adds no persisted query state, backend search index, or second scroll owner. The placeholder is “Search messages”; the search scope remains loaded messages while incomplete prefix loading continues.

### D-webui-timeline-view

[2026-10-11] Chat settings expose one browser-local Timeline view: Detailed, Grouped, or Conversation. Detailed replaces the former disabled Group tools setting; Grouped replaces its enabled setting and retains the existing historical groups, forced-open tool tail, and manual disclosure contracts. The internal API uses only `timelineView`. A valid `foxwarm_timeline_view_v1` value wins over `foxwarm_group_tools_v1`; absent/invalid new values read old false as Detailed and old true as Grouped. Mode changes write only the new key and synchronize other browser roots through the existing storage event owner. Ordinary, popup, embedded, restricted WebUI, History result, nested CTX, and Debug preference projections consume their root viewport family’s mode without new server/Session settings or access capabilities. Desktop roots retain the shared desktop value; mobile roots use the independently persisted Conversation default defined by the [mobile shell contract](../threads/webui-mobile-shell.md). Narrow panes inside a desktop root remain desktop projections.

[2026-10-16 visible updates; updated 2026-10-19] Conversation is a display-only projection that defaults to keeping every ordinary assistant text part visible in source order, including progress updates and final answers. Its browser-local Show commentary switch folds explicit `phase=commentary` text and unmarked text from requests with actual tool calls into Activity. Direct user content and attachments remain visible, including input arriving during work. Each visible text part closes the preceding process disclosure; tools, reasoning and internal inputs between successive text parts form their own collapsed process. Runtime wakeups alone do not split it. CTX remains a hard cut; no work ID, history rewrite, provider replay change, Archive scan or backend turn platform is added. Independent generated images remain accessible in their original position and may split disclosure surfaces.

By default, explicit `commentary`, explicit `final_answer`, unmarked legacy prose and provisional streaming text use the same visible text boundary. With Show commentary off, explicit phase remains authoritative: `commentary` folds and `final_answer` stays visible. When phase is absent, text folds only if the same loaded logical request has actual function calls or supported hosted search/open-page activity; otherwise it stays visible, including streaming and incomplete text. Already-loaded CTX-local `llmRequestId` and `llmSegment` records link request segments for both this classification and usage. Without request identity, classification is per message. Tools arriving in a linked segment can therefore fold earlier unmarked text, but tools from a later unrelated request or across CTX cannot. Mixed parts retain their other images and technical output. The existing viewport/follow owner remains authoritative. A metadata-only completion updates its request without creating an empty disclosure after already-visible prose. A reply-free turn retains its last commentary as the collapsed Activity preview, restoring the original result-first fallback; committed previews also enter Conversation Search. Earlier folded commentary remains readable only inside expanded Activity and has no Search hit. Expanding the process replaces its preview with the complete original fragments rather than duplicating the last commentary. Default-on behavior has no separate commentary-only cut and no duplicated process preview of ordinary text.

Processes begin collapsed. The summary/expand control stays at the top. Expanded processes also expose a bottom collapse control, without repeating usage metrics; both controls update the same disclosure, and bottom collapse restores focus to the retained top control. Opening one renders its ordered technical fragments once through the existing nested Detailed timeline: tools, reasoning, hosted search, Task notifications, System/Event and Timer messages use their original components. Standalone assistant prose remains outside these disclosures and is not repeated inside them. There is no secondary step classification or disclosure wrapper. A tool's collapsed header retains its tag and concise command/path/arguments but mounts no result or progress content; one native-header click opens its full body. Native input, reasoning and search cards retain their own disclosure defaults. Only Conversation process Reasoning uses subdued normal-weight previews, muted text and weaker tag/background treatment; its original expanded content is unchanged. No generated summaries or copied tool-result previews are added. Only Conversation process tools neutralize successful tone; genuine errors remain distinct. Stable process/request identities retain manual expansion during stream updates, and disclosure controls preserve keyboard activation and aria-expanded. The row owner derives process membership; rendering reuses the existing Detailed projection. Visible progress updates and final replies share the same prose size, color, opacity and content inset; process nesting remains a separate layout level. Replies have no bubble border/background/shadow, user bubble text matches body size, and width preferences, Markdown structures, source/copy actions and timestamps remain available. Detailed and Grouped retain their established chrome and disclosure defaults.

Activity summaries show nonzero Worked / Waited durations (or Elapsed when only the total is trustworthy), followed by actual calls, child sessions, sent messages and received messages. Zero-valued facts are omitted; compact sent/received labels still mean messages. Without supported duration or count facts the label remains Activity; there is no special Reasoning title. Calls/results pair by tool-use ID, `call_tool` counts its resolved target once, and supported hosted search/open-page output items count as calls without being converted to function calls. Hosted item IDs prevent repeated output from recounting the same search. ToolScript `run_script` and `continue_script` each count as one ordinary top-level tool invocation. Activity does not expand their subcalls or inspect script code, return data, private runs, background completion, or live progress to reconstruct internal creations/sends. Existing ToolScript progress and linked-task completion behavior are unchanged.

Creation needs the builtin's actual created-session acknowledgment, including a created child whose task delivery failed. Sends need actual successful delivery evidence: explicit send acknowledgments, awaited child initial-message delivery, and the Task mutation receipt's per-operation `sentNotifications` count. Task counts read native receipt fields first and retain reading of already-persisted JSON `output` envelopes; neither form promotes arbitrary script return data to delivery evidence. Task transfers may deliver to two recipients; silent saves, self-skipped notices, absent recipients, and failed sends do not count. Child task assignment uses the same actual notification total once. Old direct receipts without delivery evidence remain unknown; these summaries are not a complete communication audit. Received communications use real internal inter-agent/task/MCP records, including [inbound MCP external/context frames](../units/src-mcp-inbound-session-service.md) and [outbound-server notification frames](../units/src-mcp-external-service.md), excluding ordinary input, authored XML quotations, and time/compact/reminder maintenance. File delivery, managed controller inputs, timers/triggers, and process-completion events do not acquire a new Sent/Received definition.

The only external Conversation LLM error is a retry/error that is the last committed message of Chat's active context, confirmed by the existing retry classifier, regardless of `retry.final`. Non-tail retries stay inside Activity without introducing visible text boundaries; their full logs remain available through the system-event card's Details. Chat supplies `currentHistoryMessages` separately from displayed history, its viewport slice and provisional stream rows; matching an independently loaded Archive row uses its canonical sequence identity. This one original card stays outside Activity; a later real message or CTX boundary returns the old notice to Activity. Nested archive/Activity and queue timelines do not infer a current-history tail. Tool failures never color or label the Activity summary as Error; expanded results retain their real error display. Activity details use compact technical-row spacing without applying the extra CTX nesting margin; actual CTX nested layout and ordinary user layout/metadata remain unchanged.

For a complete direct-channel envelope stored in a system part, or the supported legacy text-backed source envelope, rendering and Search share one body extraction. Only the trusted outer opening/closing wrapper is metadata and follows the metadata preference. The authored body stays literal with its original whitespace and original part index; its time tags, closing XML, and quoted channel envelopes are not reinterpreted as another source or stripped from Search. The modern split opening/body-text/closing path likewise treats body text as authored content, not a candidate source envelope. Detailed/Grouped retain their previous rendering and Search behavior.

History source selection, CTX representation and active deletion/clear semantics are canonical in [Conversation and history](../behaviors/conversation-and-history.md#source-selection-and-display-are-independent). Rendering remains independent of that source selection; retrieval and membership resolution stay with [continuous-history synchronization](../threads/archive-and-recall.md#d-webui-continuous-chat-history). Conversation's pane-local Search indexes only its loaded committed ordinary assistant prose, direct user bodies and CTX summaries; manually opened Activity and nested archive detail are outside that search corpus. Detailed/Grouped retain their technical Search and transient reveal behavior under [D-webui-chat-session-search](#d-webui-chat-session-search). History search query scope and permissions are unchanged.

ProcessingStatus remains the single live status owner in Conversation. Its controls and queue geometry follow [Chat's bottom status layout](../units/webui-chat.md#d-chat-bottom-status-layout), and visible decorative captions retain the [stable accessible runtime labels](../units/webui-fox-loaders.md#behavior). Waiting preserves its reason and targets through the runtime details surface, under the [runtime presentation contract](../threads/session-runtime-presentation.md#d-session-runtime-presentation). Activity is not evidence of successful completion. Activity counts and duration summaries use the read-only evidence described above; they do not create a second live Session-status owner. Queued user previews stay visible as pending input; internal queue items use the existing queue status rather than fabricated completed Activity. Usage, metadata, and minimap preferences remain independently owned. Conversation suppresses external usage badges and shows total recorded tokens in the process statistics instead. Its token trigger shares the left statistics' type size in both standard and console treatments and remains right-aligned while open. Usage details occupy a separate right-aligned row below the full-width statistics header, bounded by the pane. When no actual usage has arrived the trigger and details are absent, without placeholder width. The total includes the reply request and each logical request only once, using its last actual usage-bearing completion/segment. A prefix without usage does not make a completed logical request partial. Missing completed-request usage remains unavailable; active incomplete-request usage remains pending. A pending request alone does not label the recorded total partial; only genuinely unavailable completed-request usage can do so. Pending/unavailable distinctions remain in details, and absent usage is never estimated as zero. Details disclose Requests, normalized Cached/Input/Output, `Cached / (Cached + Input)` cache share, reliable API time, persisted time/model/Seq attribution and the existing message-reference copy. Cache share is not a cost-saving metric or a failure signal. Totals include only this Session's normal messages, not child usage or nested compact-planner diagnostics; the minimap's current-context accounting is unchanged.

#### Activity timing: display-boundary scope

The elapsed range starts at the preceding visible user input or assistant text boundary and ends at the next such boundary, CTX or terminal retry. Shared logical-request work intervals are clipped at each visible text boundary; its request usage still has one owner, rather than being duplicated for each text part. The total elapsed range is independent from the displayed Worked/Waited sum. Request-aware body classification determines which model text is a reply boundary; ordinary progress text cuts the process clock. Empty/whitespace model text does not render an empty conversation row or cut the range, and usage/phase metadata alone does not create Activity; real accompanying reasoning/tool records remain. A text-free completion can supply the conservative display cut above without becoming an empty reply. A visible Session communication is a display boundary and clips adjacent Activity ranges; it receives no invented duration. When no preceding visible boundary exists, the first genuine Task/inter-agent/channel input or trustworthy execution origin in the already-loaded CTX scope can start the range. Session creation, time tags, and maintenance are not fallback origins; unknown earlier work stays conservative. The elapsed start remains the existing visible boundary; the waiting floor below does not move it. No internal records means no fabricated waiting-only row. A requesting-model runtime with a reliable busy/request start can present current Worked time before the first provider part arrives; this non-disclosable surface is presentation-only and disappears when real Activity/output replaces it or the runtime stops working. Queued, waiting, idle, and unknown-start states do not create it. No history, queue, or persisted metadata is added. Independent visible images stay in place without cutting this text-based clock; if they split the technical disclosure surfaces, the range's duration appears once on its first Activity surface.

Final boundary clocks are persisted message timestamps, including a preceding boundary outside the viewport. Streaming text does not save its browser arrival as a history timestamp. A runtime-confirmed open Activity temporarily ends at current time and updates through a local display clock; committing its next visible boundary fixes the endpoint. Measured logical-request and synchronous tool intervals, plus the currently active runtime's known busy interval, are clipped to each range and unioned so parallel work and shared request segments do not double count. While tools run, the current runtime tool ID may confirm the latest pending call batch, whose receipt is published only after the whole batch (including adjacent parallel execs) finishes. Missing receipts alone do not invalidate that confirmed batch when the interval before live busy is already measured or contains only the existing short-overhead gaps. This does not extend measured busy intervals or turn larger unknown preceding work into waiting; missing older requests, completed receipts without execution timing, and retries retain their fallback. A bare busy flag or unrelated tool ID adds no such exception. Request/tool waits are busy, not CPU usage; background jobs, paused script lifetimes, and other Agents' work after a synchronous return are not continuous busy. Displayed waiting estimates the continuous non-busy gaps and does not require a `wait` invocation; it is not a wait-state audit. Each gap shorter than two seconds is omitted before summing, including leading and trailing gaps; exactly two seconds qualifies. The current two-second cutoff is a display-noise heuristic. Multiple short overhead gaps cannot combine into a displayed wait. Omitted overhead is not added to Worked, so displayed Worked plus Waited need not cover the total elapsed range.

[2026-10-15] When a time divider is actually displayed before the timed Activity, Waited excludes non-busy gap portions before that divider's exact timestamp. Clip each continuous gap at this floor before applying the two-second cutoff; later genuine waits remain. Without an actual divider, preserve the existing leading idle. This is a read-only waiting adjustment, not a new input/turn boundary: Worked, Elapsed, evidence validation, counts, usage, and divider selection remain unchanged. Use the derived marker timestamp, not formatted clock text or arbitrary system time tags.

Canonical compact-completion markers are untimed Session maintenance, including the exact generated completion-plus-goal-reminder row recognized by the continuation classifier. Their cards/details remain in Activity, but a maintenance-only disclosure/range receives no Worked, Waited, or Elapsed label or live clock, both at the tail and after a later user boundary. Maintenance is not execution or request-completion evidence; it neither cuts a real Activity nor changes its effective last work record. Genuine work/coordination retains its existing timing boundaries, including leading idle when no divider supplies a waiting floor, even when Continue is unavailable. The shared frontend helper is deliberately narrow: canonical system-only completion or the exact generated pair, not authored text, unrelated reminders, or records with extra real content. This changes no history, Continue availability, CTX truncation, or full-history tail-error presentation.

CTX cuts the range at its persisted message boundary and prevents borrowing execution evidence through the summary. A metadata-confirmed final LLM retry closes at its stored timestamp, even when the notice later returns to Activity. Existing normal Stop history has no durable stop timestamp; an idle unfinished tail without trustworthy completion/pause evidence stays counts-only rather than fabricating a stop time or growing a guessed interval. Missing endpoints likewise retain counts only. Known endpoints with missing/invalid request/tool evidence, unmatched partial segments, or unmeasured failed/retry work show Elapsed rather than labeling missing busy time as waiting. No backend wait-history rows, event accounting, Archive requests, or model-input changes are introduced.

Session communications follow [D-session-communication-presentation](../threads/session-communication-presentation.md#d-session-communication-presentation): Conversation defaults to readable To/From message cards in source order. The browser-local Show inter-agent messages switch folds both directions together into Activity; successful delivery bodies, including metadata-backed ToolScript sends, remain readable alongside their native technical evidence when Activity is expanded. Hidden communications do not cut Activity timing or enter Conversation Search. Structured runtime failures follow [system events](../threads/session-runtime-presentation.md#d-session-system-events).

Visible peer messages remain input evidence for conservative Activity timing: missing processing between two deliveries produces Elapsed, not invented Waiting.
