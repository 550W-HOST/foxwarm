# Thread: tool dispatch — authorization and batches

Part of the [tool dispatch](./tool-dispatch.md) thread. Covers how a resolved target is authorized, how batches and model-requested cancellation settle, and how tool output is bounded before it reaches model context.

- [src-tools](../units/src-tools.md)

## Invariants

- Generic authorization and the current isolation compatibility layer are enforced against the canonical resolved capability source plus exact Node/server identity; structural path, target, relation, and tool-local guards remain separate and non-bypassable.
- A generic allow never bypasses exact isolated-Agent rules or structural checks. Generic deny may further restrict any Session.
- An isolated session cannot use master file paths outside its own agent directory.
- Unified wrappers are permission-neutral and cannot replace or bypass the concrete target's permission/service/structural guards. `builtin:call_tool` is neither discoverable nor selectable as a concrete target identity.
- Tool output is bounded before it enters model context.
- Recognized image bytes stay in structured image parts rather than entering text excerpts; non-image text, JSON, audio, resource, and blob content remain subject to the normal output budget.
- Tool batches emit one result for every call and append one tool message only after the batch settles. Image/result parts and function responses remain in original model-call order rather than completion order.
- Model-requested cancellation is effect-free: canceled calls do not resolve targets, publish per-call starts, run permission checks or handlers, synchronize cwd, return images, or contribute tool-loop/post-action control. A canceled call still receives its ordered function response so history pairing and the next model iteration remain valid.
- When startup config `handoffConfirmation:true` is enabled, `send_to_session` and `create_child_session` require both structured handoff review fields, including child creation without an initial message. `handoffRecall` must start with the exact recall question, contain non-placeholder recalled context, and appear before `message`; `handoffConfirmation` must use the exact confirmation prefix and suffix with a non-empty, non-placeholder review and be the final concrete argument property. Direct model execution prechecks both fields per call, while the concrete handler repeats the same check so unified, Main-management, and ToolScript invocation cannot bypass it; canceled model calls skip the review check. The two fields are control metadata and are not sent to the target Session. The default-disabled mode omits both schema properties and accepts ordinary handoffs without them.
- Direct, unified, and ToolScript calls share one `ResolvedTool` resolver/executor. Placement metadata remains process ownership rather than capability identity. A trusted current-session-effects marker—not model arguments or mere Session presence—selects Worker fences. The same argument-normalizing guard runs before concrete permissions and returns a stable retryable code even for malformed always-unsupported calls. Unified/ToolScript local calls cannot reconstruct context through child `nodesManager`/`sessionManager`.

## Design decisions

### D-dispatch-generic-tool-authorization

[2026-10-19] Version-1 rules also support concise top-level selectors, with bounded `*` patterns only for caller `session` and actual-effect `node` identities. `node:{current:true}` uses caller-owned routing; `node:{provider:...}` filters authoritative Core Provider namespaces without introducing a Provider principal or Session-to-Node permission binding. Node effect facts are separate from legacy `match.targetNode`: unrelated Main/MCP operations and the ToolScript VM cannot inherit a selected/source Node's permission. Multi-Node allows require every endpoint; Node denies match any endpoint. Registered unknown endpoints remain conditional in discovery. Existing long-form scalar/argument semantics, first-match ordering, external default-deny, loader failure behavior and isolated compatibility are unchanged. Mixed shorthand/`match` input is rejected; omitted diagnostic rule IDs become `rule-<position>`.

The explicit `args.taskId:{task:{owned:true}}` matcher is registered only for exact builtin `task`. Main resolves the canonical owner from Task authority; missing/unowned/other-owner targets do not match. Worker calls use a narrow source-fenced ownership read, and the Main effect boundary repeats authorization. This is policy expressibility, not a global change to task reads or shared description/note updates. Task list scope `owned` is distinct from the existing creator-or-owner `current-session` scope; see [task contracts](../units/src-tasks.md).

[2026-10-01] Default model injection uses the same conservative ordered visibility projection as discovery, through the current Session's generic and legacy isolation checks. Node-environment definitions use the concrete current Node; other builtin identities follow canonical placement. File placement selectors (`send_file`, `image_write_to_file`) and ToolScript file-source selectors have an unsupplied file Node, so their target-Node matchers remain conditional and legacy target-specific restrictions do not prove whole-tool denial. No argument/path enumeration or target inventory is introduced. `call_tool` remains a permission-neutral dispatcher; script containers retain ordinary builtin authorization. Surviving schemas, descriptions and order remain unchanged, and the global default registry is not mutated. Explicit schema overrides retain their existing contract; compaction requests using the default registry receive the same filtering, including `submit_compact_plan`. Policy-unavailable errors propagate before optional Shell topology lookup; the existing successful-policy cache and strict invocation checks are unchanged.

[2026-09-06] The fixed instance policy `state/tool-authorization.yaml` is the generic authorization layer intended to precede and eventually replace legacy isolation. It is a strict version-1 YAML object with ordered rules, first-match-wins semantics, and an explicit `allow|deny` default. Rules may match exact Agent, Session, canonical tool source/name/MCP server, resolved `targetNode`, bounded argument values, and selected path facts. Direct, unified `call_tool`, ToolScript, Main-local, Worker, Node-service, and MCP-service paths authorize the same resolved concrete capability; dispatcher/container wrappers never become substitute identities. Generic policy applies to non-isolated and isolated Sessions. During migration, allow only passes this layer and cannot bypass current exact isolated-Agent rules, path/target/relation checks, service fences, or tool-local validation.

Each process reads at ordinary authorization/discovery boundaries and reuses only a successful parsed policy younger than ten seconds. After expiry, async callers retry one fresh failed read/parse after 100 ms; existing synchronous visibility callers retry immediately once. Exact `ENOENT` means the compatibility empty/default-allow policy. Any other double read/parse failure raises the trusted `TOOL_AUTH_POLICY_UNAVAILABLE` error and fails the current operation closed without using an older policy. Discovery preserves rule order without enumerating argument space: a definite identity-only decision stops; a conditional possible allow keeps the capability visible; a conditional deny alone does not prove universal denial. Invocation remains the strict complete evaluation.

Master path facts and policy bases canonicalize existing symlinks and prospective paths through their nearest existing ancestor before containment checks. Source-specific derivation prevents unrelated same-name MCP tools from receiving master-file path facts. `copy_between_nodes` master-relative paths reuse its Agent-directory-relative transfer resolver, and patch facts reuse the canonical parser for all supported Add, Update, and Delete operations. This closes supported static symlink-prefix escapes, including nonexistent children and policy setter candidates, but is not a general filesystem sandbox: concurrent symlink replacement between authorization and effect remains a TOCTOU limitation.

Registered builtin Session targets may use `args.sessionId.session` with strict `self:true`, `sameAgent:true`, and/or direct `relation: parent|child|[parent,child]`. Conditions in one matcher remain AND; lists remain same-field OR; separate ordered rules express alternatives. Resolution follows each registered handler's actual defaults and aliases, never a universal absent-is-self rule. Identity comes from authoritative catalog records rather than Session ID prefixes. Worker execution obtains bounded facts from Main before publication and Main effect services recheck; discovery remains conservative and synchronous.

`set_config({target,filePath})` is the Main-owned, master-only configuration installation tool, hidden from default injection. The current policy must authorize the setter with its target and `node:master/read` of the exact candidate; the candidate cannot authorize itself. Targets `config`, `models`, and `tool-rules` share [D-config-live-install](../units/src-config.md#d-config-live-install). Tool-policy replacement retains its bounded parser, atomic exact-byte replacement, immediate Main-cache invalidation, and other processes' existing at-most-ten-second successful cache. Persisted references to the removed `set_tool_rules` builtin fail explicit migration validation rather than silently losing a deny or widening a policy-only allow.

Policy unavailability is fatal only to the current turn, not the Session or process. Every returned model call still receives an ordered paired function response; already-started parallel exec siblings settle and later calls are marked skipped. The canonical runner appends that paired tool message before delivering one terminal error and releasing normal turn ownership. It does not set persistent stopping, delete queued work, or affect another Session. Ordinary rule denial and invalid replacement candidates remain nonfatal tool errors. Foreground ToolScript persists its failed run and propagates this trusted fatal condition; background runs fail only themselves.

[2026-09-19] The same version-1 ordered policy now also accepts `match.externalId` for authenticated inbound identities. An identity-neutral rule may match external requests in its existing first-match position. An external request with no matching rule is denied even when the policy's configured internal default is `allow`, including when the policy file is absent. Internal Session matches, cache, atomic installation, and policy-unavailable behavior are unchanged. External principal identity is minted by Bearer verification; it never supplies a fabricated Agent. An inbound transport now owns a real, ephemeral external execution context; its ID can later supply a `session` fact at a concrete execution boundary. External requests without a concrete Node have no `targetNode` fact and cannot match a master-only allow. Agent-derived path and same-Agent/Session-relation facts cannot be inferred for an external source. The inbound catalog exposes only compatible first-party CLI Node tools with live scoped exec results; internal Session handlers remain separate, as specified by [D-dispatch-mcp-inbound-bridge](./tool-dispatch-mcp.md#d-dispatch-mcp-inbound-bridge).

### D-dispatch-resolved-target

[2026-08-18, updated 2026-09-07] Direct provider calls, `call_tool`, and ToolScript nested calls resolve one canonical operation before execution. The canonical capability sources are `builtin`, `node`, and `mcp`; source is independent from the exact execution Node/placement and process/service owner. Direct `read`, `write`, `edit`, `apply_patch`, `exec`, and `browse_*` calls are Node capabilities targeting the current execution environment, and explicit `source=node` calls use that same current Node when `nodeId` is omitted. Unified discovery emits those capabilities as Node results and does not duplicate them under the builtin source. `source=builtin` must reject those Node-capability names with a clear mismatch instead of retaining an alias. Obsolete dedicated Node/MCP discovery and invocation wrappers are absent rather than compatibility-routed. Permissions and tool-local validation apply to the resolved operation, while existing typed Main/Node/MCP/file services continue owning their effects.

Root schema shape does not decide argument ownership. Explicit placement metadata marks `send_file.node` and `image_write_to_file.node` as file source/target placement selectors; the resolver consumes those fields, retains their established omitted/blank/`current` normalization, and authorizes the resolved file Node. `create_child_session.node` is instead a semantic child-placement argument: it remains in canonical authorization arguments across direct, unified, ToolScript, Main-local, and Worker/Main-management paths, and reaches the child creation effect unchanged. The management capability itself executes and is authoritatively rechecked on Main. Omission inherits the source Session's current Node; an explicit accepted Node commits that Node to the new child. ToolScript starter `node` is instead a source-only selector: file-backed builtin authorization targets that resolved source while the VM execution Node remains unchanged; inline keeps the master builtin identity and rejects an explicit source selector. Source reads separately require the actual Node read capability. See [authorized ToolScript source](../units/src-toolscript.md#d-toolscript-authorized-file-source). Do not infer placement ownership merely because a future builtin schema contains a root field named `node`.

### D-dispatch-exact-agent-tool-rules

[2026-08-19] Agent metadata may persist optional exact `toolRules`. Each rule is only `effect=allow|deny`, canonical `source=builtin|node|mcp`, and an exact non-empty tool name; Node rules additionally require one exact node and MCP rules one exact server. Builtin rules accept neither. Wildcards, regex/pattern fields, session/argument/path matchers, extra fields, and duplicate/conflicting exact identities are rejected before mutation effects. The persisted replacement is bounded to 256 rules and each exact server/tool or native Node string to 128 UTF-8 bytes (qualified Provider Node IDs may use 193); input is rejected rather than truncated. Rules belong only to the exact agent and never inherit through `agent.inherit`; absent and empty rules retain the historical isolated defaults, and rules are inert for non-isolated agents.

For an isolated agent, exact deny overrides a historical default allow and exact allow may add the named capability. An allow never bypasses the authenticated target/service boundary, advertised Node tool set, master-exec prohibition, agent-scoped master paths, copy/channel/timer/session relationships, Worker placement guards, or concrete tool-local validation. Node custom-tool missing-rule behavior deliberately reaches the exact bound/current Node service, preserving the established advertised-capability contract. MCP missing-rule behavior remains deny; an isolated agent discovers and invokes only exact allowed server/tool identities through the source-fenced MCP service.

Authorization and visibility use the same identity evaluation. `search_tools`, Node topology, and MCP discovery omit denied or structurally unavailable capabilities before metadata reaches the model. Unified invocations authorize only their independently resolved builtin/Node/MCP target; MCP's concrete check remains authoritative in Main. Permission-neutral dispatcher/container `call_tool` is rejected from persisted rules, omitted from builtin discovery, and rejected as a recursive concrete target while its provider-facing direct interface remains registered. Main-local, reverse Worker, direct, unified, and ToolScript paths converge on the same target rules. Session workers receive a normalized exact-agent metadata snapshot from Main at spawn. Only workers whose installed snapshot is isolated refresh that agent before execution/discovery; missing/read-failed refreshes preserve the snapshot, while malformed refreshed rules reject the current operation. Rule-only replacement on an unchanged isolation binding is therefore live under Worker placement without an I/O fail-open or per-call metadata reads for non-isolated workers, while isolation-node changes retain the existing ownership fence.

`create_agent` and `set_agent_isolated` accept optional full `toolRules` replacement, with `[]` as canonical clearing. When `set_agent_isolated` receives rules without `nodeId`, it preserves the current isolation binding; an explicit empty `nodeId` clears isolation. Agent listings and mutation results report a concise rule count. Existing metadata without `toolRules` remains readable unchanged.

### D-dispatch-output-boundary

Tool results remain structured through execution and are normalized/guarded exactly once before becoming model input. Recognized image payloads are promoted to structured image parts before the generic text/structured-output guard runs; the guard applies to the remaining response and must never turn image base64 into a text excerpt or truncation marker. Non-image content receives no multimodal exemption.

### D-dispatch-exec-parallel-segments

Phase-one batch concurrency is intentionally narrow: only adjacent direct calls whose tool name is exactly `exec` run concurrently, with an internal maximum concurrency of four. Every non-`exec` call—including unified `call_tool`, MCP, node-dynamic, ToolScript, file, session, and wait/control tools—flushes the previous exec segment and runs serially. Each exec segment snapshots session node/cwd routing once, settles all calls, then replays cwd changes in model-call order before the next barrier; the last model call therefore owns the resulting session cwd. Results, images, errors, and progress stay model-ordered and one failure does not discard siblings. Parallel workers prepare only the next admitted item rather than pre-starting the entire queue. Stop skips every unstarted queue item and barrier while preserving already settled results; supported exec waits hand off without process termination under [the canonical control-command contract](./message-processing-pipeline.md#d-pipeline-control-commands). This is an internal scheduler contract, not a public configuration or generalized resource-lock API.

### D-dispatch-node-selection-batch-prerequisite

[2026-10-10] In an ordinary model-return batch, failure of builtin `node` with normalized `action="select"` skips every unstarted later call. Direct calls and unified `call_tool` targets use the same canonical source identity and argument parsing, including `argsJson`. Validation, target availability, and authorization failures all trigger this rule. Same-name MCP or custom Node tools and other builtin node actions do not. Existing model cancellation and preflight results retain their own responses.

Skipped calls neither resolve targets nor publish starts, execute handlers, synchronize cwd, produce images, or contribute wait/handoff effects. Each still receives an ordered paired function response with the selection-failure reason. Previously completed operations are not rolled back and already-started processes are not killed. Selection failure is not a new fatal turn boundary: the model receives the batch results and can correct the prerequisite. Existing fatal authorization-policy unavailability remains unchanged.

A successful selection is a serial barrier and clears the previous Node's cwd before the scheduler captures a later exec segment. Adjacent direct exec calls retain their bounded concurrency. Set `cwd` directly rather than relying on a preceding exec to change directories. Dependent shell steps use a single command with `&&`; calls depending on prior results or conditional failure handling use ToolScript. ToolScript nested calls retain ordinary script exceptions/control flow rather than this automatic model-batch rule. No general stop-on-error parameter or dependency scheduler is introduced.

### D-dispatch-model-tool-cancellation-and-handoff-confirmation

[2026-09-04, updated 2026-10-08] Ordinary provider-facing Foxwarm function schemas reserve optional top-level `__cancelTool` and `__cancelAllToolsThisTurn`, each accepting only boolean `true`; the dedicated compact-plan submission tool is excluded. The complete returned batch is scanned before target resolution, per-call `onToolStart` publication, or tool effect. The turn runner may already have published batch-level returned-call progress/runtime state; cancellation does not add a separate runner status. Whole-batch cancellation wins globally, while single-call cancellation and invalid reserved values affect only their own call. Execution clones remove the controls, canonical assistant calls retain them, and every skipped call receives the same minimal `{canceled:true,...}` response in model order. `call_tool` consumes only its own top-level model controls and does not recursively reinterpret the concrete target's `args` object. ToolScript host calls are not model-return batches and retain ordinary script control flow.

`handoffConfirmation` is a top-level startup boolean, defaults to `false`, and controls only the inter-agent review checkpoint; cancellation remains unconditional. When enabled, `send_to_session` always requires two exact review fields, while `create_child_session` requires them only when `message` or `taskId` is supplied; a pure child creation without either is not a handoff and does not require review fields. `handoffRecall` must begin with `Before composing this inter-agent handoff, have I recalled the applicable communication rules, the user's actual request, and the scope this recipient needs?`, include the caller's non-placeholder recalled context, and be ordered before `message`. `handoffConfirmation` must begin with `Before sending this inter-agent handoff, have I honestly checked that it is necessary, actionable, and not merely acknowledgement, duplication, or inherited-rule repetition; if I found that it should not be sent, did I omit or cancel it instead?`, end with `I have completed the check, found no issue, and confirm this inter-agent handoff should proceed.`, contain a non-empty non-placeholder review, and be the final property of the concrete argument object. Model-facing guidance requires the review to be specific to the recipient and action; acknowledgement-only messages should be omitted or combined with the next actionable handoff, and a discovered blocker should be omitted or canceled rather than padded with approval text. Model-batch preflight converts a bad review into only that call's tool error; concrete handlers repeat the check for direct, unified, Main-management, and ToolScript parity. The two fields are local control metadata and never become target-session content or task-assignment text. A model-canceled handoff is skipped before review validation. When disabled, model-facing schemas and child guidance omit both fields, and handlers accept ordinary calls without them. This is a deliberate model communication checkpoint, not target hashing or a claim about JSON generation timing. Changing the flag requires restart.
