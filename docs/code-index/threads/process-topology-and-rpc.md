# Thread: process topology and RPC

## Overview

Foxwarm uses one logical set of asynchronous service contracts with configurable process placement. A service may run in the caller's process through a local handler or in a supervised child through IPC. Placement must not create a second business API or expose mutable in-process objects to callers.

The production child-process service on this boundary is the LanceDB/vector owner ([Vector owner](../units/vector-owner.md)). Managed Main hosts every Session owner in its own process; it does not implement Session-worker placement. The Session-worker decisions below are recorded because their persisted fields (`sessionStateVersion`, `lastAppliedMailboxId`) and the `sessionWorkers` configuration key remain part of the data managed Main reads and validates.

## Configuration

- `sessionWorkers` is validated configuration with no managed placement effect. It accepts `false`, `true`, or an object; its designated toggle shape follows [D-config-feature-toggle-shorthand](../units/model-configuration.md#d-config-feature-toggle-shorthand), while `idleSeconds` defaults to 60 and is bounded from 1 through 86,400 seconds.
- `vector` defaults off and is independent from process placement. When disabled, Main creates no vector owner or client.
- `dbWorkers` defaults on. In the current scope it controls only the LanceDB/vector owner when Vector is enabled. Archive and LLM-request-journal SQLite stores are not moved behind that worker.
- `vectorMaintenance` defaults on with a 24-hour retention window and accepts the same designated boolean/object configuration shape; its exact-owner execution contract is [D-vector-owner-maintenance](../units/vector-owner.md#d-vector-owner-maintenance).
- Both placement switches are read at startup. Saving configuration does not hot-migrate a live service between processes.

## Runtime boundary

Service descriptors define serializable request, response, error, and event DTOs. The registry binds each descriptor to either a local handler or a child-process transport. Both placements remain asynchronous and use the same validation and cloning boundary; local callers do not receive handler-owned object references.

The Vector child uses a private connection to its parent ([Vector owner](../units/vector-owner.md#placement-and-lifecycle)). Transport/service separation leaves direct Unix-domain endpoints as a later topology change without changing service DTOs.

Requests carry protocol/build identity, a process generation, request and trace IDs, and optional deadlines. Child shutdown first stops new requests, drains accepted work within a bound, and then exits. Replies from an obsolete process generation are rejected.

Main owns one lazily created ToolScript/Monty pool. Main graceful shutdown closes that pool before tearing down the Main-owned services that ToolScript host calls may use. The canonical pool-lifetime decision is [D-toolscript-process-lifetime-pool](../units/toolscript.md#d-toolscript-process-lifetime-pool).

Main-local turn admission and owner drain precede dependency teardown; unfinished work keeps the existing restart checkpoint. The bounded forced-exit fallback and the distinction from user Stop are canonical in [local shutdown](./session-lifecycle.md#d-lifecycle-main-local-shutdown).

Owned Foxwarm executable entry points set short role-first presentation titles: `foxwarm:main`, `foxwarm:vector`, and `foxwarm:node <node-id>`. The title may replace the original command line in operating-system process displays and may be truncated by the display's process-name field. It is observational only: process supervision and authorization continue to use the existing PID, boot/start identity, generation/incarnation, IPC, and authenticated Node identity boundaries. Library imports and arbitrary user subprocesses do not set these titles.

The hot turn loop does not move full history, images, or tool output through a central payload broker. Explicit external history/debug reads may return the requested immutable snapshot; high-frequency service calls otherwise use bounded DTOs and stable file/blob/snapshot references where necessary.

## Vector placement

The vector service owns the LanceDB connection/table, optional derived lexical-index or shadow-rebuild connection, per-session indexing/lifecycle chains, batch state, startup backfill, embedding requests, dense/detailed hybrid searches, and vector lifecycle operations. It reads durable archive rows and independent checkpoints directly from the archive SQLite store and lexical derivative. Rename/fork/reset/rebuild remains exact-owner work behind the same one-writer boundary, except conservative pre-placement local identity reset during move-journal recovery. Archive durability and exact recall remain independent of vector availability. Descriptor v4 retains detailed hybrid search and legacy array search while adding only internal failed-creation derived reset; pre-v4 borrowed owners fail version negotiation without local fallback.

When Vector is enabled, `dbWorkers:false` runs the vector service handler locally and `dbWorkers:true` gives a supervised child ownership of LanceDB. The main process never silently opens a second fallback owner after a worker failure. When Vector is disabled, neither placement is created and `dbWorkers` has no runtime effect.

The production bootstrap completes authoritative session/archive migrations before launching the selected vector owner. Main HTTP and Session readiness do not await optional Vector initialization or its one-time derived source-time repair; the owner retains initialization under service-lifetime cancellation and remains unready until it finishes. Child readiness means required native initialization, including source-time metadata repair, has completed; startup backfill remains asynchronous. Connection/first-frame handshake limits are separate from cancellable required initialization, which follows the service lifetime; [owner lifecycle](../units/vector-owner.md#placement-and-lifecycle) defines that boundary. The native LanceDB module is loaded lazily only by the selected owner. Unexpected child exit or IPC disconnect makes semantic calls retryably unavailable. A bounded-backoff watchdog starts a new generation only after the prior PID's exit is observed. Graceful shutdown drains accepted calls and active indexing/backfill work before closing LanceDB; if needed, it escalates through SIGTERM and SIGKILL while retaining ownership until exit confirmation.

[2026-10-21] Configured Vector initialization failure is nonfatal to Main startup in either placement. Main logs the error and retains the configured owner and its unavailable state; it does not mark Vector disabled, change configuration, repair the DB, or select another owner. Semantic/direct operations reject retryably as `VECTOR_UNAVAILABLE`, distinct from explicit `VECTOR_DISABLED`; message persistence, exact Archive/history reads, and shutdown remain usable. The existing child watchdog may retry only within its observed-exit fence. Local placement gains no automatic retry scheduler. Authoritative Catalog/Archive loading and migrations remain outside this optional failure boundary and still abort startup on failure.

## Session direction

Managed Main runs each Session through its exact in-process owner: `SessionRuntime` is the command/query/event boundary, the Session save lane serializes authority commits, and `LocalSessionTurnHost` runs the canonical turn. Scheduled ToolScript uses a fixed non-model owner command; see [script action contract](../units/tasks-timers.md). The stable owner split between Session-semantic operations and Main catalog/topology/presentation operations is [D-process-topology-stable-operation-ownership](#d-process-topology-stable-operation-ownership). In-process owners are released from memory once idle and rehydrated on next use; the idle condition follows [D-process-topology-worker-owned-session](#d-process-topology-worker-owned-session) and is canonical in [D-session-owner-idle-release](../units/session-manager-bootstrap.md#d-session-owner-idle-release).

`state/sessions/<id>.json` remains the single full semantic Session authority. Managed readers accept the `sessionStateVersion:1` payload and its `lastAppliedMailboxId` cursor written by the removed TypeScript Session-worker placement ([D-process-topology-session-state-authority](#d-process-topology-session-state-authority)). Main alone writes `state/catalog.sqlite`; catalog admission and scaling are canonical in [D-main-catalog-indexed-boundary](./main-catalog-storage-and-indexed-queries.md#d-main-catalog-indexed-boundary). Canonical delete semantics: [D-lifecycle-descendant-actions](./session-lifecycle.md#d-lifecycle-descendant-actions).

## Failure boundary

- Vector indexing is best-effort. A vector-worker failure does not roll back session, archive, or compact commits.
- Deterministic block rows are replaced before append, making retry after a Lance-commit/checkpoint gap idempotent.
- Exact archive recall remains available without LanceDB. Semantic search reports non-retryable `VECTOR_DISABLED` when configured off and retryable unavailability while an enabled owner restarts.
- Process isolation is intended for fault containment and parallel throughput. It is not a security or sandbox boundary.
- SQLite locking protects database integrity but does not replace session-generation fencing for semantic ownership.

## Design Decisions

### D-process-topology-configurable-placement

[2026-08-04] Keep one implementation-facing async service contract for local and child-process placement. `sessionWorkers` defaults off and accepts a boolean or object; object presence enables it with defaults unless `enabled:false`, and its idle release is configurable. `dbWorkers` defaults on and in its first version means only the LanceDB/vector owner. Placement changes are startup-only and may use graceful drain before replacement rather than supporting mixed-version live migration.

### D-process-topology-goals

**Governing goals; directly requested for the retained process-placement design.** Fault containment, throughput and resource release explain why optional process owners exist. Security isolation is explicitly outside that choice. Current C# [delivery scope](../overview.md#d-dotnet-delivery-scope) excludes Session Worker hosting; the goal does not reopen that exclusion.

[2026-08-04] Optional workers target fault containment and parallel throughput, with on-demand session resource release. They do not claim security isolation. Session workers may hold provider credentials and connect directly to providers; simple session-local tool steps should remain inside the session worker when possible.

### D-process-topology-presentation-titles

[2026-09-06] Set process titles only at Foxwarm-owned executable entry points, with the role before any variable identity so truncated process-name displays remain useful. Titles are presentation metadata and must never replace exact lifecycle, ownership, or security identity. Do not rename embedding hosts, arbitrary user exec subprocesses, the VS Code extension host, or unrelated Node.js processes.

### D-process-topology-trusted-session-worker-boundary

**Directly selected trust constraint on [process-placement goals](#d-process-topology-goals).** Keep Session authority and provider credentials within the trusted host boundary; untrusted remote environments execute bounded Node capabilities. Local IPC details implement that separation and must not be read as permission to move the owner into a sandbox.

[2026-08-06] Session workers, authoritative Session state, and Session-control credentials stay inside Main's trusted host/deployment boundary and use only local process IPC or Unix-domain transport. Generic remote Nodes must not host Session workers; they remain bounded Node capability environments reached through fixed Main services. Future sandbox Nodes are execution environments driven by the trusted local Session worker or trusted host supervisor, not Session-worker placements. Never expose a container-runtime control socket inside an untrusted sandbox. Remote Session-worker transport is not part of the roadmap.

### D-process-topology-worker-owned-session

[2026-08-04] A future session worker owns its session's hydrated state and high-frequency turn work instead of routing full history serialization through the main process. Persisted waits and ToolScript snapshots count as idle. The initial release has no fixed maximum worker count, while leaving room for a later spawn-time resource check.

### D-process-topology-session-generation

[2026-08-04] Main durably records accepted input before the Worker processes it. One supervised process generation/incarnation owns one hot session. A fork begins as an inert candidate: main must durably register its PID plus boot/start identity and activate that exact incarnation before the child may hydrate or process. IPC disconnect alone does not release ownership, PID reuse is distinguished from the exact old process, and replacement cannot start until that process's exit is confirmed. Main-owned lifecycle operations keep respawn blocked across confirmed exit, authoritative reload, mutation, and save through one concrete supervisor-owned handback flow; no generic claim API is exposed.

### D-process-topology-session-state-authority

[2026-08-05] `state/sessions/<id>.json` remains the one full semantic Session authority for local and process placement; do not introduce immutable runtime-head artifacts or a second compatibility mirror. The file uses an explicit current format version and persists `lastAppliedMailboxId`; unversioned legacy data is upgraded once without discarding historically catalog-only state, while current-format hydration replaces rather than merges semantic fields. An owning worker must durably replace the complete JSON before SQLite can mark that exact ordered session-local mailbox prefix applied. JSON cursor ahead of SQLite is recovered by acknowledging without reapplication, including when global mailbox IDs contain gaps for other sessions; SQLite cursor ahead of JSON is impossible and fails closed. Session-runtime SQLite owns only generation/incarnation and mailbox coordination. Workers never write the shared Main catalog; bounded projection, intermediate/final delivery, and ingress seams preserve that authority while exposing only cloned DTOs. Catalog storage is canonical in [D-main-catalog-indexed-boundary](./main-catalog-storage-and-indexed-queries.md#d-main-catalog-indexed-boundary).

[2026-08-12] A v1 authority that omits only `lastAppliedMailboxId` is read as compatible cursor zero and lazily canonicalized to explicit `0` at activated load/reload or post-exit handback, including a ready Worker stopped before runtime hydration. Explicit null, strings, negative/fractional values, and unsafe integers remain invalid. Reconcile against SQLite before any canonical rewrite: SQLite ahead of normalized JSON zero remains `SESSION_WORKER_CURSOR_AHEAD`, retains the fence at handback, and must never be copied into or otherwise used to repair the JSON authority.

[2026-08-11, protocols advanced 2026-08-26] Optional raw Session `effort` and `childEffortDefault` fields follow the same exact-owner authority boundary as model settings. SessionRuntime v10 and Session-worker runtime v13 carry them through settings/results alongside the later compact-cancellation controls; committed projection publication v3 carries settings for presentation; handback mirrors them from authority before fence release. Main never validates a Worker mutation against a stale projection and never materializes a concrete model default into a Session authority or catalog stub. The later increments also carry historical tool-response pruning estimates plus the existing persisted `historyVersion` as a bounded same-count history-refresh signal; they do not add authority state.

### D-process-topology-session-events

[2026-08-04, updated 2026-08-06, 2026-08-09, 2026-08-12, 2026-08-13, and 2026-09-28] Do not add a persisted session `stateRevision`. A worker publishes a reliable, awaited, complete bounded projection only after authoritative JSON/archive persistence (and mailbox acknowledgement when applicable). Main resynchronizes from the authoritative per-session JSON whenever publication outcome/order is ambiguous and on worker lifecycle boundaries; transient model/tool/typing progress remains separate and may be dropped under backpressure. Presentation-only runtime values must be normalized to the strict bounded projection DTO before publication: malformed model tool arguments still produce an ordinary tool result and must not poison the owning Worker or require restart, while the Main publication validator continues to reject arbitrary non-string fields. The transient presentation tail must nevertheless preserve lifecycle order: a pending cumulative model-stream frame is flushed and its timer cancelled before the corresponding committed model message or a structural reset is forwarded, so a stale draft frame cannot follow canonical history. The detailed cross-module contract is [D-streaming-worker-commit-order](./streaming-pipeline.md#d-streaming-worker-commit-order). After a canonical model append/publication, non-empty model text accompanying tools or queued continuation uses one fixed `session-turn-delivery@5` Main attachment attempt with no QueueSource reply target, `turnFinal` unset, and WebUI exclusion; every attached adapter resolves its own latest passive context. Final and empty-lifecycle delivery uses the same source-blind attachment path after the committed turn, where an empty outcome is either the terminal `empty-final` or the `suspended` ending that only says the turn is waiting. The v5 boundary rejects reply-source fields and accepts both empty outcomes; read-old/drop compatibility exists only at persisted QueueSource readers. Delivery failure is logged without retry, rollback, outbox, or poison.

### D-process-topology-session-tool-placement

[2026-08-04, updated 2026-08-05, 2026-09-02, and 2026-09-06] Provider requests, prompt serialization, the canonical turn loop, ToolScript, and ordinary safe session-local tools run in the owning worker. Tool placement uses exhaustive ownership metadata that is separate from permission policy and the model schema. The master node is the colocated execution environment, not the main management process: when `currentNode=master`, registered node-environment primitives execute directly in the owning session worker; a remote current node uses the existing main-owned authenticated node connection. The exact node-environment surface is canonical in [D-dispatch-node-environment-placement](./tool-dispatch-node-execution.md#d-dispatch-node-environment-placement). Operations that depend on main-owned topology, channels, timers, node connections, or other global singleton state use a bounded reverse main-service call with a stable operation identity. This includes validating unresolved `waitExecIds` against Main's authenticated process-local remote-exec liveness claims; the Worker first accepts its own exact active execs and queued completions, and Main returns only exact IDs bound to that source Session and Agent. The reverse DTO carries no PID, process state, Session authority, or polling contract. Vector placement remains independent; an initial bounded query proxy may pass through main so long as it does not carry full history or prompt payloads. A tracked background exec prevents idle worker release until completion handback or until its registry record exceeds the shared 24-hour TTL and is removed without killing the process. Main's corresponding transient remote liveness claim uses the same TTL. Open browser tabs are ephemeral: graceful idle release closes process-local tabs and browser resources rather than keeping the worker alive.

### D-process-topology-stable-operation-ownership

**Selected derived architecture for [single Session authority](./session-ownership-and-persistence.md#active-json-authority) and [bounded catalog queries](./main-catalog-storage-and-indexed-queries.md#d-main-catalog-indexed-boundary).** Semantic operations follow the exact owner; topology/presentation use their Main owner. The Worker forwarding/handback mechanics below are retained-reference implementation, not a demand to reproduce excluded Worker hosting in C#.

[2026-08-09, updated 2026-08-11 and 2026-08-13] Each operation has one stable owner: Session-semantic reads/mutations execute through the exact Session owner, while Main-owned catalog, topology, and presentation operations remain catalog-only and never hydrate or save full Worker authority. Supported live parent/display-name mutations use one narrow typed exact-Worker catalog-field update serialized through the owner lane; success means the hot Worker adopted the Main-owned value, while propagation/catalog failure rolls Main state back before success is reported. These values are not written to semantic JSON merely for communication. With Session-worker placement enabled, an idle or never-started Session-semantic operation ensures/spawns and loads the Worker rather than opportunistically executing in Main. Before any mailbox, ownership row, ensure, or child-process effect, Worker ingress resolves identity without hydration and requires the canonical target to exist in Main's loaded catalog; an alias cannot authorize a nonexistent canonical target. The high-level Main queue sink may resolve a declared/cached persisted alias to that loaded canonical ID before entering the raw coordinator, while raw coordinator and exact-worker operations retain exact-ID admission. Busy manual-fork notification admission uses the current committed Worker projection: busy routes the existing background QueueItem through durable mailbox ingress for the active runner's safe-point ingestion, while committed-idle routes the typed exact-owner append and starts no turn. Exact-owner dequeue likewise decides inside the Worker: it includes already-durable pending ingress, signals the active owner immediately, and lets the same canonical action loop ingest and continue that input without a control mailbox item. If an idle projection becomes busy after an admission snapshot, exact-owner serialization defines ordering; no second claim or notification protocol is introduced. Main may execute such an operation temporarily only after a future closed exclusive placement boundary prevents concurrent Worker spawn/ingress until commit and ownership release. Until a closed path exists, identity move/rename, agent-wide snapshot-affecting metadata changes, managed-session control, and similar admin operations fail before effects.

### D-process-topology-btw-side-request

**Derived placement design for the directly requested [non-steering aside](../behaviors/messages-and-turns.md#ask-an-aside-without-steering-the-main-turn).** Capture the owner's context, run the side request separately, and publish only its presentation result through the owner. Worker IPC is a reference mechanism; it must not create main-turn control or mutate the live prompt snapshot.

[2026-08-11] BTW remains a side request against one exact immutable snapshot of the owning Session's history, memory snapshot, settings, and prompt-cache lineage. A busy Worker may clone its hot owner synchronously and run the `purpose:'btw'` provider call outside the serialized owner lane; the call emits no stream events, registers no turn abort, and never executes returned tool calls. Its single success, denial, or error notice enters canonical history only as one display-only message through the exact owner's serialized append/persist/full-projection lane, then uses the existing attachment-broadcast presentation path. Accepted BTW RPC/provider work prevents idle release. A legacy idle owner missing `promptCacheKey` persists one before snapshotting. Do not add a BTW mailbox item, pending-result safe-point state, generic side-request callback, or Main hydration/save fallback.

### D-process-topology-session-worker-downgrade

[2026-08-10] Session-worker placement remains experimental and defaults off. A never-enabled Session with cursor `0` may round-trip through pre-Session-worker code: an old save can remove version/cursor fields, and the current legacy reader may safely restore cursor `0`. Once a Session has any nonzero Worker cursor/lineage, pre-Session-worker code is unsupported as a writer. Current-code local placement (`sessionWorkers:false`) remains supported and preserves the cursor, but draining/disabling Worker placement does not authorize an older binary to save that lineage. Foxwarm does not provide or require lineage-retirement tooling. Old saves remove the JSON format/cursor while SQLite retains its acknowledged cursor; current code must keep treating SQLite-ahead as impossible and must never infer or mirror a missing JSON cursor from SQLite. Recovery uses a verified matching backup or a separately reviewed evidence-bound current-version repair, not continued old-code writes or a second cursor authority.

## Open questions

- Managed-session control remains intentionally low priority. Identity move/rename and agent-wide snapshot-affecting inheritance/rule changes remain pre-effect fenced until a closed lifecycle boundary exists.
- Direct Unix-domain connections among future session, vector, and master-node services may replace the initial parent/child transport when avoiding a main-process payload hop becomes relevant.
