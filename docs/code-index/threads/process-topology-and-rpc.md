# Thread: process topology and RPC

## Overview

Foxwarm uses one logical set of asynchronous service contracts with configurable process placement. A service may run in the caller's process through a local handler or in a supervised child through IPC. Placement must not create a second business API or expose mutable in-process objects to callers.

The first production-routed child-process service on this boundary is the LanceDB/vector owner. SessionRuntime has a production-used local DTO service for high-level session queries, enqueue/control, settings, and update events. Session child placement wires the normal-ingress and lifecycle vertical slices when `sessionWorkers` is enabled: ordinary channel/WebUI input and Main-side event triggers enter through one closed durable ingress operation, and idle/crash/shutdown release runs one closed flow whose Main-side handback reconciles the authority cursor and refreshes the Main catalog stub read-only before the fence is released. Durable ownership/mailbox, supervised child lifecycle, save-before-ack persistence, the canonical turn runner, reverse Main services, awaited complete committed state projection publication, exact history presentation, intermediate and committed-final delivery, closed ensure-or-spawn ingress, and background-exec-aware idle release exist. Unsupported managed/admin and unclosed cross-session/topology operations fail before effects rather than hydrating a Worker-owned Session through Main.

## Configuration

- `sessionWorkers` defaults off. It accepts `false`, `true`, or an object; its designated toggle shape follows [D-config-feature-toggle-shorthand](../units/src-config.md#d-config-feature-toggle-shorthand), while `idleSeconds` defaults to 60 and is bounded from 1 through 86,400 seconds.
- `vector` defaults off and is independent from process placement. When disabled, Main and Session workers do not create a vector owner/client or register the reverse vector proxy.
- `dbWorkers` defaults on. In the current scope it controls only the LanceDB/vector owner when Vector is enabled. Archive and LLM-request-journal SQLite stores are not moved behind that worker.
- `vectorMaintenance` defaults on with a 24-hour retention window and accepts the same designated boolean/object configuration shape; its exact-owner execution contract is [D-vector-owner-maintenance](../units/src-vector.md#d-vector-owner-maintenance).
- Both placement switches are read at startup. Saving configuration does not hot-migrate a live service between processes.

## Runtime boundary

Service descriptors define serializable request, response, error, and event DTOs. The registry binds each descriptor to either a local handler or a child-process transport. Both placements remain asynchronous and use the same validation and cloning boundary; local callers do not receive handler-owned object references.

The initial process transport uses Node's parent/child IPC channel. Its transport/service separation leaves direct Unix-domain endpoints as a later topology change without changing service DTOs.

Requests carry protocol/build identity, a process generation, request and trace IDs, and optional deadlines. Child shutdown first stops new requests, drains accepted work within a bound, and then exits. Replies from an obsolete process generation are rejected.

Each process owns its own lazily created ToolScript/Monty pool. A graceful Session-worker drain closes and reaps that native pool after accepted work is drained and before the Worker exits or its durable ownership fence is released. Main graceful shutdown closes its local pool before tearing down the Main-owned services that ToolScript host calls may use. The canonical pool-lifetime decision is [D-toolscript-process-lifetime-pool](../units/src-toolscript.md#d-toolscript-process-lifetime-pool).

The hot turn loop does not move full history, images, or tool output through a central payload broker. Explicit external history/debug reads may return the requested immutable snapshot; high-frequency service calls otherwise use bounded DTOs and stable file/blob/snapshot references where necessary.

## Vector placement

The vector service owns the LanceDB connection/table, per-session indexing chains, batch state, startup backfill, embedding requests, searches, and vector lifecycle operations. It reads durable archive rows and vector checkpoints directly from the archive SQLite store. Archive durability and exact recall remain independent of vector availability.

When Vector is enabled, `dbWorkers:false` runs the vector service handler locally and `dbWorkers:true` gives a supervised child ownership of LanceDB. The main process never silently opens a second fallback owner after a worker failure. When Vector is disabled, neither placement is created and `dbWorkers` has no runtime effect.

The production bootstrap completes authoritative session/archive migrations before starting the selected vector owner. Child readiness means LanceDB is open; startup backfill remains asynchronous. The native LanceDB module is loaded lazily only by the selected owner. Unexpected child exit or IPC disconnect makes semantic calls retryably unavailable. A bounded-backoff watchdog starts a new generation only after the prior PID's exit is observed. Graceful shutdown drains accepted calls and active indexing/backfill work before closing LanceDB; if needed, it escalates through SIGTERM and SIGKILL while retaining ownership until exit confirmation.

## Session direction

`SessionRuntime` is the external command/query/event boundary for session list/state/history projections, canonical queue insertion, typed events, stop/dequeue/retry controls, and settings. Worker-owned model/cwd/node/child-model/compact-threshold/verbose mutations route to the exact owner; display name remains a Main-owned catalog update. Its local handler delegates to `sessionManager`, but local RPC cloning and structured errors prevent callers from retaining handler-owned `Session`, history, queue, or event references. WebUI list/state/history/settings/SSE, channel message enqueue, commands, and migrated tools use this boundary. The `SessionTurnRunner` reached through MessageRouter still uses live objects and one non-RPC `LocalSessionTurnHost`; `SessionWorkerHost` constructs that same runner around one hydrated exact owner and worker-local effects. The serialized child surface is activated `runPending({limit})`, exact typed owner operations, and bounded projection/results, never a live Session or generic turn-host contract.

Normal-turn provider/tool execution now receives a small local-only current-session effects object from `LocalSessionTurnHost`. It owns current-session append/persist, model-stream notification, abort registration/cleanup, and explicit-wait rollback without requiring `llm.chat` to find the hot Session in the global map. Worker placement supplies the same runner effects for its exact owner and uses fixed typed reverse delivery for external attachment output; this is not a second queue loop or generic turn RPC.

The closed Main Management tool service retains its local transport for Main-local callers and uses the same version-5 descriptor/handler through a distinct reverse IPC direction for a Session child. Its exact 20-operation model allowlist covers inter-session/direct-channel text delivery, agent listing, timer CRUD, child creation, session listing/Main-owned display-name/message reads, cross-session archive/recall reads, Main-owned agent/session creation, other-target session deletion, and node bootstrap/pairing. Cross-session recall preserves isolation/agent scope, reloads exact archived source ranges in Main, and uses Main's selected bounded vector facade; exact current-session/current-agent recall remains in the Worker. Agent/session creation receives a detached read-only source authority for inherited settings, while `create_agent(convertSession:true)` remains pre-handler fenced because it would mutate the active source identity. Other-target deletion uses the shared operation-specific lifecycle orchestrator and repeatedly fences the exact source generation; self/alias deletion stays forbidden. A separate named `scheduleWaitTimeout` method carries the internal post-persistence wait timeout DTO; it is not arbitrary execute or another model operation. Requests contain bounded source identity/operation-specific data; arbitrary builtins and live Session/history/queue/callback values are rejected by construction. Main supervises one reverse registry/server per child before activation and fences its handler to that exact worker generation before lookup/mutation. The child never falls back to a child-local Main handler.

The Node execution facade retains local RPC for Main-local callers and borrows the Session worker's shared reverse transport for remote-node calls. Direct and unified node-environment builtins resolved to a remote node, explicit dynamic remote node calls, and ToolScript's existing wrappers share one versioned request containing source identity, a non-master authenticated node, an advertised Node-domain tool name, args, and only the optional node/cwd routing snapshot needed by parallel direct exec. Main fences each reverse handler to the exact worker source before lookup/permission/effect. The colocated `master` environment bypasses RPC and invokes the local handler directly; explicit dynamic master calls and master Node discovery remain restricted to the canonical node-environment set.

The fixed file-delivery facade also borrows that trusted-local reverse transport. Its bounded request carries source identity, normalized target/file/caption intent, and exact node/cwd routing only; Main derives agent/isolation identity, prepares master or remote-cache files, and performs the existing one-attempt session/channel/WebUI delivery. File bytes, base64, callbacks, channel objects, delivery arrays, and dependency error details never cross reverse RPC. Worker remote image writes use an atomically unique operation-private agent-temp directory on the same trusted host plus the compound Main-owned Node copy operation, removing the directory before any success return and surfacing cleanup failure.

The fixed committed-final delivery service carries only exact Worker source identity, one strictly serialized immutable `QueueSource`, bounded final text, and a fixed response/error/empty-final kind. The canonical Worker runner calls it only after its response/error append and awaited full publication. Main skips source-context lookup unless `preferDirectReply:true`; lookup absence/failure/nonexact results fall back before any send to the awaited attachment path, while a failed exact direct attempt never falls back. The attachment path preserves WebUI exclusion, send-only, turn-final, and WeWork empty-final semantics and reports only actual send attempts. Worker terminal error text shares the local formatter: LLM request failures use the presentation-only `⚠️ LLM request failed: ...` form without a terminal model row, while ordinary runtime errors use their canonically appended `Error: ...` row. Business or reverse-transport failure is logged without turn rollback, retry, outbox, or publication poison. Ordinary Main broadcast remains fire-and-forget.

The MCP external facade likewise retains local RPC for Main-local callers and borrows the worker's shared reverse transport. Its fixed v1 methods cover redacted server summaries, optional-server tool discovery, named calls with cloneable args, and managed upsert/enabled-toggle updates. Direct compatibility tools, unified wrappers, and ToolScript nested calls use the same facade; the exact-source-fenced Main handler alone reaches the authoritative MCP client live snapshot and connection owner. Stored configuration values are never returned and configured secrets remain scrubbed from surfaced errors.

When Vector is enabled, the Session worker's vector facade borrows that same reverse transport. Main registers a bounded proxy handler that calls its already selected `vector.ts` facade, so `dbWorkers:true` still reaches the supervised vector owner and Main never opens another LanceDB. When disabled, Main omits the proxy and the Session worker initializes its local facade in explicit disabled mode instead of treating the missing service as a transport failure. The worker facade never imports `vectorRuntime` or `VectorServiceManager`, opens a local owner, or falls back.

The canonical tool executor resolves one coherent source owner before common tool preparation. `LocalSessionTurnHost` plus `CurrentSessionEffects` may provide an authoritative detached Session without adding it to the process-global map; legacy/direct calls instead load exactly one existing global source by ID and never trust same-ID clones. Current-node routing, isolated permission evaluation, handler context, parallel-exec node/cwd snapshots, and the `set_goal` persist hook share that owner. The activated WorkerHost combines that exact local owner with reverse Main Management/Node/MCP/vector/delivery/presentation facades; unsupported tool branches fail before effects rather than falling back to Main hydration.

With `sessionWorkers` enabled, production bootstrap assembles the worker foundation: `SessionWorkerStore` persists one generation/incarnation fence plus ordered strict-JSON mailbox intents in a versioned dedicated SQLite database. `SessionWorkerSupervisor` starts an inert candidate, durably registers its PID plus boot/start identity, durably activates the incarnation, and only then opens the child's activation gate. It retains ownership across IPC disconnect, releases idle children through bounded drain/termination, distinguishes PID reuse during startup reconciliation, and restarts only after exact-process exit observation. Unprovable identity, unconfirmed exit, or failed exit persistence retains the fence and fails closed; process termination continues even when lifecycle persistence fails. Startup reconciles leftover fences before any spawn, then non-fatally ensures owners and runs durable pending mailbox intents; per-session resume failures keep the work retryable. Main-local `resumeBusySessions` never executes residual local busy/queue state under worker placement: it logs loudly and skips, so switching from local placement cannot run stale work through the local runner or double-write a worker-owned authority.

The existing `state/sessions/<id>.json` remains the single full semantic Session authority in both placements. Current payloads are explicitly `sessionStateVersion:1` and persist `lastAppliedMailboxId` with history, queue, wait/managed metadata, active history provenance, prompt/cache state, and settings. Unversioned legacy files receive one tolerant upgrade: only historically catalog-only stats/meta/vector fields are seeded from the catalog stub, file values win, and the complete v1 payload is durably rewritten before worker use. A historical/current v1 payload that omits only `lastAppliedMailboxId` is compatible with cursor zero and is lazily rewritten with explicit `0` during Worker load/reload or post-exit handback; explicit invalid cursor values remain rejected. Reconciliation always precedes that rewrite, so SQLite ahead of the normalized JSON cursor still fails closed without modifying the authority or releasing the fence, and SQLite is never used to infer a repair cursor. Current-version hydration exactly replaces Session-semantic state while Worker load/reload preserves Main/catalog-owned `agent`, `aliases`, `parentSessionId`, and `displayName` from its detached/current stub; authority display name is adopted only when the stub has none. Main-only pin/archive/sidebar/channel presentation state remains outside semantic replacement.

A worker applies only an ordered session-local mailbox prefix. The caller supplies a bounded count, while persistence reads canonical intent rows and payloads directly from SQLite before invoking apply. The activated child runtime accepts current QueueItem payloads, preserves each source/item boundary, and reuses the canonical wait/drop/defer/enqueue transition before running the shared queue processor against the same owner. Bound child reminders/system events reuse that exact inline transition/persist path. It explicitly rejects managed-session state and existing/incoming compact commits before replacement/ack; explicit compact paths and above-threshold auto compact fail with `SESSION_WORKER_COMPACTION_UNSUPPORTED` rather than touching Main state. It durably replaces JSON through temp write, file fsync, rename, and directory fsync, and only then marks the prefix applied and advances SQLite's acknowledgement cursor. Later turn saves reverify generation/incarnation without advancing that cursor; failed persistence/run reloads the same hot owner before later mutation, and a failed reload poisons the host until serialized recovery succeeds. Global mailbox IDs may have gaps belonging to other sessions. On recovery, JSON cursor ahead of SQLite means the already-durable prefix is acknowledged without reapplying it; SQLite ahead of JSON is an impossible ordering violation and fails closed. Applied rows may be cleaned later only through the acknowledged cursor.

Main `submitAndRun` accepts one current ordinary QueueItem for an exact canonical session ID, proves an already-ready durable generation/incarnation and matching live Supervisor entry before append, writes one immutable mailbox intent, and calls that exact Worker's existing `runPending`. Before source registration or coordination, one fixed ingress-owned normalizer rejects non-plain/accessor/cyclic/extra-field request, item, message, part, source, and image-reference shapes, validates current scalar/role/type boundaries, reconstructs the only persisted clone, and enforces a 1 MiB UTF-8 serialized QueueItem limit. Concurrent calls rely on SQLite mailbox ordering plus the Worker's existing serialized host; the coordinator does not add a second queue, lock, claim, or turn state machine. A failure after append remains a durable ambiguous submission and never falls back to local execution. A Main-memory-only registry holds the actual live ChannelContext under the complete strict QueueSource only for the duration of one submission; zero or multiple exact registrations resolve to attachment fallback, and all paths clean their registration. This ready-only variant remains the lower-level building block; production ingress uses the ensuring operation below.

Its sibling closed ingress operation `submitEnsuringWorker` covers an inactive session: when no ready durable owner exists it delegates to the supervisor's existing single-flight spawn/candidate/activation lifecycle, re-proves the exact durable ready owner, then shares the same assert/append/run path. The ingress coordinator owns the resolve/ensure/append/run composition while the supervisor alone owns spawn lifecycle and fencing; a retained fence from unreconciled startup, unproven identity, or unconfirmed exit fails closed without spawning or appending, and concurrent ensures single-flight through the supervisor. No new claim, lease, generic coordinator, or second queue abstraction is added. SessionRuntime `submitAndRun` now uses this operation, and `MessageRouter` routes ordinary busy/idle channel input through it when placement injects a submit handler, while timer/event triggers and startup pending-mailbox recovery use the same durable Worker ingress/replay boundary. Main's existing bounded delete claim and identity lock serialize claim acquisition against concrete Worker ensure-plus-mailbox admission and exact activated-call acceptance. A prior admission completes before the claim; a request that reaches admission after the claim fails retryably before spawn/mailbox/Worker effects. Provider/tool completion is not held under this lock and remains covered by Supervisor active-call drain/interrupt.

Synchronous Session-worker compaction reuses the same exact-owner history engine. Automatic runner safe points execute inline, while Main idle layered requests use one fixed forward operation after exact projection/ownership/admission checks. `/compact tools` uses a separate typed serialized exact-owner history rewrite and may wait behind an active turn; it preserves local empty-history/result semantics and publishes the complete committed projection. Neither path writes a compaction mailbox intent or background compact state; JSON persistence and full projection are awaited before success. Canonical scheduling is owned by [D-context-compact-scheduling-boundary](./context-compaction-and-recall.md#d-context-compact-scheduling-boundary).

Workers write only the per-session file. Main alone writes `state/catalog.sqlite` through the Session catalog repository; there is no Worker-side catalog writer, catalog ownership coordinator, or release/handoff API. After initial load and every complete authoritative commit, the Worker awaits publication of the full existing bounded state projection to an exact generation/incarnation Main registry. The registry is cloned, process-local, lifecycle-stale-aware presentation/coordinator state; it contains no history/body/queue payload and never becomes semantic authority. Catalog admission and scaling are canonical in [D-main-catalog-indexed-boundary](./main-catalog-storage-and-indexed-queries.md#d-main-catalog-indexed-boundary).

SessionRuntime/catalog projection merge and Main-owned lifecycle handoff are now concrete parts of the worker vertical slice. Projection merge remains read-only presentation state; lifecycle handback blocks respawn, confirms worker exit, reconciles authoritative JSON, refreshes the Main stub, performs only the closed lifecycle mutation, and releases the fence afterward. The shared deletion orchestrator may compose that handoff for an exact other-target model request, while self-delete remains forbidden. Generic callback claims and standalone release protocols remain unsupported contracts. Canonical delete semantics: [D-lifecycle-descendant-actions](./session-lifecycle.md#d-lifecycle-descendant-actions).

## Failure boundary

- Vector indexing is best-effort. A vector-worker failure does not roll back session, archive, or compact commits.
- Deterministic block rows are replaced before append, making retry after a Lance-commit/checkpoint gap idempotent.
- Exact archive recall remains available without LanceDB. Semantic search reports non-retryable `VECTOR_DISABLED` when configured off and retryable unavailability while an enabled owner restarts.
- Process isolation is intended for fault containment and parallel throughput. It is not a security or sandbox boundary.
- SQLite locking protects database integrity but does not replace session-generation fencing for semantic ownership.

## Design Decisions

### D-process-topology-configurable-placement

[2026-08-04] Keep one implementation-facing async service contract for local and child-process placement. `sessionWorkers` defaults off and accepts a boolean or object; object presence enables it with defaults unless `enabled:false`, and its idle release is configurable. `dbWorkers` defaults on and in its first version means only the LanceDB/vector owner. Placement changes are startup-only and may use graceful drain before replacement rather than supporting mixed-version live migration.

### D-process-topology-goals

[2026-08-04] Optional workers target fault containment and parallel throughput, with on-demand session resource release. They do not claim security isolation. Session workers may hold provider credentials and connect directly to providers; simple session-local tool steps should remain inside the session worker when possible.

### D-process-topology-trusted-session-worker-boundary

[2026-08-06] Session workers, authoritative Session state, and Session-control credentials stay inside Main's trusted host/deployment boundary and use only local process IPC or Unix-domain transport. Generic remote nodes must not host Session workers; they remain bounded tool/execution targets through fixed Node services. Future Docker or bwrap environments are execution placements driven by the trusted local Session worker or trusted host sandbox supervisor, not Session-worker placements. Never expose the Docker socket inside an untrusted sandbox. Remote Session-worker transport is not part of the roadmap.

### D-process-topology-worker-owned-session

[2026-08-04] A future session worker owns its session's hydrated state and high-frequency turn work instead of routing full history serialization through the main process. Persisted waits and ToolScript snapshots count as idle. The initial release has no fixed maximum worker count, while leaving room for a later spawn-time resource check.

### D-process-topology-session-generation

[2026-08-04] Main durably records an input before waking or spawning a session worker. One supervised process generation/incarnation owns one hot session. A fork begins as an inert candidate: main must durably register its PID plus boot/start identity and activate that exact incarnation before the child may hydrate or process. IPC disconnect alone does not release ownership, PID reuse is distinguished from the exact old process, and replacement cannot start until that process's exit is confirmed. Main-owned lifecycle operations keep respawn blocked across confirmed exit, authoritative reload, mutation, and save through one concrete supervisor-owned handback flow; no generic claim API is exposed.

### D-process-topology-session-state-authority

[2026-08-05] `state/sessions/<id>.json` remains the one full semantic Session authority for local and process placement; do not introduce immutable runtime-head artifacts or a second compatibility mirror. The file uses an explicit current format version and persists `lastAppliedMailboxId`; unversioned legacy data is upgraded once without discarding historically catalog-only state, while current-format hydration replaces rather than merges semantic fields. An owning worker must durably replace the complete JSON before SQLite can mark that exact ordered session-local mailbox prefix applied. JSON cursor ahead of SQLite is recovered by acknowledging without reapplication, including when global mailbox IDs contain gaps for other sessions; SQLite cursor ahead of JSON is impossible and fails closed. Session-runtime SQLite owns only generation/incarnation and mailbox coordination. Workers never write the shared Main catalog; bounded projection, intermediate/final delivery, and ingress seams preserve that authority while exposing only cloned DTOs. Catalog storage is canonical in [D-main-catalog-indexed-boundary](./main-catalog-storage-and-indexed-queries.md#d-main-catalog-indexed-boundary).

[2026-08-12] A v1 authority that omits only `lastAppliedMailboxId` is read as compatible cursor zero and lazily canonicalized to explicit `0` at activated load/reload or post-exit handback, including a ready Worker stopped before runtime hydration. Explicit null, strings, negative/fractional values, and unsafe integers remain invalid. Reconcile against SQLite before any canonical rewrite: SQLite ahead of normalized JSON zero remains `SESSION_WORKER_CURSOR_AHEAD`, retains the fence at handback, and must never be copied into or otherwise used to repair the JSON authority.

[2026-08-11] Optional raw Session `effort` and `childEffortDefault` fields follow the same exact-owner authority boundary as model settings. SessionRuntime v7 and Session-worker runtime v9 carry them through settings/results; committed projection publication v2 carries them for presentation; handback mirrors them from authority before fence release. Main never validates a Worker mutation against a stale projection and never materializes a concrete model default into a Session authority or catalog stub.

### D-process-topology-session-events

[2026-08-04, updated 2026-08-06, 2026-08-09, 2026-08-12, and 2026-08-13] Do not add a persisted session `stateRevision`. A worker publishes a reliable, awaited, complete bounded projection only after authoritative JSON/archive persistence (and mailbox acknowledgement when applicable). Main resynchronizes from the authoritative per-session JSON whenever publication outcome/order is ambiguous and on worker lifecycle boundaries; transient model/tool/typing progress remains separate and may be dropped under backpressure. Presentation-only runtime values must be normalized to the strict bounded projection DTO before publication: malformed model tool arguments still produce an ordinary tool result and must not poison the owning Worker or require restart, while the Main publication validator continues to reject arbitrary non-string fields. The transient presentation tail must nevertheless preserve lifecycle order: a pending cumulative model-stream frame is flushed and its timer cancelled before the corresponding committed model message or a structural reset is forwarded, so a stale draft frame cannot follow canonical history. The detailed cross-module contract is [D-streaming-worker-commit-order](./streaming-pipeline.md#d-streaming-worker-commit-order). After a canonical model append/publication, non-empty model text accompanying tool calls uses one fixed `session-turn-delivery@2` Main attachment attempt with serialized QueueSource metadata, `turnFinal` unset, WebUI/current WeWork stream exclusion, and QQ passive ID/sequence propagation; failure is logged without retry, rollback, outbox, or poison. Final external delivery carries the serialized QueueSource direct-reply intent to Main after the committed turn, uses one channel-send attempt, and is not automatically retried or backed by an outbox in the first version.

### D-process-topology-session-tool-placement

[2026-08-04, updated 2026-08-05] Provider requests, prompt serialization, the canonical turn loop, ToolScript, and ordinary safe session-local tools run in the owning worker. Tool placement uses exhaustive ownership metadata that is separate from permission policy and the model schema. The master node is the colocated execution environment, not the main management process: when `currentNode=master`, registered node-environment primitives execute directly in the owning session worker; a remote current node uses the existing main-owned authenticated node connection. The exact node-environment surface is canonical in [D-dispatch-node-environment-placement](./tool-dispatch.md#d-dispatch-node-environment-placement). Operations that depend on main-owned topology, channels, timers, node connections, or other global singleton state use a bounded reverse main-service call with a stable operation identity. Vector placement remains independent; an initial bounded query proxy may pass through main so long as it does not carry full history or prompt payloads. Active background exec processes prevent idle worker release until completion and its notification are durably handed back. Open browser tabs are ephemeral: graceful idle release closes process-local tabs and browser resources rather than keeping the worker alive.

### D-process-topology-stable-operation-ownership

[2026-08-09, updated 2026-08-11] Each operation has one stable owner: Session-semantic reads/mutations execute through the exact Session owner, while Main-owned catalog, topology, and presentation operations remain catalog-only and never hydrate or save full Worker authority. With Session-worker placement enabled, an idle or never-started Session-semantic operation ensures/spawns and loads the Worker rather than opportunistically executing in Main. Before any mailbox, ownership row, ensure, or child-process effect, Worker ingress resolves identity without hydration and requires the canonical target to exist in Main's loaded catalog; an alias cannot authorize a nonexistent canonical target. The high-level Main queue sink may resolve a declared/cached persisted alias to that loaded canonical ID before entering the raw coordinator, while raw coordinator and exact-worker operations retain exact-ID admission. Busy manual-fork notification admission uses the current committed Worker projection: busy routes the existing background QueueItem through durable mailbox ingress for the active runner's safe-point ingestion, while committed-idle routes the typed exact-owner append and starts no turn. Exact-owner dequeue likewise decides inside the Worker: it includes already-durable pending ingress, signals the active owner immediately, and lets the same canonical action loop ingest and continue that input without a control mailbox item. If an idle projection becomes busy after an admission snapshot, exact-owner serialization defines ordering; no second claim or notification protocol is introduced. Main may execute such an operation temporarily only after a future closed exclusive placement boundary prevents concurrent Worker spawn/ingress until commit and ownership release. Until a closed path exists, identity move/rename, agent-wide snapshot-affecting metadata changes, managed-session control, and similar admin operations fail before effects.

### D-process-topology-btw-side-request

[2026-08-11] BTW remains a side request against one exact immutable snapshot of the owning Session's history, memory snapshot, settings, and prompt-cache lineage. A busy Worker may clone its hot owner synchronously and run the `purpose:'btw'` provider call outside the serialized owner lane; the call emits no stream events, registers no turn abort, and never executes returned tool calls. Its single success, denial, or error notice enters canonical history only as one display-only message through the exact owner's serialized append/persist/full-projection lane, then uses the existing attachment-broadcast presentation path. Accepted BTW RPC/provider work prevents idle release. A legacy idle owner missing `promptCacheKey` persists one before snapshotting. Do not add a BTW mailbox item, pending-result safe-point state, generic side-request callback, or Main hydration/save fallback.

### D-process-topology-session-worker-downgrade

[2026-08-10] Session-worker placement remains experimental and defaults off. A never-enabled Session with cursor `0` may round-trip through pre-Session-worker code: an old save can remove version/cursor fields, and the current legacy reader may safely restore cursor `0`. Once a Session has any nonzero Worker cursor/lineage, pre-Session-worker code is unsupported as a writer. Current-code local placement (`sessionWorkers:false`) remains supported and preserves the cursor, but draining/disabling Worker placement does not authorize an older binary to save that lineage. Foxwarm does not provide or require lineage-retirement tooling. Old saves remove the JSON format/cursor while SQLite retains its acknowledged cursor; current code must keep treating SQLite-ahead as impossible and must never infer or mirror a missing JSON cursor from SQLite. Recovery uses a verified matching backup or a separately reviewed evidence-bound current-version repair, not continued old-code writes or a second cursor authority.

## Open questions

- Managed-session control remains intentionally low priority. Identity move/rename and agent-wide snapshot-affecting inheritance/isolation changes remain pre-effect fenced until a closed lifecycle boundary exists.
- Direct Unix-domain connections among future session, vector, and master-node services may replace the initial parent/child transport when avoiding a main-process payload hop becomes relevant.
