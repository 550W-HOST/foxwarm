# Thread: compaction lifecycle

## Overview

Owns the transient mechanics around a compaction job: snapshot planning, the shared snapshot, job, and commit engine, ready-first scheduling against ordinary input, commit fences, busy windows, cancellation, and Session-worker placement. What a plan may contain is in [context compaction](./context-compaction.md). The active-history authority contract is in the parent [thread](./context-compaction-and-recall.md#d-context-active-history-authority).

## Snapshots and jobs

- Compact planning snapshots preserve custom memory sources and mutate prompt state only on the detached clone; commit refreshes live memory using its recorded concrete snapshot identity. Canonical prompt behavior: [conditional memory snapshots](./conditional-memory-snapshots.md).
- Async and awaited modes use the same snapshot/job/result path. Planning mutates a transient session clone; live state changes only during a compatible commit. For a selected `openai-ws` leaf, actual background planning receives the scoped outbound key while awaited/synchronous planning shares the normal Session key; persisted prompt-cache lineage is unchanged. Canonical key contract: [D-model-routing-openai-ws-prompt-cache-key](./model-routing.md#d-model-routing-openai-ws-prompt-cache-key).
- Awaited planning publishes the existing transient `requesting-model` / `compaction` phase from operation admission through preparation, provider retries, commit, cancellation, failure, or no-op cleanup. Its owned release cannot clear a newer runtime phase. Background planning does not publish or replace a concurrent foreground phase.

## Commit and safe points

- A stale/incompatible snapshot, exhausted invalid plan, or terminal `LlmRequestError` aborts without rewriting live history.

Completed jobs are applied only at the owner's established safe points, under the scheduling and commit-fence rules in [D-context-compact-scheduling-boundary](#d-context-compact-scheduling-boundary).

## Cancellation

- `/stop compact` cancels only the current Session's transient compact operation. It aborts compact-plan provider work through a compact-specific signal, removes any ready `compact-commit` from the authoritative queue without disturbing ordinary items, and prevents every precommit result from rewriting live history. Cancellation is a normal no-op outcome rather than a compact failure; once the authoritative compact commit succeeds, cancellation reports completed/too-late and never rolls it back.

## Design decisions

### D-context-one-compact-engine

Async and awaited compaction share one snapshot/job/commit engine. Planning never mutates the live session, and commit replaces only a compatible consumed prefix.

### D-context-compact-cancellation

[2026-08-26] One transient per-Session compact-operation registry owns mode/phase identity, a compact-specific abort controller, and canonical completion for local background, local standalone awaited, in-turn awaited, and Worker-awaited planning. `/stop compact` is the sole user control for that registry. Ordinary `/stop` never aborts or deletes compact work: a real main turn may remain marked to stop after synchronous compact returns, while a standalone idle-started awaited compact is not a main turn and therefore cannot set or retain `stopping`. Local background production distinguishes provider planning, in-flight commit enqueue, durably ready, and committing phases; cancellation during enqueue awaits producer completion plus durable queue filtering before it reports success. Commit cancellation checkpoints run after every awaited pre-authority boundary (including prompt-snapshot rebuild and completion-message Archive append) and immediately before authority save, so cancellation rolls back inserted block/completion rows through the existing failure path. Once authoritative save is in progress/succeeds, cancellation reports completed/too-late and never rolls it back.

### D-context-compact-scheduling-boundary

[2026-08-01, updated 2026-10-01] Compact planning is not ordinary queued session work. An async-capable explicit request snapshots and starts planning immediately, including while a normal turn is active. The resulting `compact-commit` only wakes the owner; its position neither delays a completed job behind ordinary input nor splits an ordinary input batch. At each established input-consumption safe point, the owner applies an already-completed job before canonical queued-input append and the next provider request. A currently committed function call and its not-yet-committed response remain atomic: commit waits until that tool response is canonical. Ordinary Stop applies completed compact work before passive queued-input append without another provider request; Run queued retains its stop-then-run control. `asyncCompact:false` remains a provider boundary: idle explicit compaction and normal end-of-turn awaited compaction may block that owner, but a busy explicit request fails clearly rather than enqueueing or persisting a deferred plan. No planning-control queue type or migration exists; generic queue validation discards unrecognized records, and automatic threshold checks can request planning again on a later turn.

Completed-job readiness reads the existing job status and exact operation identity, including the enqueue/save window before a signal is visible. Explicit request admission likewise checks pending jobs or actual compact operations, not signals. Signal-only queues do not block idle awaited compaction; managed, busy, and ordinary-input restrictions remain unchanged. A late enqueue producer cannot clear a newer operation/result or its signals; stale signals are harmless owner wakeups. Running, cancelled, no-op, incompatible, and failed jobs do not consume ordinary queue input. Commit still uses the existing snapshot and authority fences.

Session-worker placement starts with synchronous compaction only. Automatic runner safe points and an idle explicit runtime request force the shared engine's awaited mode inside the exact Worker owner; they never create pending compact jobs or `compact-commit` records. A busy model `compact_session` call reports that background compaction is unavailable instead of changing active history inside a tool batch. Main may select/admit the exact idle generation and await its fixed forward operation, but it never hydrates or mutates the Worker Session. Transient planning progress and background planning remain deferred. Pre-final automatic maintenance may continue only after successful exact resync; unrecovered/poisoned state stops before another provider request and produces the one error final for an exact direct source without another semantic append. That direct invocation releases busy and preserves any queued work but suppresses its own finish-window trailing handoff; a later explicit trigger may consume the queue. A source-less fenced turn skips all generic history/reminder/send branches and surfaces the fixed fatal after its release attempt. Post-final maintenance failure is swallowed after its resync attempt so an already delivered successful final is never followed by a second terminal delivery, while any remaining poison continues to fence mutation. Busy release may retry exactly once only when the fixed resync-retry result proves its first attempt successfully reloaded authority; it never retries provider/tool/compact/final-delivery work.

In local placement, the idle awaited form owns one standalone busy window outside `SessionTurnRunner`. Its initial claim uses the normal critical per-session save. Main local-owner authority→catalog compositions share one per-Session process-local save lane. A transient ingress admission remains open during compact work, counts local ingress already admitted under busy, and closes/drains before finalization acquires that lane; later ingress waits. Inside the lane, finalization captures the drained semantic state, stages `busy:false` with no `busyStartedAt` or `stopping`, and commits that detached state to authoritative JSON before projecting it to the Main catalog, while the shared live Session remains busy throughout the precommit window. The detached projection is built inside the catalog metadata lock from the latest live catalog/presentation fields overlaid with the staged authoritative semantic state: catalog-only changes completed before lock acquisition are retained, while later catalog-only writes serialize after it. Other semantic setters may mutate live state but their saves wait behind the authority lane. On full success, finalization patches only its owned busy/stopping fields into live state, preserving those concurrent mutations, then clears runtime and publishes normally; the waiting setter subsequently persists the complete current live state before returning. A pre-authority failure leaves live and authority busy, releases the lane, and lets waiting setters/ingress persist under busy without starting a turn. An authority-postcommit catalog failure patches only the committed idle fields in live state, retries the same detached/live-overlay catalog projection once, publishes after retry success, and then releases the lane so any waiting full semantic save reconciles concurrent mutations. Queue handoff occurs after lane completion and is not awaited while holding the lane. Only after release handling does finalization remove the standalone Stop guard and open ingress admission. Detached finalization contains/logs its own failures rather than leaking an unhandled rejection. Both lane and gate are transient coordination, and restart/lazy hydration cannot resurrect a completed compact as ghost busy work.

The synchronous-only limitation applies to layered planning, not `/compact tools`. Historical response pruning uses the existing provider-free typed serialized exact-owner history operation, with the same empty-history classification and result surface as local placement. It never enters the planning scheduler or creates a compact queue record.
