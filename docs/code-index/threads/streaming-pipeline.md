# Thread: streaming-pipeline

## Overview

The real-time streaming flow from LLM token generation through server-side event emission to browser-based rendering in the Web UI, enabling users to see responses as they are generated.

## Steps

1. The LLM adapter initiates a streaming request to the provider (OpenAI HTTP/SSE, OpenAI Responses WebSocket, or Anthropic equivalent).
2. `collectOpenAIResponsesStream` or `collectOpenAIChatCompletionsStream` reassembles provider events, invoking presentation progress and optional raw-capture callbacks. A separate unthrottled activity callback drives the default streaming watchdog: three minutes to the first valid Responses output-item lifecycle event or nonempty generated reasoning/text/refusal/function-argument bytes, then one resettable minute between later activities of those kinds. A valid Responses `safety_buffering` metadata event restarts the current attempt with a ten-minute inactivity window and keeps that duration for its later counted activity; fresh retries start normally. Transport acknowledgements, response scaffolding, non-safety metadata, usage, empty deltas, text/argument done snapshots, and Chat Completions identity-only fields do not refresh it. Responses WebSocket JSON frames enter the same Responses accumulator as SSE events, so timeout and downstream progress semantics do not diverge by transport. A hosted image call is a separate long-running activity: reporting one latches at least a ten-minute inactivity window for the remainder of that attempt, every later image status or preview report restarts that window, the window does not fall back to the configured value when the image item itself ends because the response as a whole can still be outstanding, and any defensive partial-image payload is ignored rather than stored.
3. `createModelStreamEventEmitter` converts cumulative provider progress into versioned, offset-addressed `model-stream-update` deltas. Responses additionally preserves output-item/content/summary identities as ordered part deltas; legacy flat reasoning/text remains a derived wire projection for old readers. Reasoning/text retain the fast throttle; raw function-call argument updates use a fixed one-second throttle and final flush.
4. The WebUI channel multiplexes current-browser list and canonical per-session subscriptions over one authenticated `/api/webui/stream` WebSocket per browsing context. Legacy per-session and global SSE routes remain compatibility surfaces.
5. A revisioned subscription acknowledgement installs requested/canonical mappings before initial snapshots. The hub first activates exact-owner Worker forwarding, then loads canonical `session-state` and an explicit `model-stream-snapshot` (`draft:null` when inactive). Live events arriving during initialization remain buffered. The snapshot's stream identity and sequence watermark let the browser ignore covered pending deltas and apply every later delta exactly once.
   Under Session-worker placement, version-2 model deltas are composed during the 500 ms coalescing window; cumulative compatibility frames remain latest-wins. The final pending update is flushed onto the single presentation tail before the corresponding committed model message. Structural stream resets likewise flush older updates first and cancel their timer, so an old stream cannot reappear after reset or canonical commit.
6. The page-scoped browser transport fans session envelopes to `webui-chat` logical subscribers, updating partial response content and ProcessingStatus without polling the global session list. Normal App and Code's embedded list-data roots consume filtered logical list subscriptions on that same socket; clustered refresh intents are fixed-delay coalesced without overlapping scheduled refreshes, and session-list fetches retain a latest-request-wins application gate. The canonical scheduling contract is [D-webui-app-global-list-gate](../units/webui-app.md#d-webui-app-global-list-gate).
7. `webui-chat-timeline` renders accumulated tokens, ordered Responses reasoning/text/image-status/tool slices, and a bounded partial/raw argument preview. Each Responses reasoning output item renders as one reasoning part with indexed summaries in order, even when text or image activity lies between separate reasoning items. Partial JSON is parsed only when the one-second argument update arrives; invalid JSON remains readable raw text. Streamed Markdown is parsed from the complete cumulative source but reconciled as stable top-level Marked-token segments, so unchanged earlier blocks keep their browser DOM while only tokens whose rendered output changed are replaced.
   `webui-chat` follows the bottom only while its explicit follow latch is enabled. User wheel/scrollbar/touch/keyboard intent disables the latch before a token-driven resize can run; the growing stream then preserves the committed-message anchor until the user returns to the actual bottom.
8. The LLM response logger writes the parsed aggregate response plus bounded `rawStream.body` and `rawStream.sseBlocks` to `state/logs/recent`; if the turn ultimately fails and logs are moved to `${date}-error`, the raw stream capture moves with the response/attempt log. When the physical request can carry or receive hosted image bytes, the logger writes a content-free diagnostics capture instead, retaining only event types, item identity, status, and byte counts.
9. When the stream completes, a final event signals the end of the turn; the UI transitions from streaming state to the complete message view.
10. If the response includes tool calls, `webui-tool-timeline` renders progress indicators during execution, updating as tool results arrive via subsequent stream events.

## Design Decisions

### D-webui-multiplexed-realtime

[2026-08-22; updated 2026-09-05] Current WebUI code owns exactly one authenticated, deployment-relative realtime WebSocket per browsing context. Sidebar variants, Architecture, and every mounted split-pane Chat register logical list/session subscriptions with the page transport; components must not create their own EventSource or WebSocket. The client sends the complete subscription union with a monotonic revision, and the server installs that revision before acknowledging it, then emits initial snapshots followed by live events buffered during initialization. `subscriptions-accepted` is the register-before-history boundary: a newly registered Chat starts its history request before snapshot/live delivery can race that request, while existing subscribers do not re-bootstrap for unrelated subscription changes. Logical `onOpen` handlers receive the accepted physical socket generation. Consumers may therefore perform one initial/reconnect reconciliation per generation without repeating it when their logical ID set is re-registered on the same socket. Reconnect resends the complete union and uses existing bounded-list/history reconciliation instead of durable event replay.

The optional Logs topic shares this physical connection while using its own logical lifetime and file/byte frontier. It starts after ordinary subscription initialization and never queues logger history behind Session initialization; the bounded file-tail contract is canonical in [WebUI Logs](../units/webui-logs.md#live-contract).

This physical-connection boundary is required for correctness, not only efficiency. Independent SSE ownership can consume all six HTTP/1.1 per-origin request slots; a refresh then cannot obtain a document connection, and the old page cannot unmount to close its SSE streams, creating a navigation deadlock. A WebSocket leaves the ordinary HTTP request pool after upgrade and supports dynamic subscription changes without reopening physical connections. SharedWorker cross-tab ownership and HTTP/2 are not required for this invariant. Legacy SSE routes remain temporary compatibility surfaces but are not used by current WebUI components. Chat's first accepted registration performs a recent-tail plus one guarded-prefix bootstrap. Later registrations wait for the canonical state snapshot: equal version/count/frontier needs no history request, an append gap uses `afterSeq`, and a rewritten version uses a full snapshot.

### D-streaming-optimistic-message-identity

[2026-07-28; updated 2026-09-06] Every direct non-command WebUI send carries a bounded browser-generated `clientMessageId` through the channel message and queue item into the persisted user message metadata. Chat may render that send optimistically only on the idle/no-queue path, then reconciles the canonical stream/history row into the same slot by client identity; text equality must never delete or identify another user row. Manually composed slash commands remain non-optimistic because command dispatch does not persist a user row. Their temporary command-response rows stay browser-local and retain their mounted-timeline slot across bootstrap, reconnect, and internal history reconciliation; a page refresh or Chat remount clears them. They never enter persistence, archive/search, model context, queue preview, or the committed ContextScrollbar model. Persisted message `seq`/`id` remain canonical for general reconciliation, with timestamps only as a legacy fallback. A failed POST removes only a still-pending optimistic row; once stream/history has reconciled the ID, later transport failure cannot remove the canonical row or create a false failure notice. Initial mount registers the per-session stream before the recent-tail and guarded-prefix requests. Messages committed after either snapshot begins are journaled and replayed before acceptance. Normal contiguous committed rows are applied directly from the stream without HTTP. A delayed state-count mismatch is rechecked after the ordered message has had time to arrive; unresolved same-version gaps and queue-preview corrections use an `afterSeq` request, while history-version changes use a full correction. Post-request `session-state` fields and model-stream drafts remain stream-owned. `session-deleted` invalidates and aborts the shared request generation, clears pending reconciliation, and cannot be undone by a delayed response.

[2026-09-17] A queue-origin authoritative append is presented to the current WebSocket as one bounded `history-append` delta containing separate canonical messages plus the sanitized post-publication queue preview. Chat applies both timeline sides in one reducer action only when the batch is contiguous from its trusted sequence frontier. If an earlier canonical sequence is missing, the delta is incoherent with newer state, or an authoritative request is already in flight, Chat withholds the whole transition and immediately reconciles from the last contiguous frontier; later ordinary frames do not advance past the missing range. History correction responses likewise replace committed history and the queue preview together, while a newer mismatched queue projection defers both sides to the trailing correction. During the one-tail/one-prefix bootstrap, a newer staged batch does not discard an already assembled prefix plus tail: Chat accepts that older complete boundary, then continues with `afterSeq` to recover the staged batch atomically. A trusted HTTP `{historyVersion, latestSeq}` frontier covers every authority row through that sequence even when older rows are not mounted; later concurrent live rows advance it only as a contiguous sorted suffix, never by their maximum sequence alone. Legacy SSE continues to receive individual persisted-message events, and model-stream draft ordering is unchanged.

### D-streaming-worker-commit-order

[2026-08-12] Session-worker presentation keeps one ordered tail across cumulative model-stream frames and appended-message copies. Before forwarding a committed model message, the Worker flushes and cancels every pending coalesced cumulative frame; before forwarding a structural reset, it likewise flushes older frames and cancels the timer. The committed message may clear WebUI's synthetic draft only after its final cumulative frame, and no frame from that stream generation may arrive afterward. Preserve this transport-order barrier rather than adding persisted stream state, message-body projections, generic acknowledgements, or UI content-based deduplication. Transient presentation remains droppable and correction still comes from committed history/projection.

- [2026-07-22] WebUI streaming bottom-follow is intent-latched. Explicit upward user interaction exits follow immediately, subsequent token growth must preserve the detached viewport, and only reaching the actual bottom or using the bottom action reenables follow; do not approximate this solely by enlarging the near-bottom threshold.
- [2026-06-25] Streaming diagnostics should capture provider raw SSE without changing parsing semantics: collectors expose raw chunk/block callbacks, while the request/logging layer decides how much to retain and where to serialize it.
- [2026-06-04] WebUI `model-stream-update` remains WebUI/SSE-oriented and should not be reused directly for WeWork stream-card updates. WeWork uses lower-frequency turn-level `channelTurnProgress` broadcasts bound to the channel stream id, so card updates can show `🤔 thinking` and batch tool status without token-level churn or history pollution.
- [2026-06-05] For WeWork stream cards, an LLM response that has both model text and tool calls should be emitted as one turn-level progress/card update carrying both text and `⌛️` running tools. This avoids a separate text update being delayed ahead of the tool-status update, especially in WebSocket mode where stream pushes are ack-serialized.
- [2026-07-15] WebUI's per-session stream carries both transient model/tool events and canonical session-state snapshots. Initial history plus the subscription-time snapshot closes the fetch/subscribe race; reconnect re-fetches only that session, while global session-list SSE remains independent.

### D-streaming-delta-and-bootstrap

[2026-09-03; updated 2026-09-28] Regular model-stream updates use `streamVersion:2`, an inclusive `sequenceStart`/`sequence` coverage range, exact-owner server `startedAt`, the existing durable outer `llmRequestId`, offset-addressed `reasoningDelta`/`textDelta`, and per-index `toolCallDeltas` with optional offset-addressed raw argument text. A raw emitter event covers one sequence; Worker coalescing widens the range. The browser accepts ranges contiguous with its snapshot/event watermark, ignores fully covered ranges, safely reapplies a range whose beginning is already covered, and marks a real gap incomplete even when text offsets happen to fit. Provider collectors may remain cumulative; the emitter owns delta conversion. Tool argument events are fixed-throttled to at most once per second, while reset, request completion, and canonical commit ordering force the latest argument flush.

Responses progress also carries optional cumulative `parts` in the exact-owner draft and offset-addressed `partDeltas` in version-2 events. Each slice identifies its output item and kind; reasoning summary and message-content slices retain `summaryIndex` or `contentIndex`. Message text carries a known `commentary`/`final_answer` phase, image generation carries status only, and function-call slices reference the existing per-index throttled argument deltas. Worker coalescing merges text by slice identity rather than joining separate reasoning or text items. The browser groups summary slices from one reasoning output item into one visible thinking part and renders separate items in output-index order. Only summary text, ordinary text, tool names/arguments, and image status enter transient presentation; encrypted reasoning and image bytes do not. Flat deltas and snapshot fields are derived compatibility projections for previously open browser clients; readers of old/other-provider streams without `parts` keep their former flat behavior. Canonical append and retry semantics for normal Responses turns are in [D-streaming-early-commentary-commit](#d-streaming-early-commentary-commit); other request paths retain one completed-response append.

Every Local or Session-worker exact owner maintains one process-local cumulative draft even with zero presentation subscribers. A WebSocket subscription activates Worker forwarding before reading that exact-owner snapshot, sends the full snapshot before buffered live events, and sends an explicit no-draft snapshot when inactive. The browser ignores same-stream deltas at or below the snapshot watermark. This state is transient only: it is never written to Session JSON, history, Archive, catalog, or runtime projections, and process loss may discard it.

### D-streaming-early-commentary-commit

[2026-09-28] During a normal-turn OpenAI Responses SSE or WebSocket request, a per-request serial lane may commit an explicitly `phase:commentary` assistant message at `response.output_item.done`, together with the contiguous completed output items before it. The lane cannot cross an incomplete item or an unexecuted Foxwarm `function_call`; unknown-phase and `final_answer` text wait for completion. Completed reasoning remains opaque in presentation but persists in provider replay; hosted search/image items in a committed prefix use the established replay metadata, validated blob externalization, and post-commit image delivery. This applies neither to other providers nor to compact, BTW, or low-level calls.

The exact Session owner appends each prefix through the ordinary strict canonical boundary **before** best-effort Channel delivery. Tool execution and queued-input consumption remain after the complete provider result. Each immutable model row carries the existing `llmRequestId` and an `__meta.llmSegment` half-open output range `[outputStart, outputEndExclusive)` plus `complete`. Completion appends only uncommitted output items and records usage/timing once; when the real completed response has no remaining items, a `parts:[]` completion row carries its metadata without a fabricated final text. A genuinely empty upstream `final_answer` text item remains canonical. Serializer and timeline do not invent content from the metadata-only row, and prior Archive rows require no rewrite.

Network failure after a prefix has committed closes the old journal attempt and, if the original bounded attempt budget remains, starts a **new logical request and journal identity** from exact-owner committed history; the new manifest matches its actual provider input. Ordinary virtual routing/failure handling and total attempt budget remain in force. Pre-commit persistence failure is local, aborts that request, and must not count as a provider failure or trigger retry/failover; an append that committed before reporting an authority error remains committed. Stop drains/fences the lane and keeps already committed prefixes without inventing completion. Intermediate Channel failure is best effort and cannot cause regeneration.

The owner removes only the committed output-index prefix from its transient draft and publishes a version-2 structural trim; Session-worker forwarding flushes earlier coalesced updates before that trim and before each immutable append. Browser snapshots, live events, and history reconcile by request ID plus segment range; multiple rows from one request use segment-start render keys instead of colliding on `llmRequestId`. WebSocket reuse releases a non-image response only after replay of **all** of its committed assistant segments matches the expected provider prefix; generated-image responses continue to discard that chain.

### D-streaming-keep-reasoning-on-error

[2026-09-29] `keepReasoningOnError` is an optional concrete-model boolean, default `false`, inheriting a provider default unless explicitly overridden on a model (`false` overrides `true`). Virtual providers cannot set it; routing uses the selected concrete leaf and fingerprints that leaf's effective value. Only normal-turn OpenAI Responses SSE/WebSocket requests use it. No configuration is enabled or switched to a future default automatically.

On upstream stream/transport failure **before** `response.completed`, the owner first drains any already scheduled commentary commits. A malformed later upstream frame does not invalidate an earlier completed reasoning item. With this flag enabled, it may then strictly append the next contiguous completed reasoning output items from the uncommitted absolute output index only when each contains nonempty `encrypted_content`. A missing index, an unfinished item, summary-only reasoning, an image/hosted item, or an unexecuted Foxwarm function call stops that checkpoint: later reasoning is never spliced across it. The row is `llmSegment.complete:false` and uses the existing concrete-model-scoped opaque reasoning metadata; the provider output ID is not replayed. It has no user-visible text, media delivery, tool execution, completion metadata, or invented final answer. Already committed commentary is neither repeated nor rolled back.

Stop does not save new pending reasoning. Neither a completed response nor a local callback, post-response validation, or persistence failure enters this upstream-error checkpoint path; a failed checkpoint append is a local failure, never a provider retry or model-health failure. If the existing bounded provider attempt budget permits retry, it starts a fresh logical request/journal/stream from exact-owner committed history; otherwise the incomplete row remains available for explicit Continue. Existing same-concrete-model history filtering controls whether the opaque item reaches a later concrete request. This is durable replay of completed opaque output, **not** transport-level resume and not a guarantee that the upstream model avoids repeated computation.

### D-webui-streaming-markdown-dom-stability

[2026-09-06] Streamed assistant text and expanded reasoning preserve the DOM identity of unchanged completed top-level Markdown tokens. Each cumulative update still runs through the existing complete Marked lexer, KaTeX placeholder handling, ordinary HTML sanitizer, and typed Mermaid/display-LaTeX extraction; the browser then reconciles memoized segments by their stable lexer-token position instead of replacing one message-wide `innerHTML` subtree. A token whose correct rendered output changes remains replaceable, including the growing tail, continued lists/quotes/fences, Setext reinterpretation, and earlier reference links resolved by a later definition. This is DOM reconciliation, not a second Markdown parser or browser-selection save/restore mechanism.

The version-2 stream's `llmRequestId` correlates its draft and canonical provider-model rows. A segmented Responses draft uses the first uncommitted output index with that request ID as its render identity; when the corresponding immutable model row commits, unchanged Markdown can retain its mounted DOM. Persisted seq/id remain the history and viewport authorities. Legacy drafts without a request identity retain their existing synthetic-to-committed remount behavior.

### D-streaming-hosted-image-window

[2026-09-19; updated 2026-09-23] Hosted image generation is a long-running activity inside one physical attempt, so an attempt that reports one keeps at least a ten-minute inactivity window instead of the configured value. The latch is attempt-scoped: it survives the end, completion, or failure of the image item itself, because the response as a whole can still be outstanding after the item ends, and every reported image activity restarts the extended window, so a stream that keeps reporting image status is not bound by a single window opened at its first report. Unrelated text, heartbeat, or metadata traffic neither shortens it nor extends it indefinitely. A later attempt starts from the configured or safety-buffering value until its own image call is reported. An explicit hard deadline or user cancellation still wins. Because the same raw stream would duplicate provider image bytes, a request that can carry or receive hosted images writes only a content-free diagnostics capture.

[2026-09-23] An earlier revision scoped the window to active image items, so it restored the configured inactivity as soon as the last image item ended. A response that had reported its image but had not yet completed could therefore still be cut off at the configured value while its result stayed unconfirmed. Extending per attempt keeps the wait aligned with the lifetime of the attempt it belongs to; the retry classification and budget for such an attempt are ordinary (see [src-llm](../units/src-llm.md)).
