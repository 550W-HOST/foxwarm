## Invariants

- Worker direct and unified node-environment calls carry the exact caller selection as `callerCurrentNode`; calls targeting the exact current remote node also carry `{currentNode,cwd}` from the authoritative owner; explicit dynamic other-node calls omit cwd. This prevents Main's stale projection from becoming routing authority without leaking cwd to another target.
- Main Management, remote Node execution, MCP external, bounded vector calls, file delivery, intermediate/final delivery, and presentation events are reverse-wired for the activated WorkerHost through one shared channel. Main Management version 19 retains a fixed 27-operation allowlist plus bounded internal authorization relation/Task-owner reads, including master-only atomic policy replacement, shared task operations, and artifact preparation/publication. Its creation DTOs carry the semantic `create_session.node` and `create_child_session.agentName` fields without changing execution placement. It carries no live mutable Session, queue, patch, or child callback; operations needing source settings receive one detached read-only authority inside Main. Unsupported operations still fail before effects rather than falling back to Main hydration.
- The Node execution facade uses local or borrowed reverse transport to one Main handler. Primitive descriptors derive only safe canonical tools from filesystem access and exec presence; authenticated remote descriptors retain their advertised resident-tool set. For isolated sources, the service restricts the exact bound/current Node in both placements. The colocated `master` Node bypasses the service and runs only a canonical node-environment handler, while master Node discovery exposes exactly those definitions.
- Lifecycle is a Main-owned control plane rather than a Node capability source. Effectively isolated sources are structurally denied create/ensure/destroy regardless of an exact builtin `node` allow rule; inspect is read-only and still requires exact bound/current-Node access. Provider effect/data-retention fields are bounded descriptions, not Core guarantees.

## Design decisions

### D-dispatch-generic-node-providers

[2026-08-19, updated 2026-10-19] `Node` is the generic execution-environment concept. Provider identity remains Main-owned routing/lifecycle metadata, never a capability source, caller principal, or Session binding. Policy may select actual Nodes by that authoritative metadata. The colocated master is a direct local bypass; authenticated remote Nodes preserve their existing complete-tool resident-runtime adapter. Virtual/custom providers do not advertise or implement model tool schemas or Foxwarm file-tool grammar. They expose only fixed provider-neutral backends: filesystem `read` or `read-write` via parent resolution, stat, bounded byte read, directory entries, binary writes with `w`/`wx`/`a`, recursive mkdir, and remove; plus optional process start/poll whose raw logs are readable through the same Node filesystem. The existing Core exec manager retains waits, registry, canonical output, expiration and completion delivery. Core/shared derives canonical `read`, `write`, `edit`, and `apply_patch` definitions and semantics. Target paths stay opaque to Main host path rules and are interpreted with exact Node routing context by the provider. Unsupported capability/backend combinations fail without master fallback.

Executable-provider Nodes have Core-facing `provider-id/local-id` identities, while the adapter protocol retains its existing slash-free local IDs. The registry wraps the adapter boundary for discovery, selection/default cwd, lifecycle, filesystem and process calls; native `master` and authenticated CLI IDs/protocols remain unchanged. Canonical tool IDs delimit the tool name after the final slash, and URL consumers encode the qualified Node as one identity. Newly persisted provider exec records use the Core ID; old records reattach from their existing exact providerId plus local nodeId without rewriting history or adding ordinary-routing aliases. Existing provider Session selections and exact policy rules need deliberate reconfiguration, not a blanket migration.

Startup configuration may add trusted executable providers under the single `foxwarm-node-provider` identifier. Each fixed command launches one-shot with `shell:false` for describe/list, filesystem, exec-start/exec-poll or declared lifecycle operations. There is no protocol-version field, negotiation or previous complete-exec adapter. Descriptors advertise remote or sandbox identity, safe labels, availability, default cwd, filesystem access and exec presence; structured provider descriptions expose lifecycle parameters and retention. File/process payloads contain only target data and captured cwd, not Session/Agent state or callback/notification addresses. Core retains exact caller authority. Uncertain start never replays; query failure retains tracking; explicit loss is not success. Logs remain in the same Node namespace; provider references are private persisted metadata in the existing exec registry. Malformed/oversized/identity/process failures reject without fallback. Normal authenticated CLI versions, credentials, external owners and native persisted records are unchanged. The optional Linux SSH example implements this public protocol independently, without a Core SSH backend, dependency or security-sandbox claim.

### D-dispatch-generic-node-transfer

`copy_between_nodes` resolves both endpoints through the same Main-owned registry. Local Main retains its existing wrapper/path limits; Worker callers retain the bounded compound Node RPC. Original-call authorization covers both endpoint IDs before file effects; exact source fencing and existing isolated-source restrictions remain. The registry routes primitive transfers through their filesystem and retains the resident Main/CLI transfer adapters for their existing path roots, bytes, publication behavior and SHA256 receipts. There is no fallback from an unavailable or unsupported Provider to Main.

Primitive relative transfer paths use that environment's default directory, never the Session cwd or another Node's cwd. Main/CLI copy legs remain Agent-directory-relative; master `send_file` retains its Session-cwd default. Generic remote delivery uses the same registry transfer reader and keeps preparation, cache and delivery receipts in Main; reverse Worker delivery remains intent-only.

Shared transfer composition bounds individual primitive requests to 1 MiB of file bytes. The first destination chunk uses exclusive create or overwrite, later chunks append; an empty source still creates an empty file. A later failure leaves the normal partial prefix and produces no successful receipt, retry ledger or rollback. Existing complete transfer buffering is unchanged. Implementation is owned by [Node providers](../units/src-node-providers.md), [Node execution](../units/src-node-execution.md), [shared Node tools](../units/shared-node-tools.md) and [file delivery](../units/src-file-delivery.md).

### D-dispatch-shared-file-semantics

[2026-08-10, updated 2026-10-07] Main and Node read/write/edit/patch tools use the same semantic implementation after their own path, context, permission, and transport handling. The package ownership rule is canonical in [D-shared-package-boundary](../modules/shared-utilities.md#d-shared-package-boundary). `packages/shared/src/applyPatch.ts` owns pure parsing/matching; `packages/shared/src/fileToolCore.ts` owns filesystem patch execution over stat, ranged reads, whole-file `w`/`wx` writes, mkdir, and remove. `packages/shared/src/exactReplacement.ts` owns pure single-match exact replacement for Main, Node, and compact repair; wrappers retain argument-validation and I/O ordering.

Main file/memory wrappers, native CLI Node wrappers, and primitive Provider composition call the same patch executor directly. Native targets choose their own Agent roots/backend; primitive Providers supply their namespace and asynchronous parent operation. Authenticated remote calls run on the Node rather than returning file bytes to Main for matching. Operations retain sequential per-file application, already-applied summaries, and skipped later operations after failure; path-resolution failures retain their existing boundary behavior. Compact repair shares the pure parser/matcher but keeps its exact invocation-owned descriptor writes instead of the filesystem executor.

Public tool names/schemas, content-reference policy, isolation checks, interactive approval, native successful-path metadata, and transport remain outside the core. No extra registry, compatibility forwarding module, or validation layer is part of this seam.

### D-dispatch-native-agent-paths-and-code-targets

[2026-09-29] Native Main (including Session workers) and authenticated CLI Node Agent-owned exec launches supply `fw_agentdir` and `fw_tmp` in the child environment, with `tmp` at the executing Agent's actual directory. The directory is created before exec cwd validation; nested shell children inherit the values. Every launch replaces inherited values without changing the Main process environment, the `TMPDIR`/`TMP`/`TEMP` family, or the retained `.temp/exec` artifact layout. Changes to session cwd never change the Agent root. External owners and primitive providers have no Agent directory contract and receive neither fabricated roots nor inherited reserved values.
On POSIX, only the two exact lowercase reserved names are replaced; differently cased host variables remain independent. Windows child environments are case-insensitive, so reserved-name case variants are removed before injecting the actual Agent values.

Native file-tool paths, patch header paths, exec cwd, and target-local file-transfer paths expand only an initial `$fw_agentdir` or `$fw_tmp` through a shared target-root resolver. Any other leading `$` name rejects; mid-path, `./$...`, patch content, shell commands, memory-relative tools, `~`, and ordinary paths keep their existing meaning. Main authorization expands before canonical nearest-existing-ancestor/symlink policy checks; Node targets resolve only within their own native environment. Primitive providers reject leading Agent path tokens before provider effects but preserve opaque ordinary paths and exec behavior without host path normalization. Neither Node transfer leg is resolved against the other Node's root.

Successful native read/write/edit/apply_patch records the actual absolute path used for each input/header, in operation order. A narrow first-party CLI result sidecar is stripped at canonical resolved dispatch before any model or ToolScript result; each executed model call can persist `functionResponse.__meta.resolvedPaths` entries `{ raw, resolved, nodeId }`, binding `nodeId` to its trusted resolved dispatch target. The visible response body and file-tool output remain unchanged. Provider-neutral request preparation removes this display metadata before journal/Responses/Chat Completions/Anthropic conversion. WebUI uses each successful response's target and original display label to open Code on the execution Node (including former `~` and relative paths); older absolute-path fallback remains, but old relative paths are not inferred from later cwd or Node state. This does not grant Code access or change Code bridge URLs.

### D-dispatch-toolscript-execution-projection

[2026-10-03] `run_script` and `continue_script` return status, run ID, the explicit script result (including falsy and empty values), nonempty stdout, relevant error, and actionable waiting fields. Agent waits carry continuation ID and question once; timeout waits carry the continuation ID without timing/host bookkeeping. Managed-event waits identify the target Session and supplied condition plus whether background automatic resumption is enabled; lease/controller IDs and manual-continuation hints are omitted from this waiting metadata. Script-owned result fields and image promotion remain unchanged.

Full owner-scoped run records, snapshots, cumulative stdout, retries, and explicit get/list diagnostic tools remain intact. Normal execution errors retain the actual traceback and partial stdout without the appended internal context block; explicit inspection retains full diagnostics. No old history is rewritten.

The exact builtin execution target supplies nested-call presentation data through an in-process hook. Direct and unified ToolScript executions store it on `FunctionResponse.__meta.toolScriptSubCalls`, outside the model-visible response and the output guard. Request-local projection removes display metadata before provider serialization and canonical request journaling. Nested script calls cannot overwrite their enclosing invocation's metadata. Worker execution uses the same exact-owner hook without hydrating another Session or introducing an RPC callback. The WebUI reads this persisted metadata after reload, keeps live progress events, and falls back to historical `response.subCalls`.

[2026-10-14] Model-visible execution results use plain `--- print ---` and `--- return ---` sections, followed by a standalone `---` and readable metadata. Empty stdout and absent/undefined results omit their sections; explicit null, false, zero, empty strings and collections remain visible. Strings retain their literal text, including newlines, quotes, backslashes and separator-looking content; structured results and metadata use block YAML. These separators are for reading, not a machine-parsing protocol. The shared renderer runs only at the outer presentation boundary, after image promotion: the output guard measures/saves that same text, request-local projection renders responses identified by the existing exact-target activity metadata before removing it, and WebUI uses the same renderer. Guard summaries and historical pruning carriers retain their excerpt/locator format. Persisted native execution objects, nested script values, diagnostic get/list results, continuation stdout deltas, status/error/progress metadata and Task receipts are unchanged; canonical request journals contain the rendered model text but no display metadata. Other tool formatting and provider serializer signatures are unchanged.

### D-dispatch-programmatic-tool-data

[2026-10-03] ToolScript nested calls set a trusted `programmatic:true` execution-context hint before canonical dispatch. Ordinary direct/unified calls do not derive it from tool arguments. Resolution, source/Session identity, authorization, paths, placement and effects are unchanged. Selected first-party producers (`read`, `exec`, `search_tools`) retain their ordinary readable `output` and add named script fields directly; other tools and MCP values remain native. Producers branch before extra data collection, so ordinary calls retain their shapes and capture/render work. The final outer model-output guard still applies to explicitly returned/printed data; run diagnostics and model-invisible activity remain governed by [execution projection](#d-dispatch-toolscript-execution-projection).

Text reads expose actual selected `content` without footers, synthetic separators, empty-file labels or omission markers; existing UTF-8 decoding, line endings, directory results and images remain unchanged. `filePath` identifies the resolved source, `sizeBytes` is the stat-time source size, `selectedBytes` is the selected byte count, and known selected line bounds/total lines are included. Exec exposes captured combined text without display/status/tree footers, `status:completed|running`, completion `exitCode` (including null when unknown), `execId`, real `logPath`, and known captured `sizeBytes`. Nonzero exit remains a result. Background tracking, completion, cwd synchronization and Stop behavior are unchanged.

The full-content budget is 1,048,576 source/captured bytes, inclusive. A selected range may fit while its source is larger. Retained `content` has no display line/character/token shortening. Above the budget it is omitted and `truncated:true` accompanies bounded display and the actual locator. Running exec reads a bounded stat-time prefix snapshot, not future output; missing capture data is unavailable rather than fabricated empty text. No arbitrarily large log is fully read before deciding the budget.

Search reuses existing collectors, ranking, visibility, result limits and the first-ten schema-detail cap. Script results add source-qualified `tools` descriptors and actual nonempty warnings. Requested schemas include available MCP `outputSchema`; missing output contracts remain unknown. Ordinary display stays unchanged.

The hint crosses the current exact-owner Node RPC independently of routing snapshots and remains Core-owned for primitive providers. Primitive file composition uses the shared producer. Current CLI Nodes advertise `features.programmaticToolData` and receive the hint in trusted `tool_call` metadata. Older peers retain native results, with no manufactured data or completeness assertion. Executable adapters receive byte-oriented file operations and process start/poll without the hint; Core reads their target log through the same filesystem and produces retained programmatic data. The single current executable-provider protocol has no version negotiation or previous complete-exec result adapter. Shell HTTP supplies short complete UTF-8 text only when the actual retained sample is complete (up to 8,192 bytes); longer output, binary samples and immediate running replies omit content and report truncation. It has no full log locator or 1 MiB retention guarantee, and no new logging platform is introduced.

### D-dispatch-node-environment-placement

[2026-08-05] Keep process-placement ownership separate from permission policy and model schemas. The registered node-environment builtins are exactly `read`, `write`, `edit`, `apply_patch`, `exec`, and `browse_*`: they execute directly in the selected local environment when `currentNode=master` and use the authenticated node connection when a remote current node is selected. Unified builtin calls use the same placement boundary. Explicit dynamic `source=node,nodeId=master` calls and master Node discovery are allowed only for this exact canonical set; they invoke the existing local named handler without RPC and cannot turn Main/session/MCP tools into Node calls. `delete_file` is removed from definitions, runtime exports, permissions, and advertised master capabilities without an alias; structured `apply_patch` deletion and explicit `exec` remain available. Compound file/channel/image operations and agent-memory tools are not node-environment primitives merely because they may touch files.

### D-dispatch-worker-exact-owner

[2026-08-06, updated 2026-08-16] Session-worker placement is identified only by a trusted in-process current-session-effects marker carried into direct and ToolScript-nested ToolContexts. Safe local builtins must retain the authoritative passed Session/persist hook through the canonical dispatcher and must never fall back to a same-ID child SessionManager or child Main singleton. Reachable operations with a closed Worker or reverse Main boundary use that exact owner/service; operations whose identity/admin, managed-session, or background-compaction boundary is intentionally unsupported remain visible but fail retryably before tool-start observability, concrete permissions, or raw handler initialization. Their guard normalization mirrors handler action/target semantics. Placement is not inferred from user arguments or Session-object presence. Existing current-agent vector recall remains supported from the exact owner's agent filter. Other-target deletion is closed through the fixed Main service and shared lifecycle orchestrator, while self/alias deletion remains rejected before effect.
