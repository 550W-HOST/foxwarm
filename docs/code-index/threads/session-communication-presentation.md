# Thread: Session communication presentation

## D-session-communication-presentation

[2026-10-17; updated 2026-10-18 and 2026-11-27] Conversation defaults to displaying successful `send_to_session` messages and structured incoming inter-agent messages as readable standalone communication cards in source order. Each card has an explicit To/From direction and peer Session identity, distinct from the current assistant's replies to the user. Already-loaded names improve readability; the exact identifier remains available. Links use the ordinary authorized Session navigation path. No all-Session lookup is introduced.

The Conversation-only browser-local Show inter-agent messages switch controls both directions together and defaults on. Turning it off folds communication bodies into Activity, including delivery metadata not printed in tool results; it does not delete or rewrite messages. Detailed/Grouped remain unchanged. Only standalone communications enter Conversation Search and cut adjacent Activity timing.

Long To/From cards use the shared three-line tool-result preview, measured bottom overflow fade and thread-card height transition. Short bodies have no fade or unnecessary disclosure. Expansion reveals the full available body, preserving Markdown, selection, links and independent peer navigation; Search can reveal a matching full body transiently. The same cards are used inside expanded Activity when folded.

Tool calls/results remain technical evidence in Activity. A successful outgoing message appears after its owning response, immediately and independently of later assistant prose. Incoming cards strip only their trusted outer transport envelope; authored text and inner quotations are not reclassified as transport. Visible communications close adjacent Activity ranges. Logical-request usage retains one owner; no per-message elapsed time or token estimate is invented. Provider history, source arrays, delivery policy, queues and handoff turn-action behavior remain unchanged.

Every committed Session-sourced delivery a call causes is recorded as UI-only evidence `{id, targetSessionId, message, truncated?, deliverySeq?, task?}` in delivery order: a send, a child's initial message, and each Task notification actually sent. `task` is `{taskId, event, title, recipient}` with the recipient roles named below. A direct call keeps the list in function-response `__meta.sessionMessages`; the first record keeps the call ID and later ones add `#n`. A ToolScript subcall keeps its own `sessionMessages` list, and a nested run's deliveries are recorded on the subcall that started it, at any depth. Deliveries a background run makes after its hand-off are recorded on its `background-script-finished` event as message-level `__meta.sessionMessages`. Rows written before the list keep one `sessionMessage` per completed subcall, and readers accept both. Recording uses an explicit callback passed down the delivering call, not ambient async state, so a Session woken by the delivery never records into the sender. It does not change tool-visible results or model-visible text. Stored bodies are bounded at 32,768 UTF-16 code units, with an explicit Preview state if full paired call arguments are unavailable. Provider replay removes this metadata with the other display metadata.

Older direct/builtin-dispatched sends require a paired successful response and original call arguments. Failures, canceled/not-executed or absent receipts without actual delivery metadata, unpaired calls, arbitrary stdout, script source and authored success prose do not become sent messages. Historical scripts and Task calls lacking structured delivery evidence are not reconstructed. Canonical metadata preserves resolved destinations for aliases; unresolved legacy boundary aliases remain non-link labels.

### Task cards

[2026-11-27, user] Task deliveries that hand over work, a note or a result are communication: an assignment (`assigned`, and `transferred` to the new owner), a note to the owner and a completion to the creator. Conversation shows them sent and received as Task cards: the To/From card with a Task icon, an event label (Task assigned, Task reassigned, Task note, Task completed) and, where Tasks is available, a Task ID control that opens Tasks with that Task selected. Scoped identities have no Tasks surface and get no control. A notice from the user reads "From you". A card recorded on a background run's finish event is marked "From a background run". The body is the delivered notification text, identical on both ends, including a completion's usage line. The header also names the Task: the sender takes the title from its delivery record, the recipient from the body's generated first line `<lead><taskId> — <title>`, read only when the ID is the envelope's `taskId`. The collapsed preview starts after the generated lead lines (the first line, and `Status:` for assignments and completions), so the description, result or note shows first. The expanded card shows the full body as delivered, and Search indexes the full body. A body in another form, or with nothing after the lead, is shown unchanged; another form also has no title in the header. Notices to a previous owner (`transferred` to the previous owner, `released`) stay process detail in Activity, as do Task operations that deliver nothing. The Show inter-agent messages switch governs Task cards with To/From cards; Detailed and Grouped are unchanged.

Task envelopes name the recipient's role in a `recipient` attribute: `owner`, `previous-owner` or `creator`. It is added to newly delivered envelopes only. For older envelopes the role follows from the event, and for `transferred` from the trusted outer `hint` (the new owner receives the assignment hint). An older user-sourced transfer names no role and stays in Activity. Received cards read only the single `foxwarm-message` system part of an input, so a Session's first input that also carries the Session tag still shows its card. Sent Task cards come only from recorded evidence; Task calls made before the records existed stay in Activity.

## Owners and checks

- [Session tools](../units/session-manager-operations.md) own actual send and its delivery callback; the [Task service](../units/tasks-timers.md) reports each Task notification it sends.
- [Tool executor](../units/tools-registry.md) and [ToolScript](../units/toolscript.md) persist out-of-band presentation data.
- [Session message rendering](../units/webui-session-messages.md) owns projection, identity and cards.
- [Timeline](../modules/webui-timeline.md) owns display boundaries, Search and request accounting.
- `SessionDeliveryRecordTests` executes real direct Task, child and send calls, scripted, nested, failed and background runs, and the Activity and Session Sequence readers. `DeliverySeqTests` checks delivery positions on both sides and that no provider request carries the records. The frontend pure/native cases check trusted envelopes, recipient roles, failures, viewport cuts, source order, stable DOM and one visible Search match.
- Inter-agent and Task wrappers may carry a `deliverySeq` attribute ([D-session-delivery-seq](./session-sequence-view.md#d-session-delivery-seq)); card parsing keeps only the trusted outer wrapper and does not depend on attribute order or the attribute set.
