# Thread: tool dispatch — MCP

Part of the [tool dispatch](./tool-dispatch.md) thread. Covers the live MCP configuration snapshot, the versioned MCP facade, the inbound bridge, and explicit notifications between Foxwarm instances.

## Invariants

- MCP configuration reads use one authoritative live snapshot after first load; managed updates persist before replacing that snapshot.
- MCP list/discovery/call/config operations share one versioned local/reverse facade with source/isolation checks, exact plain-record/JSON DTO validation, cloned results/errors, full call-argument permission parity, redacted summaries, all-server stored-secret error fencing, and terminal drain fencing. Managed transport semantics are validated once by the authoritative Main client before persistence/publication.
- MCP and node credentials remain transport/runtime state and are not exposed to the model through tool summaries.

## Design decisions

### D-dispatch-mcp-inbound-bridge

[2026-09-19] An enabled inbound MCP endpoint registers `foxwarm_discover`, `foxwarm_call`, `foxwarm_node`, `foxwarm_exec_result` and `foxwarm_session` only after their concrete source owners are implemented.

Discovery uses canonical `mcp:server/tool` and `node:nodeId/tool` IDs, plus only `builtin:node_pair_list` and `builtin:node_pair_approve`, with unified ranking and deterministic order, the live Main MCP registry, compatible first-party CLI Node descriptors, and already-ready first-party resident Docker-worktree descriptors. It includes only potentially visible concrete tools under the ordered generic rule for the verified external identity and generated transport context ID. A conditional rule may make a tool discoverable; every call authorizes the exact source, target, full arguments and applicable execution path facts again. The `builtin:node` policy sees the normalized action arguments and truthful Node facts: list has no unique target Node, status uses the actually selected current Node, and select uses its validated requested Node; a master-only allow cannot select a different Node. Exec-result listing/query rechecks original `node:.../exec` arguments and exact live context ownership. MCP wrappers are not authorization identities; a guessed ID cannot bypass exact policy, enabled-server/tool checks or Node generation/capability gates. The dedicated Session wrapper resolves only bounded list/read/send to existing builtin permissions.

Headless CLI Node pairing uses the existing authenticated Node WebSocket handshake: a local administrator privately supplies the existing pairing token to a new Node; an authorized external operator can use only the two exact builtin pairing definitions and their original schema/copy to list/approve the pending request through existing Main-local handlers. Pairing permission uses the verified external identity, its live transport context and the full action arguments, with no internal ToolContext, fabricated `targetNode:master`, implicit default allow, token-returning bootstrap action, or generic builtin dispatch. Approval returns no Node authentication token to the MCP caller; credentials go only to the Node through the existing handshake. Already-ready first-party resident Docker-worktree Nodes are also available for the same five file/exec capabilities. Their external owner crosses only the in-process primitive adapter and generation-bound ExecRuntime: no fabricated source Session, new remote HMAC/wire, generic provider opt-in or lifecycle mutation is implied. External file reads cannot open a generation artifact directory, final effect boundaries recheck transport disposal, and an attempted multi-step patch cannot be classified as wholly pre-effect. Running results are bound to the original Docker generation; deleting a transport drops result authority without killing started processes. Other direct Session controls, master, executable-provider and shared-browser external effects remain unsupported.

Main's external-specific MCP facade uses the existing live client without forging an internal Session or adding a second MCP configuration store. It preserves SDK text, structured and image results and remote `isError`; inbound body, discovery and result budgets are independent so moderate tool args and images are not rejected as tiny generic catalog output. Denials and lookup failures are pre-effect errors. After invoking an outbound tool, a transport failure, abort, or over-limit result reports an unknown or possibly completed effect, with no automatic retry or false assertion of rollback. SDK timeouts and signal cancellation remain authoritative; remote cancellation is best-effort. Legacy internal MCP error redaction is unchanged. The external path does not put outbound configuration in its own responses. If remote metadata echoes a configured token or recognized authentication-header value, the affected tool is omitted without changing its ID or schema; if a remote result echoes such a value, the whole post-effect result is withheld without retry. Noncredential environment values, paths, schema literals and base64 media are preserved. Untyped environment variables/command arguments and transformed or encoded remote secrets cannot be inferred reliably; this is not a universal credential-leak guarantee. HTTP identities and SDK sessions are ephemeral; this phase provides no durable result retrieval or internal Session authority.

The Session wrapper uses exact existing `builtin:session` list, `builtin:get_session_messages` and `builtin:send_to_session` policy identities with the authenticated external principal and canonical target, never a new wrapper permission or fabricated source Agent/Session/relation. List is a global catalog capability, not a per-target read projection. Read obtains the exact local/Worker owner history with a bounded standard preview and does not expose prompts or queued input. Send writes ordinary `user` input with server-generated external provenance as a separate escaped metadata part and unmodified user text; no channel source, system-delivered message, inter-agent relation, handoff confirmation or reply wait is implied. A matched generic allow suffices even for an isolated target. Main's local queue or the exact Worker mailbox acknowledges durable admission only; HTTP disposal fences an unsent input at its final local/Worker admission boundary, but does not withdraw already-admitted input. Unknown outcomes are not automatically retried or assigned a new receipt protocol.

### D-dispatch-mcp-live-configuration

[2026-08-01, updated 2026-08-19] The first managed/runtime MCP configuration read establishes one authoritative in-memory snapshot. Subsequent MCP listing, discovery, and calls read that snapshot rather than rereading the backing file. `mcp_config` mutations must persist successfully before replacing the live snapshot, become visible to subsequent MCP operations immediately, and require no Foxwarm restart. Manual backing-file edits do not alter the live snapshot; do not add file watching or an agent-facing manual reload path. Optional per-server `timeoutSeconds` is bounded to finite 1-3600 seconds and applies only to tool calls through SDK request options; zero canonically clears the field and omission preserves the SDK default.

### D-dispatch-mcp-explicit-notifications

[2026-10-10] MCP message reception is explicitly enabled for the current trusted internal Session and one configured Streamable HTTP server through discoverable `mcp_notifications` start/stop/status. It has no remote-controlled target Session parameter and is not injected by default. Start succeeds only after the actual GET stream is ready and both peers support the Foxwarm experimental version-1 capability. Ordinary HTTP discovery/calls already reuse that exact Session/server connection; start enables local reception without rebuilding its existing remote context. Internal Session owners and verified external-context owners occupy distinct caller/server bindings. No owner is supplied from untrusted tool arguments.

The server-side `foxwarm_session` send advertises optional `allowReply:true`, meaning permission for the receiving Session to send an explicit reply, not that the input itself is a reply. Legacy wire `reply` remains accepted only as read-old compatibility; conflicting new/old values are rejected before effect. Both legitimate spellings trigger the same client reception preflight. It preserves verified external identity, concrete `builtin:send_to_session` policy and exact target admission, while including a server-owned temporary channel target in the existing escaped external-input provenance and send result. A small registered text-only Channel sends the custom `notifications/foxwarm/session_message` extension over that context's independent GET SSE. This is an external conversation/reply endpoint, not another internal or external Session authority. Failed creation leaves no registered endpoint, and context disposal unregisters it. No attachment is persisted or created in a separate volatile registry.

Replies use existing `send_to_channel`, including Main Management source fencing, concrete tool authorization and the isolated own-attachment restriction. A non-isolated authorized caller may send to any available registered endpoint; the destination is not restricted to the original recipient Session. Isolated callers do not gain an MCP-specific exception. Ordinary assistant outputs, history, logs and progress are not subscribed or broadcast to the endpoint.

The receiving Main derives its target solely from the locally authorized binding, identifies provenance by configured server and endpoint rather than a claimed remote Session, and admits text through the existing ordinary durable local/Worker input path. It wakes/queues normally and never pretends to be an internal child reply. Receiver liveness and local source permission are rechecked at admission. Managed configuration changes/disable, Session deletion, external-context disposal and shutdown fence and close bindings. Ordinary caller connections are released after 15 minutes idle, excluding in-flight requests; enabled reception uses its standard ping instead of ordinary idle disposal. Streamable HTTP cleanup uses bounded SDK DELETE followed by close, while legacy SSE uses its own close. Concurrent setup is coalesced and a failed or closed setup cannot become usable. Standard ping preserves the existing server idle lifetime; SDK same-context reconnect is distinct from message durability. The extension provides online best-effort sending only, with no ACK, EventStore, replay, outbox, automatic original-input retry or reuse of old reply targets across a new context. Its protocol boundary is the installed SDK's negotiated versions, not a claim to support later protocol revisions.

[2026-10-10] Client extension capability expresses support, not automatic reception. Session-owned HTTP clients negotiate version 1 at initialization and install a disabled handler. `mcp_notifications` start verifies actual GET readiness and peer capability, then enables delivery to the trusted current Session without changing remote Node/cwd/exec ownership. Before invoking a peer that advertises the Foxwarm extension, the canonical outbound call rejects `foxwarm_session` send with `allowReply:true` unless that connection has enabled reception. Third-party same-name tools without the advertised extension are not intercepted. External-context owners do not claim an internal receiving Session. No version upgrade or reception-control RPC is added; the remote server is not asked to prove whether a client processes notifications.

A 404/closed context is not a reason to replay a possibly executed tool. Later operations may establish a fresh context, which does not retain prior Node/cwd/exec state. Unsupported DELETE is a best-effort cleanup failure, not an invocation failure or a reason to retry an effect. Anonymous low-level calls are not pooled and still attempt remote termination before closing.

Notification reception reauthorization uses the complete existing tool permission path for start, receive, explicit-reply preflight and ping, including legacy isolated exact rules. Missing notification server names never fall back to another configuration. A moved/inactive owner is cleaned up at the next existing ping boundary; no connection migration or stable-identity layer is added.

Internal MCP results remove pure text JSON blocks duplicating structured data and unwrap structured-only results at the existing client normalization boundary. Errors, additional explanations/metadata and multimodal data remain, with the existing image-promotion/output-guard order. Raw external MCP passthrough and server wire compatibility do not change. The canonical result rules are [D-mcp-source-normalization](../units/src-mcp-client.md#d-mcp-source-normalization).
