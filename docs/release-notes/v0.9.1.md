# Foxwarm 0.9.1

Foxwarm 0.9.1 adds macOS server packages, a guided first-run setup, a combined System page and clearer tool activity. The default file and shell tools sent to the model now stay the same when a Session switches Nodes.

## Highlights

### macOS server packages

- Run the Foxwarm server on Apple Silicon Macs with macOS 15 or later, using either the framework-dependent or the self-contained package.
- The shell installer picks the macOS arm64 package automatically.

The new downloads are `foxwarm-osx-arm64.tar.gz` and `foxwarm-osx-arm64-self-contained.tar.gz`. The Linux x64, Windows x64 and Windows desktop packages are still published, and `SHA256SUMS` covers all seven archives.

### Starting and stopping on Linux and macOS

- `foxwarmctl` runs Foxwarm in tmux when tmux is installed. Without tmux, it starts Foxwarm in the background, where it keeps running after the terminal or SSH session closes. In both cases the server's PID is saved in `foxwarm.pid`.
- Start, stop, restart and update now act only on this installation's server and its own tmux pane. Other tmux windows and other installations are left alone. The first update from 0.9.0 still runs the old script; see [Upgrading](#upgrading).

### First-run setup

- A form helps you add your first provider and model, shows the model's details and lets you test the connection. You can still edit the YAML directly.
- New installations open with a welcome Session and give unnamed Sessions a title after their first message. Automatic titles remain off by default for existing installations; turn them on with `sessionAutoTitle: true` in Setup → Config.
- Foxwarm no longer keeps retrying when an API key is missing or rejected, access is denied or a model doesn't exist. The error says what went wrong and links to the model settings.
- For models set to `imageInput: false`, each image is sent as a short text note instead. Saved conversations keep their images.

### WebUI

- The new System page shows Agents, Sessions and Nodes in one place. Its Sequence view lays out each Session's activity, and the messages between Sessions, on a shared timeline.
- Conversation is now the default desktop view unless you have already chosen one; mobile already used it. Conversation hides prompt snapshots and model or Node change notices, which remain visible in the Detailed and Grouped views.
- Collapsed tool headers stay on one line. Cards with an output preview show the command or script on that line, shortened to fit; script files show their path. In Conversation view, fully collapsed cards show what the call is for.
- Expanded command and script cards show the full source with syntax highlighting and a copy button, along with the inputs and options that were passed.
- Opening a Session that already has a tab keeps that tab in place and preserves its scroll position.
- Following a Session link no longer adds a duplicate browser-history entry, so one Back press returns to the previous Session.
- The optional Code workbench now also finds editor assets installed in the installation directory, not only in the release files.

### Tools and permissions

- The default file and shell tools sent to the model stay the same when a Session switches Nodes or a Node disconnects. Each call is still checked against the target Node's capabilities and permissions, and tool discovery still reflects the selected Node.
- `exec` and `run_script` now ask the model for a short `summary` of each call's purpose, which the WebUI shows in tool activity. The schemas sent to the model require it; existing automation and direct calls without a summary still work.
- `view_session` and `recall` show tool activity more compactly, with the expansion examples listed once at the end.
- Creating or updating a timer that starts a new Session now checks the caller's `create_session` permissions for the target Agent. To match Sessions created in another Agent, `create_session` policy rules can use `args: {agentName: {agent: {sameAgent: false}}}`; use `sameAgent: true` for the caller's own Agent. Existing timers are not rechecked when they fire.
- Commands and terminals started by Foxwarm no longer inherit the server's `TMUX` and `TMUX_PANE` variables.
- In a source checkout, the stop and restart scripts now identify the server by its PID, check that it belongs to this installation and wait for it to exit, forcing it to stop after 60 seconds. They no longer send Ctrl+C to the tmux pane.

## Framework prompt

Foxwarm now reads the framework prompt directly from its bundled template, so prompt improvements arrive with each update. Put installation-specific instructions in `agents/00_SYSTEM.local.md`.

At startup, Foxwarm removes unchanged copies of earlier framework prompts. An edited copy, such as an edited `agents/00_SYSTEM.md`, is kept and still replaces the bundled prompt; the startup log explains how to switch. Move your additions into `00_SYSTEM.local.md` before deleting the edited copy.

## Upgrading

**On Linux, the update from 0.9.0 runs the 0.9.0 control script.** That script can close the whole configured tmux session (`foxwarm` by default), including any other windows in it. Before updating, save or move work in those windows and make sure the session belongs to this installation. Later commands use the new controls.

- Back up the data directory first. For server packages, run `foxwarmctl update` (`foxwarmctl.cmd update` on Windows) or run the installer again. For source installations, follow the source update instructions in the documentation.
- In a source checkout, the first stop or restart after updating still recognizes a server started by the old scripts, even though it has no PID file.
- New-Session timers are admitted conservatively: if your `create_session` rules depend on Session details that are not known when the timer is registered, registration can be rejected. Review the affected policy if this happens.
- macOS packages are tested on macOS 15 on Apple Silicon. There are no Intel Mac server packages and no macOS desktop app. Semantic history search and the browser tool are included but not yet verified on macOS.
- The macOS archives are not signed or notarized, so Gatekeeper may quarantine an archive downloaded in a browser. See the installation guide.
- Code workbench assets and HEIC/HEIF decoders still have to be installed separately.
