# Foxwarm 0.9.4

Foxwarm 0.9.4 lets tool rules ask a person for approval before a call runs, delivers events from GitHub, Cloudflare and your own scripts through inbound webhooks, and adds an encrypted secret store that agents can use without seeing the values. System gains Usage and Activity sections, browser tools are rebuilt around one `browser_*` family, and copies between Nodes stream large files in the background. On Linux x64, the default package is now a native build that needs no .NET runtime. This release also renames a handoff parameter, which affects scripts and timers, and changes the container image to run as a non-root user. Read the upgrade notes before updating.

## Security

- The optional `sandbox-node` service in `docker-compose.yml` mounted the whole data directory into a container that runs agent commands. The mount was read-only, but it exposed `models.yaml`, stored credentials and other state. It now mounts only the pairing token. If you run that service, update your Compose file.
- Text from outside Foxwarm can no longer imitate Foxwarm's own message framing. Inbound MCP messages, MCP notifications, webhook deliveries and channel messages that contain something resembling a `<foxwarm-…>` tag are stored and sent to the model with that tag made harmless.
- Usernames and passwords in MCP server URLs no longer appear in server summaries or error messages.

## Upgrade notes

- Back up the data directory first, as usual.
- **Linux self-contained package.** The native package replaces `foxwarm-linux-x64-self-contained.tar.gz`. To update such an installation to 0.9.4, run `./foxwarm/foxwarmctl update` as usual: 0.9.4 also publishes the native package under the old name, and the installation switches to the native package and keeps its data and configuration. Later updates stay on the native package. Later releases won't publish the old name, so to update a self-contained installation directly to 0.9.5 or later, rerun the installer from the directory you installed from, with the same `--dir` if you used one. You can also rerun the installer now to switch.
- **Handoff parameter renamed.** `send_to_session` and `create_child_session` now take `currentSessionTurnAction` (`continue`, `end_turn` or `wait`) instead of `afterSend`; `finish` is now `end_turn`. Calls that still pass `afterSend` are rejected before they do anything, with an error naming the replacement. Update ToolScript scripts, timer scripts and webhook handler scripts that send handoffs. Existing Session history is unaffected.
- **Container image runs as non-root.** The image now runs Foxwarm as the `node` user (uid 1000) and does not change ownership of the mounted data directory. Before starting the new image on data written by an earlier image, stop the container and run `sudo chown -R 1000:1000 <data dir>` once; otherwise the container reports that `/data` is not writable and Foxwarm does not start. Agents can still install packages with `sudo`. The image no longer includes a .NET runtime, which Foxwarm no longer needs; if your agents ran `dotnet` inside the container, install it there.
- **Container browser sandbox.** Start the container with the shipped seccomp profile (`--security-opt seccomp=seccomp-chromium.json`) and `--shm-size 1g`, as the updated install guide shows. `docker-compose.yml` already sets both and reads the profile from `docker/seccomp-chromium.json`, so keep that file next to it. Without the profile, the first browser call fails with a sandbox error.
- **Browser tools renamed.** The `browse_*` tools are gone. Browser tools are now `browser_*` (see Highlights) and need Node.js and Chromium or Chrome on the machine that runs them. Tool rules that name `browse_*` still load but no longer match anything; rewrite them for `browser_*`. Browser Node uses the same names: download the extension again from **Nodes → New nodes → Browser** to get them.
- **Back up the instance key.** Foxwarm now creates `keys/secrets.key` in the data directory at startup. It decrypts the secret store, so back it up together with `state/secrets.json`, but keep it out of Git-backed or shared backups of `state/`. If the key is missing, stored secrets cannot be read and settings that use them stay unavailable until you restore it.
- **Reverse proxies.** Large file copies to and from CLI Nodes now use `/node/transfer/`. If Foxwarm runs behind a reverse proxy, forward `/node/transfer/` GET and PUT requests to Foxwarm over HTTP/1.1 with no body size limit and request and response buffering off.
- **`node(list)` in scripts.** Each Node row in a ToolScript `node(list)` result now lists tool names instead of complete tool definitions. Use `search_tools` with `nodeId`, or `node(inspect)`, when a script needs definitions.
- **Existing Windows Desktop installations.** The Desktop app now keeps Agents under `agents\` in its data directory (`%LOCALAPPDATA%\Foxwarm\Desktop\data`, or `FOXWARM_DATA_DIR` if set), like other installations, and no longer uses the `workspace` folder next to it. Files in `workspace` are left untouched. On the first start with a data directory from an earlier Desktop version:
  - If `data\state\agents.json` exists, the app doesn't start. It shows "Foxwarm could not start" with the message "Retained C# Agent data requires its original workspace."
  - Otherwise it starts with a new main Agent in `data\agents\main`. Memory and files in `workspace` are not used.

  To start fresh, exit Foxwarm from the tray, then rename the `data` folder or set `FOXWARM_DATA_DIR` to a new directory. The next start creates a new data directory, and you set Foxwarm up again. To keep your main Agent's memory and files, exit Foxwarm and copy everything in `workspace` except its `agents` folder into `data\agents\main`.
- **Isolated Agents.** Sessions of an isolated Agent can again send messages to, or wait on, only themselves and their direct parent or child; Foxwarm 0.9.3 did not enforce this. Whether other Sessions may contact an isolated Agent's Sessions is now decided by their own tool rules.
- **Downgrading.** Foxwarm 0.9.3 refuses a configuration that contains webhook identities; remove them before going back. If you migrate an isolated Agent (see Other changes), Foxwarm records a minimum reader version in `state/installation.json`, and later versions that cannot read the migrated data refuse to start. Foxwarm 0.9.3 does not check that marker, but still enforces the Agent's legacy isolation.

## Highlights

### Approve tool calls before they run

- Tool rules can now use `action: ask` alongside `allow` and `deny`, including as `defaultAction` and in Agent-local rules. A matching call waits until someone approves or rejects it; nothing runs in the meantime.
- Pending requests appear in the WebUI question dock of the calling Session, with the tool, its arguments, the resolved targets and the reasons of the rules that asked. Approve or Reject, optionally with a note that the agent receives. The Session list, its badge and notifications show waiting requests, and the tool call in the timeline shows how it was settled.
- An `approval` block can set a deadline (`timeoutSeconds`) and name access identities that may decide (`approvers`). The administrator can always decide. A scoped WebUI identity decides only when its Session scope includes the Session and every asking rule names it.
- Deny still wins over ask, and an approved call is checked again against the current policy before it runs. Rejected and expired calls return an error to the agent; Stop cancels the request. A pending request expires when Foxwarm restarts, and the call is not replayed.
- Without a deadline, foreground calls wait until a decision or Stop. Timer scripts and webhook handlers wait at most one hour. Inbound MCP callers can't be asked, so a matching `ask` rule denies their calls.
- The new `explain_tool_authorization` tool shows how existing Sessions' calls would be decided, layer by layer, optionally against a candidate policy. It needs read access to the policy files.

### Inbound webhooks

- External services can now deliver events to a Session at `POST /webhooks/<id>`. Each webhook is an access identity with the `webhook` surface, bound to one existing Session and verified by a GitHub signature, a named header secret or a Bearer secret. Add webhooks in **Setup → Config**; they apply without a restart. Agents can't add or change them through `set_config`.
- Deliveries reach the agent as data from an outside service, not as instructions from you. With `wake: false` they are saved without starting a turn and read the next time the agent works. With `action: toolscript`, a script handles each delivery without a model turn, for example to message the Session only when a CI run fails.
- GitHub pings and events you didn't list are acknowledged without delivery, and GitHub deliveries are deduplicated. Bodies are limited to 1 MiB, and each webhook has a rate limit and bounded backlogs.
- **System → Webhooks** shows each webhook's address, target, verification method, action and recent deliveries.
- The administrator-only `POST /trigger` endpoint is deprecated and will be removed in a later release. Its responses now carry a `Deprecation` header. The Webhooks page in the documentation explains how to move a script to a `bearer` webhook.

### Secret store

- **Setup → Secrets** stores credentials encrypted on the server. Configuration refers to them as `${secret:NAME}` in provider API keys and headers, channel credentials, `llm.*ApiKey`, the ASR service key and MCP server settings. Stored values are never shown again. In Setup you can replace, describe or delete them, and see which Agent owns each one, where it is used and which referenced names are missing.
- A missing or unreadable secret fails only the provider, channel or MCP server that uses it. Foxwarm still starts.
- Agents can add secrets but never read, replace or delete them. `add_secret` stores a value under a new name from a call argument, from a file on the Agent's Node (optionally deleting the file afterwards), or from credentials already written in configuration, which it replaces with a reference. It never overwrites an existing name. A value passed directly as an argument remains in that call in the Session history; a file or a secret question keeps it out.
- `ask_user` can ask you for a secret. You enter the value in the WebUI answer form, it is stored under the requested name, and the agent learns only that it was stored. These questions can't be answered with a chat message or from a channel.
- `list_secrets` shows names, descriptions, owners, where each secret is used and whether the agent may use it on its current Node, never values.
- `exec` accepts `secretEnv` to pass stored secrets to a command as environment variables. The values reach only the command's environment, not its script, records or logs. This works on `master`, on Provider Nodes that declare `execEnv` (the container Provider example does), and on native CLI Nodes running this version. Other Nodes refuse the call before it starts.
- Tool policy decides which secrets an agent may use, through `exec`'s `secretEnv` or a `set_config` or `mcp_config` change that would send a secret somewhere new. A rule with the new `secrets` selector decides first. Otherwise a secret the Agent added itself, or received through its own question, needs no rule, and any other secret needs the same permission as an unrestricted `exec` on `master`, which can already read the store. Without tool rules, agents may use every secret. Agents made from the `restricted-worker` or `channel-assistant` templates, and isolated Agents, need a `secrets` rule for secrets they don't own. Deny and ask rules also apply to owned secrets, and `secrets: {owned: true}` selects them.
- Foxwarm masks known credentials as `[[FW_SECRET:<name>]]` in tool output, Session history, model requests and server logs. This covers stored secrets and credential-shaped values in your configuration, such as API keys, credential headers and URL credentials, as well as access tokens and the Node pairing token. Masking is accident protection, not a security boundary for code that deliberately transforms a value.
- Agents can't write a marker for a current secret back into files, memory or configuration, and `exec` on `master` drops inherited environment variables whose value is a known secret. `node_bootstrap_info` now writes the pairing token to an owner-only file instead of returning it.

### Text redaction for model requests

- A model can be set to replace personal data in text before it is sent to the provider, using a text-detection service you run. Placeholders in the model's reply and tool arguments are restored to the original text before you or your tools see them. Redaction is off by default; turn it on with `textRedaction` in `models.yaml` for all models, a provider or one model.
- Options include the detection `endpoint` and `apiKey`, `threshold`, `excludeLabels`, `keepValues` that are never replaced, `maxConcurrency` per detection service and `batchBytes` to combine short texts into fewer detection calls.
- If detection fails, the request is not sent. A failover route that starts on a redacting model never falls back to a model without redaction.
- Usage details show how much was redacted, **System → Usage** has a Text redaction section, and messages in a redacting Session have a **Sent version** action that marks what was replaced. Detection results are kept encrypted in `state/text-redaction.sqlite`, so a restart doesn't change what is sent.

### Usage and Activity in System

- **System → Usage** reports cost, tokens and requests for today, this week, this month or a custom range, grouped by Agent, Session tree, Session, model, provider or purpose, with a chart and a table that drills down to Sessions. It counts every model request, not only conversation turns. Requests that Foxwarm recorded before the upgrade are added in the background.
- The status bar total now shows today's or this month's recorded cost from the same data and opens System → Usage.
- **System → Activity** lists which tools ran, on which Nodes and with what result. It shows changes from the last seven days by default and can filter by kind, result, source, text, Session, Agent, Node or tool. Each call expands into its target, files, deciding rules and approval, and links to the call in its Session. The Session inspector links to its tree's activity.
- Both sections are available to the administrator only.

### Browser tools

- One `browser_*` tool family now serves both a machine's own headless Chromium and your shared browser tabs through Browser Node: `browser_tabs`, `browser_open`, `browser_close`, `browser_navigate`, `browser_read`, `browser_screenshot`, `browser_click`, `browser_fill`, `browser_type`, `browser_press`, `browser_select`, `browser_scroll`, `browser_wait` and `browser_evaluate`.
- The headless browser is available on `master` and on CLI Nodes when Node.js and Chromium or Chrome are installed there. Choose a browser with `PUPPETEER_EXECUTABLE_PATH`. Chromium's own sandbox stays on. If it can't start, the error says why and how to fix it.
- Browser tools follow the same Node selection and tool rules as other Node tools.

### Restricted workers and disposable containers

- The `node-setup` skill now includes a container Provider for Docker and Podman. It creates one disposable container per Node from profiles that you define. Containers run without network access, with all capabilities dropped and no image pulls. Profiles can also offer Code and Terminal. Its opt-in real-engine check has passed on Ubuntu 24.04 with rootless Podman and with Docker's standard rootful daemon; other platforms and engines, including rootless Docker and Docker Desktop, are untested.
- The `agent-management` skill adds `restricted-worker` and `channel-assistant` templates, each with memory and an Agent-local rules file. The development workflow example gains `provision` and `release` steps.
- The `isolated-worker` skill is retired. Use the `restricted-worker` template with a Node, such as a container Provider Node, instead.

### File copies between Nodes

- `copy_between_nodes` now streams files with bounded memory instead of loading them whole, between `master`, Provider Nodes and CLI Nodes. CLI Nodes use a separate authenticated transfer for files of 64 KiB and more; older CLI Nodes keep the previous transfer.
- A copy that takes longer than its `timeout` (15 seconds by default, at most 60) continues in the background and returns a `transferId`. Wait for it with `wait` and `waitExecIds`, or stop it with the new `cancel_transfer` tool. Stop also moves an unfinished copy to the background instead of cancelling it.

### Native Linux package

- On Linux x64, Foxwarm is now published as a native build, `foxwarm-linux-x64-native.tar.gz` (about 96 MiB), which needs no .NET runtime. It replaces the self-contained Linux package.
- The Linux installer uses the native package for new installations, even when .NET is installed. `--framework-dependent` selects `foxwarm-linux-x64.tar.gz`, which still uses the installed ASP.NET Core 10 runtime. Rerunning the installer with `--native` or `--framework-dependent` switches an existing Linux installation between the two and keeps its data and configuration; `update` keeps the installed package type.
- Both Linux packages need glibc 2.34 or later (for example Ubuntu 22.04, Debian 12 or RHEL 9) and the system ICU and OpenSSL libraries, which most Linux systems have.
- Semantic history search now works on the same systems. Earlier 0.9.x Linux packages needed glibc 2.39 for it.
- The container image now runs the native Linux build, without a .NET runtime.
- Windows and macOS packages and the Windows Desktop app are unchanged.

## Other changes

### Nodes and Sessions

- The model's Node list now shows only Nodes where its tools might be allowed, plus its current Node, and Providers show only the lifecycle actions the caller might use. In the administrator's Chat Node picker, Nodes the Session's tools can't use are marked but remain selectable.
- `agentDefaultNode` in `config.yaml` sets the Node for new Sessions of Agents that have no `defaultNode` of their own. It changes placement only and grants no access.
- New Sessions are placed by explicit choice, then a parent Session in the same Agent, then the Agent's default Node, then `agentDefaultNode`, then `master`. Same-Agent children and forks follow their parent's Node again. `create_session` and `create_agent` no longer fall back to the caller's Node.
- `create_child_session` and `create_session` accept a `model` suggestion with `modelId` and `effort`. A configured child model and `forceModel` take precedence. The result reports what was chosen and why.
- `session` with `action: "list"` accepts a `query` that matches Sessions the same way as the WebUI search.
- Task completion notices to the Task's creator now include the model and estimated cost used by the Task's owner.
- On CLI Nodes, `exec` without a `cwd` now starts in the Agent directory, as it does on `master`.
- Code and Terminal now work on Provider Nodes whose Provider supports them. The CLI Node has a `--stdio` mode that serves only these services, so a Provider can reach it through `docker exec` or `ssh`.

### Legacy isolation migration

- Administrators can migrate an isolated Agent to the generic replacement, an Agent-local rule layer plus a default Node, through the new isolation migration routes. The inventory shows what the generated rules translate, cover, drop, narrow or widen, and blocks cases it can't express. The migration runs per Agent and only when you request it.
- After migration, legacy isolation stays in force on top of the new rules. Automatic migration and removal of legacy isolation will come in later releases.

### WebUI

- A message sent while the agent is starting a turn now appears once and stays in place, and the status shows Sending… until the agent starts work.
- Unsent `ask_user` answers are kept as drafts when you collapse the dock, switch Sessions or reload the page.
- In `ask_user` text answers, Enter follows the Chat send key setting, and Enter that confirms IME input never submits.
- When a Session's state can't be loaded, Chat shows why, for example a missing or damaged data file, instead of a generic connection banner. Repeated failures are retried at growing intervals.
- In tree mode, the Sidebar orders Sessions by the latest activity anywhere in their subtree. Expanded branches first show the children active in the last 24 hours, between three and five.
- The model picker shows a child effort setting even when the child model follows the Session, and offers a "Follow this session" choice.
- Timeline text no longer shows through below the chat input.

### Installers, package controls and Desktop

- The one-line Windows installer and the package's control commands now work under PowerShell's default Restricted execution policy.
- Start reports success only once Foxwarm is serving. If the port is taken, start names it and prints no sign-in link. The Linux and macOS control script and installer report the same way, and installer reruns print the sign-in link again.
- Stop and restart act only on this installation's own Foxwarm process, and restart checks the launcher before stopping anything.
- Running `Foxwarm.exe` directly from an unpacked package, without choosing a data directory, no longer fails to start.
- The Linux and macOS installer no longer exits before printing the sign-in link on a first install.
- The Windows Desktop app is now built on WinUI 3, with the Windows App SDK included in the package. It still needs the WebView2 Runtime.
- A command's completion could be delivered again after a restart if Windows kept the exec registry file locked, for example by antivirus or backup software. Foxwarm and the CLI Node now retry saving it.

### Prompt caching

- Earlier parts of a model request now stay unchanged from one request to the next more often, so providers can reuse their prompt cache further into long Sessions.
- Open `ask_user` questions no longer add a reminder to every request.
- The Task progress reminder is saved once in the Session history instead of being added to each request. Grouped and Detailed views show it as a card; Conversation view hides it.
- Results of earlier hosted web searches no longer change when the model searches again.

### Other fixes

- Setup shows a channel's runtime error only while the channel is failing, and clears it when the channel recovers. The error is a short sentence that says what failed and why; details stay in the server log. Reconnects that a channel handles on its own are no longer shown as errors.
- Closing a terminal on a CLI Node now waits for the shell to exit, so shells that ignore hangup no longer keep running. A terminal that closes on the server shows its final error or exit status.
- Searching tools across all MCP servers queries the servers in parallel, up to a limit, and skips servers whose tools the caller's rules deny entirely.
