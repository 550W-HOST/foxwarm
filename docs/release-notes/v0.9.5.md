# Foxwarm 0.9.5

Foxwarm 0.9.5 completes the move from legacy Agent isolation to Agent rules. At its first start it converts the remaining isolated Agents, and after that only tool rules apply. Context compaction now follows a fixed schedule that keeps old history at coarser detail, so long Sessions carry a smaller and more even summary of their past. Agents with restricted tool rules see only the Sessions and Agents their rules let them use, and file transfers resolve relative paths the same way the file tools do. Read the upgrade notes before updating, especially if you use isolated Agents, channel guests or the Linux self-contained package.

## Upgrade notes

- Back up the data directory first, as usual.
- **Linux self-contained package.** Foxwarm 0.9.4 also published its native Linux package as `foxwarm-linux-x64-self-contained.tar.gz`. 0.9.5 no longer publishes that name, so a Linux installation still using the self-contained package of 0.9.3 or earlier can't update directly to 0.9.5. Either run `./foxwarm/foxwarmctl update 0.9.4` and then `update` again, or rerun the installer from the directory you installed from, with the same `--dir` if you used one. Installations already on 0.9.4 update as usual.
- **Legacy isolated Agents.** At the first start, before accepting work, Foxwarm converts every Agent still marked isolated into Agent-local tool rules and makes the Agent's Node its default Node. Sessions of these Agents that had no Node of their own move to that Node. After that, legacy isolation is no longer enforced.
  - Agents that can't be converted safely, for example because they already had their own rules, are blocked: their rules deny every call until you replace them. The earlier rules are kept in the Agent's migration record in `state/agents.json` so you can merge them by hand.
  - System → Agents and the server log show the result for each Agent.
  - The converted rules don't reproduce every detail of legacy isolation. These Agents can now list and inspect other Nodes, although their rules still keep their tools on their own Node. A `node` given explicitly when creating a Session now takes precedence over the Agent's default Node. Large tool output is saved on `master` in the Agent's directory.
- **Removed isolation settings.** `set_agent_isolated`, the `isolatedNode` and `toolRules` options of `create_agent`, `/agent isolated`, `/agent create --isolated` and the isolation setting in the WebUI are gone. The agents API rejects `isolatedNode`. Update ToolScript and timer scripts that use them to `set_agent_rules` plus `defaultNode`.
- **Files and channel sends.** Files received through channels or uploaded in the WebUI are now always saved on `master` in the Agent's directory. Formerly isolated Agents can no longer send to channels.
- **Channel guests.** Set `guestAgent.template` in the channel's configuration to an Agent whose rules apply to guests. Without it, new guests are refused unless the configuration sets `guestAgent.isolated: false`. Existing guest Agents are converted like other isolated Agents.
- **Compaction keep share.** `llm.compactKeepPercent`, the `keepPercent` argument of `compact_session` and the percentage in `/compact [keep%]` keep their names and the 0.3 default, but they now mean something else. They used to be a share of the history's rows. Now they set how much recent history stays unsummarized, in estimated tokens, as a share of the automatic compaction threshold, or of the unsummarized history if that is smaller. Check any value you changed from the default.
- **Relative paths in file transfers.** `copy_between_nodes`, `send_file` and `image_write_to_file` now resolve a relative path like `read`, `write` and `edit` do. A path on the Session's current Node is relative to the Session working directory. A path on any other Node, or one used when no working directory is set, is relative to that Node's default directory. Before, `copy_between_nodes` always used the Agent directory. Automation that passes relative paths from a Session with a working directory should use absolute paths or expect the new location.
- **CLI Nodes.** A CLI Node that hasn't been updated ignores the Session working directory for these transfers and keeps using its Agent directory. Update Node clients together with the Main server.
- **Removed parameters.** `send_file.text` (use `caption`), `recall.agentName` and the `recall` scope value `all`, which behaved as `current-agent`, are gone. Calls that pass them are refused.
- **Cancel controls.** Tool schemas no longer list `__cancelTool` and `__cancelAllToolsThisTurn`. The framework prompt describes them once, and tools accept them as before. An existing Session picks up the description when its prompt is next rebuilt.
- **Downgrading.** Foxwarm 0.9.4 runs on data converted by 0.9.5 and enforces both the legacy isolation and the converted rules of these Agents. Earlier releases can't read the converted rules, so they refuse every call by these Agents and by Agents they created until you upgrade again.
  - When 0.9.5 starts again, it reconciles each converted Agent with what the older release left. If the Agent's isolation settings changed, rules that nobody edited are generated again from the new settings, and edited rules block the Agent until you replace them. Turning isolation off keeps the converted rules.
  - Converted rules edited outside 0.9.5, by an older release or by hand, are kept only while they still end in a rule that denies every other call. Otherwise the Agent is blocked.

## Highlights

### Log-compressed context compaction

- Each compaction writes one new summary block for the history after the newest block, then performs the merges a fixed rule requires. When a level holds more than three blocks, its two oldest merge into one block of the next level. Recent history keeps fine detail and older history keeps progressively less, so the number of blocks grows slowly as a Session gets longer.
- Foxwarm chooses the operations, and the model writes only the summaries. A new block has a budget of 3,000 estimated tokens and a merged block 1,500, memory facts included. A summary well over its budget goes back to the model for shortening, at most twice. If all summaries together still exceed 24,000 tokens, the oldest blocks are folded together.
- Existing Sessions are reorganized into this shape during their ordinary compactions, at most three merges per compaction, oldest first. Sessions with many blocks take several compactions to get there, and their summaries shrink gradually.
- Preserved messages and notices no longer prevent merges. A preserved message inside a merged block leaves the active context with the merge and stays readable through `recall`.
- Summaries are written in the main language of their sources, with code, identifiers and technical terms unchanged.
- The planner sees the current status of the Tasks that the compacted history mentions, so a finished Task no longer stays open through later merges. It sees only the status, not titles or other content.
- Memory facts of merged blocks leave the active context with the merge, so merge summaries now keep the decisions that still matter, with a reference to their source messages.
- Guidance given to a manual compaction now shapes the summaries only. Which operations run is fixed.
- In in-context compaction (the experimental `in-context-compaction` skill), rewriting a single block keeps its level, and a level-1 block becomes level 2. Budgets are advisory there: the result lists summaries over budget in `overBudget` instead of rejecting them, and the next regular compaction brings the layout back into shape.

### Session and Agent lists follow tool rules

- The model's `session` list, the recent child Sessions in `session` status and `list_agents` now show the caller's own Session and Agent plus the Sessions and Agents its tool rules might let it read, message, assign Tasks to, stop, rename or manage. Counts include only listed Sessions.
- Agents without restrictive rules see the same lists as before. The WebUI, the channel `/status` command, inbound MCP and scoped WebUI access are unchanged.
- The rules still decide every call. A hidden Session isn't protected by being left out of a list.
- If the tool policy can't be read, these lists fail instead of showing everything.

## Other changes

### Agents and rules

- System → Agents marks an Agent `restricted` when its own rules end in a rule that denies every other call, and `blocked` while the rules from a failed conversion are unchanged, with a notice that gives the reason. The Sessions filter for isolated Sessions and the Node lock in the Chat Node picker are gone.
- `list_agents` and `/agent list` show the number of local rules instead of isolation details.
- An isolated Agent that other Agents inherit from stays available as an inheritance source after conversion.
- The access-control skill no longer includes the offline generator for isolated-Agent rules.

### Tools

- Default tool declarations are about 15% shorter.
- Tool descriptions now give one rule for relative paths in `read`, `write`, `edit`, `exec`, `copy_between_nodes`, `send_file` and `image_write_to_file`. Descriptions of `call_tool`, `create_child_session`, `wait`, `task` and `submit_compact_plan` were corrected; for example, `call_tool` without a `nodeId` uses the Session's current Node.
- Exact `recall` targets (`B#N`, `msg:B#N`, `msg#A-B`) are logged to `state/logs/recall-targets.jsonl` with Session and block identifiers, levels and ages, but no content. The file rotates at 4 MiB.
