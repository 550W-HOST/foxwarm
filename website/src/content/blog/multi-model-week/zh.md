Foxwarm 的开发有很大一部分是 Foxwarm 自己在做。我们的开发实例里有一个长期运行的协调会话，它把需求拆成任务，交给子会话去实现、审阅或调研；用户也会直接开会话做某个功能，再由这个会话安排自己的子会话。每个子会话可以用不同的模型。

用了一段时间，有人提了一句："GPT 经常说没用的东西。"这句话不难验证：子会话之间的每条消息都留在 Archive 里，每次模型请求也记下了当时用的是哪个模型。我们取了 11 月 11 日到 18 日这一周的数据，想回答两个问题：

1. 不同模型在协调、实现、审阅、调研这些角色上各有什么表现？
2. "说没用的东西"是真的吗？多说的是哪些内容？

这一周的规模：约 100 个会话，一万六千多次模型请求，669 条会话之间的消息，其中 316 条是会话之间直接发的消息，353 条是任务的派发和完成通知。涉及五个模型：Claude Opus 5.5、Claude Sonnet 5.5、GPT-6 Astra、GPT-6.1 Sol、GPT-6.1 Terra。

## 先说清楚：这不是对照实验

这些数据来自日常开发，有几个偏差要先摆出来：

- **工作量很不均衡。** Opus 承担了大部分工作，一万六千多次请求里有 12,179 次是它。Terra 只跑了一个会话，Sol 只有五段。
- **任务没有随机分配。** 协调会话通常按任务挑模型，难的给 Opus，简单的给 Sonnet。但这一周有大约一天，一个子会话模型的设置覆盖了协调会话的选择，那段时间新建的子会话全部跑在 Astra 上。Astra 因此拿到了一批没有挑选过的任务，算是一个意外的样本。即便如此，各模型拿到的任务类型仍然不同。
- **评判者也是模型。** 下面按角色的分析由 Opus 子会话读记录完成，这篇文章的初稿也是 Opus 写的。消息质量那部分，我们请了 Opus 和 Sol 各做一遍盲评，专门用来检查这一点。

所以这里给出的是一份有证据的观察记录，不是排行榜。

## 用量

| 模型 | 会话数 | 请求数 | 估算成本 | 每次请求 | 请求耗时 中位数 / P90 |
|---|---|---|---|---|---|
| Claude Opus 5.5 | 52 | 12,179 | $1,003 | $0.082 | 9.0 s / 23 s |
| GPT-6 Astra | 24 | 1,888 | $388 | $0.206 | 15.9 s / 46 s |
| Claude Sonnet 5.5 | 23 | 1,999 | $54 | $0.027 | 7.7 s / 18 s |
| GPT-6.1 Sol | 5 | 209 | $8.7 | $0.041 | 20.9 s / 61 s |
| GPT-6.1 Terra | 1 | 65 | $0.63 | $0.010 | 9.2 s / 15 s |

成本是按我们配置的单价估算的，和实际账单可能有出入。有些会话中途换过模型，所以会话数加起来比总数多。

Astra 每次请求的价格是 Opus 的 2.5 倍左右，但完成同样一个任务，它用的请求数大约只有 Opus 的三分之一，单个任务的总花费差不多。Sol 单价便宜，单次请求却最慢。

## 按角色看

### 审阅：Astra 最可靠，也最贵

Astra 做了 9 次独立审阅，对象多是 Opus 写的权限系统改动。它提出的发现全部被采纳，没有一条被驳回。其中几条分量很重：

- 一次改动的 CI 已经全绿，正准备合入。Astra 找出一个阻断问题：用来解释权限决定的只读操作，会顺带触发节点发现，并写入节点元数据。
- 审批的指纹没有包含会话关系，旧的批准可以放行一个已经变了的请求。
- 名字前后加空格，就能绕过针对某个管理命令的禁止规则。

它的做法是自己搭语料、写复现，每轮都重跑几十万次比较。证据很硬，代价也明显：9 次审阅花了约 $178。有一组复审还连续 4 次被模型提供方的内容过滤拒绝，理由是"cybersecurity risk"，没留下报告，协调会话只好自己去读它留下的探针。做安全相关审阅时，这个风险要提前考虑。

Opus 做了 4 次审阅，合计约 $14.5。它的发现大多成立，严重程度定得准，对外部贡献者 PR 的架构判断，后来直接成了回复的依据。它也有一次把问题的触发条件说大了：作者顺着调用链指出，正常换模型时会插入一条通知，不会触发这个问题。Opus 两分钟内复核并承认。

两边都漏过同一类问题：审阅时没有跑已有的 e2e 测试和发布构建，改动推上去后，CI 才发现三十多个 e2e 测试文件还在调用已删除的工具。

### 实现：没有明显的赢家

Astra 擅长按证据调试。有一次协调会话认为某个缓存问题是 A 引起的，Astra 用 `git show` 证明只有在特定条件下才会走到 A，随后在原始代码上复现了真正的竞态。它做的 Android 节点和打包优化，都是审阅一次就通过，用户在真机上试过也认可。

它的问题是爱加机制。在一个接入原生 Web 搜索的任务里，它先后 5 次提出扩大范围，每次都有协议依据，协调会话也都批准了，最后交付了两千八百多行。直到用户问了一句"什么 compaction 缺口"，范围才收住。同一个功能把模型返回的每个文本块存成一段，界面上一条回答碎成十几张卡片。作者和审阅都没发现，是用户看到截图说了一句"太鬼畜了兄弟"。

Opus 的写作、产品判断和报告可读性最好。核对官网文章时，它找出了好几处和事实不符的地方。它的问题出在安全逻辑：权限系统那组改动里，同一类漏洞反复出现，靠 Astra 的审阅兜底。还有一次，它把自己测试脚本的错误（窗口跑到了屏幕外，点错了按钮）报成了产品卡死。

Sonnet 做的是范围清楚的任务，几乎不越界，成本是 Opus 和 Astra 的几分之一，质量接近 Opus。Sol 的两次实现，一次干净利落，一次留下了一个会让会话永久卡住的竞态。

### 调研：Sol 准确、便宜

Sol 做了两份产品定位调研，各花约 $2，每条结论都带来源。其中一份纠正了 Opus 的一个过时判断：Opus 以为某个竞品不支持 MCP，Sol 查到它的稳定版早就有了。这是这一周 GPT 纠正 Claude 最清楚的一例。

### 协调：转述可靠，判断偏少

Astra 当协调者时，能准确转述用户意图。用户质疑范围后，它立刻叫停了子会话；作者纠正审阅结论时，它把证据转给审阅方复核，确认后再按缩小的范围交付。它的弱点是对子会话的扩大请求照单全收。

Terra 只做过一次协调，整个会话花了 $0.63。它如实转述用户的要求，遇到歧义会主动问，但把"再合并一下"理解反了方向，也没拦住子会话加了用户不想要的测试。Terra 可以放心转述，但不能指望它做判断。

## 消息本身：GPT 多说了什么

回到最开始那句话。为了不让判断受口味左右，我们做了一次盲评。

**方法。** 取 GPT 系模型这一周发出的全部 137 条消息，再按消息类型配对，随机抽 137 条 Opus 的消息。两组打乱顺序，隐去发送者，分给三个子会话逐句标注。每一句归入五类之一：

- **有用**：结果、证据、决定、问题，收件人需要据此行动；
- **复述**：收件人已经知道的内容，比如把对方的提案念回去，或者重复常驻规则；
- **"没做"声明**：没人问、也没有风险的"我没有 push、没有部署、工作区是干净的"；
- **低价值细节**：40 位完整 commit hash、交付目录的字节数、已经解决的环境折腾；
- **预防性禁令**：在派活时禁止没人提过、也不太可能发生的做法。

第一轮由三个 Opus 子会话标注。之后我们把完全相同的输入和说明交给三个 Sol 子会话，再标一遍。

**结果。** 下表是无用内容的占比，每格前面是 GPT，后面是 Opus：

| 消息类型 | Opus 标注 | Sol 标注 |
|---|---|---|
| 全部 | 25.9% / 11.7% | 27.8% / 17.2% |
| 派活 | 28% / 5% | 34% / 16% |
| 批复子会话的提案 | 29% / 6% | 29% / 8% |
| 完成报告 | 31% / 14% | 32% / 22% |
| 子会话的中途消息 | 15% / 16% | 16% / 19% |

两轮对同一条消息的打分，相关系数是 0.74。

**两边都认同的部分。** 换了评判者，这几条结论都没变：

- 批复时把对方的提案复述回去，在 GPT 的批复里约占 22%，Opus 只有 6%–8%。子会话提出方案，GPT 回一句"按你提出的范围完成：……"，后面把方案又讲一遍，真正新增的只有一两句。
- 完成报告的结尾，常常列一串没做的事。比如"No fixes, commits, pushes or shared/live runtime restarts. … No release verdict."，以及"Total delivery: 26 files, 561,167 bytes, below the 20 MiB limit."。Sol 标出这类声明在 GPT 报告里占 15%，在 Opus 报告里占 6%。
- 派活时重复子会话本来就继承的规则（测试怎么跑、不许 push、不许建子会话），还会预先禁止没人提过的东西，比如"No new scheduler, persistence authority or metadata hash."。
- 子会话的中途消息，单看内容 GPT 不比 Opus 差，问题在条数。Astra 当子会话时，平均每个任务发 1.7 条中途消息，Opus 是 0.7 条。其中不包含任何问题或请求的，Astra 平均每个任务 0.55 条，Opus 是 0.23 条。典型的一句是"I will continue read-only consumer/design investigation meanwhile."。

**两边不一致的部分。**

- **可读性。** Opus 给 GPT 消息的平均分比给 Opus 消息低 0.92（满分 5），Sol 只低 0.14。完成报告这一项，Sol 给两边打了同样的分。只有派活一项，两个评判者都认为 GPT 写得难读：一整段不带主语的名词串，中间夹着十几条禁令。
- **hash、字节数这些细节。** Opus 认为 GPT 明显更多，Sol 看来两边差不多。
- **严格程度。** Sol 判 Opus 消息的无用占比，比 Opus 自评高 5.5 个百分点；对 GPT 只比 Opus 严 1.9 个百分点。这可能是 Opus 对同家族手软，也可能是 Sol 对同家族手软，这组数据分不出来。

所以，"GPT 说没用的东西"这句话成立，但具体指什么要说准：GPT 爱复述、爱声明自己没做什么、爱在派活时堆规则。"GPT 的电报体难读"更像是 Opus 的口味，换 Sol 来评就不成立了。

## 我们改了什么

Foxwarm 的 memory 文件可以按模型生效：用 `<foxwarm-if model-id="*gpt*">` 包起来的内容，只会出现在 GPT 模型的系统提示里。我们原本就在里面放了一些写作规则，比如不要把内容压成电报体、不要在回答末尾列"没有改变什么"。问题在于，这些规则都是按"回复用户"写的，模型写会话之间的消息时，并没有把它们用上。

这次在 GPT 专用的部分里加了一节，专门管会话之间的消息和任务文本：

- 批复提案时，只写决定和新增的要求；提案方已经知道自己的计划和证据，引用即可，不必复述。
- 报告里，已经发过的计划、测量和表格直接引用，不再重复。push、部署、重启、工作区和清理的状态，只在派活时要求汇报，或者情况和预期不同时才写。
- 派活时，写清目标、范围、负责的资源和这个任务特有的限制。常驻规则只在这次有变化时才提。禁止某种做法，只针对这个任务里确实可能犯的错，并写出原因。
- 中途消息只在有问题、卡住、需要对方决定，或者有影响对方工作的发现时才发。
- commit 用短 ID，交付大小和已经解决的环境折腾都不写。

规则写进系统提示，模型也未必在写消息的那一刻想得起来。Foxwarm 有一个可选的交接检查：开启后，`send_to_session` 和 `create_child_session` 要求模型在写正文之前，先填一个 `handoffRecall` 字段，回想"要说什么、哪些规则适用"。我们在新加的那一节第一条就写明：这些规则管哪几个字段，并且要在 `handoffRecall` 里对照检查。这样，规则在模型写消息之前就会被想起来。

另外，上面看到 Astra 被纠正后才收住范围。我们给 GPT-6 系列补了一条：被纠正后，要改的是理解和之后的做法，不只是措辞；已经撤回的假设，不要以新要求或新禁令的形式留在后续的计划和交接里。

这些规则先在我们自己的实例上跑了一天，随后改写成英文，放进了 Foxwarm 默认的框架提示词，从 0.9.7 起所有安装都会带上。同时进去的还有一组只对 GPT-6.2 生效的规则，参考了 OpenAI Codex 的模型说明，其中一条要求最终报告写明所有没完成、没验证的部分。

## 一周之后

规则生效后，我们又取了一周（11 月 18 日到 25 日）的消息，用同样的标注说明复测。

先说这次复测能回答什么、不能回答什么：

- **GPT 这一周说得很少。** 它只发了 21 条消息，去掉 6 条按要求写的文风测试答案，和工作有关的只剩 15 条：8 份完成报告、7 条中途消息。
- **最该看的两类消息没有样本。** 这一周没有 GPT 当协调者，派活和批复一条都没有，而改动前差距最大的正是这两类。
- **模型也换了。** 改动前的 GPT 消息几乎全是 GPT-6 Astra 发的；这一周换成了 GPT-6.2 Sol 和 GPT-6.1 Terra，GPT-6.2 还多了前面那组新规则。看到的变化，没法全部算在消息规则头上。

**方法。** 从这一周按消息类型配对抽了同样多的 Opus 消息，再从上一周的样本里，按同样的类型各抽 21 条 GPT 和 Opus 消息作参照。84 条消息一起打乱，隐去发送者和时间，Opus 和 Sol 各标一遍。这样前后两周用的是同一批评判者、同一次标注，不受两轮之间口径漂移的影响。

无用内容占比（只算工作消息）：

| | Opus 标注 | Sol 标注 |
|---|---|---|
| 改动前 GPT | 28.9% | 34.4% |
| 改动后 GPT | 25.5% | 26.7% |
| 改动前 Opus | 19.4% | 31.6% |
| 改动后 Opus | 13.4% | 26.0% |

这张表只看完成报告和中途消息，所以和前面全量盲评的数字不能直接比。两个评判者都认为 GPT 少了一些废话，但 Opus 的消息在同一时期也变短了。按 Opus 的口径，GPT 和 Opus 的差距从 9.5 个百分点变成 12.1 个，没有缩小；按 Sol 的口径，差距从 2.8 个百分点变成 0.7 个，基本消失。这么小的样本，这两种读法都站得住。

全量统计（不抽样）里，下面几项变化比较清楚：

- **完整 commit hash 没了。** 改动前，GPT 每份完成报告平均有 0.92 个 40 位 hash，改动后一个都没有。
- **中途消息少了。** GPT 子会话平均每个任务的中途消息从 1.58 条降到 0.62 条，不含任何问题或请求的从 0.56 条降到 0.25 条，和 Opus 同期持平。
- **报告短了。** GPT 完成报告的长度中位数从 1,869 字符降到 1,223 字符。
- **复述少了，也更好读了。** 复述类内容在 Opus 标注里从 7.2% 降到 1.2%，在 Sol 标注里从 10.7% 降到 7.5%。可读性，Opus 打的分从 3.10 升到 3.67，Sol 从 4.10 升到 4.47。

没变的是报告结尾那串"没做什么"。两个评判者给的比例都在 15% 上下，和改动前一样。典型的一句是"工作区干净。没有推送，也没有重启或部署。"，而这几份任务都没要求汇报这些。这里也有我们自己的原因：GPT-6.2 的新规则要求报告写明没完成、没验证的部分，"macOS 包没有在本地构建验证"这种句子本来就是该写的限制；派活模板也要求子会话报告工作区种子和依赖不一致的情况。标注说明没有把这几类和真正多余的声明分开，评判者也看不到派活原文，所以这一项的数字偏高。不过像上面那句纯粹的"没有推送"，规则显然没压住。

能对上具体、可检查的规则，例如"commit 用短 ID""中途消息只在需要时发"，效果比较明显。"不要列没做的事"这种需要模型自己判断场合的规则，基本没起作用。派活和批复的效果，要等 GPT 再当协调者时才能看到。

## 我们现在怎么分工

这一周的数据给出的分工建议很朴素：

- **安全和权限相关的审阅交给 Astra。** 它的发现可信，能抓到 CI 抓不到的问题。要提前想好被内容过滤拦下时怎么办，并明确要求审阅范围包括已有的 e2e 测试和发布构建。
- **Opus 做产品、界面、文档和协调。** 它写的安全逻辑一定要有人独立审阅。
- **Astra 做实现时，适合调试和跨平台工程。** 派活时要给出范围上限，并要求它按 CI 的实际范围验证。
- **Sonnet 和 Sol 做中等规模的任务最划算。** Sol 做并发或集成相关的改动时，要安排审阅。
- **Terra 适合转述和执行，不要指望它做判断。**

这些结论都来自一个团队、一周的数据，换一种任务组合，结论可能会变。能变的前提是：消息和每次请求都完整记录下来，并且可以回头去查。
